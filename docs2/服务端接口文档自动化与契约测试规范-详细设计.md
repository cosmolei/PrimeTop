# 服务端接口文档自动化与契约测试规范 — 详细设计

> 版本：v1.0 | 更新日期：2026-05-26 | 模块归属：服务端基础架构

---

## 1. 概述

### 1.1 设计背景

原始设计文档（§13.4 可维护性需求）明确要求"前后端接口应维护统一 API 文档"。随着 PrimeTop 业务模块增长（用户服务、学习服务、题目服务、错题服务、AI 服务、支付服务等），手工维护接口文档成本高、易过期、易出错。本规范旨在建立一套 **接口文档自动生成 + 契约测试驱动** 的体系，保障前后端接口一致性，降低联调成本，提升 API 变更的可控性。

### 1.2 设计目标

| 目标 | 衡量标准 |
| --- | --- |
| 接口文档 100% 自动生成 | 所有 REST API 均由代码注解/配置自动产出 OpenAPI 3.1 文档 |
| 接口变更实时可感知 | PR 合入时自动检测 Breaking Change 并阻断/告警 |
| 契约测试覆盖率 ≥ 90% | 核心业务接口均有 Consumer/Provider 契约测试 |
| Mock 服务一键可用 | 前端开发可基于最新文档自动获取 Mock Server |
| 文档站点持续更新 | CI 流水线自动发布至内部文档站点 |

### 1.3 适用范围

- 所有 RESTful API（BFF 层 + 内部服务间 HTTP 调用）
- WebSocket 消息协议（可选，后期扩展）
- 不覆盖 gRPC 内部调用（由 protobuf 原生保证契约）

## 3. 技术选型

| 组件 | 选型 | 理由 |
| --- | --- | --- |
| API 规范格式 | OpenAPI 3.1 | 行业标准，工具链成熟 |
| 文档自动生成 | springdoc-openapi 2.x | Spring Boot 原生集成，零配置生成 |
| 文档渲染 | Redoc + Swagger UI | Redoc 用于正式文档站，Swagger UI 用于调试 |
| Breaking Change 检测 | oasdiff | 专为 OpenAPI 设计的 Diff 工具，支持多种规则 |
| 契约测试 | Spring Cloud Contract | 与 Spring Boot 深度集成，支持 Consumer/Provider 模式 |
| Mock Server | Prism (Stoplight) | 原生 OpenAPI 支持，请求校验 + 动态 Mock |
| 文档站点托管 | VitePress + 静态部署 | 与项目现有文档体系一致 |
| CI 集成 | GitHub Actions / GitLab CI | Pipeline 阶段化，自动执行 |

#### 4.1.2 全局 OpenAPI 配置类

```java
@Configuration
public class OpenApiConfig {

    @Bean
    public OpenAPI primeTopOpenAPI(
            @Value("${app.api.version:1.0.0}") String apiVersion
    ) {
        return new OpenAPI()
                .info(new Info()
                        .title("PrimeTop API")
                        .description("启硕 PrimeTop 全学段 AI 辅助学习软件 — 服务端接口文档")
                        .version(apiVersion)
                        .contact(new Contact()
                                .name("PrimeTop 后端团队")
                                .email("backend@primetop.cn"))
                        .license(new License()
                                .name("Internal Use Only")
                                .url("https://docs.primetop.io")))
                .externalDocs(new ExternalDocumentation()
                        .description("PrimeTop 设计文档")
                        .url("https://docs.primetop.io/design"))
                // 安全方案
                .addSecurityItem(new SecurityRequirement().addList("BearerAuth"))
                .addSecurityItem(new SecurityRequirement().addList("ApiKeyAuth"))
                .schemaRequirement("BearerAuth",
                        new SecurityScheme()
                                .type(SecurityScheme.Type.HTTP)
                                .scheme("bearer")
                                .bearerFormat("JWT")
                                .description("用户登录令牌"))
                .schemaRequirement("ApiKeyAuth",
                        new SecurityScheme()
                                .type(SecurityScheme.Type.APIKEY)
                                .in(SecurityScheme.In.HEADER)
                                .name("X-Api-Key")
                                .description("服务间调用密钥"))
                // 分组标签
                .tags(List.of(
                        new Tag().name("user").description("用户服务"),
                        new Tag().name("learning").description("学习服务"),
                        new Tag().name("question").description("题目服务"),
                        new Tag().name("mistake").description("错题服务"),
                        new Tag().name("ai").description("AI 辅导服务"),
                        new Tag().name("content").description("内容服务"),
                        new Tag().name("payment").description("支付服务"),
                        new Tag().name("notification").description("通知服务")
                ));
    }

    @Bean
    public GroupedOpenApi userApi() {
        return GroupedOpenApi.builder()
                .group("用户服务")
                .pathsToMatch("/api/v1/users/**", "/api/v1/auth/**")
                .addOpenApiMethodFilter(method ->
                        method.getDeclaringClass().getPackageName()
                                .startsWith("cn.primetop.user"))
                .build();
    }

    @Bean
    public GroupedOpenApi learningApi() {
        return GroupedOpenApi.builder()
                .group("学习服务")
                .pathsToMatch("/api/v1/learning/**", "/api/v1/study-plans/**")
                .build();
    }

    @Bean
    public GroupedOpenApi questionApi() {
        return GroupedOpenApi.builder()
                .group("题目服务")
                .pathsToMatch("/api/v1/questions/**", "/api/v1/ocr/**")
                .build();
    }

    @Bean
    public GroupedOpenApi aiApi() {
        return GroupedOpenApi.builder()
                .group("AI 辅导服务")
                .pathsToMatch("/api/v1/ai/**", "/api/v1/conversations/**")
                .build();
    }

    // 其他分组按需添加...
}
```

```bash
#!/bin/bash
# scripts/merge-openapi.sh
# 将各服务生成的 OpenAPI spec 合并为统一文档

set -euo pipefail

OUTPUT_DIR="docs/api"
SERVICES=("user" "learning" "question" "mistake" "ai" "content" "payment" "notification")
COMBINED="$OUTPUT_DIR/openapi-combined.json"

mkdir -p "$OUTPUT_DIR"

# 使用 openapi-merger 合并
npx @redocly/cli bundle \
  --output "$COMBINED" \
  --ext json \
  $(for svc in "${SERVICES[@]}"; do
    echo "target/openapi-${svc}/openapi.json"
  done)

echo "✅ 合并完成: $COMBINED"
```

## 6. Breaking Change 检测

### 6.1 检测规则

使用 **oasdiff** 在 CI 中自动检测 API 变更类型：

| 变更类型 | 严重级别 | 是否阻断 | 说明 |
| --- | --- | --- | --- |
| 删除接口路径 | 🔴 Breaking | 阻断 | 移除已发布的 API 端点 |
| 删除/重命名请求参数 | 🔴 Breaking | 阻断 | 已有客户端会发送旧参数 |
| 必填参数新增 | 🔴 Breaking | 阻断 | 旧客户端不会发送新参数 |
| 响应字段删除/类型变更 | 🔴 Breaking | 阻断 | 客户端解析旧结构会失败 |
| 枚举值缩减 | 🔴 Breaking | 阻断 | 客户端可能发送已移除的值 |
| 新增可选参数 | 🟡 Compatible | 告警 | 安全，但需文档更新 |
| 新增响应字段 | 🟢 Compatible | 通过 | 安全（前端应容错） |
| 新增 API 路径 | 🟢 Compatible | 通过 | 纯新增功能 |
| 修改接口描述 | ⚪ Info | 通过 | 文档层面变更 |

### 6.2 CI 集成脚本

#### 6.2.1 GitHub Actions Workflow

```yaml
# .github/workflows/api-contract-check.yml
name: API Contract Check

on:
  pull_request:
    paths:
      - 'server/**/controller/**'
      - 'server/**/dto/**'
      - 'contracts/**'
      - 'docs/api/**'

jobs:
  detect-breaking-changes:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # 需要完整历史

      - name: Generate current OpenAPI spec
        run: |
          ./gradlew :server:bootRun &
          sleep 30
          curl -s http://localhost:8080/v3/api-docs > openapi-current.json
          kill %1

      - name: Compare with base branch spec
        run: |
          # 获取基准分支的 spec
          git checkout ${{ github.base_ref }}
          ./gradlew :server:bootRun &
          sleep 30
          curl -s http://localhost:8080/v3/api-docs > openapi-base.json
          kill %1
          git checkout -

      - name: Run oasdiff breaking change check
        uses: oasdiff/oasdiff-action@main
        with:
          command: breaking
          base: openapi-base.json
          revision: openapi-current.json
          format: html

      - name: Upload diff report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: api-diff-report
          path: diff-report.html

  contract-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run provider contract tests
        run: |
          ./gradlew :server:contractTest

      - name: Publish contract test report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: contract-test-report
          path: server/build/reports/contractTests/
```

#### 6.2.2 Breaking Change 豁免流程

当确实需要引入 Breaking Change 时（如大版本升级）：

1. 在 PR 中添加标签 `api-breaking-change`
2. 填写 Breaking Change 说明模板（影响范围、迁移方案、时间表）
3. 至少 2 名后端 + 1 名前端 Reviewer 审批
4. 同步通知客户端团队制定适配计划

```yaml
# breaking-change-template.yml
breaking_change:
  affected_endpoints:
    - DELETE /api/v1/users/{userId}/settings
  migration_plan: |
    1. 新增 /api/v2/users/{userId}/preferences
    2. 保留旧接口 2 个版本周期（约 4 周）
    3. 客户端 v2.1.0 切换到新接口
    4. v2.3.0 移除旧接口
  client_impact: Android v2.0.x, iOS v2.0.x
  deadline: 2026-07-15
```

### 7.2 前端 Mock 拦截层（Flutter）

```dart
// lib/core/network/mock_interceptor.dart
class MockInterceptor extends Interceptor {
  final bool enabled;
  final Map<String, dynamic> overrides;

  MockInterceptor({
    required this.enabled,
    this.overrides = const {},
  });

  @override
  void onRequest(RequestOptions options, RequestInterceptorHandler handler) {
    if (!enabled) {
      return handler.next(options);
    }

    final key = '${options.method} ${options.path}';
    if (overrides.containsKey(key)) {
      // 返回 Mock 数据，延迟模拟网络延迟
      Future.delayed(
        Duration(milliseconds: 200 + Random().nextInt(300)),
        () => handler.resolve(
          Response(
            requestOptions: options,
            statusCode: 200,
            data: overrides[key],
          ),
        ),
      );
      return;
    }

    handler.next(options);
  }
}
```

## 9. API 版本管理策略

### 9.1 版本控制规则

| 策略 | 规则 | 示例 |
| --- | --- | --- |
| URL 路径版本 | 主版本号放在路径中 | `/api/v1/users`, `/api/v2/users` |
| 兼容性保证 | 同一主版本内必须向后兼容 | v1.x 新增字段不破坏旧客户端 |
| 废弃流程 | 接口废弃至少保留 2 个版本周期 | Deprecation → Sunset 头 → 移除 |
| 废弃标记 | 通过 OpenAPI `deprecated` 字段 + Sunset 响应头 | 见下方示例 |

### 9.2 废弃标记实现

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface DeprecatedApi {
    /** 废弃日期 */
    String since();
    /** 计划移除日期 */
    String removalDate();
    /** 替代接口 */
    String alternative();
    /** 说明 */
    String note() default "";
}
```

```java
@RestController
@RequestMapping("/api/v1/users")
public class UserController {

    @DeprecatedApi(
        since = "2026-07-01",
        removalDate = "2026-09-01",
        alternative = "GET /api/v2/users/{userId}/profile",
        note = "v2 接口增加学段能力维度数据"
    )
    @GetMapping("/{userId}/settings")
    @Operation(
        summary = "[已废弃] 获取用户设置",
        deprecated = true,
        description = "此接口已废弃，请使用 GET /api/v2/users/{userId}/profile"
    )
    public ApiResponse<UserSettingsVO> getUserSettings(
            @PathVariable String userId,
            HttpServletResponse response) {
        // 自动添加 Sunset 和 Link 响应头
        response.setHeader("Sunset", "Sat, 01 Sep 2026 00:00:00 GMT");
        response.setHeader("Link",
            "</api/v2/users/" + userId + "/profile>; rel=\"successor-version\"");
        return ApiResponse.success(userService.getSettings(userId));
    }
}
```

```java
@Data

        ApiResponse<T> resp = new ApiResponse<>();
        resp.setCode(0);
        resp.setMessage("success");
        resp.setData(data);
        resp.setTimestamp(OffsetDateTime.now());

        ApiResponse<T> resp = new ApiResponse<>();

    }
```

```dart
class ApiClient {

  late final DefaultApi _api;

  ApiClient({required String baseUrl, String? token}) {

    if (token != null) {

    if (response.data?.code != 0) {
```

### 15.1 注解检查清单

每个接口上线前必须满足：

- [ ] Controller 类有 `@Tag` 注解
- [ ] 每个方法有 `@Operation` 注解（含 summary、description）

### 15.3 常见问题

**Q: 已有项目没有注解怎么办？**
A: 先用 springdoc 自动生成基础 Spec（无注解也能生成路径和参数），再逐步补齐注解和描述。按 P0 接口优先补充。

**Q: 契约测试和集成测试的区别？**
A: 契约测试验证的是接口的"形状"（字段名、类型、状态码），不关心业务逻辑。集成测试验证业务正确性。两者互补。

**Q: 前端团队如何获取最新 API 文档？**
A: 文档站 docs.primetop.io 每次合入 PR 自动更新。也可在本地 `docker compose up mock-server` 获取交互式 Mock。

**Q: SSE/WebSocket 接口如何文档化？**
A: SSE 使用 OpenAPI 3.1 的 `text/event-stream` 媒体类型描述事件结构；WebSocket 暂不纳入自动文档，使用单独的协议说明文档。
