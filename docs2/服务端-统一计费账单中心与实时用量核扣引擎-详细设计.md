# 服务端-统一计费账单中心与实时用量核扣引擎 详细设计

## 1. 概述

### 1.1 模块定位

统一计费账单中心（Billing & Metering Engine，简称 BME）是 PrimeTop 平台的核心商业基础设施，负责全量用户消费行为的实时计量、额度核扣、账单生成与费用结算。它是连接"用户订阅会员 → 享受权益额度 → 消耗 AI/拍题/语音等高成本资源 → 生成消费账单 → 触发续费/升级"这一完整商业闭环的枢纽系统。

### 1.2 核心职责

| 职责 | 说明 |
|------|------|
| 实时计量 | 对 AI 问答、拍题 OCR、语音 ASR/TTS、作文批改等高成本接口调用进行实时计数与计量 |
| 额度核扣 | 根据用户会员等级与权益配置，对每次资源消费执行免费额度扣减或增值计费 |
| 账单生成 | 按计费周期生成用户消费账单明细，支持日结、月结与实时查询 |
| 用量预警 | 当免费额度接近耗尽、增值费用超出阈值时触发通知与限流 |
| 费用结算 | 与支付服务、会员服务联动，执行增值费用扣款、欠费处理与退款冲正 |
| 成本归集 | 将用户消费数据归集到成本分析平台，支撑 AI 调用成本分析与模型ROI评估 |

### 1.3 依赖关系

- **上游：** AI 服务（Token 用量）、拍题服务（OCR 计数）、语音服务（ASR/TTS 秒数）、作文批改服务、其他增值功能调用
- **下游：** 会员服务（权益查询）、支付服务（扣款/退款）、消息服务（额度提醒/账单通知）、数据分析平台（成本归集）、运营后台（消费看板）

### 2.1.14 v1.0 表结构修正（ALTER）

```sql
-- §4.2 Java 代码引用 quota.getUnitPrice()，但 v1.0 user_quota 无此列。
-- 修正：从 quota_plan_item 快照单价与超额策略到额度账户，避免扣减时回查计划表。
ALTER TABLE user_quota
    ADD COLUMN unit_price      DECIMAL(10,4) NOT NULL DEFAULT 0 COMMENT '超额单价快照（生成账户时从 quota_plan_item 冻结）',
    ADD COLUMN overflow_action VARCHAR(32)  NOT NULL DEFAULT 'DENY' COMMENT '超额策略快照: DENY/CHARGE/DEGRADE';

-- §3.11 幂等语义分流依据（G1）：同 eventNo 重试时比对 payload 是否一致
ALTER TABLE billing_event
    ADD COLUMN payload_hash CHAR(16) NULL COMMENT '请求体 SHA-256 截取16字节，幂等冲突分流依据',
    ADD KEY idx_payload_hash (event_no, payload_hash);

-- Redis Hash 同步冗余这两个字段（§2.2 HSET 示例相应补齐），Lua 脚本读取本地 Hash 即可完成决策。
```

> 快照语义：账户创建时冻结当时的 `unit_price` 与 `overflow_action`，周期内运营调价不影响已生成账户，新周期生效——保证同周期内计费口径一致、账单可复算。

### 2.2 Redis 数据结构

#### 用户额度计数器（高频实时读写）

```
Key:  quota:{userId}:{resourceCode}:{yyyyMM}
Type: Hash
TTL:  周期天数 × 86400 + 3600 (buffer)

HSET quota:10086:AI_CHAT:202607 "limit" 100 "used" 37 "remaining" 63 "overflowUsed" 0 "version" 5
```

#### 计费事件缓冲队列（异步落库）

```
Key:  billing:event:buffer
Type: List (LPUSH / BRPOP)
LPUSH billing:event:buffer '{"eventNo":"EVT20260716001",...}'
```

#### 幂等去重集合

```
Key:  billing:event:dedup:{yyyyMMdd}
Type: Set, TTL 48h
SADD billing:event:dedup:20260716 "EVT20260716001"
```

#### 分钟级频率限制

```
Key:  ratelimit:billing:{userId}:{resourceCode}:{yyyyMMddHHmm}
Type: String (INCR), TTL 120s
INCR ratelimit:billing:10086:AI_CHAT:202607161300
```

### 3.2 预检额度

**POST** `/api/v1/billing/quota/check`

在业务服务发起高成本操作前调用，判断用户是否有足够额度。

请求体：
```json
{
  "userId": 10086,
  "resourceCode": "AI_CHAT",
  "quantity": 1,
  "previewOnly": false
```

## 4. 业务逻辑

### 4.1 计费事件处理流程

```
业务服务调用(AI/OCR/TTS)
    │
    ├─ 1. 调用前: POST /quota/check (预检额度)
    │     → allow=true: 继续
    │     → allow=false: 返回额度不足提示
    │
    ├─ 2. 执行业务操作
    │
    └─ 3. 调用后: POST /event/submit (上报消费)
          │
          ├─ Step A: 幂等检查 (Redis SISMEMBER)
          │   → 已存在: 返回原结果
          │
          ├─ Step B: 写计费事件 (billing_event表 + Redis队列)
          │
          ├─ Step C: 执行额度扣减 (Redis Lua + DB乐观锁)
          │   → 参见 4.2 额度扣减算法
          │
          ├─ Step D: 记录消费明细 (consumption_record)
          │
          └─ Step E: 检查预警阈值
              → remaining < threshold: 发通知
```

### 4.2 额度扣减算法（核心）

采用 **Redis Lua 原子扣减 + DB 乐观锁异步持久化** 双写策略。

#### Redis Lua 脚本（原子扣减）

```lua
-- KEYS[1] = quota:{userId}:{resourceCode}:{cycle}
-- ARGV[1] = quantity
local key = KEYS[1]
local quantity = tonumber(ARGV[1])
local limit = tonumber(redis.call('HGET', key, 'limit'))
local used = tonumber(redis.call('HGET', key, 'used'))
local overflowAction = redis.call('HGET', key, 'overflowAction')
local remaining = (limit == -1) and 999999999 or (limit - used)

if remaining >= quantity then
    -- 完全从免费额度扣减
    redis.call('HINCRBY', key, 'used', quantity)
    redis.call('HINCRBY', key, 'remaining', -quantity)
    return {0, quantity, 0, 0}  -- {code, freeDeduct, paidDeduct, overflow}
elseif overflowAction == 'CHARGE' then
    -- 部分免费 + 部分超额计费
    local freePart = math.max(0, remaining)
    local overflowPart = quantity - freePart
    if freePart > 0 then
        redis.call('HINCRBY', key, 'used', freePart)
        redis.call('HINCRBY', key, 'remaining', -freePart)
    end
    redis.call('HINCRBY', key, 'overflowUsed', overflowPart)
    return {0, freePart, 0, overflowPart}
elseif overflowAction == 'DEGRADE' then
    -- 降级：扣减可用部分，标记降级
    local usable = math.min(quantity, remaining)
    redis.call('HINCRBY', key, 'used', usable)
    redis.call('HINCRBY', key, 'remaining', -usable)
    return {1, usable, 0, 0}  -- code=1 表示降级
else
    -- DENY: 拒绝
    return {-1, 0, 0, 0}
end
```

#### Java 服务层实现

```java
@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public DeductResult deduct(DeductRequest request) {
    String quotaKey = String.format("quota:%d:%s:%s",
        request.getUserId(), request.getResourceCode(), request.getCycleDate());

    // 1. Redis 原子扣减
    List<Long> result = redisTemplate.execute(deductScript,
        List.of(quotaKey), String.valueOf(request.getQuantity()));

    long code = result.get(0);
    long freeDeduct = result.get(1);
    long overflow = result.get(3);

    if (code == -1) {
        return DeductResult.deny("QUOTA_EXHAUSTED");
    }

    // 2. DB 乐观锁扣减（保证最终一致）
    UserQuota quota = userQuotaMapper.selectByUserResource(
        request.getUserId(), request.getResourceCode(), request.getCycleStartDate());

    int updated = userQuotaMapper.deductWithVersion(
        quota.getId(), freeDeduct, overflow, quota.getVersion());

    if (updated == 0) {
        // 版本冲突，重试一次
        quota = userQuotaMapper.selectByUserResource(...);
        updated = userQuotaMapper.deductWithVersion(
            quota.getId(), freeDeduct, overflow, quota.getVersion());
        if (updated == 0) {
            // 记录补偿任务，异步修复
            compensationService.recordConflict(request, freeDeduct, overflow);
        }
    }

    // 3. 计算超额费用
    BigDecimal overflowFee = overflow > 0
        ? quota.getUnitPrice().multiply(BigDecimal.valueOf(overflow))
        : BigDecimal.ZERO;

    return DeductResult.success(freeDeduct, overflow, overflowFee);
}
```

#### DB 扣减 SQL（乐观锁）

```sql
UPDATE user_quota
SET quota_used = quota_used + #{freeDeductAmount},
    quota_remaining = quota_remaining - #{freeDeductAmount},
    overflow_used = overflow_used + #{overflowAmount},
    version = version + 1,
    updated_at = NOW()
WHERE id = #{id} AND version = #{currentVersion}
```

### 4.3 额度周期重置

定时任务每日 00:05 执行：

1. 查询 `cycle_end <= NOW()` 的 `user_quota` 记录
2. 获取用户当前会员计划，确定新周期额度上限
3. 创建新的 `user_quota` 记录（新周期）
4. Redis 创建新的 quota hash key
5. 旧 key 设置短 TTL 自动过期
6. 记录 `quota_grant`（type=PLAN_RESET）
7. 对有超额消费的用户触发账单生成

### 4.4 账单生成流程

每月1日 02:00 定时执行：

1. 查询上月有消费记录的所有用户
2. 按 `resource_code` 维度聚合 `consumption_record`
3. 计算超额总费用 = SUM(overflow_amount × unit_price)
4. 扣减优惠减免
5. 生成 `billing_statement` + `billing_statement_detail`
6. 如 `actual_fee > 0`：创建 `settle_order` → 调用支付服务
7. 发送账单通知

### 4.5 状态流转

#### user_quota 状态

```
INIT ──周期开始/计划生效──► ACTIVE ──额度用尽──► DEPLETED ──充值/新周期──► ACTIVE
                              └──账户冻结──► FROZEN ──解冻──► ACTIVE
                              └──周期过期──► EXPIRED ──新周期──► ACTIVE
```

#### billing_statement 状态

```
PENDING(待结算) ──生成完成──► SETTLED(已结算) ──结算单扣款成功──► PAID(已支付)
PENDING ──actual_fee=0──► PAID(零元账单免结算，守卫G6)
PENDING ──超期未缴──► OVERDUE(逾期) ──用户补缴──► PAID
OVERDUE ──补缴且扣款成功──► PAID
任何非PAID状态 ──退订/全额冲正──► CANCELLED(已取消)
```

> v1.1 修正：v1.0 图中的 `SETTLED→FAILED` 不属于账单状态机——「扣款失败」是**结算单**（settle_order: PENDING/PROCESSING/SUCCESS/FAILED）的状态，账单在结算单失败期间维持 SETTLED 并由结算单重试驱动；账单层 DDL 枚举（PENDING/SETTLED/PAID/OVERDUE/CANCELLED）与本图一致。结算单 FAILED 重试 3 次后，账单转 OVERDUE 进入欠费处置（见 §6.3）。

### 4.6 消费冲正流程

当业务侧发现错误扣减时（如 AI 调用失败但已扣额度），调用冲正接口：

1. 根据 `consumption_record.record_no` 查询原扣减记录
2. 创建反向冲正记录（`status=REVERSED` 关联 `reverse_record_id`）
3. Redis HINCRBY 回补额度（`used -= amount`, `remaining += amount`）
4. DB 乐观锁更新 `user_quota` 回补
5. 如果原消费有超额费用，同步退款

### 4.7 状态守卫规则总表（v1.1 增补，G1-G12）

| 守卫 | 约束对象 | 规则 | 违反时行为 |
|------|----------|------|------------|
| G1 | billing_event | 同 eventNo 同 payload_hash → 返回原结果；不同 payload_hash → 拒绝 | 55604 + P2 告警 |
| G2 | user_quota | 任何扣减不得产生负数（quota_used ≤ quota_limit 或 limit=-1） | DB CHECK 约束 + Lua 拒绝 |
| G3 | consumption_record | 冲正仅允许一次：`status='SUCCESS' AND reverse_record_id IS NULL` 才可执行（CAS） | 55632 |
| G4 | 冲正回补 | 冲正目标周期 = 当前活跃周期才直接回补 user_quota；跨周期冲正转 quota_grant(COMPENSATE) 授予新额度 | 55633 + 转补偿 |
| G5 | billing_statement | uk(user_id, statement_type, period_start) 唯一，重复生成幂等跳过 | 静默跳过并登记 |
| G6 | billing_statement | actual_fee = 0 的账单直接置 PAID，不创建结算单 | 零元免结算 |
| G7 | billing_statement.paid_at | 仅由结算单 SUCCESS 回调驱动置位，禁止人工直接改 PAID | 审计拦截 |
| G8 | OVERDUE 联动 | 账单 OVERDUE 超 24h → 向门控引擎下发 DEGRADE_LIST（限制超额资源，保留基础学习功能） | 服务限制而非封号 |
| G9 | 周期重置 | uk_user_resource_cycle 防重置任务重复建账户；重置前校验无同周期 ACTIVE 账户 | 跳过并告警 |
| G10 | quota_grant(ADMIN) | 后台调整必须携带 APPROVED 状态审批工单号，双人复核 | 55651 |
| G11 | 预警通知 | 同用户同资源同周期最多 alert_limit(≤2) 次，超限静默 | 丢弃不入队 |
| G12 | 对账修复 | 差异修复仅允许 Redis/明细 向 DB 账本对齐，禁止用 Redis 覆盖 DB | 修复任务拒绝反向写 |

### 5.1 计费 SDK（业务服务集成）

```java
/**

 * 使用方式：
 *   billingClient.checkAndDeduct(userId, "AI_CHAT", 1, businessNo);

@Component
public class BillingClient {

    @Autowired
    private BillingApi billingApi;

    /**
     * 预检 + 扣减（一体化，大多数场景使用）
     * @return CheckResult 包含是否允许、扣减结果

    public CheckResult checkAndDeduct(Long userId, String resourceCode,

        // 1. 预检

                .previewOnly(false)
                .build());

        if (!check.getData().isAllow()) {
            return CheckResult.denied(check.getData().getReason());
        }

        // 2. 执行业务（由调用方完成）
        // ...

        // 3. 上报消费
        String eventNo = generateEventNo(businessNo);
        BillingEventRequest event = BillingEventRequest.builder()
            .eventNo(eventNo)
            .userId(userId)
            .resourceCode(resourceCode)

            .businessNo(businessNo)

        return CheckResult.success(resp.getData().getDeductionResult());
    }

    /**
     * v1.1 修正：eventNo 必须从 businessNo 确定性派生，保证业务方重试时携带同一 eventNo，
     * 从而命中幂等去重（G1）。v1.0 使用"时间戳+md5"，每次重试生成新号，会导致重复扣减。
     *
     * @param businessNo 业务流水号（如 conv_20260716_xyz）
     * @param attempt    同一 businessNo 内的多笔计量序号（同一业务产生多笔计费时递增，常规传 0）
     */
    private String generateEventNo(String businessNo, int attempt) {
        return "EVT-" + businessNo + "-" + String.format("%02d", attempt);
    }
}
```

### 5.2 额度预警检查（定时任务）

```java
/**
 * 每30分钟执行，检查用户额度是否达到预警阈值
 * 阈值规则: remaining < max(limit * 0.2, 5)  -- 低于20%或剩余不足5次
 */
@Scheduled(cron = "0 */30 * * * ?")
public void checkQuotaAlert() {
    int batchSize = 500;
    int offset = 0;

    while (true) {
        List<UserQuota> quotas = userQuotaMapper.selectActiveQuotas(offset, batchSize);
        if (quotas.isEmpty()) break;

        for (UserQuota quota : quotas) {
            int threshold = Math.max((int)(quota.getQuotaLimit() * 0.2), 5);
            if (quota.getQuotaRemaining() <= threshold
                && !alertService.isAlreadyAlerted(quota.getUserId(),
                    quota.getResourceCode(), quota.getCycleStart())) {

                // 发送预警通知
                alertService.sendQuotaAlert(
                    quota.getUserId(),
                    quota.getResourceCode(),
                    quota.getQuotaRemaining(),
                    quota.getQuotaLimit());

                // 标记已预警
                alertService.markAlerted(quota.getUserId(),
                    quota.getResourceCode(), quota.getCycleStart());
            }
        }

        offset += batchSize;
    }
}
```

### 5.3 计费事件异步消费者

```java
/**
 * 从 Redis 队列消费计费事件，批量写入 DB
 * 如果 Redis 故障，降级为业务服务同步写入
 */
@Component
public class BillingEventConsumer implements Runnable {

    @Override
    @Scheduled(fixedDelay = 100)  // 每100ms执行一次
    public void run() {
        while (true) {
            // BRPOP 阻塞读取，超时5秒
            String eventJson = redisTemplate.opsForList()
                .rightPop("billing:event:buffer", 5, TimeUnit.SECONDS);

            if (eventJson == null) break;

            try {
                BillingEvent event = JSON.parseObject(eventJson, BillingEvent.class);

                // 幂等检查
                String dedupKey = "billing:event:dedup:"
                    + DateUtil.format(event.getEventTime(), "yyyyMMdd");
                Boolean isNew = redisTemplate.opsForSet()
                    .add(dedupKey, event.getEventNo()) == 1;

                if (!isNew) continue;  // 已处理

                // 执行扣减
                DeductResult result = quotaDeductEngine.deduct(
                    DeductRequest.fromEvent(event));

                // 记录消费明细
                consumptionRecordService.save(event, result);

            } catch (Exception e) {
                log.error("Consume billing event failed: {}", eventJson, e);
                // 失败事件放入死信队列
                redisTemplate.opsForList().leftPush(
                    "billing:event:dead", eventJson);
            }
        }
    }
}
```

## 6. 错误处理

### 6.1 Redis 降级策略

| 场景 | 处理 |
|------|------|
| Redis 不可用（预检时） | 降级到 DB 查询额度，记录告警 |
| Redis 不可用（扣减时） | 仅 DB 事务扣减，Redis 恢复后异步对账修复 |
| Redis 部分-key 丢失 | 定时任务全量扫描 user_quota，重建 Redis 缓存 |

### 6.2 并发冲突处理

| 场景 | 处理 |
|------|------|
| Redis Lua 与 DB 不一致 | 每日凌晨对账任务，以 DB 为准修复 Redis |
| DB 乐观锁冲突 | 立即重试1次，仍失败则记录补偿任务异步处理 |
| 重复事件提交 | 基于 eventNo 幂等，返回首次处理结果 |

### 6.3 异常处理矩阵

| 异常 | 影响 | 处理策略 |
|------|------|----------|
| billing_event 写入失败 | 事件丢失 | 重试3次 → 写本地文件 → 告警人工处理 |
| 额度扣减 Redis 失败 | 无法扣减 | 降级直接 DB 扣减（SELECT FOR UPDATE 行锁） |
| 额度扣减 DB 失败 | Redis 已扣 DB 未扣 | 记录补偿日志 → 对账任务修复 → 告警 |
| 账单生成失败 | 账单缺失 | 次日重试 → 告警 → 人工补账 |
| 支付扣款失败 | 欠费 | 重试3次 → 标记 OVERDUE → 限制服务 → 人工介入 |

### 6.4 补偿机制

```java
/**
 * 每小时执行，处理补偿队列中的冲突记录
 */
@Scheduled(cron = "0 0 * * * ?")
public void processCompensation() {
    List<CompensationTask> tasks = compensationTaskMapper
        .selectPendingTasks(100);

    for (CompensationTask task : tasks) {
        try {
            // 根据任务类型执行补偿
            switch (task.getType()) {
                case "DEDUCT_CONFLICT":
                    // DB 额度与 Redis 不一致，以 DB 账本为权威修复 Redis（守卫G12，禁止反向）
                    syncRedisFromLedger(task);
                    break;
                case "MISSING_CONSUMPTION":
                    // 事件已受理但消费记录缺失，按 billing_event 重放补写
                    rebuildConsumptionRecord(task);
                    break;
                case "REVERSE_PENDING":
                    // 冲正中断（Redis 已回补但 DB 未更新，或反之），重新执行幂等冲正
                    resumeReverse(task);
                    break;
                case "REDIS_REBUILD":
                    // Redis 额度 Key 丢失/损坏，按 DB 账本重建 Hash
                    rebuildRedisQuota(task);
                    break;
                case "STATEMENT_REBUILD":
                    // 账单与明细不一致，重算账单（幂等：先删明细再重建）
                    rebuildStatement(task);
                    break;
                default:
                    log.warn("Unknown compensation type: {}", task.getType());
                    compensationTaskMapper.updateStatus(task.getId(), "SKIPPED");
                    return;
            }

            compensationTaskMapper.updateStatus(task.getId(), "DONE");

        } catch (Exception e) {
            log.error("Compensation task failed: taskId={}", task.getId(), e);
            // 指数退避：1min → 2min → 4min → 8min → 16min，最多重试 5 次
            int nextRetry = task.getRetryCount() + 1;
            if (nextRetry >= 5) {
                compensationTaskMapper.markDead(task.getId(), e.getMessage());
                // 死信立即告警，转人工处理（资金相关问题不允许静默丢弃）
                alertService.sendP2("BME_COMPENSATION_DEAD", task, e);
            } else {
                compensationTaskMapper.retryLater(task.getId(), nextRetry,
                    LocalDateTime.now().plusMinutes(1L << nextRetry));
            }
        }
    }
}
```

> 抢占语义：补偿任务由多实例并发调度时，先执行 `UPDATE compensation_task SET status='PROCESSING' WHERE id=? AND status='PENDING' AND next_run_at<=NOW()`，更新行数=1 才获得执行权，天然防止重复执行。

### 6.5 日终对账体系（v1.1 新增）

资金链路的最终防线。每日 03:30（账单生成后）执行四组恒等式校验，差异登记 `billing_recon_diff` 并自动/人工修复。

#### 6.5.1 恒等式一：账户账本 ↔ 消费明细（数量守恒）

对每个活跃 `(user_id, resource_code, cycle)` 账户：

```text
DB.quota_used == SUM(明细.free_deduct_amount + 明细.paid_deduct_amount)，且状态=SUCCESS
DB.overflow_used == SUM(明细.overflow_amount)，且状态=SUCCESS
Redis.used == DB.quota_used  且  Redis.overflowUsed == DB.overflow_used
```

```sql
-- 差异扫描（每日 03:30，按 cycle_start 分片，游标断点续跑）
SELECT q.user_id, q.resource_code, q.id AS quota_id,
       q.quota_used AS ledger_used,
       COALESCE(SUM(CASE WHEN c.status = 'SUCCESS'
                         THEN c.free_deduct_amount + c.paid_deduct_amount END), 0) AS detail_used
FROM user_quota q
LEFT JOIN consumption_record c
       ON c.user_id = q.user_id
      AND c.resource_code = q.resource_code
      AND c.created_at >= q.cycle_start
      AND c.created_at <  q.cycle_end
WHERE q.cycle_start = ?  -- 当日活跃周期
GROUP BY q.user_id, q.resource_code, q.id, q.quota_used
HAVING ledger_used <> detail_used;
```

#### 6.5.2 恒等式二：事件 ↔ 明细（完整性）

```sql
-- 受理成功的计费事件必须有对应扣减明细（预检拒绝的合理缺明细事件除外）
SELECT e.event_no, e.id
FROM billing_event e
LEFT JOIN consumption_record c ON c.event_id = e.id
WHERE e.event_time >= ? AND e.event_time < ?
  AND c.id IS NULL;
-- 命中 → 登记 MISSING_CONSUMPTION 补偿任务重放补写
```

#### 6.5.3 恒等式三：账单 ↔ 明细（金额守恒）

```text
statement.overflow_total_fee == SUM(detail.overflow_fee)         （容差 ±0.0001）
statement.actual_fee == overflow_total_fee - discount_fee        （容差 ±0.0001）
```

差异 > 0.01 元：账单置回 PENDING 并重建（STATEMENT_REBUILD）；已 PAID 账单差异走人工财务流程（MANUAL），禁止自动改已支付账单。

#### 6.5.4 恒等式四：结算单 ↔ 支付订单

`settle_order.status=SUCCESS ⇔ payment_order 已支付且金额一致`；掉单/金额不一致推送《服务端-支付对账与资金清结算服务》三方对账流程，本引擎只登记差异不自行补单。

#### 6.5.5 差异分类与处置矩阵

| 类别 | 表现 | 修复方向 | 时限 |
|------|------|----------|------|
| A：Redis 多扣 | Redis.used > DB.quota_used | 以 DB 重建 Redis（G12） | 当日自动 |
| B：Redis 少扣 | Redis.used < DB.quota_used | 以 DB 重建 Redis | 当日自动 |
| C：明细缺失 | 恒等式二命中 | 按 billing_event 重放补写 | 当日自动 |
| D：金额不一致 | 恒等式三命中 | 未支付重建；已支付转人工 | 未支付当日 / 已支付 48h |
| E：结算掉单 | 恒等式四命中 | 推送支付对账服务 | 24h

对账报告每日 07:00 前输出至《管理后台-会员订阅与财务运营工作台》；`AUTO_FIXED` 之外未清差异 > 10 条或金额合计 > 100 元触发 P2 告警。
