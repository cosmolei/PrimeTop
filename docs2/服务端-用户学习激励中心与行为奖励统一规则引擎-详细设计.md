# 服务端-用户学习激励中心与行为奖励统一规则引擎 详细设计

> 模块代号：`incentive-hub`
> 所属域：用户增长与留存域
> 关联模块：积分系统、成就系统、打卡系统、运营活动系统、消息通知系统

---

## 1. 模块概述

### 1.1 设计目标

构建一个**统一的、可配置的行为激励规则引擎**，作为全站 Gamification 的中枢神经。该引擎监听用户学习行为事件（答题正确、每日登录、完成任务、连续打卡等），实时评估激励规则，自动触发奖励动作（发放积分、解锁徽章、播放庆祝动画、推送通知等）。

### 1.2 为什么需要这个引擎

当前系统已有多个独立的激励子系统：

| 现有模块 | 职责 | 局限 |
|----------|------|------|
| 积分获取规则计算与虚拟资产交易结算服务 | 积分发放与消费 | 仅管积分数值，不关心触发时机 |
| 学习打卡记录与成就解锁计算引擎 | 打卡记录与成就解锁 | 仅管打卡和勋章，不处理其他行为奖励 |
| 运营活动与成长激励体系 | 运营层面激励策略 | 偏运营配置，不处理实时事件流 |

**缺失的部分**：没有一个统一的规则引擎来：
- 监听**所有**用户行为事件
- 按**可配置规则**判断是否命中激励条件
- 统一调度奖励发放（积分、勋章、动画、弹窗、通知）
- 处理规则优先级、互斥、冷却
- 支持运营人员动态配置规则，无需发版

### 1.3 核心能力

1. **事件订阅**：通过消息队列订阅用户行为事件流
2. **规则评估**：基于 CEL/JSON 表达式引擎实时匹配规则
3. **奖励编排**：支持多种奖励类型的组合发放与优先级控制
4. **防刷冷却**：同一规则对同一用户的触发频率控制
5. **规则管理 API**：运营后台 CRUD 管理激励规则
6. **效果追踪**：规则命中日志与 A/B 实验对接

### 2.2 模块职责边界

| 职责 | 说明 |
|------|------|
| **本引擎负责** | 事件监听、规则匹配、奖励编排与分发、冷却控制、规则配置管理 |
| **本引擎不负责** | 积分余额管理（积分服务负责）、勋章存储（成就服务负责）、推送通道管理（通知服务负责） |

### 2.3 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 消息队列 | Kafka | 高吞吐、有序消费、事件回溯 |
| 规则表达式引擎 | CEL (Common Expression Language) | Google 开源，Go/Java 友好，沙箱安全 |
| 缓存 | Redis 7.x (Lua脚本) | 原子操作保障冷却与计数 |
| 规则存储 | PostgreSQL | 事务一致性、JSONB 支持灵活配置 |
| 规则版本管理 | PostgreSQL schema_migrations | 版本快照 + 审计 |
| 任务调度 | 延迟队列 (Redis ZSET) | 延迟奖励、定时触发 |

## 3. 数据结构设计

### 3.1 PostgreSQL 表结构

#### 3.1.1 激励规则定义表 `incentive_rules`

```sql
CREATE TABLE incentive_rules (
    id              BIGSERIAL PRIMARY KEY,
    rule_code       VARCHAR(64) NOT NULL UNIQUE,       -- 规则唯一编码：DAILY_LOGIN_BONUS
    rule_name       VARCHAR(128) NOT NULL,              -- 规则名称：每日登录奖励
    rule_group      VARCHAR(64) NOT NULL DEFAULT 'DEFAULT', -- 规则分组：DEFAULT / EXAM_PREP / SUMMER_CAMP
    description     TEXT,
    status          VARCHAR(16) NOT NULL DEFAULT 'DRAFT', -- DRAFT / ACTIVE / PAUSED / ARCHIVED
    
    -- 触发条件
    trigger_event   VARCHAR(64) NOT NULL,               -- 触发事件类型（见 3.2 事件类型枚举）
    condition_expr  TEXT NOT NULL,                       -- CEL 条件表达式
    
    -- 奖励定义（JSON 数组，支持多奖励）
    rewards         JSONB NOT NULL DEFAULT '[]'::jsonb,
    
    -- 限制条件
    cooldown_seconds BIGINT NOT NULL DEFAULT 0,          -- 冷却时间（秒），0=无限制
    max_triggers_per_user INT NOT NULL DEFAULT 0,        -- 每用户最大触发次数，0=无限
    max_triggers_per_day  INT NOT NULL DEFAULT 0,        -- 每用户每日最大触发次数，0=无限
    priority        INT NOT NULL DEFAULT 100,            -- 优先级（越小越高）
    mutex_group     VARCHAR(64),                         -- 互斥组：同组只触发优先级最高的一条
    
    -- 生效范围
    target_user_segment VARCHAR(64),                     -- 目标用户分群：ALL / FREE / VIP / NEW_USER
    target_grade_range  VARCHAR(32),                     -- 目标年级范围：1-6;7-9;10-12;ALL
    start_at        TIMESTAMPTZ,                         -- 生效开始时间
    end_at          TIMESTAMPTZ,                         -- 生效结束时间
    
    -- A/B 实验
    experiment_id   VARCHAR(64),                         -- 关联实验 ID
    experiment_variant VARCHAR(32),                      -- 实验变体：CONTROL / TREATMENT_A
    
    -- 元数据
    version         INT NOT NULL DEFAULT 1,
    created_by      BIGINT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_rules_status_event ON incentive_rules(status, trigger_event) 
    WHERE status = 'ACTIVE';
CREATE INDEX idx_rules_group ON incentive_rules(rule_group, status);
CREATE INDEX idx_rules_mutex ON incentive_rules(mutex_group, priority) 
    WHERE status = 'ACTIVE';
```

#### 3.1.2 规则触发日志表 `incentive_rule_logs`

```sql
CREATE TABLE incentive_rule_logs (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    rule_id         BIGINT NOT NULL,
    rule_code       VARCHAR(64) NOT NULL,
    rule_version    INT NOT NULL,
    
    trigger_event_id   VARCHAR(128) NOT NULL,            -- 原始事件 ID（幂等去重）
    trigger_event_type VARCHAR(64) NOT NULL,
    trigger_payload JSONB,                                -- 触发时的完整事件载荷
    
    rewards_executed JSONB NOT NULL DEFAULT '[]'::jsonb,  -- 实际执行的奖励列表
    execution_status VARCHAR(16) NOT NULL DEFAULT 'SUCCESS', -- SUCCESS / PARTIAL / FAILED / SKIPPED
    error_message   TEXT,
    
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_logs_user_time ON incentive_rule_logs(user_id, created_at DESC);
CREATE INDEX idx_logs_rule_time ON incentive_rule_logs(rule_id, created_at DESC);
CREATE UNIQUE INDEX idx_logs_event_unique ON incentive_rule_logs(trigger_event_id, rule_id);
```

#### 3.1.3 用户激励状态表 `user_incentive_states`

```sql
CREATE TABLE user_incentive_states (
    user_id         BIGINT PRIMARY KEY,
    
    total_trigger_count INT NOT NULL DEFAULT 0,          -- 累计触发总次数
    daily_trigger_count INT NOT NULL DEFAULT 0,          -- 今日触发次数
    daily_reset_date     DATE NOT NULL DEFAULT CURRENT_DATE,
    
    last_trigger_at  TIMESTAMPTZ,                        -- 最近一次触发时间
    last_rule_code   VARCHAR(64),                         -- 最近触发的规则
    
    streak_days      INT NOT NULL DEFAULT 0,             -- 连续激励天数
    streak_last_date DATE,                                -- 最近激励日期
    
    -- 各类型累计统计（用于成就/里程碑判断）
    total_points_earned    BIGINT NOT NULL DEFAULT 0,
    total_badges_earned    INT NOT NULL DEFAULT 0,
    total_celebrations_shown INT NOT NULL DEFAULT 0,
    
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

#### 3.1.4 用户-规则触发计数表 `user_rule_counters`

```sql
CREATE TABLE user_rule_counters (
    user_id         BIGINT NOT NULL,
    rule_id         BIGINT NOT NULL,
    trigger_count   INT NOT NULL DEFAULT 0,
    last_trigger_at TIMESTAMPTZ,
    last_event_id   VARCHAR(128),                        -- 最近事件 ID（幂等）
    
    PRIMARY KEY (user_id, rule_id)
);
```

**请求体：**
```json
{
  "rewardLogIds": [500001, 500002, 500003]
}
```

**校验规则：**
- `rewardLogIds` 必填，单次最多 100 个；超出返回 `56312`。
- 所有 logId 必须属于当前登录用户，且 `execution_status = 'SUCCESS'` 或 `'PARTIAL'`，否则该条记为失败并返回明细。
- 已确认过的记录重复提交返回成功但 `alreadyAcked=true`（幂等，不报错）。

**响应体（200 OK）：**
```json
{
  "code": 0,
  "data": {
    "total": 3,
    "acked": 2,
    "alreadyAcked": 1,
    "failed": 0,
    "details": [
      { "rewardLogId": 500001, "status": "ACKED" },
      { "rewardLogId": 500002, "status": "ACKED" },
      { "rewardLogId": 500003, "status": "ALREADY_ACKED" }
    ]
  }
}
```

**用途：** 客户端在庆祝动画/弹窗展示完成后回执，用于统计"奖励触达率"（展示漏斗），并驱动 `total_celebrations_shown` 计数，供规则条件 `totalTriggerCount` 类表达式引用。

### 4.4 事件订阅与发布契约

#### 4.4.1 上游消费（Inbound）

| Topic | 消费组 | 事件类型 | 说明 |

### 5.2 规则匹配引擎实现

#### 5.2.1 激活索引（Activation Index）

规则按 `trigger_event` 分桶缓存在本地 Caffeine 缓存（1 分钟 TTL，靠 `incentive.rule.changed` 事件主动失效）：

```java
@Component
public class RuleActivationIndex {
    // triggerEvent -> 按 priority 升序的规则列表（仅 ACTIVE 且生效窗口内）
    private volatile Map<String, List<RuleDefinition>> index = Map.of();
    private final LoadingCache<String, List<RuleDefinition>> cache;

    public List<RuleDefinition> activate(String eventType, long userId) {
        List<RuleDefinition> candidates = index.getOrDefault(eventType, List.of());
        return candidates.stream()
                .filter(r -> r.inEffectiveWindow(Instant.now()))
                .filter(r -> segmentMatch(r, userId))
                .filter(r -> gradeMatch(r, userId))
                .toList();
    }
}
```

#### 5.2.2 CEL 条件编译缓存

CEL 表达式编译开销大，按 `ruleId + version` 缓存编译产物，规则更新时 version 递增自然失效：

```java
@Component
public class CelConditionEvaluator {
    private final Cache<String, CelExpression> compiledCache =
        Caffeine.newBuilder().maximumSize(5000).build();

    public boolean evaluate(RuleDefinition rule, EvalContext ctx) {
        CelExpression expr = compiledCache.get(
            rule.getRuleId() + ":" + rule.getVersion(),
            k -> compile(rule.getConditionExpr()));
        try {
            return expr.evaluate(Boolean.class, ctx.toBindings());
        } catch (EvaluationException e) {
            // 表达式异常视为"不匹配"，记 warn 日志，不得阻断其他规则
            log.warn("rule {} condition eval error: {}", rule.getRuleCode(), e.getMessage());
            return false;
        }
    }
}
```

#### 5.2.3 求值上下文（EvalContext）

```java
public class EvalContext {
    private Map<String, Object> event;     // eventId/eventType/timestamp/payload.*
    private Map<String, Object> user;      // userId/isVip/grade/dailyLoginCount/totalTriggerCount...
    private Map<String, Object> counters;  // ruleTriggerCount/todayTriggerCount/streakDays...
    // 绑定规则：payload.xxx 直接展开为顶层变量，便于运营书写
}
```

**安全约束：** CEL 沙箱默认禁用外部函数注入；表达式最大长度 2000 字符；编译超时 200ms；求值超时 50ms。

### 5.3 奖励编排执行

#### 5.3.1 奖励分发策略表

| 奖励类型 | 执行器 | 失败语义 |
|----------|--------|----------|
| POINTS | 调用积分服务 gRPC `GrantPoints`（带 rewardLogId 幂等键） | 重试 3 次后标记该奖励 FAILED，其余奖励继续 |
| BADGE | 调用成就服务 gRPC `UnlockBadge` | 徽章已存在视为成功（幂等） |
| CELEBRATION_ANIMATION | 写 Redis `pending_anim:{userId}`（客户端轮询/SSE 拉取） | 写失败降级为跳过，不阻塞 |
| POPUP_MESSAGE | 写 Redis `pending_popup:{userId}` + 发布 `incentive.reward.granted` | 同上 |
| NOTIFICATION | 调用通知服务（异步消息） | 重试 3 次后跳过 |
| UNLOCK_FEATURE | 写用户权益临时表 `user_feature_unlocks` | 失败则整条规则回滚该奖励 |

**部分失败原则：** 多奖励组合中单个失败不影响其他奖励执行，`execution_status = 'PARTIAL'`，失败奖励记 `error_message` 供对账。

#### 5.3.2 金额表达式求值

`amountExpr` 支持 CEL 表达式（如 `payload.streakCorrectCount * 10`），求值结果必须为正整数，否则回退到 `amount` 字段；两者都缺省记配置错误并跳过该奖励。

### 5.4 冷却与限频（Lua 原子脚本）

```lua
-- KEYS[1] = cooldown:{userId}:{ruleId}
-- KEYS[2] = counter:{userId}:{ruleId}        (HASH: count, lastEventId)
-- KEYS[3] = daily:{userId}:{ruleId}:{yyyyMMdd}
-- ARGV[1] = cooldownSeconds
-- ARGV[2] = maxTriggersPerUser   (0=unlimited)
-- ARGV[3] = maxTriggersPerDay    (0=unlimited)
-- ARGV[4] = eventId
local cooldown = tonumber(ARGV[1])
local maxTotal = tonumber(ARGV[2])
local maxDaily = tonumber(ARGV[3])
local eventId  = ARGV[4]

-- 幂等：同一事件不重复计数
if redis.call('HGET', KEYS[2], 'lastEventId') == eventId then
    return {0, 'DUPLICATE_EVENT'}
end
-- 冷却检查
if cooldown > 0 and redis.call('EXISTS', KEYS[1]) == 1 then
    return {0, 'COOLDOWN'}
end
-- 累计上限
local cnt = redis.call('HGET', KEYS[2], 'count') or 0
if maxTotal > 0 and tonumber(cnt) >= maxTotal then
    return {0, 'TOTAL_LIMIT'}
end
-- 每日上限
local dcnt = redis.call('GET', KEYS[3]) or 0
if maxDaily > 0 and tonumber(dcnt) >= maxDaily then
    return {0, 'DAILY_LIMIT'}
end

-- 通过：原子递增 + 设置冷却
redis.call('HINCRBY', KEYS[2], 'count', 1)
redis.call('HSET', KEYS[2], 'lastEventId', eventId)
redis.call('EXPIRE', KEYS[2], 86400 * 400)  -- 覆盖最大累计窗口
redis.call('INCR', KEYS[3])
redis.call('EXPIRE', KEYS[3], 172800)        -- 跨日保留 2 天防零点抖动
if cooldown > 0 then
    redis.call('SET', KEYS[1], 1, 'EX', cooldown)
end
return {1, 'OK'}
```

**互斥仲裁：** 同 `mutex_group` 多条规则同时命中时，仅执行 priority 最小的一条，其余规则记 `SKIPPED/MUTEX`（在 Lua 之前于应用层完成裁决，避免 Lua 复杂度）。

### 5.5 延迟奖励调度

支持"事件触发后延迟 N 秒/分钟发放"（如"连续学习 30 分钟奖励"拆成事件 + 延迟确认）：

- 规则可配置 `delaySeconds`，匹配成功后奖励不立即执行，而是写入 Redis ZSET `incentive:delay:due`（score = 执行时间戳）。
- 调度器每 5 秒 `ZRANGEBYSCORE` 拉取到期任务，投递至本地线程池执行；执行前**重新校验**规则仍 ACTIVE 且用户仍满足条件（如延迟期间用户已达标升级则跳过重复档）。

### 5.6 幂等设计

| 幂等点 | 机制 | 说明 |
|--------|------|------|
| 事件消费 | DB 唯一索引 `(trigger_event_id, rule_id)` | 重复事件插入触发日志时冲突，捕获后 ack 跳过 |
| 奖励发放 | rewardLogId 作为下游幂等键 | 积分/成就服务以 rewardLogId 去重 |
| Lua 限频 | `lastEventId` 比对 | 同事件不重复计数 |
| 管理端写操作 | `Idempotency-Key` 请求头（24h Redis 去重） | 防运营重复点击重复建规则 |

**消费位点提交：** 仅当整个批次写入触发日志成功后才提交 Kafka offset；批次内单条失败不影响整批（记日志后跳过）。

## 7. 事件 Outbox

管理端规则写操作与触发日志写入采用 Outbox 模式，保证 DB 与消息最终一致：

```sql
CREATE TABLE incentive_outbox (
    id           BIGSERIAL PRIMARY KEY,
    aggregate_type VARCHAR(32) NOT NULL,   -- RULE / REWARD_LOG
    aggregate_id   VARCHAR(64) NOT NULL,
    event_type   VARCHAR(64) NOT NULL,     -- RuleChangedEvent / RewardGrantedEvent ...
    payload      JSONB NOT NULL,
    status       VARCHAR(16) NOT NULL DEFAULT 'PENDING', -- PENDING/SENT/FAILED
    retry_count  INT NOT NULL DEFAULT 0,
    next_retry_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_outbox_poll ON incentive_outbox(status, next_retry_at) WHERE status = 'PENDING';
```

- Relay 每 2 秒轮询 PENDING，成功发送后置 SENT；失败按指数退避重试（1m/5m/30m/2h，上限 8 次后置 FAILED 告警）。
- 触发日志采用"日志表即 Outbox"：`incentive_rule_logs` 由 CDC（Debezium）直读发布 `incentive.reward.granted`，减少一次双写。

## 9. 降级策略

| 编号 | 故障场景 | 降级行为 | 红线 |
|------|----------|----------|------|
| D1 | Kafka 消费滞后 | 正常消费即可（激励非强实时，滞后 < 5min 可接受）；滞后 > 10min 告警 | 不得跳过幂等直接发奖 |
| D2 | Redis 不可用 | 冷却/限频检查旁路（fail-open 视为通过），触发日志照常落库，事后离线对账剔除超频部分 | 单规则超发率 > 5% 时熔断该规则 |
| D3 | 用户分群服务不可用 | 含 segment 条件的规则 fail-open；纯分群规则跳过 | 不影响 ALL 类规则 |
| D4 | 下游奖励服务（积分/成就）大面积超时 | 重试 3 次后写入 `reward_retry_queue`（DB 表），Relay 异步补偿 30min | 不阻塞事件消费主循环 |
| D5 | CEL 编译缓存击穿 | 单飞（singleflight）重建，并发请求等待同一编译结果 | 编译失败永不缓存负结果 |
| D6 | 延迟队列积压 | 丢弃 delaySeconds > 600 的非关键奖励，保留 POINTS 类 | 不得丢弃已写入日志的应得奖励 |
| D7 | 规则中心 DB 只读 | 缓存 TTL 内继续服务；超过 10 分钟进入"只触发兜底规则集"（每日登录、连续答对两条内置规则） | 兜底规则集内嵌代码，不依赖 DB |
| D8 | 触发日志写入失败 | 事件重投本地磁盘 WAL，恢复后补写；补写前不提交 offset | 绝不"先奖后记账" |

| `incentive_outbox_pending_count` | Gauge | > 5000 告警（56316） |
| `incentive_delay_queue_depth` | Gauge | > 50 万告警 |
| `incentive_skipped_ratio{reason}` | Counter | MUTEX/COOLDOWN 占比突增 > 3σ 告警（疑似配置错误） |
| `incentive_rule_config_refresh_failures` | Counter | 连续 3 次失败告警（56318） |
| 容量基线 | — | DAU 50 万、峰值事件 8000 QPS、规则 500 条 ACTIVE、单事件平均激活规则数 ≤ 20 |

## 11. 合规要点

| 编号 | 要点 |
|------|------|
| C1 | 激励规则变更全量审计（who/when/what diff），审计日志保留 3 年，不得修改历史触发日志 |
| C2 | 未成年人防沉迷联动：22:00-08:00 时段命中规则仅记账，延迟到 08:00 后发放奖励（调用防沉迷服务判定） |
| C3 | 激励不涉及现金等价物直接发放；UNLOCK_FEATURE 类奖励不得绕过会员/付费体系定价（与支付域边界） |
| C4 | `trigger_payload` 含用户行为明细，属个人信息，按最小必要原则仅保留规则求值所需字段，30 天后转冷存储并脱敏 |
| C5 | 弹窗/动画类奖励受"通知疲劳管控"约束：单用户每小时非必要庆祝 ≤ 3 次，超限自动降级（对接统一通知偏好中心） |
| C6 | 运营配置高危规则（单笔积分 > 500 或日发放积分总量 > 10 万）需双人审批，审批记录入 `incentive_rule_audit` |

## 12. 契约对齐

| 编号 | 契约方 | 边界裁决 |
|------|--------|----------|
| R1 | 积分获取规则计算与虚拟资产交易结算服务 | 积分"数值结算、流水、过期"归积分服务；本引擎只管"何时发、发多少"的触发决策。rewardLogId 作为积分流水 source_id 保证可对账 |
| R2 | 学习打卡记录与成就解锁计算引擎 | 打卡连续天数的"事实认定"归打卡引擎；本引擎消费其事件做奖励编排，不回写打卡状态。徽章归属归成就服务，本引擎仅发起解锁指令 |
| R3 | 运营活动与成长激励体系 | 运营活动（限时双倍积分等）以"规则组（rule_group）+ 生效窗口"形式配置进本引擎，不另起炉灶；活动引擎只做活动页与报名 |
| R4 | 统一学习干预编排与智能频控引擎 | 激励弹窗/通知的频控最终裁决归频控引擎：本引擎先投放意图，频控引擎可否决（幂等 ack 前检查） |
| R5 | 消息队列与事件驱动架构 | 事件 Schema 统一注册中心管理，新增 BehaviorEventType 须先在注册中心登记并通知本引擎升级消费白名单 |
| R6 | 客户端奖励展示 | 客户端只消费 `pending_anim/pending_popup` 与 ack 接口；不得本地自算奖励金额 |
| R7 | AB测试与实验平台 | 规则级实验由实验平台分流，本引擎仅按 `experiment_variant` 过滤规则，不自建分流 |
| R8 | 防沉迷与未成年人保护机制 | 时段管控以防沉迷服务结论为准（C2），本引擎不重复实现时段规则 |
| R9 | 通知服务 | NOTIFICATION 类奖励走通知服务模板，本引擎不透传原始文案，避免文案绕过审核 |
