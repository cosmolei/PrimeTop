# 服务端 - 统一用户行为埋点平台与事件流处理管线 详细设计

## 1. 概述

### 1.1 模块定位

统一用户行为埋点平台是 PrimeTop 所有数据分析、个性化推荐、学情诊断、风控审计等上层能力的数据基础设施。本模块负责 **从客户端 SDK 到服务端存储查询的全链路事件管线**，包括事件接收、校验、摄入 Kafka、流式处理、落盘存储和查询服务。

### 1.2 核心职责

| 职责 | 说明 |
| --- | --- |
| 事件接收 | 提供 HTTP 批量上报接口，接收客户端 SDK 发送的行为事件 |
| 事件校验 | Schema 注册中心校验 + 敏感字段脱敏 + 幂等去重 |
| 事件分发 | 写入 Kafka Topic，供下游流处理 / 批处理消费 |
| 流式处理 | 实时聚合（计数、窗口统计）、CEP 模式检测、实时特征推送 |
| 事件存储 | ClickHouse 存原始 + 聚合数据，Elasticsearch 存检索副本 |
| 查询服务 | 面向 BI / 学情分析的统一事件查询 API |
| 数据治理 | 数据质量监控、延迟告警、隐私合规审计 |

### 1.3 依赖关系

```
客户端埋点 SDK
       │ HTTP POST /api/v1/track/batch
       ▼
┌──────────────────────────────┐
│     Track Gateway Service    │  ← 本模块
│  (接收 · 校验 · 摄入 · 查询)   │
└──────┬───────────┬───────────┘
       │           │
       ▼           ▼
   Kafka Cluster   ClickHouse
       │               
       ├─→ Flink Stream (实时聚合)
       │      │
       │      ├─→ Redis (实时特征)
       │      ├─→ 知识追踪服务
       │      └─→ 风控引擎
       │
       ├─→ Elasticsearch (检索副本)
       │
       └─→ Data Warehouse (离线 ETL)
```

**上游依赖：**
- 客户端埋点 SDK（Flutter / Native）
- 服务端统一认证（用户身份解析）

**下游消费方：**
- 学情分析服务（学习时长统计、学科掌握度）
- 个性化推荐引擎（用户画像、兴趣建模）
- 知识追踪模型引擎（答题行为 → 掌握度更新）
- 用户流失预警引擎（活跃度下降检测）
- 运营数据看板（DAU、留存等）
- 风控引擎（异常行为检测）

### 2.1 顶层事件结构

所有埋点事件共享统一顶层结构，通过 `event_type` 区分具体业务含义。

```json

  "event_type": "question.answer_submitted",
  "event_category": "learning",
  "timestamp": 1719567420000,
  "timezone": "Asia/Shanghai",
  "app_version": "1.2.0",
  "platform": "android",
  "device_id": "dev_a3f5e8b2c1d4",
  "user": {
    "user_id": "u_100234",
    "student_id": "s_56789",
    "grade": "grade_7",
    "stage": "middle_school",
    "is_anonymous": false
  },
  "session": {
    "session_id": "ses_abc123def456",
```

### 2.2 核心字段说明

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `event_id` | string(UUID) | ✅ | 事件唯一 ID，用于幂等去重 |
| `event_type` | string | ✅ | 事件类型，格式 `模块.动作` |
| `event_category` | enum | ✅ | `learning` / `social` / `commerce` / `system` |
| `timestamp` | long | ✅ | 客户端事件发生时间（毫秒） |
| `timezone` | string | ✅ | 用户所在时区 |
| `app_version` | string | ✅ | APP 版本号 |
| `platform` | enum | ✅ | `android` / `ios` / `web` / `mini_program` |
| `device_id` | string | ✅ | 设备唯一标识（设备指纹哈希） |
| `user.user_id` | string | ✅ | 登录用户 ID（未登录时为匿名 ID） |
| `user.student_id` | string | ❌ | 学生档案 ID（已绑定学生档案时） |
| `user.grade` | string | ❌ | 当前年级 |
| `session.session_id` | string | ✅ | 会话 ID（APP 启动 → 退出为一次会话） |
| `context.page` | string | ❌ | 当前页面路由 |
| `context.module` | string | ❌ | 当前功能模块 |
| `properties` | object | ✅ | 业务扩展属性 |

## 3. Schema 注册中心

### 3.1 设计思路

不可控的 `properties` 字段是埋点系统的灾难。通过 Schema 注册中心实现 **事件结构强约束 + 演进管理**。

### 3.2 Schema 定义格式

```json
{
  "schema_id": "question.answer_submitted@v2",
  "event_type": "question.answer_submitted",
  "version": 2,
  "status": "active",
  "required_fields": [
    "question_id",
    "subject",
    "is_correct",
    "duration_ms",
    "source"
  ],
  "optional_fields": [
    "knowledge_points",
    "user_answer",
    "correct_answer",
    "attempt_count",
    "practice_session_id",
    "difficulty_level"
  ],
  "field_types": {
    "question_id": "string",
    "subject": "enum:math,physics,chemistry,biology,chinese,english,history,geography,politics",
    "is_correct": "boolean",
    "duration_ms": "integer:0-3600000",
    "knowledge_points": "array<string>",
    "user_answer": "string",
    "correct_answer": "string",
    "attempt_count": "integer:1-10",
    "source": "enum:practice_assessment,exam_simulation,photo_search,error_review,ai_dialogue",
    "practice_session_id": "string",
    "difficulty_level": "integer:1-5"
  },
  "pii_fields": ["user_answer"],
  "created_at": "2026-01-15T00:00:00Z",
  "updated_at": "2026-03-20T00:00:00Z",
  "changelog": [
    "v1 → v2: 新增 knowledge_points(数组), difficulty_level; 移除 score 字段"
  ]
}
```

### 3.3 Schema 生命周期

```
draft → review → active → deprecated → retired
```

- **draft**: 新建或修改中，未生效
- **review**: 评审中
- **active**: 生产环境校验依据
- **deprecated**: 仍可接收旧版本数据，但新 SDK 应升级
- **retired**: 不再接收

### 3.4 兼容性策略

| 变更类型 | 策略 |
| --- | --- |
| 新增 optional 字段 | 向后兼容，minor 版本 +1 |
| 删除字段 | 先标记 deprecated，保留 2 个版本周期后 retired |
| 修改字段类型 | 不兼容，需新建 major 版本，新旧共存 |
| required → optional | 兼容 |
| optional → required | 不兼容，需新建 major 版本 |

## 4. 事件接收 API

### 4.1 批量上报接口

```
POST /api/v1/track/batch
Content-Type: application/json
Authorization: Bearer <access_token>
X-Device-Id: dev_a3f5e8b2c1d4
X-Sdk-Version: sdk_1.0.3

{
  "batch_id": "batch_uuid_001",
  "events": [
    { ... event1 ... },
    { ... event2 ... },
    { ... eventN ... }
  ]
}
```

**约束：**
- 单批次最多 50 条事件
- 单批次压缩后最大 256KB
- 客户端应使用 gzip 压缩（`Content-Encoding: gzip`）

### 4.2 响应格式

**成功：**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "accepted": 48,
    "rejected": 2,
    "errors": [
      {
        "index": 3,
        "event_id": "evt_xxx",
        "reason": "schema_validation_failed",
        "detail": "field 'duration_ms' must be integer"
      },
      {
        "index": 7,
        "event_id": "evt_yyy",
        "reason": "duplicate_event_id"
      }
    ]
  }
}
```

### 4.3 事件上报策略（客户端 SDK 侧）

| 策略 | 配置 | 说明 |
| --- | --- | --- |
| 批量大小 | 20 条或 5 秒到达先到条件 | 减少请求频率 |
| 重试 | 指数退避，最多 3 次 | 网络失败场景 |
| 本地队列 | SQLite 持久化，最大 10000 条 | 离线/弱网缓存 |
| 优先级 | 高优先级（支付/错误）立即发送 | 关键事件不延迟 |
| 压缩 | gzip | 减少带宽 |
| 去重 | 本地 event_id 集合 LRU 缓存 | 避免重复生成 |

## 5. 服务端接收层设计（Track Gateway）

### 5.1 处理流水线

```
HTTP Request
    │
    ▼
┌─────────────────┐
│  1. 认证解析     │  ← JWT Token → user_id 解析
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  2. 限流检查     │  ← 每用户 100 events/min, 每设备 200 events/min
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  3. 批次拆分     │  ← 拆成单事件
└────────┬────────┘
         │  (并行处理)
         ▼
┌─────────────────┐
│  4. Schema 校验  │  ← 从 Schema Registry 获取校验规则
└────────┬────────┘
         │
    ┌────┴────┐
    │ 通过    │ 拒绝
    ▼         ▼
┌────────┐ ┌────────────┐
│ 5. 富化 │ │ Reject Log │ → Kafka dead-letter topic
└───┬────┘ └────────────┘
    │
    ▼
┌─────────────────┐
│  6. PII 脱敏     │  ← 对 pii_fields 执行脱敏
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  7. 幂等检查     │  ← Redis Bloom Filter (event_id)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  8. Kafka 发送   │  ← 按 event_category 路由 Topic
└─────────────────┘
```

### 5.2 事件富化（Enrichment）

服务端在写入 Kafka 前补充以下字段：

| 富化字段 | 来源 | 说明 |
| --- | --- | --- |
| `server_ts` | 系统时钟 | 服务端接收时间戳 |
| `receive_delay_ms` | `server_ts - timestamp` | 客户端到服务端的延迟 |
| `ip_hash` | 请求 IP 哈希 | 地域分析，不存原始 IP |
| `country` / `province` | IP 反查 | 省份级地域 |
| `user_plan` | 用户服务 | `free` / `monthly` / `annual` |

### 5.3 PII 脱敏规则

| 字段类型 | 脱敏方式 | 示例 |
| --- | --- | --- |
| 手机号 | 中间 4 位掩码 | `138****5678` |
| 用户答案中的姓名 | 正则替换为 `[NAME]` | `张三同学` → `[NAME]同学` |
| IP 地址 | 仅保留省份 | `1.2.3.4` → `province:guangdong` |
| 设备序列号 | SHA256 哈希 | 原始值不可逆 |

### 5.4 Kafka Topic 路由

```java
public String resolveTopic(TrackEvent event) {
    return switch (event.getEventCategory()) {
        case "learning"  -> "track-learning-events";
        case "commerce"  -> "track-commerce-events";
        case "social"    -> "track-social-events";
        case "system"    -> "track-system-events";
        default          -> "track-unknown-events";  // 告警
    };
}
```

| Topic | 分区数 | 保留时间 | 说明 |
| --- | --- | --- | --- |
| `track-learning-events` | 24 | 7 天 | 学习行为事件 |
| `track-commerce-events` | 6 | 30 天 | 交易转化事件 |
| `track-social-events` | 6 | 7 天 | 社交互动事件 |
| `track-system-events` | 6 | 3 天 | 系统行为事件 |
| `track-dead-letter` | 3 | 14 天 | 校验失败事件 |

**分区策略：** `partition = hash(user_id) % partition_count`，保证同一用户事件有序。

## 6. 流处理层设计

### 6.1 Flink Stream 处理拓扑

```
Kafka: track-learning-events
    │
    ▼
┌─────────────────────────────────┐
│  Source: Kafka Consumer          │
│  group: flink-learning-stream    │
└─────────────┬───────────────────┘
              │
    ┌─────────┴─────────┐
    │                   │
    ▼                   ▼
┌────────────┐   ┌──────────────┐
│ Branch A:  │   │  Branch B:   │
│ 实时聚合    │   │  CEP 检测    │
└─────┬──────┘   └──────┬───────┘
      │                  │
      ▼                  ▼
┌────────────┐   ┌──────────────┐
│ Redis      │   │  Alert /     │
│ (特征更新)  │   │  Push Notify │
└────────────┘   └──────────────┘
```

### 6.2 Branch A：实时聚合算子

#### 6.2.1 用户学习时长聚合

```java
// 5 分钟滚动窗口 — 聚合每个用户的学习时长
DataStream<UserStudyDuration> dailyDuration = learningEvents
    .filter(e -> e.getEventType().equals("learning.session_end"))
    .keyBy(TrackEvent::getUserId)
    .window(TumblingEventTimeWindows.of(Time.minutes(5)))
    .aggregate(new StudyDurationAggregator());

// 结果写入 Redis，供首页和学情服务实时查询
dailyDuration.addSink(new RedisSink<>(
    redisConfig,
    (JedisCluster jedis, UserStudyDuration dur) -> {
        String key = String.format("study:daily:%s:%s", dur.getDate(), dur.getUserId());
        jedis.hincrBy(key, dur.getSubject(), dur.getDurationSec());
        jedis.expire(key, 86400 * 7);  // 7 天过期
    }
));
```

#### 6.2.2 答题正确率滚动计算

```java
// 1 小时滑动窗口 — 计算各知识点最近答题正确率
DataStream<KnowledgeAccuracy> kpAccuracy = answerEvents
    .filter(e -> e.getEventType().equals("question.answer_submitted"))
    .flatMap(new ExtractKnowledgePoints())    // 一题多个知识点 → 展开多条
    .keyBy(e -> Tuple2.of(e.getUserId(), e.getKnowledgePointId()))
    .window(SlidingEventTimeWindows.of(Time.hours(1), Time.minutes(10)))
    .aggregate(new AccuracyAggregator());

// 写入 Redis 实时特征
kpAccuracy.addSink(new RedisSink<>(
    redisConfig,
    (jedis, acc) -> {
        String key = String.format("kp_accuracy:%s:%s",
            acc.getUserId(), acc.getKnowledgePointId());
        jedis.hset(key, "correct_count", String.valueOf(acc.getCorrect()));
        jedis.hset(key, "total_count", String.valueOf(acc.getTotal()));
        jedis.hset(key, "accuracy", String.valueOf(acc.getAccuracy()));
        jedis.expire(key, 3600);  // 1 小时过期
    }
));
```

#### 6.2.3 核心 Redis 实时特征 Key 设计

| Key Pattern | 类型 | TTL | 说明 |
| --- | --- | --- | --- |
| `study:daily:{date}:{user_id}` | Hash | 7d | 当日各科目学习时长（秒） |
| `study:weekly:{week}:{user_id}` | Hash | 30d | 周学习时长汇总 |
| `kp_accuracy:{user_id}:{kp_id}` | Hash | 1h | 知识点最近正确率 |
| `qa_count:daily:{date}:{user_id}` | String | 7d | 当日答题总数 |
| `ai_usage:daily:{date}:{user_id}` | String | 7d | 当日 AI 调用次数 |
| `streak:current:{user_id}` | String | 7d | 连续学习天数 |

### 6.3 Branch B：CEP 复杂事件检测

#### 6.3.1 学习困难模式检测

检测条件：5 分钟内连续答错 3 题 + 每题用时 < 10 秒（可能乱答）

```java
// CEP Pattern: 连续 3 次答错且用时极短
Pattern<TrackEvent, ?> strugglePattern = Pattern
    .<TrackEvent>begin("first_wrong")
        .where(e -> isWrongAnswer(e) && getDuration(e) < 10000)
    .timesOrMore(2)
    .consecutive()
    .within(Time.minutes(5));

CEP.pattern(answerStream.keyBy(TrackEvent::getUserId), strugglePattern)
    .select((events) -> {
        // 触发学习困难预警
        return StruggleAlert.builder()
            .userId(events.get(0).getUserId())
            .knowledgePoints(extractKps(events))
            .timestamp(System.currentTimeMillis())
            .suggestion("推荐切换到更基础的知识点学习")
            .build();
    })
    .addSink(new AlertSink());  // → 推送到 AI 辅导服务做主动干预
```

#### 6.3.2 其他 CEP 检测规则

| 模式名 | 条件 | 触发动作 |
| --- | --- | --- |
| `rapid_exit` | 打开页面 → < 3 秒退出 | 记录无效浏览，不计数 |
| `ai_abuse` | 1 分钟内发送 > 10 条无意义消息 | 触发限流 + 安全审核 |
| `study_streak_broken` | 连续学习中断 | 触发激励推送 |
| `late_night_study` | 23:00 后持续学习 > 30 分钟 | 防沉迷提醒推送 |
| `bulk_purchase_intent` | 反复查看付费页但未购买 | 延迟推送优惠券 |

```sql
    `session_id`     String,
    `page`           LowCardinality(String),
    `module`         LowCardinality(String),
    `subject`        LowCardinality(String) DEFAULT '',
    `properties`     String,              -- JSON 原文
    `ip_hash`        String DEFAULT '',
    `province`       LowCardinality(String) DEFAULT '',
    `user_plan`      LowCardinality(String) DEFAULT '',
    `event_date`     Date MATERIALIZED toDate(timestamp)
)
ENGINE = MergeTree
PARTITION BY toYYYYMMDD(event_date)
ORDER BY (event_type, user_id, timestamp)
TTL event_date + INTERVAL 90 DAY
SETTINGS index_granularity = 8192;
```

**设计要点：**
- `PARTITION BY` 按天分区，便于按日期范围查询和数据生命周期管理
- `ORDER BY` 以 `event_type` 为首列，利用 ClickHouse 稀疏索引加速类型过滤
- `LowCardinality(String)` 用于枚举字段，大幅压缩存储
- `properties` 保留 JSON 原文，兼顾灵活性和查询能力
- 90 天 TTL，超过 90 天的数据由批处理 ETL 汇入数据仓库

### 9.2 SDK 本地处理流程

```dart
// Flutter SDK 伪代码
class TrackSDK {
  final Queue<TrackEvent> _queue = PersistentQueue();  // SQLite 持久化
  final int _maxBatchSize = 20;
  final int _flushIntervalMs = 5000;
  Timer? _flushTimer;

  void track(String eventType, Map<String, dynamic> properties) {
    final event = TrackEvent(
      eventId: Uuid().v4(),
      eventType: eventType,
      timestamp: DateTime.now().millisecondsSinceEpoch,
      // ... 填充公共字段
      properties: properties,
    );

    _queue.add(event);

    // 关键事件立即发送
    if (_isHighPriority(eventType)) {
      _flush();
    }
  }

  void _startFlushTimer() {
    _flushTimer = Timer.periodic(
      Duration(milliseconds: _flushIntervalMs),
      (_) => _flush(),
    );
  }

  Future<void> _flush() async {
    if (_queue.isEmpty) return;

    final batch = _queue.take(_maxBatchSize);
    final batchId = Uuid().v4();

    try {
      final response = await _httpClient.post(
        '/api/v1/track/batch',
        headers: {
          'Content-Encoding': 'gzip',
          'X-Batch-Id': batchId,
          'X-Sdk-Version': sdkVersion,
        },
        body: gzip.encode(jsonEncode({
          'batch_id': batchId,
          'events': batch.map((e) => e.toJson()).toList(),
        })),
      );

      if (response.statusCode == 200) {
        batch.commit();  // 从 SQLite 删除
      } else {
        batch.rollback(); // 保留在队列，下次重试
      }
    } catch (e) {
      batch.rollback();
      // 指数退避
      _flushTimer?.cancel();
      _flushTimer = Timer.periodic(
        Duration(seconds: _nextBackoff()),
        (_) => _flush(),
      );
    }
  }

  bool _isHighPriority(String eventType) {
    return eventType.startsWith('order.') ||
           eventType.startsWith('app.error') ||
           eventType.startsWith('paywall.');
  }

  int _backoffCount = 0;
  int _nextBackoff() {
    final delay = min(60, pow(2, _backoffCount).toInt());
    _backoffCount++;
    return delay;
  }
}
```

## 12. 错误处理与可靠性

### 12.1 错误分类与处理

| 错误场景 | 处理策略 |
| --- | --- |
| Schema 校验失败 | 写入 dead-letter topic，不阻断正常事件 |
| Kafka 发送超时 | 本地内存队列暂存 + 异步重试 3 次 |
| Kafka 不可用 | 降级写入本地 RocksDB → 恢复后回补 |
| ClickHouse 写入失败 | Kafka offset 不提交 → 重试 |
| Flink Checkpoint 失败 | 从最近 checkpoint 恢复，可能重复（幂等保护） |
| Redis 写入失败 | 降级跳过（实时特征非关键路径） |
| 查询超时 | 返回降级结果（空数据 + 提示稍后重试） |

### 12.2 Exactly-Once 语义保障

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│   Kafka     │────→│    Flink     │────→│  ClickHouse  │
│  (源)       │     │  Checkpoint  │     │  (Sink)      │
│             │     │  + 两阶段提交 │     │  idempotent  │
└─────────────┘     └──────────────┘     │  insert      │
                                          └──────────────┘
```

- **Kafka → Flink**：Checkpoint 机制保证 offset 提交与处理状态一致
- **Flink → ClickHouse**：利用 `event_id` 做 ReplacingMergeTree 去重，实现幂等写入
- **重复事件防护**：Redis Bloom Filter 在 Gateway 层做 event_id 去重（99.9% 去重率）

## 16. 接入指南（面向开发人员）

### 16.1 新事件类型接入流程

1. **定义 Schema**：在 Schema Registry 中创建新事件类型定义
2. **评审**：数据团队 + 业务团队评审字段合理性
3. **发布**：Schema 状态置为 `active`
4. **客户端接入**：SDK 中添加埋点调用代码
5. **验证**：联调环境发送测试事件，检查接收、校验、存储全链路
6. **上线**：灰度发布，观察事件量和数据质量

### 16.2 消费事件数据方式

| 使用方 | 接入方式 | 示例 |
| --- | --- | --- |
| 实时服务 | 订阅 Kafka Topic | 学情服务订阅答题事件实时更新掌握度 |
| 离线分析 | 查询 ClickHouse | BI 看板查询留存率 |
| 数据仓库 | Kafka Connect S3 Sink | 全量数据归档到数仓 |
| 问题排查 | 查询 Elasticsearch | 查某用户某时间段的所有行为 |

### 16.3 注意事项

- **禁止在 properties 中嵌套过深的 JSON**（最多 3 层），影响 ClickHouse JSON 提取性能
- **禁止在埋点中传输大段文本**（如完整作文内容），应只传 content_id，内容走业务库查询
- **新增 required 字段需提前 2 周通知客户端团队**，确保 SDK 版本已发版
- **事件命名遵循 `模块.动作` 格式**，如 `question.answer_submitted`、`plan.task_completed`
- **时间戳使用客户端时间**，服务端仅做延迟检测，不修正时间戳（避免分布式时钟不一致）
