## 1. 文档定位与背景

### 1.1 问题：处罚"决策"很多，"执行"没有归属

平台侧已有多份文档负责**产生**处罚决策：

| 上游文档 | 产生的决策 | 对执行层的期待（原文明示） |
| --- | --- | --- |
| 服务端-内容举报与违规处置流转服务 | 判决产出 `penaltyCodes: [USER_MUTE_1D, USER_BAN_PERM, USER_DEVICE_BLOCK, CONTENT_TAKEDOWN...]` | "处置动作**执行**（下线/禁言/封禁）→ 账号体系 / 权限管理：本服务编排并跟踪执行结果" |
| 服务端-用户生成内容安全审核与未成年人社交保护引擎 | 实时拦截/隐藏/删除 + "封禁" | "处置执行服务：执行拦截/隐藏/删除/封禁等操作" |
| 服务端-用户账号安全与登录风控引擎 | 撞库确认 72 小时 → "封禁待审" | "账号解锁/封禁操作" |
| 服务端-AI对话安全审计与敏感内容自动上报服务 | 高危对话上报 → 处置建议 | 需要落地为账号/能力级处罚 |
| 管理后台-用户查询与账号运维服务 | 人工封禁/解封按钮 | 需要底层服务支撑 |

但经核查，三份账号体系文档（`账号体系-详细设计.md`、`用户账号体系-详细设计.md`、`用户基础服务与身份认证系统-详细设计.md`）对"封禁/禁言/冻结/BANNED/处罚"**零覆盖**，全库也没有任何文档定义"处罚台账/封禁执行"。典型断裂场景：

1. 举报判决通过，`USER_MUTE_7D` 指令发出，但**没有任何服务负责把账号置为禁言态、在 UGC 写入时拦截、7 天后自动解除**；
2. 登录风控判定"封禁待审"，但账号表没有状态字段承载，封禁期间 Token 是否吊销、已登录设备是否踢下线无定义；
3. 申诉成功（`violation.case.reversed`）产生 `account.unmute` 撤销动作，无人消费；
4. 累犯没有梯度升级：三次轻微违规与一次轻微违规处罚相同；
5. 被封禁的年卡会员，订阅继续扣费/续费是否允许、能否退款，无规则。

**本服务即补齐这条执行链路**：作为账号状态与处罚执行的**唯一权威（Source of Truth）**，向上承接各类处罚指令，向下编排认证中心、设备指纹、内容服务、通知中心完成执行，并负责台账、到期解除、申诉撤销、梯度升级、豁免保护与审计。

### 1.2 职责边界（做什么 / 不做什么）

| 职责 | 归属 |
| --- | --- |
| 账号主状态（正常/冻结/限时封禁/永久封禁）与能力门控（禁言等）的存储与判定 | **本服务** |
| 处罚指令幂等接收、逐项执行、execStatus 回报 | **本服务** |
| 处罚台账、累积违规分、梯度升级计算 | **本服务** |
| 到期自动解除、申诉撤销执行 | **本服务** |
| 豁免名单（测试号/名师/B端机构号）与二级审批 | **本服务** |
| 违规**案件的流转**（举报领取/判决/申诉受理） | 内容举报与违规处置流转服务（本服务只消费其判决结果） |
| 风险分计算、设备指纹采集、IP 信誉 | 统一风控决策中心 / 设备指纹与反作弊风控引擎 |

| 处罚通知文案渲染与多渠道投递 | 统一通知消息模板引擎（本服务发事件+结构化参数） |

## 2. 领域概念与统一语言

| 术语 | 英文/字段 | 说明 |
| --- | --- | --- |
| 处罚指令 | PenaltyCommand | 一次原子执行请求，含 1..N 个处罚动作项（PenaltyItem）。上游判决/风控/人工操作均转化为指令 |
| 处罚动作码 | penalty_code | 平台统一枚举：`USER_WARNING`、`USER_MUTE_1D/3D/7D/30D`、`USER_BAN_LIMITED`、`USER_BAN_PERM`、`USER_DEVICE_BLOCK`、`CAP_AI_CHAT_LIMIT`、`CAP_SNAPSHOT_LIMIT`、`CAP_COMMENT_LIMIT`（与举报处置服务判决协议完全一致，禁止各自新增） |
| 账号主状态 | account_status | `NORMAL` / `FROZEN`（限制登录）/ `BANNED_LIMITED`（限时封禁）/ `BANNED_PERM`（永久封禁）/ `DEACTIVATED`（用户自主注销，非处罚态） |
| 能力门控 | capability gate | 叠加在 NORMAL 之上的细粒度限制：`mute`（禁言，全 UGC 写禁止）、`ai_chat_limit`、`snapshot_limit`、`comment_limit`。**禁言不是账号状态，是能力态**——这与举报处置服务的 `USER_MUTE_*` 语义对齐 |
| 处罚台账 | penalty_ledger | 不可变事实表，记录每一次施加于用户的处罚（谁、因何案件、什么处罚、起止时间、撤销原因） |
| 违规积分 | violation_score | 0~100 累积分，用于梯度升级与风控画像衰减。UGC 审核引擎已有 0~100 语义，本服务为全平台统一账户 |
| 豁免名单 | exemption | `TEST_ACCOUNT`（永不处罚）、`PROTECTED`（名师/官方号，处罚需二级审批）、`B2B_ORG`（机构账号，处罚前需通知商务） |
| 撤销 | revert | 申诉成功或人工纠错后，逆向执行处罚（解除禁言/封禁、回滚违规分） |
| 到期解除 | expire | 时效性处罚（禁言 N 天、限时封禁）到期自动解除 |

## 3. 总体架构

```text
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 举报处置服务  │ UGC安全审核   │ 登录风控引擎  │ 管理后台运维  │
│ (判决penalty) │ (实时拦截)    │ (封禁待审)    │ (人工封/解)   │
└──────┬───────┴──────┬───────┴──────┬───────┴──────┬───────┘
       │  统一内部 API │              │              │
       ▼              ▼              ▼              ▼
┌─────────────────────────────────────────────────────────────┐
│           用户违规处罚执行与账号状态管控服务（本服务）          │
│  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌─────────────┐  │
│  │ 指令接收   │ │ 梯度策略   │ │ 账号状态机 │ │ 到期解除调度  │  │
│  │ 幂等/校验  │ │ 升级/降级  │ │ CAS+缓存   │ │ 延迟任务+兜底 │  │
│  └───────────┘ └───────────┘ └───────────┘ └─────────────┘  │
│  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌─────────────┐  │
│  │ 执行编排   │ │ 台账/审计  │ │ 豁免/审批  │ │ 事件发布     │  │
│  │ Saga补偿  │ │ violation │ │ 二级审批   │ │ Outbox      │  │
│  └───────────┘ └───────────┘ └───────────┘ └─────────────┘  │
└────┬─────────┬──────────┬──────────┬───────────┬────────────┘
     ▼         ▼          ▼          ▼           ▼
 认证中心   设备指纹服务  通知中心   会员/订阅   消息队列(MQ)
(token吊销)(设备黑名单) (用户/监护人)(冻结/退款) (penalty.* 事件)

读路径（高频）：API网关 / 登录服务 / UGC写入 / AI对话入口
     └──► GET /internal/v1/users/{id}/account-state （两级缓存，P99 < 5ms）
```

**关键设计决策：**

1. **读写分离双路径**：处罚是低频写（日均千级），但状态判定是超高频读（登录、每次 UGC 写入、每次 AI 对话入口校验，日均千万级）。读路径走两级缓存（本地 Caffeine 30s + Redis），写路径强一致落库后主动失效缓存。
2. **禁言=能力门控而非账号状态**：被禁言用户仍可正常学习（看课、做题、问 AI），仅 UGC 写入被拦——未成年人产品不应因社交违规阻断学习主链路。
3. **封禁/冻结=账号主状态**：影响登录与全量功能，变更时必须吊销全端 Token。
4. **指令幂等 + 逐项回报**：与举报处置服务 `violation.case.event` 的 `execStatus: SUCCESS/PARTIAL` 协议对齐，部分失败可重试可人工介入。

## 4. 账号状态模型

### 4.1 账号主状态机

```text
                    ┌────────────────────────────────────┐
                    │          DEACTIVATED                │
                    │      （用户自主注销，非处罚）          │
                    └──────────────▲─────────────────────┘
                                   │ 注销流程（数据导出与账户注销服务）
┌──────────┐  FROZEN指令   ┌──────┴─────┐  BAN_LIMITED指令  ┌──────────────┐
│  NORMAL  │ ───────────► │   FROZEN   │ ───────────────► │ BANNED_LIMITED│
│          │ ◄─────────── │(限制登录)   │ ◄─────────────── │ (限时封禁)     │
└────┬─────┘  解冻/到期    └────────────┘   到期/撤销       └──────┬───────┘
     │                                                        │ 升级(累犯/二审)
     │  BAN_PERM 指令（二级审批后）                              ▼
     └────────────────────────────────────────────► ┌──────────────┐
                （永久封禁不可自动恢复，仅人工+法务复核） │  BANNED_PERM │
                                                    └──────────────┘
```

**状态语义与拦截行为矩阵：**

| account_status | 登录 | 已登录会话 | 学习功能 | UGC 写入 | AI 对话 | 支付/续费 |
| --- | --- | --- | --- | --- | --- | --- |
| NORMAL | ✅ | ✅ | ✅ | 受能力门控 | 受能力门控 | ✅ |
| FROZEN | ❌ 提示"账号已冻结，申诉入口" | 全端踢下线（Token 吊销） | ❌ | ❌ | ❌ | ❌ |
| BANNED_LIMITED | ❌ 提示剩余封禁时长 | 全端踢下线 | ❌ | ❌ | ❌ | ❌（自动续费强停） |
| BANNED_PERM | ❌ | 全端踢下线 | ❌ | ❌ | ❌ | ❌（进入退款评估） |
| DEACTIVATED | ❌（冷静期内可恢复，见注销文档） | 全端踢下线 | ❌ | ❌ | ❌ | ❌ |

> FROZEN 用于"证据未实锤但风险极高"场景（如登录风控"封禁待审"），与 BANNED_* 的区别：解冻更快（复核通过即恢复）、对用户文案更缓和、不进入违规分累积（未定性）。

**状态迁移表（完整）：**

| 当前状态 | 事件 | 目标状态 | 守卫条件 | 副作用 |
| --- | --- | --- | --- | --- |
| NORMAL | freeze 指令 | FROZEN | 非豁免或已过二级审批 | 吊销全端 Token、清缓存、通知 |
| FROZEN | unfreeze（复核通过/撤销） | NORMAL | 存在 ACTIVE 态 freeze 指令 | 通知、清缓存 |
| FROZEN | freeze_expire 到期 | NORMAL | `frozen_until <= now` 且未续冻 | 同上 |
| FROZEN | escalate_to_ban（复核定罪） | BANNED_LIMITED / BANNED_PERM | 二级审批（PERM 必须） | 同封禁 |
| NORMAL/FROZEN | ban_limited 指令 | BANNED_LIMITED | 二级审批 | 吊销 Token、停续费、通知+监护人告知 |
| BANNED_LIMITED | ban_expire 到期 | NORMAL | `banned_until <= now` | 清缓存、通知"已解封"、续费恢复评估 |
| BANNED_LIMITED | revoke（申诉成功） | NORMAL | 指令状态=EXECUTED 且申诉链路有效 | 同上+违规分回滚 |
| BANNED_LIMITED | escalate（累犯升级/新判决） | BANNED_PERM | 二级审批 | 通知、退款评估 |
| BANNED_PERM | manual_unban（人工+法务复核） | NORMAL | 双审批人、审批单留痕 | 审计高亮、通知 |
| 任意处罚态 | deactivate（用户申请注销） | DEACTIVATED | 注销服务流程 | 走注销文档链路 |

### 4.2 能力门控（Capability Gate）叠加模型

能力门控存储为 `user_account_state.capabilities` JSON 数组，每项含 `code / until / penaltyCommandId`：

```json
{
  "mutes": [
    { "code": "mute", "scope": "ALL_UGC", "until": "2026-08-23T03:12:00Z", "penaltyCommandId": "PC20260816000042" }
  ],
  "limits": [
    { "code": "ai_chat_limit", "dailyQuota": 3, "until": "2026-08-30T00:00:00Z", "penaltyCommandId": "PC20260816000043" }
  ]
}
```

| 能力码 | 拦截点 | 对应 penalty_code |
| --- | --- | --- |
| mute | UGC 发布/评论/回复/昵称头像修改 | USER_MUTE_1D/3D/7D/30D |
| ai_chat_limit | AI 对话入口（降为每日 3 次） | CAP_AI_CHAT_LIMIT |
| snapshot_limit | 拍题入口（降为每日 5 次） | CAP_SNAPSHOT_LIMIT |
| comment_limit | 仅评论/回复禁写（可发动态） | CAP_COMMENT_LIMIT |

**叠加规则**：同类能力多条并存取 `until` 最晚者；解除（revert/expire）只清除由指定 `penaltyCommandId` 施加的那一条——保证"申诉成功精确撤销本次处罚，不影响其他在罚期"。

### 4.3 并发控制模型

- `user_account_state` 带 `version` 乐观锁；状态变更统一为 `UPDATE ... SET status=?, version=version+1 WHERE user_id=? AND version=?`，影响 0 行即并发冲突，重读后按状态机守卫重试（最多 3 次）。
- **同一用户处罚指令串行化**：以 `penalty:lock:{userId}` 分布式锁（服务端-分布式锁实现规范，TTL 10s）包裹"读状态→计算→CAS 写"，避免并发判决互相覆盖（如同时 MUTE_1D 与 MUTE_7D，取重者）。
- 写成功后 `DEL acct:state:{userId}`（Redis）并广播本地缓存失效消息（频道 `penalty.state.invalidate`，本地缓存 TTL 30s 兜底）。

## 5. 数据结构定义

### 5.1 user_account_state（账号状态表，本服务权威）

```sql
CREATE TABLE `user_account_state` (
  `user_id`           BIGINT UNSIGNED NOT NULL COMMENT '用户ID（同账号体系）',
  `account_status`    VARCHAR(20)  NOT NULL DEFAULT 'NORMAL'
      COMMENT 'NORMAL/FROZEN/BANNED_LIMITED/BANNED_PERM/DEACTIVATED',
  `status_changed_at` DATETIME(3)  NULL COMMENT '当前状态生效时间',
  `frozen_until`      DATETIME(3)  NULL COMMENT 'FROZEN 到期时间（NULL=需人工解冻）',
  `banned_until`      DATETIME(3)  NULL COMMENT 'BANNED_LIMITED 到期时间（NULL=PERM/人工）',
  `banned_reason`     VARCHAR(255) NULL COMMENT '封禁原因摘要（对用户可见文案 key）',
  `capabilities`      JSON         NULL COMMENT '能力门控数组，见 §4.2',
  `violation_score`   TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '累积违规分 0-100',
  `last_penalty_at`   DATETIME(3)  NULL COMMENT '最近一次处罚时间（梯度时间窗锚点）',
  `exempt_level`      VARCHAR(20)  NOT NULL DEFAULT 'NONE'
      COMMENT 'NONE/TEST_ACCOUNT/PROTECTED/B2B_ORG',
  `version`           INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '乐观锁版本',
  `created_at`        DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`        DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`user_id`),
  KEY `idx_status_until` (`account_status`, `frozen_until`),
  KEY `idx_status_until2` (`account_status`, `banned_until`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='账号状态与处罚权威表';
```

### 5.2 penalty_command（处罚指令表，幂等核心）

```sql
CREATE TABLE `penalty_command` (
  `id`                 VARCHAR(32)  NOT NULL COMMENT '指令ID，PC+yymmdd+序列',
  `idempotent_key`     VARCHAR(128) NOT NULL COMMENT '幂等键：source+sourceRef，如 report:R20260815...:judge:v3',
  `source`             VARCHAR(30)  NOT NULL
      COMMENT 'REPORT_JUDGE/UGC_AUDIT/LOGIN_RISK/AI_SAFETY/ADMIN_MANUAL/RISK_CENTER',
  `source_ref`         VARCHAR(64)  NOT NULL COMMENT '上游单据号（reportNo/审核批次/风控决策ID/审批单号）',
  `target_user_id`     BIGINT UNSIGNED NOT NULL,
  `items`              JSON         NOT NULL COMMENT 'PenaltyItem 数组：[{code,expireDays,reason,...}]',
  `status`             VARCHAR(20)  NOT NULL DEFAULT 'RECEIVED'
      COMMENT 'RECEIVED/APPROVING/EXECUTING/EXECUTED/PARTIAL/REVERTED/EXPIRED/REJECTED/CANCELLED',
  `approval_ticket`    VARCHAR(64)  NULL COMMENT '二级审批单号（USER_BAN_PERM/USER_DEVICE_BLOCK 必填）',
  `expire_at`          DATETIME(3)  NULL COMMENT '整条指令处罚效果到期时间（取 items 最晚者）',
  `exec_report`        JSON         NULL COMMENT '逐项执行结果，对齐 violation.case.executed 协议',
  `retry_count`        TINYINT      NOT NULL DEFAULT 0,
  `created_at`         DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at`         DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_idempotent` (`idempotent_key`),
  KEY `idx_user_status` (`target_user_id`, `status`),
  KEY `idx_expire` (`status`, `expire_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='处罚指令';
```

### 5.3 penalty_ledger（处罚台账，不可变，只 INSERT）

```sql
CREATE TABLE `penalty_ledger` (
  `id`                 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `penalty_command_id` VARCHAR(32)  NOT NULL,
  `user_id`            BIGINT UNSIGNED NOT NULL,
  `penalty_code`       VARCHAR(30)  NOT NULL COMMENT '与指令 items 对应',
```

## 6. API 接口设计

统一走 API 网关。内部接口（`/internal/**`）走服务间鉴权（mTLS + 服务账号，见服务端-请求上下文传递与服务间调用规范）；管理端接口需权限 `penalty:manage`（PROTECTED 解封等高危操作需 `penalty:manage:level2`）。响应遵循平台统一封装 `{code, message, data}`（服务端-统一响应封装与分页查询规范）。

### 6.1 下发处罚指令（内部，核心写入口）

```
POST /internal/v1/penalty-commands
Idempotency-Key: report:R2026081500001234567:judge:v3      （或 Header X-Idempotent-Key）
```

```json
{
  "source": "REPORT_JUDGE",
  "sourceRef": "R2026081500001234567",
  "targetUserId": 10086,
  "operatorId": null,
  "autoPolicy": false,
  "items": [
    { "code": "USER_MUTE_7D", "reasonCode": "POLICY_BULLY", "reasonText": "学习圈辱骂他人" },
    { "code": "CONTENT_TAKEDOWN", "targetResource": "ugc:post:88231002" }
  ]
}
```

- `autoPolicy=true` 时**不传 items 的处罚强度**，仅传 `reasonCode + severity`，由本服务按 §7 梯度策略计算动作（登录风控/UGC 审核走此模式）；`autoPolicy=false` 时直采 items（举报判决已定罚）。
- 同步返回（最佳努力执行后）：

```json
{
  "code": 0,
  "data": {
    "commandId": "PC20260816000042",
    "status": "EXECUTED",
    "items": [
      { "penaltyCode": "USER_MUTE_7D", "targetUserId": 10086,
        "expireAt": "2026-08-23T03:12:00Z", "execStatus": "SUCCESS" },
      { "penaltyCode": "CONTENT_TAKEDOWN", "targetResource": "ugc:post:88231002",
        "execStatus": "SKIPPED", "detail": "委托举报处置编排，非本服务执行项" }
    ]
  }
}
```

- **幂等**：`uk_idempotent` 唯一键；重复提交返回首次结果（HTTP 200，`data.duplicated=true`）。
- **需审批**：items 含 `USER_BAN_PERM` / `USER_DEVICE_BLOCK` 且目标非 TEST_ACCOUNT → 同步返回 `status=APPROVING` + `approvalTicket`，审批通过后异步执行（审批流复用服务端-业务状态机与通用工作流引擎）。
- **错误码**：

| code | HTTP | 场景 | 上游处理 |
| --- | --- | --- | --- |
| `PENALTY_USER_NOT_FOUND` | 404 | 用户不存在 | 校验上游数据 |
| `PENALTY_EXEMPT_REJECTED` | 422 | TEST_ACCOUNT 拒绝处罚 | 记录跳过，事件回报 SKIPPED |
| `PENALTY_AWAITING_APPROVAL` | 202 | 转二级审批 | 等审批事件 |
| `PENALTY_CONFLICT` | 409 | 幂等键相同但参数不同 | 修正后重试（key 含版本号可避免） |
| `PENALTY_INVALID_ITEM` | 400 | 未知 penalty_code / 参数缺失 | 修正请求 |

## 7. 梯度处罚策略引擎

### 7.1 计算流程（autoPolicy=true 时）

```text
输入: reasonCode + severity + targetUserId
  │
  ①查豁免 → TEST_ACCOUNT 直接 REJECTED(SKIPPED)；PROTECTED/B2B_ORG → 转审批并通知
  │
  ②统计 180 天窗口内该 reasonCode 的台账 ACTIVE+REVERTED+EXPIRED 记录数 → occurrence=N
  │
  ③查规则 (reasonCode, severity, occurrence)；
  │    命中不到则按 severity 兜底默认表：
  │      MINOR    → USER_WARNING，score +5
  │      MODERATE → USER_MUTE_1D，score +15
  │      SEVERE   → USER_MUTE_7D，score +30
  │      CRITICAL → USER_BAN_LIMITED(30d)，score +50，need_approval=1
  │
  ④未成年人(年龄<18 或学段∈{幼儿,小学,初中})规则降级：
  │    CRITICAL 的 PERM → MUTE_30D + 强制监护人告知（对齐举报处置合规红线：
  │    "不得对未成年人永久封号而不告知监护人"）
  │
  ⑤violation_score 跨阈值自动升级：
  │    score ≥ 60 → 本次处罚至少升一档（WARNING→MUTE_1D→MUTE_7D→BAN_LIMITED 30d）
  │    score ≥ 85 → 直接 USER_BAN_LIMITED(90d) + 二级审批
  │
  ⑥产出 PenaltyItem[] + score_delta → 进入执行编排
```

### 7.2 规则示例（初始种子数据）

| reason_code | severity | occurrence | base_penalty | score_delta |
| --- | --- | --- | --- | --- |
| UGC_RISK_BULLY | MODERATE | 1 | USER_MUTE_1D | 15 |
| UGC_RISK_BULLY | MODERATE | 2 | USER_MUTE_7D | 20 |
| UGC_RISK_BULLY | SEVERE | 1 | USER_MUTE_7D | 30 |
| UGC_RISK_FRAUD | CRITICAL | 1 | USER_BAN_LIMITED(30d)+USER_DEVICE_BLOCK | 50（需审批） |

| LOGIN_CREDENTIAL_STUFF | SEVERE | 1 | FROZEN(72h)（复核通道） | 20 |

### 7.3 违规分衰减

每日 03:00 定时任务：对 90 天内无新处罚的用户 `violation_score = max(0, score - ceil(score*0.05))`（指数衰减），保证"改过自新"路径；每次处罚 `last_penalty_at` 刷新。衰减只改分不改台账。

### 8.2 编排骨架与补偿（关键代码示例，Java/Spring）

```java
@Service
public class PenaltyCommandExecutor {

    // 步骤定义：每步独立可重试、可跳过、失败不阻断后续步骤（除状态变更失败=整体失败）
    private static final int MAX_RETRY = 3;

    public ExecReport execute(PenaltyCommand cmd) {
        ExecReport report = new ExecReport(cmd.getId());
        UserAccountState state = stateRepo.findForUpdate(cmd.getTargetUserId())
                .orElseGet(() -> stateRepo.lazyCreate(cmd.getTargetUserId()));

        // ① 豁免守卫（TEST_ACCOUNT 拒绝；PROTECTED 走审批已在接收阶段拦截）
        if (state.getExemptLevel() == ExemptLevel.TEST_ACCOUNT) {
            return report.reject(ExecStatus.REJECTED, "TEST_ACCOUNT protected");
        }

        boolean affectLogin = cmd.getItems().stream()
                .anyMatch(i -> i.getCode().affectsAccountStatus()); // BAN_*/FREEZE

        // ② 台账先行（同事务）
        List<PenaltyLedger> ledgers = ledgerService.bookKeeping(cmd, state);

        // ③ 状态与能力变更（分布式锁 + 乐观锁 CAS，见 §4.3）
        StateChangeResult scr = stateMachine.apply(cmd, state);
        logStep(cmd, "STATE_CHANGE", scr.isSuccess(), scr.getDetail());
        if (!scr.isSuccess()) return report.fail(scr);   // 整体失败，进重试队列

        // ④ 下游编排：失败只记 PARTIAL，不回滚状态（状态是事实，下游可补偿）
        if (affectLogin) {
            StepResult r = retryable(() -> authCenterClient.revokeAllTokens(cmd.getTargetUserId()),
                                     "TOKEN_REVOKE", cmd);
            // 认证中心内部实现：SCAN 设备会话 → 逐 jti 写 auth:revoke:{jti}（TTL=Token剩余期）
        }
        for (PenaltyItem item : cmd.itemsOf("USER_DEVICE_BLOCK")) {
            StepResult r = retryable(() -> deviceClient.blocklist(cmd.getTargetUserId(),
                                     item.getDeviceIds(), item.getUntil()),
                                     "DEVICE_BLOCK", cmd);
        }
        StepResult n1 = retryable(() -> notifyClient.sendUserPenalty(cmd, scr), "NOTIFY", cmd);
        if (state.isMinor()) {
            StepResult n2 = retryable(() -> notifyClient.sendGuardianPenalty(cmd, scr), "NOTIFY_GUARDIAN", cmd);
            // 未成年处罚必须监护人告知（合规红线），失败单告警人工跟进
        }
        if (affectLogin) {
            StepResult s = retryable(() -> subscriptionClient.freezeIfNeeded(cmd), "SUBSCRIPTION", cmd);
            // 自动续费强停；PERM 触发退款评估工单（不自动退）
        }

        // ⑤ Outbox 事件（与 ②③ 同 DB 事务；此处补偿写保证最终必达）
        outboxService.ensurePublished("penalty.executed", PenaltyEvents.executed(cmd, report));

        // ⑥ 缓存失效 + 到期任务
        cacheInvalidator.evict(cmd.getTargetUserId());
        ledgers.stream().filter(l -> l.getOriginalUntil() != null)
               .forEach(l -> delayTaskClient.register(
                       "penalty-expire", cmd.getId(),
                       l.getOriginalUntil(), Map.of("ledgerId", l.getId())));

        return report.done(scr);
    }

    private StepResult retryable(Supplier<StepResult> action, String step, PenaltyCommand cmd) {
        for (int i = 1; i <= MAX_RETRY; i++) {
            try {
                StepResult r = action.get();
                executionLogRepo.insert(cmd.getId(), step, r.getStatus(), r.getDetail(), i);
                return r;
            } catch (Exception e) {
                if (i == MAX_RETRY) {
                    executionLogRepo.insert(cmd.getId(), step, "FAILED", e.getMessage(), i);
                    return StepResult.failed(e.getMessage());
                }
                sleepBackoff(i); // 200ms * 2^(i-1) + jitter
            }
        }
        throw new IllegalStateException("unreachable");
    }
}
```

### 8.3 状态变更 CAS（状态机核心）

```java
public StateChangeResult apply(PenaltyCommand cmd, UserAccountState state) {
    RLock lock = redisson.getLock("penalty:lock:" + state.getUserId());
    if (!lock.tryLock(2, 10, TimeUnit.SECONDS)) {
        return StateChangeResult.busyRetry();      // 上层按指数退避重试 3 次
    }
    try {
        AccountStatus from = state.getAccountStatus();
        AccountStatus to = transition(from, cmd);  // 按 §4.1 迁移表 + 守卫条件
        if (to == null) {
            // 非法迁移：如 NORMAL 直接 BAN_PERM（缺审批）→ 拒绝并留痕
            return StateChangeResult.illegal(from, cmd);
        }
        // 同类重罚覆盖：新 MUTE_7D 与在罚 MUTE_1D 并存时取 until 最晚（§4.2 叠加规则）
        state.applyItems(cmd.getItems(), clock.now());
        int affected = stateRepo.casUpdate(state, from, to);   // version 乐观锁
        if (affected == 0) return StateChangeResult.conflict(); // 重读重试
        outboxService.publishTx("account.state.changed",
                AccountEvents.changed(state.getUserId(), from, to, state.getVersion()));
        return StateChangeResult.ok(from, to);
    } finally {
        lock.unlock();
    }
}
```

```java
public AccountStateView queryState(long userId, String scene) {
    AccountStateView v = localCache.getIfPresent(userId);        // Caffeine 30s
    if (v != null) return v;
    String key = "acct:state:" + userId;
    v = redis.get(key, AccountStateView.class);                  // TTL 5min
    if (v == null) {
        UserAccountState s = stateRepo.findById(userId).orElse(UserAccountState.normalDefault(userId));
        v = AccountStateView.from(s);
        redis.setex(key, Duration.ofMinutes(5), v);
    }
    localCache.put(userId, v);                                   // 布隆防穿透：不存在的用户缓存 NORMAL 空对象 60s
    return v;
}
// 写路径失效：DEL redis key + MQ 广播 penalty.state.invalidate → 各实例 localCache.invalidate(userId)
```

**解除语义细则：**

1. 能力门控解除只移除 `penaltyCommandId` 匹配项（§4.2），不影响其他在罚；

## 10. penalty_command 状态机汇总

```text
RECEIVED ──校验失败──► REJECTED
   │
   ├─需审批──► APPROVING ──审批通过──► EXECUTING ──全成功──► EXECUTED ─┬─时效到期──► EXPIRED
   │              │                      │                          │
   │              └─审批驳回──► CANCELLED ├─部分失败──► PARTIAL ──────┤
   └─无需审批──► EXECUTING               │   （补偿重试后可转 EXECUTED）├─申诉/人工撤销──► REVERTED
                                          └─状态变更失败──► RECEIVED(重试) └─PERM 无到期，人工 unban→REVERTED
```

| 状态 | 语义 | 后续可迁移 |
| --- | --- | --- |
| RECEIVED | 已接收待处理 | EXECUTING / REJECTED |
| APPROVING | 二级审批中 | EXECUTING / CANCELLED |
| EXECUTING | 编排执行中 | EXECUTED / PARTIAL / RECEIVED(重试) |
| EXECUTED | 全部执行成功 | EXPIRED / REVERTED |
| PARTIAL | 部分下游失败（状态已生效） | EXECUTED(补偿后) / EXPIRED / REVERTED |
| REVERTED | 已撤销/解除（终态，台账可查链路） | — |
| EXPIRED | 时效到期自动解除（终态） | — |
| REJECTED / CANCELLED | 拒绝（豁免/非法）/ 审批驳回 | — |

## 11. 错误处理与补偿矩阵

| 失败点 | 影响 | 策略 | 兜底 |
| --- | --- | --- | --- |
| 幂等键冲突且参数不同 | 上游重试风暴 | 409 + `PENALTY_CONFLICT`，要求 key 加版本 | — |
| DB 状态 CAS 连续 3 次冲突 | 指令滞留 | 回 RECEIVED，指数退避重试，>5 次告警 | 人工工单（安全工作台） |
| 认证中心 Token 吊销失败 | 封禁后仍在线 | PARTIAL + 重试 3 次 | 网关侧每请求校验 account-status（读缓存 ≤30s 陈旧容忍），最终一致 |
| 设备指纹 blocklist 失败 | 换号复发 | PARTIAL + 重试 | 风控画像标记，下次登录风控加强核验 |
| 通知失败 | 用户不知情 | 重试 3 次 | 未成年监护人告知失败→人工外呼工单（合规必须触达） |
| 会员冻结失败 | 封禁期继续扣费 | 重试 + 告警 | 支付对账任务发现"封禁态扣费成功"→自动冲正+退款工单 |
| Outbox 投递失败 | 上游 case 滞留 EXECUTING | Outbox 补偿扫描（5min） | 对账任务：penalty_command vs violation.case 状态 diff 告警 |
| 到期延迟任务丢失 | 超期羁押 | §9 兜底扫描（60s 容差） | 指标 `penalty_overdue_release` 告警 |
| 审批单超时（72h 未处理） | 重罚无法落地 | 自动升级提醒主管；期间账号保持 FROZEN（而非放任） | SLA 告警 |
| 服务宕机重启 | EXECUTING 中断 | 指令表+execution_log 断点续跑（按 step 补齐） | 启动扫描 EXECUTING 超过 10min 的指令 |

## 12. 安全与审计

1. **接口安全**：`/internal/**` mTLS + 服务账号白名单；管理端接口走 RBAC（`penalty:manage` / `penalty:manage:level2`），全部操作进审计日志（服务端-审计日志与操作追溯系统：before/after 快照、操作者、IP、审批单号）。
2. **二级审批**：`USER_BAN_PERM`、`USER_DEVICE_BLOCK`、PROTECTED 账号任意处罚、PERM 解封——四类强制；审批流复用业务状态机与通用工作流引擎，审批人与发起人不得相同。
3. **台账不可变**：penalty_ledger 仅 INSERT；state 变更只允许通过 `end_type` 字段表达生命周期，禁止 UPDATE 处罚内容字段。
4. **用户可见性**：处罚通知须含原因 key、到期时间、申诉入口（拉起举报处置服务申诉链路）；FROZEN 登录页文案区分"冻结"与"封禁"。
5. **数据合规**：台账保留 3 年（合规审计需要），到期转入归档库（服务端-数据归档与生命周期管理策略）；reason_text 属用户相关敏感数据，管理端展示走脱敏规则引擎。

## 13. 监控指标与告警

| 指标 | 口径 | 告警阈值 |
| --- | --- | --- |
| `penalty_exec_success_rate` | EXECUTED / (EXECUTED+PARTIAL) 5min | < 99% 告警 |
| `penalty_state_query_p99` | §6.2 接口延迟 | > 10ms（缓存击穿排查） |
| `penalty_overdue_release` | 兜底扫描解除数（>0 即延迟任务失效） | > 5/h 告警 |

## 14. 容量估算

- 写路径：日均处罚指令 ≤ 5k，峰值 50 QPS（运营专项整治），单实例轻松承载；核心是**读**：DAU 100 万 × 登录+UGC 校验+AI 入口 ≈ 日均 3000 万读，两级缓存命中率目标 > 99.5%，DB 读 QPS < 200，单主库可承载。
- 表增长：penalty_ledger 日均 1 万行（含多 item），年 365 万行，3 年 ~1100 万行，按 user_id+imposed_at 索引无压力；执行日志 5 倍量级，保留 90 天后归档。
- Redis：`acct:state:{userId}` 100 万 key × ~0.5KB ≈ 500MB，符合容量规划。

## 15. 验收场景（测试用例级）

1. 举报判决 MUTE_7D → 登录态不受影响，发动态被拦（文案含剩余时间），7 天后自动可发，台账 EXPIRED；
2. 禁言期间发 AI 对话正常、拍题正常（学习主链路不被社交处罚阻断）；
3. 同一判决重复投递（同幂等键）→ 返回首次结果，台账仅一条；
4. MUTE_1D 在罚期间又判 MUTE_7D → until 取最晚，两条台账独立，1D 到期不解除（7D 仍在罚）；
5. MUTE_1D 申诉成功 revert → 立即可发动态，但另一条 MUTE_7D 不受影响（按 commandId 精确解除）；
6. BAN_LIMITED(30d) 执行 → 全端 Token 吊销、重新登录提示剩余天数、自动续费已强停；
7. BAN_LIMITED 期间自动续费仍扣款成功（模拟）→ 对账任务自动冲正并生成退款工单；
8. 未成年人 CRITICAL 判决 PERM → 自动降级 MUTE_30D + 监护人收到告知通知；
9. TEST_ACCOUNT 下发任意处罚 → REJECTED，台账留 SKIPPED 痕迹；
10. PROTECTED 账号处罚 → APPROVING，主管驳回 → CANCELLED，账号全程不受影响；
11. `USER_BAN_PERM` 无审批直接调用内部 API → `PENALTY_ILL` 拒绝（守卫：无 approvalTicket）；
12. PERM 解封走双审批接口，审批人=发起人 → 拒绝；
13. 认证中心吊销超时（模拟）→ 指令 PARTIAL、网关仍拦截新请求、补偿后 EXECUTED；
14. 到期延迟任务被杀 → 兜底扫描 5 分钟内解除，指标 `penalty_overdue_release` 计数；
15. 高频读：封禁生效后 ≤30s 内网关/UGC 侧可见（本地缓存过期上限），写后主动失效场景 ≤1s 生效；
16. 180 天窗口累犯：第 2 次 UGC_RISK_BULLY MODERATE → 自动 MUTE_7D（occurrence=2 规则），无需人工改判；
17. violation_score 累积到 85 后再犯 MINOR → 自动升档 BAN_LIMITED(90d) 并转审批。
