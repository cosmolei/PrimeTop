# 服务端 - 用户转化漏斗分析与增长归因引擎 详细设计

> 版本：v1.0 | 日期：2026-06-18 | 状态：初稿

## 1. 模块概述

### 1.1 功能定位

用户转化漏斗分析与增长归因引擎（User Conversion Funnel & Growth Attribution Engine）是 PrimeTop 平台增长分析体系的核心组件，负责对用户从注册到付费的关键旅程进行漏斗建模、转化率分析、流失节点诊断和跨触点归因，为产品迭代、增长实验和商业化决策提供量化支撑。

**与现有分析模块的边界划分：**

| 现有模块 | 关注点 | 本模块差异 |
|---------|--------|-----------|
| 用户活跃度统计与留存分析引擎 | DAU/WAU/MAU、留存率、Cohort 分析 | 本模块关注**转化路径**而非活跃度快照，回答"用户为何转化/流失"而非"多少用户活跃" |
| 用户流失预警与智能挽留策略引擎 | 识别流失风险用户并触发挽留干预 | 本模块关注**全局转化漏斗**和**归因**，不负责个体级别的实时干预 |
| 运营活动创建配置与效果归因分析 | 单次运营活动的效果追踪与 ROI | 本模块关注**产品级跨周期归因**，而非单次活动效果 |
| 用户生命周期价值预测与会员升级意向 | 个体 LTV 预测与升级倾向打分 | 本模块关注**群体级转化漏斗**和**多触点归因模型** |

### 1.2 核心能力

| 能力 | 说明 |
|------|------|
| 漏斗定义与管理 | 可配置多步骤转化漏斗，支持条件过滤、事件组合、时间窗口约束 |
| 实时转化率计算 | 按天/周/月粒度计算各步骤转化率、整体转化率、步骤间流失率 |
| 多维下钻分析 | 按学段、年级、渠道、设备、会员状态等维度拆解漏斗 |
| 同群对比（Cohort Funnel） | 不同注册批次/特征群体的漏斗表现对比 |
| 多触点归因分析 | 首次触点、末次触点、线性、时间衰减、马尔可夫链等归因模型 |
| 转化时间分析 | 各步骤间转化耗时分布（P50/P90/P99）、最佳转化窗口识别 |
| 漏斗异常告警 | 转化率异常下跌、步骤流失率突增时自动告警 |
| 增长实验看板 | A/B 实验中各实验组的漏斗表现对比 |

### 1.3 核心业务漏斗定义

| 漏斗 | 步骤流 | 关键转化目标 |
|------|--------|-------------|
| 新用户激活漏斗 | 注册 → 完善档案 → 首次AI问答 → 收到回复 → 首次拍题 → 加入错题本 | 7日内完成首次学习行为 |
| 免费转付费漏斗 | 注册 → 首次AI使用 → 触达会员引导 → 试用 → 购买 | 完成付费订单 |
| 拍题转化漏斗 | 拍照 → OCR识别成功 → 查看解析 → 查看完整步骤 → 加入错题本 | 完成错题收录 |
| 学习习惯养成漏斗 | Day1活跃 → Day2活跃 → Day3活跃 → Day7活跃 → Day14活跃 | 14日持续活跃 |
| 功能发现漏斗 | 首页展示 → 功能入口点击 → 功能使用 → 功能复用 | 功能留存 |

## 3. 数据模型设计

### 3.1 漏斗定义模型（PostgreSQL）

```sql
CREATE TABLE growth_funnel_definition (
    id              BIGSERIAL PRIMARY KEY,
    funnel_key      VARCHAR(64) NOT NULL UNIQUE,
    name            VARCHAR(128) NOT NULL,
    description     TEXT,
    category        VARCHAR(32) NOT NULL,  -- registration/onboarding/engagement/monetization/retention
    owner           VARCHAR(64),
    status          VARCHAR(16) NOT NULL DEFAULT 'active',
    conversion_window_days  INT NOT NULL DEFAULT 30,
    step_max_gap_hours      INT NOT NULL DEFAULT 168,
    visibility      VARCHAR(16) NOT NULL DEFAULT 'internal',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    created_by      VARCHAR(64) NOT NULL
);

CREATE TABLE growth_funnel_step (
    id              BIGSERIAL PRIMARY KEY,
    funnel_id       BIGINT NOT NULL REFERENCES growth_funnel_definition(id),
    step_order      INT NOT NULL,
    step_name       VARCHAR(128) NOT NULL,
    match_conditions JSONB NOT NULL,
    is_optional         BOOLEAN NOT NULL DEFAULT false,
    is_conversion_goal  BOOLEAN NOT NULL DEFAULT false,
    UNIQUE(funnel_id, step_order)
);
CREATE INDEX idx_funnel_step_funnel ON growth_funnel_step(funnel_id, step_order);
```

**match_conditions JSON 结构说明：**

```json
{
  "events": [
    {
      "event_name": "ai_conversation_send",
      "conditions": [
        {"field": "is_first_time", "op": "eq", "value": true}
      ]
    }
  ],
  "session_filter": {
    "min_duration_sec": 10
  }
}
```

- `events`：匹配事件列表，多个事件之间为 **OR** 关系
- `events[].conditions`：同一事件的附加条件，之间为 **AND** 关系
- `session_filter`：可选的会话级过滤条件

**条件操作符（`op`）支持：**

| 操作符 | 含义 | 示例值 |
|--------|------|--------|
| `eq` | 等于 | `true`、`"text"`、`123` |
| `neq` | 不等于 | `false` |
| `in` | 包含 | `["text", "voice"]` |
| `not_in` | 不包含 | `["image"]` |
| `gt` / `gte` | 大于 / 大于等于 | `10` |
| `lt` / `lte` | 小于 / 小于等于 | `100` |
| `between` | 区间 | `[10, 50]` |
| `regex` | 正则匹配 | `"^\\d{4}$"` |

### 3.2 漏斗日级聚合表（ClickHouse）

```sql
CREATE TABLE growth_funnel_daily
(
    date            Date CODEC(Delta, ZSTD),
    funnel_key      LowCardinality(String),

    -- 维度
    platform        LowCardinality(String),    -- ios / android / web / mini_program
    app_version     LowCardinality(String),
    channel         LowCardinality(String),    -- organic / referral / paid / social
    stage           LowCardinality(String),    -- preschool / primary / junior / senior
    grade           LowCardinality(String),
    is_new_user     UInt8,

    -- 步骤数据（数组，索引 = 步骤序号 - 1）
    step_entered     Array(UInt64),
    step_converted   Array(UInt64),
    step_dropped     Array(UInt64),
    step_median_hours Array(Float32),
    step_p90_hours   Array(Float32),

    -- 整体指标
    total_entered    UInt64,
    total_converted  UInt64,
    overall_rate     Float32,

    computed_at      DateTime CODEC(Delta, ZSTD)
)
ENGINE = MergeTree()
PARTITION BY (toYYYYMM(date))
ORDER BY (date, funnel_key, platform, channel, stage, grade, is_new_user)
TTL date + INTERVAL 730 DAY;
```

### 3.3 用户触点记录表（ClickHouse）

```sql
CREATE TABLE user_touchpoint
(
    event_id         String,
    user_id          UInt64,
    session_id       String,
    event_name       LowCardinality(String),
    event_category   LowCardinality(String),  -- learning/social/commercial/system
    event_timestamp  DateTime64(3),
    feature_module   LowCardinality(String),  -- ai_tutor/photo_search/sync_class/mistake_book/...
    feature_action   LowCardinality(String),  -- view/click/complete/share/purchase
    user_stage       LowCardinality(String),

    is_pre_conversion   UInt8,
    conversion_event_id String DEFAULT '',
```

```sql
    touchpoint_module   VARCHAR(64) NOT NULL,
    touchpoint_action   VARCHAR(64),
    period_start        DATE NOT NULL,
    period_end          DATE NOT NULL,
    total_conversions   INT NOT NULL,
    attributed_conversions FLOAT NOT NULL,
    attribution_weight  FLOAT NOT NULL,
```

## 5. 核心算法实现

### 5.1 漏斗计算引擎

漏斗计算的核心语义：**有序步骤匹配 + 时间窗口约束**。用户在某日内进入漏斗（匹配步骤 1），随后在该日 + `conversion_window_days` 内按顺序完成后续步骤；相邻步骤间隔不得超过 `step_max_gap_hours`；可选步骤（`is_optional`）允许跳过，跳过时视为自动通过（converted = entered）。

**ClickHouse 漏斗查询（WindowFunnel）：**

```sql
SELECT
    date,
    platform,
    channel,
    stage,
    windowFunnel(604800 /* 7 天秒数 */)(
        event_timestamp,
        event_name = 'user_register_success',
        event_name = 'profile_grade_selected',
        event_name = 'ai_conversation_send' AND is_first_time = 1,
        event_name = 'photo_search_submit' AND is_first_time = 1,
        event_name = 'mistake_add',
        event_name = 'membership_trial_start',
        event_name = 'order_complete'
    ) AS levels
FROM behavior_events
WHERE event_timestamp BETWEEN '2026-06-01' AND '2026-06-16'
  AND user_id != 0
GROUP BY date, platform, channel, stage;
```

`levels` 为 UInt8：值为 k 表示用户至少完成了前 k 个步骤（0 = 未进入漏斗）。聚合时按 levels 分布累加各步骤的 `step_entered`；相邻级别差值即为该步骤 `dropped`。

**Java 服务层聚合逻辑：**

```java
@Service
public class FunnelComputeService {

    private final ClickHouseJdbcTemplate chTemplate;
    private final FunnelDefinitionRepository funnelRepo;

    /**
     * 计算单日漏斗聚合结果。
     * 设计要点：
     *  1. 按 (date, platform, channel, stage, grade, is_new_user) 分桶聚合；
     *  2. levels 分布直方图 → 各步骤 entered/converted/dropped；
     *  3. 可选步骤的跳过逻辑在窗口函数层天然成立（level 不递减）。
     */
    @Retryable(maxAttempts = 3, backoff = @Backoff(delay = 2000, multiplier = 2))
    public FunnelDailyAggregate computeDaily(String funnelKey, LocalDate date) {
        FunnelDefinition funnel = funnelRepo.findActiveByKey(funnelKey)
                .orElseThrow(() -> new BizException(FUNNEL_NOT_FOUND, funnelKey));

        String sql = buildWindowFunnelSql(funnel, date);
        List<Map<String, Object>> rows = chTemplate.queryForList(sql);

        List<FunnelDailyBucket> buckets = rows.stream()
                .map(this::mapBucket)
                .toList();

        return FunnelDailyAggregate.builder()
                .funnelKey(funnelKey)
                .date(date)
                .buckets(buckets)
                .build();
    }

    private FunnelDailyBucket mapBucket(Map<String, Object> row) {
        long[] levels = parseLevelsHistogram(row.get("levels_histogram"));
        long total = Arrays.stream(levels).sum();

        long[] stepEntered = new long[levels.length];
        long[] stepDropped = new long[levels.length];
        for (int k = levels.length - 1; k >= 0; k--) {
            stepEntered[k] = (k == levels.length - 1) ? total
                    : stepEntered[k + 1] + levels[k + 1];
            stepDropped[k] = stepEntered[k] - (k == levels.length - 1 ? levels[k]
                    : stepEntered[k + 1]);
        }
        return FunnelDailyBucket.builder()
                .platform((String) row.get("platform"))
                .channel((String) row.get("channel"))
                .stage((String) row.get("stage"))
                .totalEntered(total)
                .stepEntered(stepEntered)
                .stepDropped(stepDropped)
                .build();
    }
}
```

**可选步骤语义：** 若步骤 k 标记 `is_optional=true`，查询侧将其从 `windowFunnel` 的事件列表中剔除，仅保留对其后步骤的时序约束；计算 `step_entered[k]` 时取与前一非可选步骤相同的值，`converted[k] = entered[k]`。

### 5.2 归因计算引擎（马尔可夫链实现）

```java
@Component
public class MarkovAttributionCalculator {

    /**
     * 马尔可夫归因：
     *  1. 为每个转化用户构建触点序列（含 conversion / null 终止态）；
     *  2. 统计状态转移概率矩阵 P；
     *  3. 移除触点 i 后重算转化概率 p_i(-i)，
     *     RemovalEffect_i = p_convert - p_i(-i)；
     *  4. 按 RemovalEffect 归一化分配转化数。
     */
    public Map<String, Double> calculate(
            List<List<String>> userPaths, Set<String> allTouchpoints) {

        double pConvert = absorbingProbability(userPaths, null);

        Map<String, Double> removalEffects = new HashMap<>();
        double sumEffects = 0.0;
        for (String tp : allTouchpoints) {
            double pWithout = absorbingProbability(userPaths, tp);
            double effect = Math.max(0.0, pConvert - pWithout);
            removalEffects.put(tp, effect);
            sumEffects += effect;
        }

        if (sumEffects <= 0) {
            // 退化场景：所有触点 RemovalEffect 均为 0，退化为线性均分
            double even = pConvert / allTouchpoints.size();
            return allTouchpoints.stream()
                    .collect(toMap(tp -> tp, tp -> even));
        }
        return removalEffects.entrySet().stream()
                .collect(toMap(Map.Entry::getKey,
                        e -> pConvert * e.getValue() / sumEffects));
    }

    private double absorbingProbability(List<List<String>> paths, String removedTp) {
        Map<String, Map<String, Long>> transitions = new HashMap<>();
        long conversions = 0, nulls = 0;

        for (List<String> path : paths) {
            List<String> filtered = path.stream()
                    .filter(tp -> !tp.equals(removedTp)).toList();
            for (int i = 0; i < filtered.size() - 1; i++) {
                transitions.computeIfAbsent(filtered.get(i), k -> new HashMap<>())
                        .merge(filtered.get(i + 1), 1L, Long::sum);
            }
            String last = filtered.get(filtered.size() - 1);
            if ("conversion".equals(last)) conversions++;
            else if ("null".equals(last)) nulls++;
        }
        long total = conversions + nulls;
        return total == 0 ? 0 : (double) conversions / total;
    }
}
```

**性能约束：** 马尔可夫移除效应计算复杂度为 O(T × N)，T 为触点数（通常 ≤ 20），N 为用户路径数。单日路径量超过 50 万时采用**抽样计算**（分层随机抽样 10 万条，置信区间 ±0.3%），并在结果表中记录 `sample_size` 与 `confidence_interval`。

### 5.3 异常检测（漏斗转化率 Z-Score）

```java
@Component
public class FunnelAnomalyDetector {

    private static final double CRITICAL_Z = 3.0;
    private static final double WARNING_Z  = 2.0;

    /**
     * 以过去 28 天同星期（周一 vs 周一）为基线计算 Z-Score，
     * 排除节假日（运营日历维护 holiday_calendar 表）。
     */
    public List<FunnelAnomaly> detect(String funnelKey, int stepOrder, LocalDate date) {
        List<Double> baseline = dailyQuery.queryStepRates(funnelKey, stepOrder,
                date.minusDays(84), date.minusDays(1));

        if (baseline.size() < 14) return List.of(); // 基线不足不告警

        DescriptiveStatistics stats = new DescriptiveStatistics(
                baseline.stream().mapToDouble(Double::doubleValue).toArray());
        double mean = stats.getMean();
        double stddev = Math.max(stats.getStandardDeviation(), 0.005); // 防止除零

        double today = dailyQuery.queryStepRate(funnelKey, stepOrder, date);
        double z = (today - mean) / stddev;

        if (Math.abs(z) < WARNING_Z) return List.of();

        double deviation = (today - mean) / mean;
        String severity = Math.abs(z) >= CRITICAL_Z ? "critical" : "warning";
        String type = deviation < 0 ? "rate_drop" : "spike";

        FunnelAnomaly anomaly = FunnelAnomaly.builder()
                .funnelKey(funnelKey)
                .stepOrder(stepOrder)
                .anomalyType(type)
                .severity(severity)
                .expectedRate(mean)
                .actualRate(today)
                .deviation(deviation)
                .zScore(z)
                .detectedAt(Instant.now())
                .periodStart(date.atStartOfDay().toInstant(ZoneOffset.UTC))
                .periodEnd(date.plusDays(1).atStartOfDay().toInstant(ZoneOffset.UTC))
                .possibleCauses(guessCauses(funnelKey, stepOrder, date))
                .build();
        return List.of(anomaly);
    }

    /** 辅助诊断：同日是否有发布、实验、活动、服务故障 */
    private List<String> guessCauses(String funnelKey, int step, LocalDate date) {
        List<String> causes = new ArrayList<>();
        releaseService.findByDate(date).ifPresent(r ->
                causes.add("当日发布版本 " + r.getVersion()));
        experimentService.findRunningOn(date).forEach(e ->
                causes.add("实验进行中: " + e.getName()));
        incidentService.findByDate(date).ifPresent(i ->
                causes.add("服务事件: " + i.getTitle()));
        return causes;
    }
}
```

## 6. 状态流转

### 6.1 漏斗定义生命周期

```text
              创建
                │
                ▼
        ┌───────────────┐    编辑规则     ┌───────────────┐
        │    DRAFT      │──────────────▶│    DRAFT      │
        │  （草稿）      │◀──────────────│               │
        └──────┬────────┘   保存草稿     └───────────────┘
               │ validate
               │ 通过后
               ▼
        ┌───────────────┐   重新编辑    ┌───────────────┐
   ┌───▶│    ACTIVE     │◀─────────────│   PAUSED      │
   │    │  （生效中）    │──────────────▶│  （暂停计算）  │
   │    └──────┬────────┘   暂停        └───────────────┘
   │           │ 数据回填成功
   │           ▼
   │    ┌───────────────┐
   │    │   BACKFILLED  │──┐
   │    │ （回填完成）   │  │ 删除（软删）
   │    └───────────────┘  ▼
   │              ┌───────────────┐
   └──────────────│  ARCHIVED     │
                  │  （已归档）    │
                  └───────────────┘
```

| 状态 | 含义 | 允许操作 |
|------|------|---------|
| `DRAFT` | 草稿，不参与计算 | 编辑、删除、激活 |
| `ACTIVE` | 生效中，每日参与调度 | 编辑（生成新版本）、暂停、归档 |
| `PAUSED` | 暂停计算，历史结果保留 | 恢复、归档 |
| `BACKFILLED` | 创建后已完成历史数据回填 | 归档 |
| `ARCHIVED` | 已归档只读 | 无（如需重启需新建） |

**版本化语义：** 修改 ACTIVE 漏斗的步骤定义时不原地更新，而是生成 `version + 1` 的新版本，历史版本结果保留并按版本号归档查询；跨版本趋势对比需显式指定版本。

```text
                               ▼                    ▼
                            FAILED ◀────────────  RETRY(最多3次)

                            MANUAL_REVIEW
```

## 7. 错误处理

### 7.1 错误码定义

| 错误码 | HTTP 状态 | 含义 | 处理建议 |
|--------|-----------|------|---------|
| `GROWTH_FUNNEL_NOT_FOUND` | 404 | 漏斗不存在或已归档 | 检查 funnel_key 拼写 |
| `GROWTH_FUNNEL_INVALID_DEF` | 400 | 漏斗定义校验失败 | 返回字段级校验明细 |
| `GROWTH_FUNNEL_DUPLICATE_KEY` | 409 | funnel_key 重复 | 更换 key 或先归档旧漏斗 |
| `GROWTH_ATTRIB_INSUFFICIENT_DATA` | 200* | 归因数据不足（转化数 < 30） | 返回 `data` 为空并带 `warning` 字段，前端展示"样本量不足" |
| `GROWTH_BACKFILL_RUNNING` | 409 | 该漏斗已有回填任务进行中 | 查询任务进度或等待完成 |
| `GROWTH_QUERY_TIMEOUT` | 504 | 即席查询超时（> 30s） | 缩小时间范围或使用预聚合接口 |

\* 业务软错误，HTTP 仍返回 200，通过响应体 `code` 区分。

### 7.2 容错与降级策略

| 场景 | 策略 |
|------|------|
| ClickHouse 查询超时/不可用 | 降级读取 T-1 预聚合结果（Redis 缓存 24h），响应头标记 `X-Data-Stale: true` |
| Kafka 消费积压 > 500 万 | 漏斗计算自动切换为 T-1 数据并触发告警；恢复后自动补算缺口 |
| 归因样本量不足 | 不返回伪造精度，返回线性模型结果 + `low_confidence=true` 标记 |
| 回填任务失败重试 3 次 | 转入 MANUAL_REVIEW，通知数据工程值班同学 |
| 漏斗定义循环引用（步骤条件引用自身漏斗） | 激活前校验拒绝，返回 `GROWTH_FUNNEL_INVALID_DEF` |

### 7.3 幂等性保证

- 日级聚合任务以 `(funnel_key, date, bucket_dims)` 为幂等键，写入采用 `INSERT ... ON CONFLICT`（PG）或 `ReplacingMergeTree`（CH，按 `computed_at` 取最新）；
- 回填任务与日级任务写同一张聚合表时，回填以更高 `computed_at` 覆盖，保证最终一致；
- API 创建漏斗时客户端需携带 `Idempotency-Key` 头，服务端按 key 缓存 24h 防重复创建。

```text
                              01:30 漏斗计算 ←─┤
                                              ▼
                              growth_funnel_daily (CH)
                                              │
           03:00 归因计算 ← user_touchpoint ──┤
                                              ▼
                    growth_attribution_result (PG) → 看板/实验平台/告警
```

## 9. 监控与告警

| 监控项 | 指标 | 阈值 |
|--------|------|------|
| 日级计算任务 | 完成时间 / 成功率 | 超过 04:00 未完成即告警 |
| Kafka 消费滞后 | consumer lag | > 500 万持续 10 分钟告警 |
| API 查询 | P99 延迟 / 错误率 | P99 > 2s 或 5xx > 1% 告警 |
| 归因计算 | 样本覆盖率（转化用户中有触点路径的比例） | < 85% 告警（埋点缺失信号） |
| 存储 | ClickHouse 分区大小 / TTL 淘汰 | 单分区 > 100GB 告警 |

**业务告警接入统一告警中心：** critical 级别异常（`z_score ≥ 3`）自动创建告警单并 @增长团队值班群；连续触发同一漏斗同一步骤 3 天自动升级为 P1 复盘工单。

| 项 | 设计 |

## 11. 验收标准

1. 创建包含 7 步（含 2 个可选步骤）的漏斗后，次日 04:00 前产出 T-1 聚合结果，与人工抽样核验误差 ≤ 0.5%；
2. 同一用户跨日完成漏斗步骤时，窗口边界（conversion_window_days 边界 ±1 秒）行为符合 §5.1 语义定义；
3. 归因 6 种模型对同一份模拟路径数据计算结果与参考实现（Python 离线脚本）偏差 ≤ 0.1%；
4. ClickHouse 不可用时，概览接口降级返回缓存且带 `X-Data-Stale` 标记，恢复后自动补算；
5. 步骤转化率较 28 天基线下跌 3σ 时，critical 告警在 10 分钟内送达告警中心；
6. 回填 180 天历史数据（8 并发）总耗时 ≤ 2 小时，且不影响在线查询 P99 延迟超过 1.5 倍。
