# 客户端-多渠道打包与国内应用商店上架交付体系 - 详细设计

## 1. 设计目标

### 1.1 背景

《CI-CD流水线与自动化构建发布系统》§12 仅覆盖 Google Play 与 App Store 的基础发布流程，而 PrimeTop 是面向国内 K12 场景的教育产品，Android 端真正的分发主战场是华为、小米、OPPO、vivo、荣耀、应用宝等国内应用商店，以及官网直装、市场活动推广、OEM 预装等渠道。当前 docs2 中"渠道号 / 渠道包 / 上架流程 / 应用宝"等关键词均为 0 覆盖，存在明显缺口：

1. 国内安卓渠道需要"一个版本 → N 个渠道包"的多渠道打包能力，并保证加固与签名链路正确。
2. 各商店提审是逐渠道独立进行的，需要统一的发版/提审状态管理，避免"发了哪些渠道、哪家被拒、哪家还没提"靠人脑记忆。
3. 渠道是增长归因的基础信号（安装渠道），需要与分享链接渠道（点击渠道）合并归因。
4. 教育类 App 在国内商店上架有额外资质与合规材料要求（软著、APP 备案、教育移动应用备案等），需要成体系的交付清单。

### 1.2 设计目标

1. 建立统一的渠道标识体系与渠道注册表，覆盖商店、官网、活动、预装、内测五类渠道。
2. 提供"母包构建 → 加固 → 多渠道写入 → 产物校验 → 分发"的标准打包流水线，产物可审计。
3. 提供发版（Release）与渠道提审（Submission）两级状态机，支撑多渠道并行提审与被拒重提。
4. 客户端运行时可靠读取渠道号，首次激活幂等上报，与链接渠道归因合并。
5. 沉淀国内主流商店的上架矩阵、资质清单、常见被拒原因与应对预案。
6. 版本升级检查支持渠道维度覆盖（某渠道审核滞后时的最低版本线）。

### 1.3 术语定义

| 术语 | 说明 |
| --- | --- |
| 母包（Base APK） | 由 CI 构建出的、不含渠道信息的签名正式包 |
| 渠道包（Channel APK） | 在母包基础上写入渠道号后的最终分发包 |
| 安装渠道（Install Channel） | 由渠道包内置 channel_code 标识的渠道 |
| 链接渠道（Link Channel） | 由分享/推广深链接携带的渠道参数 |
| 加固（Hardening） | 对 APK 进行的第三方安全加固（腾讯乐固、360加固保等） |
| 发版（Release） | 一个 platform + versionCode 维度的发布计划 |
| 提审（Submission） | 某个渠道对某个发版的一次商店提审过程 |

## 3. 渠道体系设计

### 3.1 渠道标识规范

- `channel_code`：小写字母、数字、下划线，长度 ≤ 32，全局唯一，创建后不可修改。
- `platform`：1=android / 2=ios / 3=harmony / 0=all（如官网渠道可能同时提供多端下载）。
- `channel_type`：1=store（商店）/ 2=official（官网）/ 3=promotion（市场活动）/ 4=oem（预装）/ 5=internal（内测）。

### 3.2 初始渠道枚举

| channel_code | 名称 | 类型 | platform | 说明 |
| --- | --- | --- | --- | --- |
| official | 官网 | official | 0 | 官网直装 APK |
| internal_fir | 内测分发 | internal | 1 | 内部测试（fir.im / 蒲公英托管） |
| huawei | 华为应用市场 | store | 1 | AppGallery Connect |
| xiaomi | 小米应用商店 | store | 1 | 小米开放平台 |
| oppo | OPPO 软件商店 | store | 1 | OPPO 开放平台 |
| vivo | vivo 应用商店 | store | 1 | vivo 开放平台 |
| honor | 荣耀应用市场 | store | 1 | 荣耀开放平台 |
| tencent_myapp | 应用宝 | store | 1 | 腾讯应用开放平台 |
| meizu | 魅族应用商店 | store | 1 | 魅族开放平台（低优先级，可选） |
| appstore | Apple App Store | store | 2 | iOS 唯一正式渠道 |
| testflight | TestFlight | internal | 2 | iOS 内测 |
| harmony_appgallery | 鸿蒙应用市场 | store | 3 | HarmonyOS NEXT 原生包（预留） |
| promo_{name} | 活动渠道段 | promotion | 1 | 如 promo_douyin_k12、promo_baidu_sem，动态创建 |
| oem_{name} | 预装渠道段 | oem | 1 | 如 oem_lenovo_pad，动态创建 |

> 活动渠道由运营在后台按 `promo_` 前缀规范动态创建，走 §7.1 渠道注册 API，无需发版。

### 3.3 渠道号注入技术方案对比

| 方案 | 原理 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| Gradle productFlavors | 每渠道完整编译 | 实现简单 | N 渠道 = N 次完整构建，慢；渠道多时矩阵爆炸 | ❌ 弃用（flavor 仅保留 dev/staging/prod 环境维度） |
| meta-data + 渠道文件 | 打包后改 zip 注入文件 | 快 | 破坏 v2 签名，需重签，与加固流程冲突 | ❌ 弃用 |
| Walle（美团） | 写入 APK Signing Block 自定义区块 | 秒级出包、不破坏 v2/v3 签名、支持加固后写入 | — | ✅ 可选 |
| VasDolly（腾讯） | 同上，支持 V1+V2 双写、命令行批量 | 秒级出包、批量能力强、与乐固等加固链路兼容好 | — | ✅ 采用 |

**选型：VasDolly**（Walle 作为等价备选，切换成本仅在读包 SDK 层）。

写入原理：在 APK 的 Signing Block 中追加一个自定义 channel block。该区块不参与 v2/v3 签名的摘要计算，因此写入后**无需重新签名**，也不会破坏签名校验；加固流程会重打包重签名，故必须**先加固、后写渠道**。

### 3.4 平台策略

- **Android**：VasDolly 写入 signing block；兜底链见 §6.1。
- **iOS**：渠道固定为 `appstore`（上架包）或 `testflight`（TF 构建），无需打包差异；TestFlight 判定依据 `ITunesMetadata`/分发方式，客户端通过 build 阶段注入的 `Info.plist` 键 `PTDistribution`（appstore/testflight/adhoc）识别。
- **HarmonyOS（预留）**：华为侧逐步推进原生鸿蒙包，`harmony_appgallery` 渠道 + `.app` 产物，数据模型中 `platform=3` 已预留；Flutter 侧等鸿蒙适配成熟后接入，不阻塞本期。

## 5. 构建与打包流水线

### 5.1 流水线总览

```text
[CI 构建任务]                    [加固子任务]                [渠道打包子任务]           [校验与登记]
assembleRelease ──► 母包 ──► 上传加固平台 ──► 加固包+重签名 ──► VasDolly 批量写渠道 ──► apksigner verify
(产出 base.apk      (base.apk)   (乐固/360)     (harden.apk)      (channel/*.apk)       + 渠道回读校验
 + mapping.txt)                                                                  + SHA256 对账
                                                                                      │
                                                                          写 channel_package 表 +
                                                                          归档 release-manifest.json
```

关键顺序约束：**先加固、后写渠道**。加固会重打包并重签名，若先写渠道则信息丢失；VasDolly 在加固后的签名包上写入 signing block 区块不破坏签名。

### 5.3 打包脚本（CI 内执行）

```bash
#!/usr/bin/env bash
# scripts/build-channel-packages.sh
# 用法: ./build-channel-packages.sh <versionName> <versionCode> <hardened_apk>
set -euo pipefail

VERSION_NAME=$1; VERSION_CODE=$2; HARDENED_APK=$3
CHANNELS=$(mysql -h"$DB_HOST" -u"$DB_U" -p"$DB_P" -N -e \
  "SELECT channel_code FROM primetop.release_channel
    WHERE status=1 AND platform=1 AND channel_type IN (1,2,3,4);" | tr '\n' ' ')

# 1. 生成渠道清单文件
echo "$CHANNELS" | tr ' ' '\n' | grep -v '^$' > channel.txt

# 2. 批量写入渠道（输出到 channel/ 目录）
java -jar tools/VasDolly.jar put -c channel.txt "$HARDENED_APK" -o channel/

# 3. 逐产物校验：签名 + 渠道回读 + SHA256
BUILD_TOOLS="$ANDROID_HOME/build-tools/34.0.0"
for apk in channel/*.apk; do
  name=$(basename "$apk" .apk)
  ch=$(echo "$name" | awk -F- '{print $NF}')

  # 3.1 签名校验（必须通过 v2）
  "$BUILD_TOOLS/apksigner" verify --verbose "$apk" | grep -q "Verified using v2 scheme: true"

  # 3.2 渠道回读校验（读出的渠道必须与文件名一致）
  read_ch=$(java -jar tools/VasDolly.jar getChannel -f "$apk")
  [ "$read_ch" = "$ch" ] || { echo "CHANNEL_MISMATCH: $apk => $read_ch"; exit 3; }

  # 3.3 重命名并计算摘要
  final="primetop-android-${VERSION_NAME}-${VERSION_CODE}-${ch}.apk"
  mv "$apk" "out/$final"
  sha256sum "out/$final" >> "out/checksums.txt"
done
echo "ALL_PACKAGES_VERIFIED"
```

## 6. 客户端运行时渠道读取与上报

### 6.1 Android 平台通道实现

```kotlin
// android/app/src/main/kotlin/com/primetop/app/ChannelPlugin.kt
class ChannelPlugin(private val context: Context) : MethodChannel.MethodCallHandler {
    companion object {
        const val DEFAULT_CHANNEL = "official" // 兜底渠道
        const val CHANNEL = "primetop/channel"
        fun register(flutter: FlutterEngine) {
            MethodChannel(flutter.dartExecutor.binaryMessenger, CHANNEL)
              .setMethodCallHandler(ChannelPlugin(flutter.context))
        }
    }

    override fun onMethodCall(call: MethodCall, result: MethodChannel.Result) {
        when (call.method) {
            "getChannel" -> {
                // 兜底链：signing block(加固/渠道包) → meta-data(本地调试包) → official
                var ch: String? = ChannelReader.getChannel(context)   // VasDolly SDK
                if (ch.isNullOrEmpty()) {
                    ch = runCatching {
                        context.packageManager.getApplicationInfo(
                            context.packageName, PackageManager.GET_META_DATA
                        ).metaData?.getString("PT_DEFAULT_CHANNEL")
                    }.getOrNull()
                }
                result.success(mapOf(
                    "channelCode" to (ch ?: DEFAULT_CHANNEL),
                    "source" to when {
                        !ch.isNullOrEmpty() && ch != "official" -> "signingBlock"
                        ch == "official" -> "metaData"
                        else -> "fallback"
                    }
                ))
            }
            else -> result.notImplemented()
        }
    }
}
```

### 6.2 Dart 侧读取与缓存

```dart
class ChannelService {
  static const _ch = MethodChannel('primetop/channel');
  static const _cacheKey = 'pt.install.channel';
  static const _reportedKey = 'pt.activation.reported';

  Future<ChannelInfo> resolve() async {
    // 1. 本地缓存命中直接返回（渠道不可变，避免重复读签名块）
    final cached = LocalStore.getString(_cacheKey);
    if (cached != null) return _build(cached);

    // 2. 平台读取
    final map = await _ch.invokeMethod('getChannel');
    final code = map['channelCode'] as String;
    await LocalStore.setString(_cacheKey, code);

    // 3. 合并深链接渠道（首启时由路由系统解析 promo_* 链接后写入）
    final link = LocalStore.getString('pt.link.channel');
    return _build(code, linkChannel: link);
  }

  /// 首次激活上报（幂等：本地标志 + 服务端唯一索引双保险）
  Future<void> reportActivationIfNeeded({required DeviceFingerprint fp}) async {
    if (LocalStore.getBool(_reportedKey) ?? false) return;
    final info = await resolve();
    final resp = await api.post('/api/v1/client/activation', data: {
      'deviceId': fp.hashed,
      'channelCode': info.channelCode,
      'platform': info.platform,
      'versionCode': BuildConfig.versionCode,
      'linkChannel': info.linkChannel,
    });
    // 服务端幂等：重复上报返回 firstActivation=false，同样视为成功
    await LocalStore.setBool(_reportedKey, true);
    Telemetry.track('app_first_open', {
      'channel_code': info.channelCode,
      'platform': info.platform,
    });
  }
}
```

### 6.3 归因合并规则（信号级）

- `install_channel`：来自渠道包，随安装固定，本模块上报。
- `link_channel`：来自分享/推广深链接 `?ch=promo_xxx`，由路由系统在首启写入本地，本模块上报。
- 合并裁决：`promo_*` 链接渠道仅当发生在激活前 7 天内才生效为该用户的增长归因渠道；最终归因规则由《用户转化漏斗分析与增长归因引擎》定义，本模块只保证两个信号准确、及时上报。

## 8. 状态流转

### 8.1 发版状态机（app_release.status）

```text
DRAFT ──build_start──► BUILDING ──build_ok──► HARDENING ──harden_ok──► PACKAGING ──all_verified──► PACKAGE_READY
  │                      │                      │                        │
  │                  build_fail             hard_fail              package_fail
  │                      ▼                      ▼                        ▼
  └──────────────── BUILD_FAILED ◄──────── HARDEN_FAILED ◄──────── PACKAGING_FAILED
                             (重试回 BUILDING/HARDENING/PACKAGING)

PACKAGE_READY ──first_submission──► RELEASING ──any_channel_live──► RELEASED ──close──► CLOSED
                    (≥1 提审单非 DRAFT)              (≥1 LIVE)
```

| 状态 | 含义 | 触发者 |
| --- | --- | --- |
| DRAFT | 发版计划创建 | 管理员 |
| BUILDING / BUILD_FAILED | CI 构建中 / 失败 | CI 回调 |
| HARDENING / HARDEN_FAILED | 加固中 / 失败 | CI 回调 |
| PACKAGING / PACKAGING_FAILED | 渠道包生成校验中 / 失败 | CI 回调 |
| PACKAGE_READY | 产物齐全且全部校验通过 | 系统（自动） |
| RELEASING | 已开始向商店提审 | 管理员 |
| RELEASED | 任一渠道已 LIVE | 系统（提审事件联动） |
| CLOSED | 版本归档 | 管理员 |

### 8.2 提审状态机（store_submission.status）

```text
DRAFT ──submit──► SUBMITTING ──accepted──► IN_REVIEW ──reject──► REJECTED ──resubmit──► IN_REVIEW
                       │                      │                                    (submit_round+1)
                  submit_fail                approve                              │
                       ▼                      ▼                                    ▼
                   SUBMIT_FAILED          SCHEDULED ──go_live──► LIVE ──new_release──► SUPERSEDED
                       │                      │        │
                     (重试)                withdraw   take_down
                                              ▼        ▼
                                           WITHDRAWN TAKEN_DOWN
```

| 状态 | 含义 | 关键规则 |
| --- | --- |---|
| DRAFT | 提审单创建未提交 | — |
| SUBMITTING / SUBMIT_FAILED | 开放平台受理中 / 提交失败 | 失败可重试；自动化对接阶段由开放平台 API 回调驱动 |
| IN_REVIEW | 商店审核中 | 人工或 API 轮询更新 |
| REJECTED | 审核被拒 | 必须记录 reason；进入 §9.4 整改流程 |
| SCHEDULED | 审核通过待发布 | 可配置定时发布 |
| LIVE | 该渠道当前线上版本 | 联动 app_release → RELEASED |
| TAKEN_DOWN | 商店下架/主动下架 | 触发紧急预案评估（§10.6） |
| WITHDRAWN | 审核中主动撤回 | 回 DRAFT 可重新提交 |
| SUPERSEDED | 被更新版本替代 | 历史留存 |

### 8.3 状态机实现

基于《服务端-业务状态机与通用工作流引擎》的通用实现，本模块仅提供配置：

```java
@Configuration
public class SubmissionStateMachineConfig {

    @Bean
    public StateMachineSpec<SubmissionStatus, SubmissionEvent> submissionSpec() {
        return StateMachineSpec.<SubmissionStatus, SubmissionEvent>builder()
            .initial(SubmissionStatus.DRAFT)
            .transition(SubmissionStatus.DRAFT, SubmissionEvent.SUBMIT, SubmissionStatus.SUBMITTING)
            .transition(SubmissionStatus.SUBMITTING, SubmissionEvent.ACCEPTED, SubmissionStatus.IN_REVIEW)
            .transition(SubmissionStatus.SUBMITTING, SubmissionEvent.SUBMIT_FAIL, SubmissionStatus.SUBMIT_FAILED)
            .transition(SubmissionStatus.SUBMIT_FAILED, SubmissionEvent.RETRY, SubmissionStatus.SUBMITTING)
            .transition(SubmissionStatus.IN_REVIEW, SubmissionEvent.REJECT, SubmissionStatus.REJECTED,
                guard: ctx -> ctx.payloadContains("reason"))           // 被拒必须带原因
            .transition(SubmissionStatus.IN_REVIEW, SubmissionEvent.APPROVE, SubmissionStatus.SCHEDULED)
            .transition(SubmissionStatus.IN_REVIEW, SubmissionEvent.WITHDRAW, SubmissionStatus.WITHDRAWN)
            .transition(SubmissionStatus.REJECTED, SubmissionEvent.RESUBMIT, SubmissionStatus.IN_REVIEW,
                action: ctx -> ctx.increaseSubmitRound())              // 轮次 +1
            .transition(SubmissionStatus.SCHEDULED, SubmissionEvent.GO_LIVE, SubmissionStatus.LIVE,
                action: ctx -> ctx.markLiveAndTouchRelease())          // 联动发版状态
            .transition(SubmissionStatus.LIVE, SubmissionEvent.TAKE_DOWN, SubmissionStatus.TAKEN_DOWN)
            .transition(SubmissionStatus.LIVE, SubmissionEvent.SUPERSEDED, SubmissionStatus.SUPERSEDED)
            .build();
    }
}
```

每次转移写 `submission_event` 流水，禁止直接 UPDATE status 绕过状态机（DAO 层拦截）。

| 85301 | 渠道编码不合法/已存在 | 创建渠道时校验 |
| 85302 | manifest 对账失败（产物数 ≠ 渠道数） | 阻断 PACKAGE_READY |

### 10.2 构建/加固/打包失败

- CI 子任务失败自动重试 1 次；仍失败置对应 *_FAILED 并通知发版负责人（飞书机器人，复用 CI-CD 通知通道）。
- 加固平台不可用超过 2h：允许管理员对官网/内测渠道走"未加固直出"（`is_hardened=0`），商店渠道不允许跳过。

### 10.3 产物被篡改防护

- 分发前：`apksigner verify` + SHA256 与 `channel_package` 登记值对账（§5.3 已内置）。
- 运行时：客户端启动做签名摘要自校验（与远端配置下发期望值比对，接入《客户端安全防护体系》完整性校验），不一致则上报并拒绝敏感操作。

### 10.4 提审同步丢失

自动化对接阶段（V2）开放平台回调丢失时：每日 10:00 定时任务轮询各平台提审状态（走《服务端定时任务调度与批处理框架》），状态差异 > 24h 告警。

### 10.5 渠道伪造与防刷

- 渠道号仅用于统计与归因，**绝不与任何用户权益/奖励挂钩**（避免渠道码刷量套利）。
- `client_activation_log` 按 deviceId + 时间窗限流；异常渠道（新增 activation 环比 > 500%）触发《服务端-教育平台统一风控决策中心》核查。

### 10.6 紧急下架与应急响应

```text
触发条件（任一）：
  a) 线上版本存在资损/严重内容安全缺陷；
  b) 监管通报要求下架整改；
  c) 商店单方面下架（TAKEN_DOWN 事件）。
流程：
  1) 值班响应（生产事故 OnCall 体系，P1 级）
  2) 可热修 → 走《客户端-Flutter代码推送热更新与动态补丁分发管理引擎》紧急补丁
  3) 不可热修 → 服务端 version_check 将问题版本 min_version_code 提至修复版（强制升级）
     + 各商店后台提交新版本审核 + 必要时临时下架存量问题版本
  4) 全部动作记入 submission_event + 事故复盘（排障根因分析引擎）
```

## 11. 安全与合规要点

1. **签名密钥**：发布 keystore、加固平台凭据、商店开放平台密钥全部托管于《服务端-密钥管理与敏感配置安全策略》体系；keystore 密码双人分片保管，CI 仅在构建瞬间解密注入。
2. **mapping.txt**：与产物同版本归档（SHA256 绑定），崩溃还原时按 versionCode+buildNo 精确匹配，保留至版本下线 + 180 天。
3. **商店测试账号**：专用账号 + 数据隔离标记，避免审核数据污染生产统计（《种子数据管理与自动化测试数据生成引擎》同源机制）。
4. **未成年人合规联动**：上架材料中的家长模式截图、时长管控说明必须与《防沉迷与未成年人保护机制》《家长端使用管控与权限配置服务》实际功能一致，防止审核演示与线上功能不符。
