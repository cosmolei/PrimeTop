## 1. 模块概述

### 1.1 功能定位

本模块是学生端作业管理的**服务端核心引擎**，负责从教师发布作业、学生接收作业、作业完成追踪、智能催交提醒，直到作业提交确认与完成度分析的全生命周期管理。

与已有模块的边界划分：

| 已有模块 | 覆盖范围 | 与本模块关系 |
| --- | --- | --- |
| 服务端-教师班级管理与作业发布服务 | 教师创建、编辑、发布、批改作业 | 上游：教师发布后触发本模块 |
| 客户端-学生班级与作业提交页面 | 学生端作业列表、提交交互UI | 下游：本模块提供数据接口 |
| 服务端-多源学习任务统一调度与优先级仲裁引擎 | 通用学习任务的优先级排序 | 协作：作业作为任务源之一接入 |
| 服务端-每日任务智能生成与学习计划执行追踪服务 | 学习计划和每日任务追踪 | 协作：作业任务纳入每日任务 |

### 1.2 核心能力

1. **作业生命周期状态机**：管理从"已发布"到"已完成"的完整状态流转
2. **智能催交调度**：基于截止时间、学生行为模式、学科负荷动态生成催交提醒
3. **作业负荷均衡分析**：跨学科汇总学生作业量，检测过载/冲突
4. **作业完成度统计**：个人、班级、学科维度的作业完成率与质量分析
5. **家长通知联动**：作业状态变更时按策略通知家长
6. **作业-学习计划联动**：将作业自动纳入学生学习计划与每日任务

## 3. 作业状态机设计

> **v1.1 重大修订（F1/F2 承载）**：v1.0 采用 ASSIGNED/VIEWED/LATE_SUBMIT 九态词汇，与 E2E《学生作业接收完成提交与反馈闭环完整链路》§4.2 权威状态机（PENDING/IN_PROGRESS/SUBMITTED/GRADING/GRADED/RETURNED/OVERDUE/EXPIRED 八态 + WITHDRAWN/EXEMPTED 记录态）不一致，且缺 GRADING/RETURNED/EXPIRED 三态、TRANSITIONS 缺 GRADED→RETURNED 转移与自身事件表矛盾。v1.1 将状态词汇收敛至 E2E 权威：
> - `VIEWED` 废除为状态，降级为 `viewed_at IS NOT NULL` 派生标记（首次查看仅记回执，不变更状态机）；
> - `LATE_SUBMIT` 废除为状态，降级为提交属性 `is_late`/`late_submit_hours`（宽限期内补交直接 OVERDUE → IN_PROGRESS → SUBMITTED）；
> - 新增 `GRADING`（批改中）/`RETURNED`（退回重做）/`EXPIRED`（宽限期外失效）三态；
> - `WITHDRAWN`/`EXEMPTED` 为记录态（不计入未交率，客户端 §8.1 展示映射对齐）。

### 3.1 状态定义与流转图

```
                    ┌──────────────┐
                    │   PENDING    │  已分配，未查看（查看仅记 viewed_at，不变更状态）
                    └──────┬───────┘
                           │ 学生开始作答（打开第一题，E2E 步骤③ start）
                           ▼
                    ┌──────────────┐
     ┌──────────────│ IN_PROGRESS  │  作答中（有草稿）
     │              └──────┬───────┘
     │                     │ 学生提交（E2E 提交闸门，幂等）
     │                     ▼
     │              ┌──────────────┐
     │              │  SUBMITTED   │  已提交，待批改
     │              └──────┬───────┘
     │                     │ 客观题同步判题/AI 初评接入
     │                     ▼
     │              ┌──────────────┐
     │              │   GRADING    │  批改中（客观题已出/主观题待教师复核）
     │              └──────┬───────┘
     │                     │ 教师批改发布（grading publish）
     │                     ▼
     │              ┌──────────────┐
     │     重做完成  │   RETURNED◀──┤  教师退回重做（仅 SUBMITTED/GRADED 可退）
     │   重新提交──┘│   GRADED     │  已批改（可重新批改 GRADED→GRADING）
     │              └──────┬───────┘
     │                     │ 退回：RETURNED → IN_PROGRESS（学生重新打开）
     │                     ▼
     │              （回到 IN_PROGRESS）
     │
     │ 截止时间已过，仍未提交（PENDING/IN_PROGRESS）
     ▼
┌──────────────┐  宽限期内学生补交（OVERDUE → IN_PROGRESS）
│   OVERDUE    │───────────────▶ 回 IN_PROGRESS，提交后 is_late=1
└──────┬───────┘
       │ 宽限期（默认 72h，作业级可覆盖）耗尽
       ▼
┌──────────────┐
│   EXPIRED    │  终态：不可再提交（客户端「已失效」页）
└──────────────┘

记录态（叠加于任意活跃/终态之上，以记录列承载，不进状态机主链）：
┌──────────────┐
│  EXEMPTED    │  教师标记免交（exempted_at/exempted_by/exempt_reason）
└──────────────┘
┌──────────────┐
```

## 5. 智能催交提醒调度引擎

### 5.1 催交策略矩阵

催交调度引擎根据作业状态、时间节点、学生行为模式、历史数据综合决策。

#### 5.1.1 提醒阶段定义

| 阶段 | 触发时机 | 提醒类型 | 目标 | 强度 |
| --- | --- | --- | --- | --- |
| T1 预提醒 | 截止前 24h ± 2h | `PRE_DUE` | 未开始(ASSIGNED)的学生 | 低 |
| T2 临近提醒 | 截止前 4h ± 1h | `PRE_DUE_URGENT` | 未提交(ASSIGNED/VIEWED/IN_PROGRESS) | 中 |
| T3 截止提醒 | 截止时刻 | `AT_DUE` | 仍未提交 | 高 |
| T4 逾期提醒 | 截止后 2h | `OVERDUE` | 逾期未交(OVERDUE) | 高 |
| T5 升级提醒 | 截止后 24h | `ESCALATION` | 仍未交，同时通知家长 | 最高 |

#### 5.1.2 智能调度因子

催交引擎在标准阶段基础上，引入以下动态调整因子：

```java
/**
 * 智能催交调度因子
 */
public class ReminderScheduleFactors {
    // 1. 学生历史响应因子
    private double responsivenessScore;     // 0-1，基于历史催交后的响应速度
    private double avgFirstReminderDelay;    // 历史平均：首次提醒到提交的时间（小时）
    
    // 2. 作业特征因子
    private int estimatedDurationMin;        // 预估完成时长
    private double difficultyScore;          // 难度评分1-10
    private int questionCount;               // 题目数
    
    // 3. 时间因子
    private LocalDateTime now;               // 当前时间
    private LocalDateTime dueAt;             // 截止时间
    private Duration remainingTime;          // 剩余时间
    
    // 4. 学生行为因子
    private StudentActivityPattern pattern;  // 学生活跃时段模式
    
    // 5. 负荷因子
    private int concurrentAssignments;       // 当前并发作业数
    private String loadLevel;               // LIGHT/NORMAL/HEAVY/OVERLOADED
}

/**
 * 学生活跃时段模式
 */
public class StudentActivityPattern {
    // 各时段活跃概率 [0-1]，基于过去30天行为统计
    private Map<HourBucket, Double> hourlyActiveProbability;

    // 每日作业高峰活跃时段（Top2），如 [19, 20]
    private int[] peakHours;
    // 最近一次催交后的响应耗时（小时），null=从未响应
    private Double lastResponseDelayHours;
    // 模式样本量（近30天有效学习日数），<7 时视为冷启动退化为标准时间窗
    private int sampleDays;

    /** 判定给定时刻是否落在学生高活跃窗口（活跃概率 ≥ 全天均值×1.5） */
    public boolean isHighActivityWindow(LocalDateTime t) {
        double prob = hourlyActiveProbability.getOrDefault(HourBucket.of(t), 0.0);
        return prob >= avgProbability() * 1.5;
    }

    /** 下一个高活跃窗口起点（自给定时刻起 24h 内，无则返回 null） */
    public LocalDateTime nextHighActivityStart(LocalDateTime from) {
        for (int h = 0; h < 24; h++) {
            LocalDateTime t = from.plusHours(h);
            if (isHighActivityWindow(t)) return t;
        }
        return null;
    }
}

// 状态词汇说明：v1.1 状态机已收敛 E2E 权威（§3），本节注释中 v1.0 的
// ASSIGNED/VIEWED 分别对应 PENDING 与 viewed_at 派生标记，LATE_SUBMIT 对应 is_late 提交属性。
```

#### 5.1.3 催交时机决策算法

标准阶段（T1-T5）给出的是**基准窗口**；调度引擎在每个窗口内进一步计算**最优触发时刻**，避免在学生不活跃的时段发出提醒（发了也看不见，还消耗提醒额度）。

**时机得分模型（ReminderTimingScorer）**

```java
/**
 * 催交时机打分：score ∈ [0,100]，取窗口内得分最高且 ≥ 60 分的时刻触发；
 * 若整个窗口无合格时刻，取窗口末端触发（保底不漏 T3/T4 关键提醒）。
 */
public double scoreTiming(LocalDateTime candidate, ReminderScheduleFactors f) {
    // F1 时间紧迫度（越接近截止越高，窗口外为 0）
    double urgency = clamp01(f.getRemainingTime().toMinutes() / 60.0 / 24.0 == 0
            ? 1.0 : min(1.0, 24.0 / (double) f.getRemainingTime().toHours()));

    // F2 活跃窗口命中（学生该时段历史活跃概率，冷启动取全天均匀 0.5）
    double active = f.getPattern().getHourProbability(candidate);

    // F3 历史响应因子（该学生对催交的历史响应率，无史取 0.5）
    double responsive = f.getResponsivenessScore();

    // F4 负荷惩罚（并发作业越多，越提前提醒，负向修正时刻而非得分）
    // 不参与打分，见 shiftForLoad()

    return urgency * 0.40 + active * 0.35 + responsive * 0.25;
}

/**
 * 负荷前置修正：HEAVY 时提醒时刻提前 2h，OVERLOADED 提前 4h（提前量不早于 T1 窗口起点），
 * 依据：负荷重的学生需要更长缓冲完成多科作业。
 */
public LocalDateTime shiftForLoad(LocalDateTime planned, ReminderScheduleFactors f) {
    int aheadHours = switch (f.getLoadLevel()) {
        case "OVERLOADED" -> 4;
        case "HEAVY" -> 2;
        default -> 0;
    };
    return planned.minusHours(aheadHours);
}
```

**算例**：数学作业截止 6-21 22:00，学生张三活跃高峰 19-21 点（概率 0.8），历史响应率 0.7，当前负荷 NORMAL。T1 基准窗口为 6-20 20:00±2h，调度器逐 30 分钟采样打分：20:00（urgency 0.42×0.40 + active 0.8×0.35 + 0.7×0.25 = 0.603）… 19:30 得分最高 0.62 ≥ 60 分 → 于 6-20 19:30 发出 PRE_DUE 提醒。

#### 5.1.4 催交决策管线

```
[扫描器 每5min] → [候选生成] → [过滤器链] → [时机调整] → [渠道选择] → [发送编排] → [回执追踪]
  分片×16        标准阶段T1-T5    见下表         活跃窗口+      APP_PUSH→     委托通知服务    响应即熔断
  游标断点续跑    命中未提交实例    六道过滤       负荷前置       WECHAT→SMS    (见5.1.6)     (更新responsiveness)
```

**过滤器链（依次短路）**

| # | 过滤器 | 规则 | 命中动作 |
| --- | --- | --- | --- |
| 1 | 终态过滤 | status ∈ SUBMITTED/GRADING/GRADED/EXPIRED/EXEMPTED/WITHDRAWN | 跳过（RETURNED 保持催交范围） |
| 2 | 阶段去重 | 该实例该 reminder_type 已有 DELIVERED 记录（uk_sa_type_attempt 兜底） | 跳过 |
| 3 | 冷却过滤 | Redis 冷却键存在（同作业 2h / 同学生跨作业 1h） | 跳过，等下轮 |
| 4 | 日额过滤 | 该学生当日已收催交 ≥ 3 条（未成年人硬上限，C2） | 跳过并标记 deferred_next_day |
| 5 | 免打扰过滤 | 当前时刻 ∈ 21:30-次日 08:00（学生默认窗，偏好中心可收紧不可放宽） | 入延迟队列，08:00 后补发（T3/T4 保留，营销类丢弃） |
| 6 | 家长代收过滤 | 学段 ∈ 幼儿/小学低年级（1-3 年级） | 改投家长通道（WECHAT/家长 APP_PUSH），学生端仅站内信静默记录 |

| 幼儿/小学低年级 | 面向家长："孩子的{subject}作业还剩 {n} 题，约 {m} 分钟，今晚亲子时间可以完成哦" | "作业已过截止时间，明天可与老师沟通补交安排" |
| 小学高年级/初中 | "你的{subject}作业还剩 {n} 题，预计 {m} 分钟，安排在 {suggest_time} 完成怎么样？" | "这份作业已超时，还在补交期内（剩 {g} 小时），完成后记得提交" |
| 高中 | "「{title}」截止 {due}，剩余 {n} 题" | "已超时 {h} 小时，补交窗口 {g} 小时后关闭" |

- **T5 ESCALATION 家长版**：仅含学科/作业名/超时时长/建议，**不含题目内容、不含班级其他学生信息、不含成绩**（C4/C7）。
- 模板经通知模板引擎渲染（变量白名单/长度/敏感词复检），本引擎只产模板编码+变量包。

#### 5.1.6 频控、合并与响应熔断

**频控矩阵**

| 维度 | 规则 | 承载 |
| --- | --- | --- |
| 同实例同类型 | 每阶段类型对同一作业实例仅 1 次（FAILED 重试递增 attempt，仍算同阶段） | uk_sa_type_attempt DB 兜底 |
| 同实例跨类型 | 冷却 2h（T3/T4/T5 豁免——关键节点不受冷却限制，但受日额限制） | Redis 冷却键 |
| 同学生跨作业 | 冷却 1h + 日上限 3 条（未成年人硬上限，C2；T5 家长通知不计入学生日额） | Redis 计数 + Lua 原子 |
| 合并 | 同学生 10min 内多条催交 → 委托《多源通知智能合并引擎》合并为一条（REMINDER 类可合并，载荷含作业数） | 合并引擎 G 规则 |

**响应熔断（学生响应即停）**：`assignment_reminder_log.student_response` 由事件驱动回填——订阅 `assignment.task.submitted`（提交）、答题 start/answers 事件（打开/活跃）后：

1. 将该学生**全部 pending 状态提醒**（已入延迟队列未发出的）置 `delivery_status=CANCELED_BY_RESPONSE`；
2. 后续扫描器对该实例因终态过滤自然跳过；
3. 响应耗时回写 `StudentActivityPattern.lastResponseDelayHours`，日终任务重算 `responsivenessScore`（见 §5.1.9）。

#### 5.1.7 T5 升级提醒（ESCALATION 家长通知）

| 项 | 规则 |
| --- | --- |
| 触发 | 截止后 24h 仍未提交（OVERDUE 态），或 GRACE_EXPIRED 转 EXPIRED 时（二选一先到先发，类型同为 ESCALATION） |
| 接收方 | 绑定家长（家庭账户多家长时按家长通知偏好主收人；未绑定家长则降级为站内信教师可见，不阻断） |
| 前置开关 | `reminder_strategy_config.escalation_enabled`（学校级策略，默认开；关闭时 T5 仅发学生端站内信） |
| 频控 | 同一作业对同一家庭仅 1 次；同家庭日 ESCALATION 上限 1 条 |
| 内容红线 | 不含题目内容/成绩/班级他人信息（C4/C7）；文案经成长型话术审查 |
| 时间窗 | 家长默认免打扰 22:00 后延迟至次日 08:00-09:00 高打开率窗口 |

#### 5.1.8 教师手动催交

- 入口收敛 E2E 权威端点 `POST /api/v1/homework/{homeworkId}/notify`（24h 频控归《服务端-教师班级管理与作业发布服务》通知接口）；
- 本引擎承接**批量下发执行**：收教师服务指令（内部 gRPC `BatchNudge`）后，对未提交学生按 §5.1.4 管线过滤（含日额/免打扰），**手动催交不占学生日额 3 条中的阶段额度，但计入同日总量 5 条硬顶**；
- 手动催交类型 `reminder_type=MANUAL`，同样受响应熔断与记录留痕。

#### 5.1.9 催交效果追踪

```
responsivenessScore = 0.6 × 响应率(近30天催交后24h内打开或提交的比例)
                   + 0.4 × 响应速度分(近30天平均响应延迟映射:[0,2h]→1.0 线性衰减到 [24h,+]→0)
EMA 平滑：score_new = 0.7 × score_old + 0.3 × score_window   （防单次波动）
冷启动：样本 < 5 次时固定 0.5；样本 < 7 学习日的活跃模式同样退化标准窗口
```

- 日终任务 04:20 全量重算，写 `sa:pattern:{studentId}`（24h TTL，滚动续期）；
- 指标输出：各阶段提醒→响应漏斗（埋点 `hw_reminder_funnel`），供运营看板与策略调参（§16 M3）。

### 5.2 逾期扫描与宽限期管理

**双触发源收敛（R3）**：上游教师服务定时任务发 `assignment.deadline.reached` 事件（事件驱动，秒级）；本引擎另有 ZSET 自扫描兜底（每 5min，防事件丢失）。两源都以**DB 状态 CAS 为唯一裁决**：

```
源A: assignment.deadline.reached 事件 ─┐
                                      ├→ UPDATE student_assignment
源B: ZSET sa:overdue:scan 扫描      ─┘   SET status=OVERDUE
                                         WHERE id=? AND status IN (PENDING, IN_PROGRESS)   ← CAS
               仅一方生效（影响行数=1），另一方自然空转，天然幂等
```

**宽限期状态机**

```
OVERDUE ──(grace_period_hours 内学生补交)──▶ IN_PROGRESS ──提交──▶ SUBMITTED (is_late=1)
   │
   └──(due_at + grace 耗尽，GRACE_EXPIRED 扫描 CAS)──▶ EXPIRED 终态
       RETURNED 态若宽限期耗尽同样转 EXPIRED（守卫 G7）
```

- `grace_period_hours` 默认 72，作业级可覆盖（教师发布时设置，1-720h 校验，58361）；
- `GRACE_EXPIRED` 扫描：`idx_status_due` 索引，`WHERE status IN (OVERDUE, RETURNED) AND due_at + grace < now`，分片 CAS 批量（500/批）；
- 转 EXPIRED 后：触发 T5 ESCALATION（若策略允许且未发过）、熔断 pending 提醒、`overdue_handled=1`。

### 5.3 家长通知联动策略矩阵

| 状态变更 | 通知家长 | 条件 |
| --- | --- | --- |
| 作业分配（PENDING） | 否 | 由 E2E 发布通知链路负责（令牌桶限速） |
| T4 OVERDUE | 幼儿/小学低年级：是（家长代收场景本身已发）；其余：否 | 仅学段判断 |
| T5 ESCALATION | 是 | §5.1.7 全部规则 |
| GRACE_EXPIRED→EXPIRED | 是（合并入 T5，不单独发） | — |
| 成绩发布 GRADED | 否 | 归批改闭环与家长学情报告，防多源打扰 |
| 免交 EXEMPTED | 否 | 教师已当面沟通场景为主 |

> 家长通道投递统一经《服务端-家长端学情报告聚合与通知服务》可见度分级（L1-L3）与《统一通知偏好授权中心》频控，本引擎只发结构化事件载荷，不直连推送渠道（R12）。

### 5.4 负荷快照生成（§6 前置）

- **增量触发**：assignment 实例状态变更事件（received/submitted/expired/exempted）→ 重算该学生当日快照（uk_student_date 幂等 upsert）；
- **全量对账**：每日 04:00 全量重刷当日（分片 16，游标断点），增量/全量差异>5% 告警（M7）；
- **读路径**：`sa:daily_load:{studentId}:{date}` 1h TTL，cache-aside 只 DEL 不 SET；
- 与《服务端-跨学科作业负载协同调控与学生作业总量智能管控引擎》边界（R5）：本引擎是**个人负荷快照与 overloaded 事件的生产者**，总量管控决策（协调教师/顺延建议）归彼引擎。

## 9. 状态机守卫总表（G1-G14）

> v1.1 新增：§3.1-§3.3 定义了状态与事件，本节给出**执行层守卫**——违反即拒绝操作或触发补偿，全部守卫在状态 CAS 同一事务或同一过滤器链中执行。

| 守卫 | 规则 | 违反处置 |
| --- | --- | --- |
| G1 状态 CAS | 一切状态变更必须带前置条件（`WHERE status IN (...)` 或 `WHERE version=?`，F4）；影响行数=0 即放弃并重读 | 放弃本轮操作；连续失败告警 M1 |
| G2 查看不变态 | `STUDENT_VIEWED` 仅回写 `viewed_at`（独立 UPDATE），禁止任何 `→VIEWD` 类状态转换（F1） | 拒绝转换请求，记录审计 |
| G3 迟交属性化 | `is_late=1` 仅允许出现在 OVERDUE→IN_PROGRESS→SUBMITTED 补交路径；`late_submit_hours=submitted_at-due_at` 保留 2 位小数 | 非法标记回滚事务 |
| G4 提交回放 | CAS →SUBMITTED 失败且当前态已是 SUBMITTED：返回首次提交结果（58306，200 语义），不重复扇出事件 | — |
| G5 退回必增轮次 | `TEACHER_RETURN` 同事务对受影响题目 `attempt_no+1`（F5）；无递增的退回非法 | 回滚整个退回事务 |
| G6 批改不洗史 | GRADED→GRADING 仅批改链重走；禁止借该转移清空 `submitted_at/score/teacher_comment` 等事实列 | 拒绝写操作 |
| G7 宽限终态裁决 | 仅 OVERDUE/RETURNED 且 `due_at+grace < now` 可 CAS→EXPIRED；EXPIRED/EXEMPTED/WITHDRAWN 为终态，禁止任何复活转移（教师重发=新实例新 ID） | 拒绝转移；EXPIRED 后提交返回 58305 |
| G8 免交单向 | EXEMPTED 可从任意活跃态进入；同事务熔断该实例全部 pending 提醒并从统计口径剔除（分子分母同剔，§7.1）；免交后禁止回到活跃态（撤销免交=教师重新布置） | 拒绝 EXEMPTED→活跃态转移 |
| G9 撤回存量处置 | WITHDRAWN 批量 CAS；已提交未批实例**不删数据只变状态**（提交内容与逐题记录原样保留供教师查看）；已 GRADED 实例保留成绩与批改记录（F8） | 迁移脚本抽查存量一致性 |
| G10 催交幂等 | 同实例同 `reminder_type` 仅允许一次 DELIVERED（`uk_sa_type_attempt` 兜底 + §2.2.4 60s 发送锁）；FAILED 重试递增 attempt，仍计同阶段一次 | 撞键即判重静默跳过 |
| G11 日额硬顶 | 未成年人阶段类催交日 ≤3 条、含手动总量日 ≤5 条（§2.2.7 Lua 原生校验）；达顶即 `deferred_next_day` / 手动指令部分执行并在响应中列明跳过名单 | 宁可漏发绝不超发（C2） |
| G12 免打扰不可放宽 | 默认窗 21:30-08:00；学生/家长偏好中心只能收紧；窗口内 T3/T4/T5 入 §2.2.8 延迟队列补发、T1/T2 丢弃不补（C1） | 配置校验拒绝放宽值 |
| G13 家长代收 | 幼儿/小学 1-3 年级催交一律改投家长通道，学生端仅站内信静默记录，不重复触达学生（渠道字段记家长通道编码） | 过滤器 #6 强制改道 |
| G14 时间权威 | due/grace/免打扰判定一律以服务端时钟（DB NOW()）为准，客户端倒计时仅展示；扫描节点与 DB 时钟偏差 >2s 暂停过期判定并告警 | 宁晚勿错（D9） |

### 10.1 八场景幂等表

| # | 场景 | 机制 | 裁决 |

| 1 | 提交网络重试 | E2E 闸门 `submitToken` 幂等（10min）+ 本引擎 G4 回放 | 重复请求返回首次结果，事件不重复扇出 |
| 2 | 逾期双源竞态（事件 vs ZSET 同轮命中） | 两源汇入同一 `UPDATE ... WHERE status IN (PENDING,IN_PROGRESS)` CAS（R3） | 单方生效，另一方空转；天然幂等 |
| 3 | 催交并发双发（分片重叠/调度器双实例） | 60s 发送锁抢占 + `uk_sa_type_attempt` 撞键兜底（G10/F3） | 后到者判重静默跳过，不产生第二条 DELIVERED |
| 4 | 宽限末刻补交 vs EXPIRED 扫描竞态 | 双方各自 CAS（→SUBMITTED / →EXPIRED）行锁串行 | 先提交者胜；EXPIRED 已生效则补交拒绝 58305，客户端展示「已过补交窗口」 |
| 5 | 免交与催交并发 | 免交事务先熔断 pending 提醒再提交；同实例行锁串行化 | 扫描器终态过滤兜底，零穿透 |
| 6 | 撤回与提交并发 | WITHDRAWN 批量 CAS；撤回窗（发布后 10min，对齐 E2E）内已提交实例走 G9 保留路径 | 撤回后到达的提交返回 58315「作业已被教师撤回」 |
| 7 | 负荷快照并发重算 | `uk_student_date` 幂等 upsert，多事件触发以最后完成者为准 | 全量对账 04:00 纠偏（差异 >5% 告警 M7） |
| 8 | 完成度聚合重跑/回刷 | `uk_date_scope` upsert 幂等；小时级增量仅覆盖当日+昨日；回刷窗口 ≤7 天且双人审批（对齐数仓回刷护栏） | 重跑不产生重复计数，消费方按 event_id 幂等 |

### 10.2 并发控制补充

- **扫描器分片互斥**：`sa:scan:lock:{shard}` 10s TTL，抢占失败即跳过本轮该分片（下轮游标续跑，不双跑）；
- **CAS 失败重试**：状态 CAS 失败重读后仅重试一次，仍失败放弃并告警（M1 区分 version 冲突与非法转移两类）；
- **Outbox 投递**：Relay 进程 `SELECT ... WHERE status='PENDING' AND next_retry_at<=now LIMIT 200 FOR UPDATE SKIP LOCKED`，多实例安全。

### 11.3 Relay 与对账

- Relay 批拉投递，失败 2^n 退避（1s/2s/4s/8s/16s），5 次转 DEAD 并 P2 告警；
- **日终 04:30 对账恒等式**：`outbox(SENT) 数 = Σ 消费方 ack 计数`（按 event_type 分组，差异 >0.5% 告警 M9）；同时核对 `status.changed` 总数 ≈ 状态变更审计日志数；
- 消费方全部按 `(event_id, consumer)` 记录消费台账，重复投递安全。

### 16.2 容量估算（DAU 50 万，学生日活 35 万）

- **student_assignment**：日新增 ~70 万行（人日均 2 份）；在线 12 个月 + 归档 24 个月（按月分区）；
- **状态变更**：日 ~350 万次；Outbox 日 ~420 万事件（status.changed ~250 万 + reminder.sent ~90 万 + 其余）；
- **assignment_reminder_log**：日增 ~90 万行，在线 180 天 + ClickHouse 归档（C9）；
- **assignment_load_snapshot**：日 35 万行；**assignment_completion_daily**：日 ~45 万行（四维度），保留 13 个月；
- **Redis 峰值**：dashboard 35 万×~200B ≈ 70MB；pattern 35 万×~1KB ≈ 350MB（24h TTL）；overdue ZSET 活跃 ~8 万 member；deferred ZSET 夜间峰值 ~15 万；日额 Hash ~35 万×48h；
- **催交扫描器**：16 分片 × 5min，单片候选 <3 万，单轮 P95 <90s（M2 阈值 120s 留 25% 余量）；
- **横向扩展**：引擎无状态多实例 + 分片锁互斥；扫描/聚合任务实例数 ≤16（分片数上限）。

## 17. 验收场景（18 条）

1. 教师发布作业 → 实例批量生成 PENDING → 学生看板计数即时更新（缓存失效链路 <3s）。
2. 学生首次打开作业详情：状态保持 PENDING，`viewed_at` 回写（G2）。
3. 开始作答 PENDING→IN_PROGRESS；重复调用 start 接口幂等不重复记 `started_at`。
4. 提交闸门：IN_PROGRESS→SUBMITTED；网络重试重复提交返回首次结果（G4，58306），事件仅扇出一次。
5. 截止前提交 `is_late=0`；截止后宽限期内补交 `is_late=1` 且 `late_submit_hours` 精确到 0.01h（G3）。
6. 双源逾期收敛：模拟事件与 ZSET 同轮命中同一实例，仅一次 OVERDUE 生效、仅一条 T4（R3）。
7. 日额递延：学生当日已收 3 条阶段催交，第 4 条被 G11 拦截并标 `deferred_next_day`，次日 08:00 后窗口内补发。
8. 免打扰：22:30 命中 T3 → 入延迟队列次日 08:00 补发；同时段 T1 直接丢弃不补（C1/G12）。
9. 幼儿/小学 1-3 年级学生催交：学生端仅站内信，家长通道收到代收内容（G13），学生设备无推送触达。
10. 响应熔断：催交发出后学生 10min 内提交 → 该实例全部 pending 提醒转 `CANCELED_BY_RESPONSE`，响应耗时回写模式缓存。
11. T5 ESCALATION：截止 24h 未交 → 家长收到升级通知且内容仅含白名单字段（C4/C7）；同家庭同作业仅 1 次。
12. 宽限期 72h 耗尽 → EXPIRED；EXPIRED 后提交被拒 58305（G7）；GRACE_EXPIRED 与补交竞态以 CAS 先到者胜（场景 4）。
13. 退回重做：指定题 `attempt_no` 递增、实例重新纳入催交范围、旧轮次答案只读可查（G5）。
14. 免交：实例转 EXEMPTED，pending 提醒全部熔断；完成度统计分子分母同步剔除（G8/§7.1）。
15. 撤回：全班批量 WITHDRAWN；已提交未批实例数据保留，教师端可查看提交快照（G9）。
16. 负荷过载：三科叠加触发 OVERLOADED → `assignment.load.overloaded` 事件双消费方各收到一次（负载管控引擎/教师端软提醒），催交时机前置 4h（§5.1.3）。
17. 完成度聚合故障：物化表当日缺失 → 查询自动回退实时 SQL 并带 `degraded=1` 标记（D6）。
18. Redis 宕机演练：发送锁/日额退化 DB 兜底，催交继续投递且无重复 DELIVERED（D1/G10）。
