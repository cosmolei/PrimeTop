# 服务端架构与部署设计 - 详细设计文档

## 1. 模块概述

服务端架构是 PrimeTop 系统的技术基础，支撑所有客户端请求处理、业务逻辑执行、AI 能力调用和数据持久化。本文档详细描述服务端的整体架构、服务拆分、技术选型、部署策略和可扩展性设计。

### 1.1 架构目标

1. **高可用性**：核心服务支持多实例部署，单点故障不影响系统整体可用性
2. **可扩展性**：支持水平扩展以应对用户增长，特别是 AI 调用和数据查询场景
3. **成本可控**：通过合理的资源分配、缓存策略和请求降级控制运营成本
4. **研发效率**：MVP 阶段采用模块化单体架构，后续可平滑演进为微服务
5. **安全合规**：实现完善的鉴权、审计、数据加密和内容安全机制
6. **可观测性**：提供完善的日志、监控、告警和性能分析能力

### 2.3 服务演进路径

```
阶段1（MVP）：模块化单体
  - 所有服务部署在一个容器
  - 代码按模块清晰划分
  - 共享数据库和缓存
  - 快速迭代，降低运维复杂度

  ↓（用户量 > 10万，或团队规模 > 10人）

阶段2（V1.0）：应用层拆分
  - 按业务域拆分为独立应用
  - 每个应用独立部署（用户服务、学习服务、AI服务等）
  - 仍共享数据库，开始引入服务间通信

  ↓（用户量 > 100万，或出现明显性能瓶颈）

阶段3（V1.5）：数据层拆分
  - 引入微服务网关
  - 数据库按业务域拆分
  - 引入服务注册与发现
  - 独立的数据存储策略

  ↓（大规模场景）

阶段4（V2.0）：完整微服务
  - 服务完全解耦
  - 独立的数据库、缓存、消息队列
  - 引入服务网格（Istio）
  - 完整的可观测性体系
```

### 4.1 数据库连接配置

```python
# config/database.py
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession
from sqlalchemy.orm import declarative_base, sessionmaker
from contextlib import asynccontextmanager

DATABASE_URL = "postgresql+asyncpg://user:password@localhost:5432/primetop"

engine = create_async_engine(
    DATABASE_URL,
    pool_size=20,
    max_overflow=40,
    pool_pre_ping=True,
    echo=False
)

async_session_maker = sessionmaker(
    engine,
    class_=AsyncSession,
    expire_on_commit=False
)

@asynccontextmanager
async def get_db_session():
    async with async_session_maker() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
        finally:
            await session.close()
```

## 5. 缓存设计

### 5.1 Redis 使用策略

| 场景 | Key 模式 | TTL | 说明 |
|------|----------|-----|------|
| 用户信息缓存 | `user:{user_id}` | 30 分钟 | 完整用户信息（含档案） |
| Token 黑名单 | `token_blacklist:{jti}` | Token 剩余有效期 | 退出登录后加入 |
| 每日额度计数 | `quota:{type}:{user_id}:{date}` | 2 天 | 拍题、AI 调用次数限制 |
| 限流计数 | `ratelimit:{ip}:{endpoint}:{minute}` | 1 分钟 | 接口级别限流 |
| 热点题目 | `question:hot:{question_id}` | 1 小时 | 高频访问题目 |
| 章节目录 | `chapter:tree:{textbook_id}:{grade_id}` | 24 小时 | 教材章节树 |
| 知识点关联 | `kp:related:{kp_id}` | 12 小时 | 知识点关联关系 |
| 分布式锁 | `lock:{name}:{id}` | 30 秒 | 防止并发操作 |

### 5.2 缓存工具类

```python
# utils/cache.py
import json
from typing import Any, Optional
from redis.asyncio import Redis

class CacheService:
    def __init__(self, redis: Redis):
        self.redis = redis

    async def get(self, key: str) -> Optional[Any]:
        data = await self.redis.get(key)
        if data:
            return json.loads(data)
        return None

    async def set(self, key: str, value: Any, ttl: int = None):
        await self.redis.setex(key, ttl or 300, json.dumps(value))

    async def delete(self, key: str):
        await self.redis.delete(key)

    async def incr(self, key: str, ttl: int = None) -> int:
        count = await self.redis.incr(key)
        if count == 1 and ttl:
            await self.redis.expire(key, ttl)
        return count

    async def acquire_lock(self, key: str, ttl: int = 30) -> bool:
        """获取分布式锁"""
        return await self.redis.set(key, "1", nx=True, ex=ttl)

    async def release_lock(self, key: str):
        await self.redis.delete(key)
```

### 13.1 鉴权中间件

```python
# middleware/auth.py
from fastapi import Request, HTTPException, status
from app.utils.jwt import verify_token
from app.utils.cache import get_cache

async def auth_middleware(request: Request, call_next):
    # 白名单路径
    if request.url.path in [
        "/api/v1/auth/sms/send",
        "/api/v1/auth/register/phone",
        "/health",
        "/ready"
    ]:
        return await call_next(request)

    # 提取 Token
    auth_header = request.headers.get("Authorization", "")
    if not auth_header.startswith("Bearer "):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="未登录"
        )

    token = auth_header[7:]

    # 验证 Token
    try:
        payload = verify_token(token)
    except Exception:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Token 无效或已过期"
        )

    # 检查黑名单
    cache = get_cache()
    if await cache.get(f"token_blacklist:{payload['jti']}"):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Token 已失效"
        )

    # 注入用户信息
    request.state.user_id = int(payload['sub'])
    request.state.user_type = payload.get('type', 'student')

    return await call_next(request)
```

```python
# middleware/ratelimit.py
from fastapi import Request, HTTPException, status
from app.utils.cache import get_cache
from ipaddress import ip_address

async def ratelimit_middleware(request: Request, call_next):
    cache = get_cache()

    # IP 限流
    client_ip = request.client.host
    ip_key = f"ratelimit:ip:{client_ip}:minute"
    ip_count = await cache.incr(ip_key, ttl=60)
    if ip_count > 1000:  # 每分钟 1000 次
        raise HTTPException(
            status_code=status.HTTP_429_TOO_MANY_REQUESTS,
            detail="请求过于频繁，请稍后再试"
        )

    # 用户限流
    if hasattr(request.state, 'user_id'):
        user_id = request.state.user_id
        user_key = f"ratelimit:user:{user_id}:minute"
        user_count = await cache.incr(user_key, ttl=60)
        if user_count > 300:  # 每分钟 300 次
            raise HTTPException(
                status_code=status.HTTP_429_TOO_MANY_REQUESTS,
                detail="请求过于频繁，请稍后再试"
            )

    # 接口级别限流
    endpoint = request.url.path
    endpoint_key = f"ratelimit:endpoint:{endpoint}:minute"
    endpoint_count = await cache.incr(endpoint_key, ttl=60)
    if endpoint_count > 100:  # 每接口每分钟 100 次
        raise HTTPException(
            status_code=status.HTTP_429_TOO_MANY_REQUESTS,
            detail="该接口请求过于频繁，请稍后再试"
        )

    return await call_next(request)
```

## 15. 常见问题

### Q1: 如何从单体架构演进到微服务架构？

**A**: 渐进式演进路径：
1. **代码层面拆分**：先在单体应用内部按模块清晰划分代码
2. **应用层拆分**：将不同模块部署为独立应用，共享数据库
3. **数据层拆分**：引入服务间通信（gRPC/HTTP），拆分数据库
4. **完整微服务**：引入服务网格，实现完整的服务治理

### Q2: 如何处理服务间调用？

**A**: 阶段演进：
- **阶段1**：直接函数调用（单体）
- **阶段2**：HTTP 调用（应用层拆分）
- **阶段3**：gRPC 调用（数据层拆分，性能更好）
- **阶段4**：服务网格（完整微服务，负载均衡、熔断、重试等）

### Q3: 如何保证数据一致性？

**A**:
- **强一致性场景**：使用分布式事务（Saga 模式或 TCC）
- **最终一致性场景**：使用消息队列 + 补偿机制
- **幂等性设计**：所有写操作设计为幂等，支持重试

### Q4: 如何进行容量规划？

**A**: 基于业务指标进行预估：
- **用户量预估**：未来 6-12 个月的目标用户数
- **并发预估**：假设 5% 用户同时在线，其中 10% 发起请求
- **资源计算**：每个请求的 CPU/内存/IO 占用
- **安全系数**：预留 30-50% 冗余
