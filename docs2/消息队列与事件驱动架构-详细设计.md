# 消息队列与事件驱动架构 - 详细设计

## 1. 概述

### 1.1 模块定位

消息队列与事件驱动架构是 PrimeTop 系统的异步通信 backbone，负责解耦业务模块、削峰填谷、保障最终一致性，并支撑学习提醒、系统通知、家长提醒等跨模块通知场景。

### 1.2 核心职责

| 职责 | 说明 |
|------|------|
| 异步事件发布 | 业务模块按规范发布领域事件，不阻塞主流程 |
| 可靠消息投递 | 保证消息至少被处理一次（At-Least-Once），避免丢消息 |
| 顺序性保障 | 同一用户/对话/错题的事件保证处理顺序 |
| 重试与死信 | 可配置的重试策略、指数退避、死信队列与告警 |
| 削峰填谷 | 高频拍题、AI调用等场景通过队列保护下游系统 |
| 监控可观测 | 消息吞吐、延迟、积压、错误率实时监控与告警 |

### 1.3 依赖关系

```
业务服务层 (用户服务、学习服务、错题服务、规划服务、内容服务、支付服务、消息服务)
        ↓ 发布事件
消息总线 (消息队列与事件驱动)
        ↓ 消费事件
消费者服务 (消息服务、数据分析服务、通知服务、审计服务、数据分析服务)
        ↓
存储/外部系统 (MySQL、Redis、ES、ClickHouse、推送渠道、短信渠道、邮件渠道)
```

### 1.4 适用场景

| 场景 | 使用队列类型 | 典型消费者 |
|------|-------------|-----------|
| 学习提醒/复习提醒 | RabbitMQ Delayed Exchange 或 Redis Stream Delay | 消息服务 → 推送/短信/邮件 |
| AI 对话上下文保存 | RabbitMQ Fanout | 内容存档、数据分析 |
| 错题录入触发复习计划 | RabbitMQ Direct | 规划服务 |
| 订单支付成功触发权益开通 | RabbitMQ Direct/Topic | 会员服务、消息服务 |
| 系统通知/公告发布 | RabbitMQ Fanout | 多端推送、站内信 |
| 用户行为数据实时分析 | Kafka / RabbitMQ (大流量) | ClickHouse / ES |
| 离线任务处理（学习报告生成） | Redis Stream 或 RabbitMQ | 报告服务 |
| 家长端通知（学情更新） | RabbitMQ Topic | 消息服务（家长端） |

### 1.5 不适用场景

- 强一致性场景（例如订单支付扣款）：使用分布式事务或同步调用
- 极高吞吐日志（例如前端埋点流）：考虑 Kafka
- 低延迟点对点 RPC：使用服务间直接调用（gRPC/HTTP）

## 2. 选型与部署架构

### 2.1 消息中间件选型

| 组件 | 选型 | 版本 | 用途 |
|------|------|------|------|
| 主要消息队列 | RabbitMQ | 3.12+ | 业务事件、通知、削峰 |
| 延迟消息 | RabbitMQ Delayed Message Plugin 或 Redis Stream | RabbitMQ 3.12 插件 / Redis 7.x | 定时提醒、延时任务 |
| 高吞吐日志流 | Kafka（可选） | 3.5+ | 学习行为日志埋点流、分析流（中期演进） |
| 原生轻量队列（备选） | Redis Stream / Redis List | 7.x | MVP 简化方案（若先不部署 RabbitMQ） |

**选型理由**：
- RabbitMQ 管理界面完善、Exchange/Queue 模型灵活、支持延迟消息（插件）、社区成熟
- 支持 At-Least-Once、Dead Letter、Confirms 等可靠性机制
- 便于与 Spring Boot、Node.js、Go 等主流框架集成
- 部署相对轻量，适合 MVP 到 V1.0 阶段

### 2.2 部署架构

```
┌─────────────────────────────────────────────────────────────────┐
│                              生产环境                              │
├─────────────────────────────────────────────────────────────────┤
│  ┌──────────┐      ┌──────────────┐      ┌──────────────────────┐ │
│  │ Producer │─────→│  RabbitMQ    │─────→│  Consumer Group      │ │
│  │  Service │      │  (主集群)     │      │  (多个消费进程)      │ │
│  └──────────┘      └──────────────┘      └──────────────────────┘ │
│  ┌──────────┐      ┌──────────────┐      ┌──────────────────────┐ │
│  │ Producer │─────→│  RabbitMQ    │─────→│  DLQ + 告警        │ │
│  │  Service │      │  (主集群 DLQ) │      │  (监控与重处理)      │ │
│  └──────────┘      └──────────────┘      └──────────────────────┘ │
│                                                                  │
│  策略：                                                             │
│  - 主集群采用 3 节点镜像队列（Quorum Queues）保证高可用              │
│  - 管理控制台开启 HTTPS 与 RBAC                                    │
│  - 消息持久化开启磁盘队列                                          │
│  - 开启 Federation 或 Shovel（如果跨机房）                          │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 RabbitMQ 配置清单

| 配置项 | 建议值 | 说明 |
|--------|--------|------|
| 集群模式 | Quorum Queues（镜像队列） | 3 节点形成法定人数 |
| 持久化 | true | 消息和队列均持久化 |
| 自动删除 | false | 队队列不自动删除 |
| 消息 TTL | 7 天（可配置） | 死信保留期 |
| 队列长度限制 | 100,000（可按场景调） | 避免无限增长 |
| 消费者预取 | 10-20（按处理能力） | 保证处理顺序与并发 |
| 心跳检测 | 60s | 检测连接健康 |
| 流控 | 启用 | 避免生产过快压垮消费 |
| 监控导出 | Prometheus exporter | Grafana 面板 |

| Exchange 名称 | 类型 | 用途 | 绑定示例 |
|---------------|------|------|----------|
| `primetop.events.direct` | direct | 点对点路由，明确消费者 | `learning.task_completed` → 学习任务完成消费者 |

## 4. API 封装与客户端集成

### 4.1 统一消息客户端接口（Java/Spring）

```java
public interface MessagePublisher {
    /**
     * 发布事件（同步确认）
     */
    CompletableFuture<Confirm> publish(DomainEvent event);

    /**
     * 发布事件（异步，不等待确认）
     */
    void publishAsync(DomainEvent event);

    /**
     * 发布延迟消息
     */
    void publishDelayed(DomainEvent event, long delayMillis);
}

public interface MessageConsumer {
    /**
     * 订阅并消费消息
     */
    void subscribe(String queue, ConsumerHandler handler, ConcurrencyConfig config);

    /**
     * 订阅并消费消息（带幂等控制）
     */
    void subscribeWithIdempotency(String queue, IdempotentConsumerHandler handler, ConcurrencyConfig config);
}
```

### 4.5 消费消息示例（带幂等与重试）

```java
@Component
public class LearningTaskCompletedConsumer {
    @Autowired
    private IdempotencyService idempotencyService;
    @Autowired
    private AnalyticsService analyticsService;

    @RabbitListener(
        queues = "queue.learning.task_completed",
        containerFactory = "rabbitListenerContainerFactory"
    )
    public void handleTaskCompleted(Message message, Channel channel) {
        String eventId = message.getMessageProperties().getHeader("eventId");
        if (idempotencyService.isProcessed(eventId)) {
            channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
            return;
        }

        try {
            String json = new String(message.getBody(), StandardCharsets.UTF_8);
            LearningTaskCompletedEvent event = objectMapper.readValue(json, LearningTaskCompletedEvent.class);

            // 处理业务逻辑
            analyticsService.recordTaskCompletion(event);

            // 标记已处理（可配合数据库唯一约束或 Redis SETNX）
            idempotencyService.markProcessed(eventId, Duration.ofDays(7));

            channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
        } catch (Exception e) {
            log.error("Failed to process task completed event", e);
            // 根据异常类型决定是重试还是进入死信队列
            if (isRecoverable(e)) {
                channel.basicNack(message.getMessageProperties().getDeliveryTag(), false, true);
            } else {
                channel.basicNack(message.getMessageProperties().getDeliveryTag(), false, false);
            }
        }
    }

    private boolean isRecoverable(Exception e) {
        // 可恢复的异常类型列表
        return e instanceof TransientException || e instanceof TimeoutException;
    }
}
```

## 5. 幂等性保障

### 5.1 幂等表设计（MySQL）

```sql
CREATE TABLE message_idempotency (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    event_id VARCHAR(64) NOT NULL COMMENT '事件ID',
    event_type VARCHAR(128) NOT NULL COMMENT '事件类型',
    processed_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '处理时间',
    consumer VARCHAR(64) NOT NULL COMMENT '消费者标识',
    result JSON COMMENT '处理结果（可选）',
    UNIQUE KEY uk_event_consumer (event_id, consumer),
    KEY idx_event_type (event_type),
    KEY idx_processed_at (processed_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='消息幂等控制表';
```

### 5.2 Redis 幂等锁（高并发场景）

```bash
# 示例：使用 Redis SETNX 实现
SET event_id:{eventId}:consumer:{consumer} 1 NX EX 604800
```

### 5.3 幂等处理流程

```
1. 消费者收到消息，提取 eventId 与 consumer 标识
2. 查询幂等表或 Redis 锁
   - 已处理：ACK 并跳过
   - 未处理：执行业务逻辑，写入幂等表/Redis 锁
3. 处理成功：ACK
4. 处理失败：根据异常类型决定 NACK（重试）或进入 DLQ
```

## 6. 错误处理与死信机制

### 6.1 死信交换器配置

```
Exchange: primetop.dlx
Queue: queue.dlx.{original_queue_name}
Arguments:
  x-dead-letter-exchange: primetop.dlx
  x-dead-letter-routing-key: dlq.{original_queue_name}
  x-message-ttl: 86400000  # 24 小时
```

### 6.2 死信消费者与告警

```java
@Component
public class DeadLetterConsumer {
    @Autowired
    private AlertService alertService;

    @RabbitListener(queues = "queue.dlx.learning.task_completed")
    public void handleDeadLetter(Message message, Channel channel) {
        String json = new String(message.getBody(), StandardCharsets.UTF_8);
        // 记录到审计日志或专门死信表
        // 触发告警（钉钉/企微/邮件）
        alertService.sendAlert("Dead Letter in learning.task_completed", json);
        channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
    }
}
```

### 6.3 重试策略

| 场景 | 最大重试次数 | 初始间隔 | 退避策略 |
|------|------------|---------|---------|
| 网络超时 | 5 | 2s | 指数退避（2^n） |
| 下游服务不可用 | 10 | 5s | 指数退避（1.5^n） |
| 业务可恢复异常 | 3 | 1s | 固定间隔 |
| 数据冲突 | 3 | 1s | 固定间隔 |

## 7. 监控与可观测性

### 7.1 核心指标

| 指标 | 类型 | 说明 |
|------|------|------|
| `rabbitmq_queue_messages` | Gauge | 队列消息积压数 |
| `rabbitmq_queue_messages_ready` | Gauge | 队列待消费消息数 |
| `rabbitmq_queue_messages_unacked` | Gauge | 已消费未确认消息数 |
| `rabbitmq_queue_consumers` | Gauge | 消费者数量 |
| `rabbitmq_queue_message_rate_publish` | Gauge | 消息发布速率（条/秒） |
| `rabbitmq_queue_message_rate_deliver` | Gauge | 消息投递速率（条/秒） |
| `rabbitmq_queue_message_rate_ack` | Gauge | 确认速率（条/秒） |
| `rabbitmq_queue_message_rate_nack` | Gauge | 拒绝速率（条/秒） |
| `rabbitmq_queue_message_rate_dlx` | Gauge | 死信速率（条/秒） |

### 7.2 告警规则

| 告警名称 | 条件 | 等级 | 通知渠道 |
|---------|------|------|---------|
| 队列积压 | `queue_messages > 10000` 持续 5 分钟 | Warning | 钉钉/企微 |
| 消费者离线 | `consumers == 0` 持续 2 分钟 | Critical | 钉钉/企微 + 短信 |
| 死信过多 | `message_rate_dlx > 10` 持续 1 分钟 | Warning | 钉钉/企微 |
| 确认率低 | `ack_rate / deliver_rate < 0.95` 持续 5 分钟 | Warning | 钉钉/企微 |
| 连接失败 | RabbitMQ 连接失败 | Critical | 钉钉/企微 + 电话 |

### 7.3 日志与追踪

- 所有消息发布与消费均记录 `eventId` 与 `correlationId`
- 对接 OpenTelemetry/Zipkin 实现分布式追踪
- 死信消息转存到 MySQL 或 Elasticsearch 以便人工排查

## 8. 安全与权限

### 8.1 RabbitMQ 访问控制

| 用户 | 权限范围 | 说明 |
|------|---------|------|
| primetop_producer | 写入所有 Exchange | 各业务服务发布消息 |
| primetop_consumer_{service} | 订阅特定队列 | 按服务最小化权限 |
| primetop_admin | 全权限 | 运维管理 |

### 8.2 数据脱敏

- 消息负载中不应包含完整密码、银行卡号等敏感字段
- 如需传递，先做哈希或脱敏，或通过带签名的令牌传递

### 8.3 传输加密

- 生产环境开启 TLS/SSL（amqps）
- 管理控制台开启 HTTPS

---

## 9. 容灾与备份

### 9.1 集群高可用

- 采用 3 节点 Quorum Queue，任意 1 节点故障不丢消息
- 节点部署在不同可用区

### 9.2 备份策略

| 类型 | 频率 | 保留期 |
|------|------|-------|
| 队列定义（元数据） | 每次 CI/CD 版本发布 | 永久（Git 管理） |
| 消息内容 | 不备份（消息为暂态） | - |
| 死信消息（MySQL） | 每日 | 30 天 |
| 配置 | 每次 CI/CD 版本发布 | 永久（Git 管理） |

### 9.3 恢复预案

- 节点宕机：自动切换至剩余节点
- 集群不可用：降级为同步调用或本地缓存，并告警
- 消息丢失：通过业务日志补偿（例如重算计划）

### 10.1 学习提醒（延迟消息）

```java
// 发布：任务截止前 1 小时提醒
LearningTaskDueReminderEvent event = new LearningTaskDueReminderEvent();
event.setUserId(userId);
event.setTaskId(taskId);
event.setReminderTime(Instant.now().plus(Duration.ofHours(1)));

long delayMillis = Duration.between(Instant.now(), event.getReminderTime()).toMillis();
messagePublisher.publishDelayed(event, delayMillis);
```
