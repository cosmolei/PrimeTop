## 1. 概述

### 1.1 模块定位

PrimeTop 平台需要从外部内容供应商（教材出版社、教辅机构、独立教研团队、名师作者等）获取大量教育内容——包括题库、知识点解析、视频微课、试卷真题、作文范文等。这些内容并非一次性买断，而是基于 **使用量分成 / 按次计费 / 订阅收入分成** 等多种商业条款进行结算。

本引擎负责 **自动化追踪内容使用量 → 按合同规则计算版权费 → 生成结算单 → 对账确认 → 触发付款流程**，是平台内容采购成本管理的核心后端服务。

### 1.2 核心职责

| 职责 | 说明 |
|------|------|
| 内容使用量采集 | 追踪每条供应商内容在平台上的实际使用情况（播放、查看、答题引用等）|
| 版权费计算 | 根据供应商合同条款（固定费、按次、分成、阶梯价）自动计算应付金额 |
| 结算周期管理 | 按月/季/年生成结算单，支持账期管理与审批流 |
| 对账确认 | 供应商在线核对结算明细，确认或发起争议 |
| 付款集成 | 确认后对接财务付款流程，记录付款凭证 |
| 成本分析与预测 | 按供应商、内容类型、学科等维度分析内容采购成本趋势 |

## 2. 数据模型

### 2.1 核心实体关系

```
supplier (供应商)
  ├── 1:N ── supplier_contract (合同)
  │             ├── 1:N ── contract_pricing_rule (计费规则)
  │             └── 1:N ── contract_content_scope (内容范围)
  ├── 1:N ── supplier_content_item (供应商内容映射)
  └── 1:N ── settlement_order (结算单)
                ├── 1:N ── settlement_detail (结算明细)
                └── 1:N ── settlement_dispute (争议记录)

content_usage_daily (日使用量聚合)
  └── N:1 ── supplier_content_item

payment_record (付款记录)
  └── N:1 ── settlement_order
```

### 2.4 计费规则表 `contract_pricing_rule`

```sql
CREATE TABLE contract_pricing_rule (
    id                  BIGSERIAL PRIMARY KEY,
    contract_id         BIGINT NOT NULL REFERENCES supplier_contract(id),
    rule_code           VARCHAR(32) NOT NULL,              -- 规则编码
    rule_name           VARCHAR(128) NOT NULL,             -- 规则名称
    billing_model       VARCHAR(20) NOT NULL,              -- 计费模式，见下方枚举
    content_type        VARCHAR(32),                       -- 适用内容类型，NULL=全部
    subject             VARCHAR(32),                       -- 适用学科，NULL=全部
    unit_price          DECIMAL(10,4) DEFAULT 0,           -- 单价（按次/按量模式）
    revenue_share_rate  DECIMAL(6,4) DEFAULT 0,            -- 分成比例（0~1）
    -- 阶梯定价
    tier_config         JSONB,                             -- 阶梯定价配置
    /*
     * tier_config 示例（按使用量阶梯）:
     * [
     *   {"min": 0,     "max": 1000,  "unit_price": 0.50},
     *   {"min": 1001,  "max": 5000,  "unit_price": 0.40},
     *   {"min": 5001,  "max": null,  "unit_price": 0.30}
     * ]
     *
     * tier_config 示例（按收入阶梯分成）:
     * [
     *   {"min": 0,      "max": 10000,  "rate": 0.15},
     *   {"min": 10001,  "max": 50000,  "rate": 0.20},
     *   {"min": 50001,  "max": null,   "rate": 0.25}
     * ]
     */
    usage_metric        VARCHAR(32) NOT NULL DEFAULT 'VIEW', -- VIEW/PLAY/DOWNLOAD/ANSWER_REF/CITE/SUB_ACTIVE
    dedup_window_minutes INT DEFAULT 60,                    -- 去重窗口（同一用户N分钟内重复使用计一次）
    effective_from      DATE NOT NULL,                      -- 规则生效日
    effective_to        DATE,                               -- 规则失效日（NULL=长期有效）
    priority            INT DEFAULT 0,                      -- 优先级（多条规则匹配时取最高）
    status              VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
    created_at          TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_pricing_contract ON contract_pricing_rule(contract_id);
CREATE INDEX idx_pricing_model ON contract_pricing_rule(billing_model);
CREATE INDEX idx_pricing_content_type ON contract_pricing_rule(content_type);

COMMENT ON COLUMN contract_pricing_rule.billing_model IS
'FIXED_ANNUAL=年度固定授权费, PER_USE=按次计费, REVENUE_SHARE=收入分成, TIERED_PER_USE=阶梯按次, TIERED_SHARE=阶梯分成, HYBRID_FIXED_PLUS_OVERFLOW=保底+超额按次';
```

    fail_reason         VARCHAR(512),

## 3. 使用量采集与聚合管线

### 3.1 计费口径定义（什么算一次有效使用）

计费口径直接决定钱，必须先于代码定义清楚。`dedup_count` 是唯一进入计费的量；
`raw_count` 仅作对账参考。

| usage_metric | 计一次的条件（全部满足） | 去重窗口内例外 |
|--------------|--------------------------|----------------|
| VIEW | 阅读器内停留 ≥ 10s 且阅读进度 ≥ 5%（同一 session 同一内容首达阈值时上报） | 同用户重复阅读不计费 |
| PLAY | 视频有效播放：单次播放时长 ≥ 30s 或完成率 ≥ 20%；音频同口径 | 同用户重复播放不计费 |
| DOWNLOAD | 资源包/试卷下载任务到达 100% | 下载失败重试不重复计 |
| ANSWER_REF | 供应商题目的作答提交成功（判题完成，含答错） | 草稿自动保存、重复提交不计 |
| CITE | AI 回答中每引用一条供应商 RAG 素材计 1 次（同一次回答同素材只计 1） | 同一回答的重生成/重放不计 |
| SUB_ACTIVE | 派生指标，非事件：周期内活跃付费会员中使用过该合同内容的去重用户数（结算时由 `paid_unique_users` 聚合） | 不适用 |

**反作弊剔除规则（写行时过滤）：**

1. 单用户单内容单日 dedup_count 超阈值（PLAY/VIEW 默认 50）→ 超出部分只计 raw 不计 dedup，行 `metadata.fraud_flag=true`；
2. `raw_count > 1000 且 unique_users = 0` 的桶（理论不可能，说明用户 ID 缺失）→ 全部降为 raw 不计费；
3. 收入分摊时剔除 `fraud_flag=true` 行的 `associated_revenue` 资格。

### 3.2 事件源订阅矩阵

消费《学习行为事件标准化 Schema 注册中心》定义的 `primetop.events.*` Topic，
本模块只消费、不修改事件，映射关系如下：

| 源 Topic | 源事件 | 映射 metric | 生产方 |
|----------|--------|-------------|--------|

### 3.3 去重窗口设计

采用**固定对齐窗口**而非滑动窗口，避免跨窗双计：

```
windowBucket = floor(occurredAt / dedup_window_minutes)   // 窗口起点对齐，同一窗口内同用户同内容同指标只计 1 次
key = usage:dedup:{metric}:{contentId}:{userId}:{windowBucket}
SETNX key 1 EX dedup_window_minutes*60
```

- 去重窗口时长取计费规则 `dedup_window_minutes`（默认 60），映射解析前用默认值；
- SETNX 失败（重复）→ `raw_count` 照常 +1，`dedup_count` 不变；
- 窗口内首次 → raw 与 dedup 同的 +1。

### 3.4 归属解析（事件 → 供应商/合同）

```
resolve(contentType, contentId, occurredAt):
  1. 查 supplier_content_item (content_type, content_id)，本地 Caffeine 缓存 5min
  2. 多版本授权命中（同内容多条 AUTHORIZED）：取 authorized_at <= occurredAt < authorization_end 区间命中者；
     同一时刻仅一条有效（uk_supplier_content 已按 supplier 维度唯一，跨供应商重复授权在接入时拦截）
  3. 授权已过期/撤销（REVOKED/EXPIRED）且 occurredAt >= authorization_end → 丢弃（版权到期引擎已下线内容，不应再产生事件）
  4. 未命中 → 推入 Redis List usage:orphan（保留 7 天），计数告警
```

### 3.6 补数、重放与日终对账

- **幂等**：事件按 eventId 去重（Redis SETEX 48h + Bloom 兜底）；Kafka 重放安全；

- **日终对账 Job（01:30）**：日表 Σdedup（按 metric） vs 埋点平台 ClickHouse 事件计数，
  差异率 > 2% → 自动重建该日 + 告警；连续 3 天差异 → P2 工单；
- **孤儿队列**：`usage:orphan` 长度 > 0 连续 24h → 告警 53920，内容接入映射补齐后一键回放。

               groupId = "royalty-usage-ingest")
public class UsageIngestConsumer {

    public void onEvent(Envelope env) {
        if (!dedupByEventId(env.getEventId())) return;                 // 事件级幂等

        if (item == null) { orphanQueue.push(env); return; }           // §3.4

        boolean paid = membershipSnapshot.isPaid(env.getUserId());

## 4. 版权费计算引擎

### 4.1 计费规则匹配算法

对每一条「日表行 × 计费规则」的组合做匹配，匹配不到规则则整行降级（见降级矩阵 D4）：

```
matchRule(contract, item, metric, statDate):
  candidates = SELECT * FROM contract_pricing_rule
               WHERE contract_id = contract.id AND status = 'ACTIVE'
                 AND usage_metric = metric
                 AND effective_from <= statDate
                 AND (effective_to IS NULL OR effective_to >= statDate)
  过滤 scope：contract_content_scope 中 included=FALSE 命中 → 排除
             included=TRUE 且 scope 命中（content_type/subject/grade_range/具体 ID 列表）→ 保留
  if candidates 为空 → fallback：取合同级 DEFAULT_RULE（unit_price=0），同时告警 53901
  排序：priority DESC, rule_code ASC，取第一条
  if 前两条 priority 相同且计费单价不同 → 计算继续但打 AMBIGUOUS 标签入 metadata，告警 53909
  return first
```

> grade_range 解析：'1-6' 解析为闭区间，item.grade_level 需落在区间内；content_id_list
> 为 JSONB 数组，命中检查用 PostgreSQL `content_id @> ?` 索引加速。

### 4.2 六种计费模型算法与算例

#### 4.2.1 FIXED_ANNUAL（年度固定授权费）

```
周期摊销额 = unit_price × period_days / 365     -- 四舍五入保留 2 位，HAlF_UP
```

- 不依赖使用量；生成一条**合同级固定费明细**：`content_type='CONTRACT_FEE'，content_id=0`；
- 算例：年费 ¥120,000，季度周期 91 天 → 120000 × 91/365 = ¥29,917.81；
- 跨授权起止日的首尾周期按实际在授权区间内的天数摊销。

#### 4.2.2 PER_USE（按次计费）

```
金额 = Σ日表 dedup_count × unit_price
```

算例：¥0.5/次，周期内 dedup 合计 12,340 次 → ¥6,170.00。

#### 4.2.3 TIERED_PER_USE（阶梯按次，分段累进）

```
tieredCharge(tiers, totalCount):
  amount = 0; remain = totalCount
  for t in tiers 按 min 升序:
    span = (t.max == null) ? remain : min(remain, t.max - t.min + 1)
    if span <= 0: continue
    amount += span × t.unit_price
    remain -= span
    if remain <= 0: break
```

算例：阶梯 [0–1000:¥0.5, 1001–5000:¥0.4, 5001–∞:¥0.3]，总量 6,500 次：
1000×0.5 + 4000×0.4 + 1500×0.3 = 500 + 1600 + 450 = **¥2,550.00**。

> 注意是分段累进而非整档适用（6,500 全按 ¥0.3 只得 ¥1,950，对双方都不公平，禁止）。

#### 4.2.4 REVENUE_SHARE（收入分成）

```
金额 = Σ日表 associated_revenue × revenue_share_rate
```

收入来源见 §4.6 收入分摊。算例：分摊收入 ¥86,000，分成率 15% → ¥12,900.00。

#### 4.2.5 TIERED_SHARE（阶梯分成，按累计分摊收入分段累进）

算法同 4.2.3，把 count 换成 Σassociated_revenue、unit_price 换成 rate。
算例：阶梯 [0–10000:15%, 10001–50000:20%, 50001–∞:25%]，分摊收入 ¥60,000：
10000×0.15 + 40000×0.20 + 10000×0.25 = 1500+8000+2500 = **¥12,000.00**。

#### 4.2.6 HYBRID_FIXED_PLUS_OVERFLOW（含免费量按次）

```
tier_config = {"included_quota": 10000, "unit_price": 0.30}
金额 = max(0, totalCount - included_quota) × unit_price
```

配合同合同另一条 FIXED_ANNUAL 规则实现“年度固定授权费 + 超量按次”（§1.4 出版社场景）。

#### 4.2.7 SUB_ACTIVE（按付费活跃用户数）

```
金额 = 周期内 paid_unique_users 按日去重后周期级去重 × unit_price
周期级去重：对每日 paid UV 做周期汇总时用 bitmap/HLL 合并（误差 <1%），或结算重建时精确回算
```

### 4.3 保底、封顶与零结算

```
final 计算顺序（含税口径，税在 §4.4 处理）：
  1. gross = Σ可变计费明细 + 固定费摊销明细
  2. if minimum_guarantee > gross:
       adjustment(MINIMUM_GUARANTEE, +（minimum_guarantee - gross)）
       gross = minimum_guarantee
  3. if cap_amount IS NOT NULL AND cap_amount < gross:
       adjustment(CAP_DISCOUNT, -(gross - cap_amount))
       gross = cap_amount
  4. final_amount = gross
  5. final_amount == 0 → 仍生成结算单（ZER0 金额单），跳过付款，状态直接 CONFIRMED(auto)
     → 保持周期完整性，供应商可查为何为 0
```

保底与封顶同周期同时命中：先保底抬升再封顶削减（结果等于封顶，两条调整都留痕）。

### 4.4 税额计算（价内税口径）

| invoice_type | 处理 |
|--------------|------|
| SPECIAL / VAT_NORMAL / GENERAL | 净额 = final_amount / (1 + tax_rate)；税额 = final_amount - 净额（含税价内税，供应商向我方开具增值税发票） |
| NONE | 净额 = final_amount，税额 = 0（个人供应商仅需收据） |

- 供应商为 INDIVIDUAL 时的劳务报酬个人所得税**代扣代缴由财务线下处理**，v1.0 引擎不计算（付款单 remark 提示财务）；
- tax_amount 记 0 时发票服务仍可登记收据。

### 4.5 精度与舍入规则

1. 全链路 DECIMAL 运算，禁止 float/double；
2. 明细金额：HALF_UP 保留 2 位（中间过程保留 4 位）；
3. 订单汇总 = Σ明细 + Σ调整差额，**不重新四舍五入**；
4. 分摊类计算（收入分摊、保底在多内容间的分摊）产生的尾差：
   |Σ明细 - final| ≤ ¥0.05 → 补一条 ROUND_DIFF 调整行吸收；> ¥0.05 → 阻断生成并告警 53908。

### 4.6 收入分摊算法（REVENUE_SHARE 前置）

**问题**：订阅收入是平台级流水，无法直接归属到某条供应商内容。采用
**「日直线确认 + 有效使用占比分摊」**模型：

```
输入：收入池 P（period, MEMBERSHIP），池内净收入 net（§2.13，已扣除退款）
周期天数 D，日确认收入 R_day = net / D（保留 4 位）

对周期内每一天 d、每一条有效日表行 i（fraud_flag != true，且内容 AUTHORIZED）：
  weight(i,d) = dedup_count(i,d) × 内容类型权重 W(metric)   -- W: PLAY=1.0/VIEW=0.6/CITE=0.8/ANSWER_REF=1.0/DOWNLOAD=1.2
  share(i,d) = weight(i,d) / Σ所有供应商内容 weight(*,d)
  associated_revenue(i,d) = R_day × share(i,d)              -- 保留 4 位，日末位行吸收尾差使 Σ= R_day

约束：Σ associated_revenue(全部行, 周期) == net（误差 ≤ 0.01，日终对账强制校验）
```

分摊在结算单生成时触发（先锁池 → 写回日表 → 再计费），幂等：
`revenue_share_pool.status=LOCKED` 后不可重算；重生成结算单时复用已分摊结果不重分。

防蹭说明：分母只含 AUTHORIZED 供应商内容的使用量，平台自产内容不参与稀释分成（商业条款常见约定，
若合同约定相反，在合同配置 `share_denominator=ALL_CONTENT` 覆盖，v1.0 不开放）。

### 4.7 计算引擎核心代码

```java
public class RoyaltyCalculator {

    /** 对单合同单周期执行计费，返回明细+调整+汇总（纯函数，可重放入幂等） */
    public CalculationResult calculate(ContractCtx ctx, Period period) {
        List<SettlementDetail> details = new ArrayList<>();

        // ① 可变计费：按 (content, metric) 聚合周期用量
        Map<UsageKey, Long> usage = usageRepo.sumDedupByContentAndMetric(ctx.contractId, period);
        for (var e : usage.entrySet()) {
            PricingRule rule = ruleMatcher.match(ctx, e.getKey(), period);      // §4.1
            BigDecimal amount = switch (rule.billingModel) {
                case PER_USE        -> rule.unitPrice.multiply(BigDecimal.valueOf(e.getValue()));
                case TIERED_PER_USE -> tieredCharge(rule.tiers(), e.getValue());  // §4.2.3
                case HYBRID_FIXED_PLUS_OVERFLOW -> hybridOverflow(rule.tiers(), e.getValue());
                case REVENUE_SHARE  -> rule.shareRate.multiply(attributedRevenue(e.getKey(), period));
                case TIERED_SHARE   -> tieredShare(rule.tiers(), attributedRevenue(e.getKey(), period));
                case SUB_ACTIVE     -> rule.unitPrice.multiply(paidUv(ctx, e.getKey(), period));
                default             -> BigDecimal.ZERO; // FIXED_ANNUAL 不在行级计
            };
            details.add(buildDetail(e.getKey(), rule, e.getValue(), amount.setScale(2, RoundingMode.HALF_UP)));
        }

        // ② 固定费摊销
        ruleMatcher.matchFixedRules(ctx, period).forEach(r ->
            details.add(buildContractFeeDetail(r, amortize(r.unitPrice, period))));   // §4.2.1

        // ③ 保底/封顶 + 尾差吸收（§4.3/§4.5）
        return FinalAmountAdjuster.apply(details, ctx.minimumGuarantee, ctx.capAmount);
    }

    private BigDecimal tieredCharge(List<Tier> tiers, long count) {
        BigDecimal amount = BigDecimal.ZERO; long remain = count;
        for (Tier t : tiers) {                       // 已按 min 升序
            long span = t.max == null ? remain : Math.min(remain, t.max - t.min + 1);
            if (span <= 0) continue;
            amount = amount.add(t.unitPrice.multiply(BigDecimal.valueOf(span)));
            remain -= span;
            if (remain <= 0) break;
        }
        return amount;
    }
}
```

## 5. 结算单生成与生命周期

### 5.1 触发方式

| 触发源 | 说明 |
|--------|------|
| 周期 Cron | 每日 02:00 扫描 `settlement_day = 今日日号` 且周期已结束的 EFFECTIVE 合同（月结：上月周期；季/年结同理） |
| 手动触发 | 工作台 `POST /admin/api/v1/settlements/generate`（补单/补数后重算） |
| PER_USE 合同 | v1.0 不做实时结算，仍按月聚合出单（说明写入合同备注），避免高频出款成本 |

### 5.2 生成主流程（九步）

```
① 冻结检查：period_end + 2 天（T+2 数据缓冲）已过，否则推迟（允许强制覆盖 bypass_freeze=true 需管理员权限）
② 幂等抢占：分布式锁 royalty:settle:gen:{contractId}:{period} + 部分唯一索引 uk_settlement_contract_period 双保险
③ 用量汇总：Σcontent_usage_daily → 校验非空（空且无固定费仍生成零金额单）
④ 收入分摊：含 REVENUE_SHARE/TIERED_SHARE 规则的合同 → 确保池 LOCKED → 执行 §4.6 分摊写回日表
⑤ 明细计算：RoyaltyCalculator.calculate()（§4.7，纯函数可重放）
⑥ 保底/封顶/税/尾差：FinalAmountAdjuster + §4.4 税额 → final_amount
⑦ 持久化：settlement_order(DRAFT) + details + adjustments 同事务落库，usage_locked_at=NOW()
⑧ 发送：DRAFT → PENDING_CONFIRM；邮件（结算单 PDF/导出任务链接）+ 站内通知（统一通知服务，模板 royalty.settlement.sent），
   sent_at=NOW()，dispute_deadline = 发送日 + 10 自然日（合同可配 7/10/15，§约束）
⑨ 事件：Outbox 发 SettlementGenerated + SettlementSent
```

### 5.3 结算单状态机

```
                     ┌──────────────(手动/自动重发)─────────────┐
                     ▼                                          │
 DRAFT ──发送──▶ PENDING_CONFIRM ──供应商确认──▶ CONFIRMED ──财务发起付款──▶ PAYMENT_PENDING
   │                │      ▲                                        │ 凭证回填            │ 发票核销登记
   │                │      │到期自动确认(auto_confirmed=true)          ▼                    ▼
   │                │      └──────────────────────────────────▶ CONFIRMED      PAID ──▶ COMPLETED
   │                │争议
   │                ▼                                              ▲
   │            DISPUTED ──全部争议 CLOSED/RESOLVED──▶ RESOLVED ──金额调整后──┘
   │                │
   └──任何非终态───▶ CANCELLED（人工+审计原因必填；重生成= CANCELLED 旧单 + 新单 predecessor_id 指向旧单）
```

**守卫表：**

| # | 迁移 | 守卫条件 | 违反错误码 |
|---|------|----------|-----------|
| G1 | → PENDING_CONFIRM | 状态=DRAFT 且明细已生成且通知渠道可用（不可用时保持 DRAFT 重试） | 53903 |
| G2 | → CONFIRMED（手动） | 状态=PENDING_CONFIRM 且无 OPEN/UNDER_REVIEW 争议 且操作人为供应商门户账号 | 53903/53905 |
| G3 | → CONFIRMED（自动） | 状态=PENDING_CONFIRM 且 dispute_deadline < 今日 且无 OPEN/UNDER_REVIEW 争议 | — |
| G4 | → DISPUTED | 状态=PENDING_CONFIRM 且 dispute_deadline 未过 且单据争议数 < 5 | 53905/53906 |
| G5 | DISPUTED → RESOLVED | 单据全部争议状态 ∈ {RESOLVED, CLOSED} | 53903 |
| G6 | RESOLVED → CONFIRMED | 调整行已落库且 final_amount 重算完成 | 53903 |
| G7 | CONFIRMED → PAYMENT_PENDING | 收款账户信息完整（bank_account_no 解密可用）且付款金额>0 | 53907 |
| G8 | PAYMENT_PENDING → PAID | 存在 payment_status=PAID 的付款记录且 Σamount = final_amount | 53908 |
| G9 | PAID → COMPLETED | 发票/收据已登记且发票金额 = final_amount（±0.01） | 53908 |
| G10 | → CANCELLED | 仅 DRAFT/PENDING_CONFIRM/RESOLVED 可取消；已确认后不可取消只能争议/红冲（红冲走负金额新单，v1.1） | 53903 |

### 5.4 自动确认 Job

```java
@Scheduled(cron = "0 30 1 * * *")
public void autoConfirmExpired() {
    List<SettlementOrder> due = settlementDao.findPendingBeyondDeadline(LocalDate.now());
    for (SettlementOrder o : due) {
        if (disputeDao.existsOpenOrUnderReview(o.getId())) continue;      // G3
        int n = settlementDao.casUpdate(o.getId(), "PENDING_CONFIRM", "CONFIRMED",
                Map.of("confirmed_at", now(), "confirmed_by", "SYSTEM_AUTO", "auto_confirmed", true));
        if (n == 1) outbox.publish(SettlementConfirmed.of(o, /*auto=*/true));
    }
}
```

> 自动确认是默认合同约定（沉默视为同意），dispute_deadline 提前在发送邮件中高亮提示；
> 高风险合同（年金额 > ¥500,000）强制不自动确认，需供应商显式点击确认（合同级开关 `require_explicit_confirm`）。

### 5.5 重算与重生成

| 场景 | 处理 |
|------|------|
| 争议调整（金额变化） | RESOLVED → 落 DISPUTE_ADJUST 调整行 → final_amount 重算 → CONFIRMED（不换单号，历史明细保留） |
| 用量补数后重算 | 手动「重生成」：旧单 CANCELLED + 新单 DRAFT（predecessor_id 链）；旧单明细不可变 |
| 误生成 | CANCELLED（不重生成）；原因必填入审计 |

重生成链查询：`WITH RECURSIVE` 沿 predecessor_id 遍历展示完整历史。

### 5.6 生成服务关键代码

```java
@Service
public class SettlementGenerator {

    @Transactional
    public SettlementOrder generate(Long contractId, YearMonth period, boolean bypassFreeze) {
        String lockKey = "royalty:settle:gen:" + contractId + ":" + period;
        if (!redisLock.tryLock(lockKey, 10, TimeUnit.MINUTES)) throw new BizException(53904, "生成任务进行中");
        try {
            if (settlementDao.existsActive(contractId, period)) throw new BizException(53904);   // 幂等双保险

            Period p = periodResolver.resolve(contractId, period);                                // ①②
            if (!bypassFreeze && p.endDate().plusDays(2).isAfter(LocalDate.now()))
                throw new BizException(53911, "周期数据未冻结（T+2），不得生成");

            revenueAttributor.ensureAttributed(p, contractId);                                     // ④ 分成合同先分摊

            CalculationResult r = royaltyCalculator.calculate(contractCtx(contractId), p);         // ⑤⑥
            SettlementOrder order = settlementDao.insert(Draft.of(contractId, p, r.summary()));    // ⑦
            detailDao.batchInsert(r.details().stream().map(d -> d.withSettlement(order.getId())).toList());
            adjustmentDao.batchInsert(r.adjustments().stream().map(a -> a.withSettlement(order.getId())).toList());

            sendAndTransition(order);                                                              // ⑧⑨
            return order;
        } finally { redisLock.unlock(lockKey); }
    }
}
```

### 6.4 争议流程

```
OPEN ──平台受理──▶ UNDER_REVIEW ──裁定──▶ RESOLVED（含金额调整）/ ESCALATED（升级合同/法务）
                              └──────▶ CLOSED（无调整，维持原金额）
ESCALATED ──线下解决后──▶ RESOLVED / CLOSED
```

**争议类型与处理动作：**

| dispute_type | 典型诉求 | 处理动作 |
|--------------|----------|----------|
| USAGE_COUNT | 用量少计/多计 | 触发指定日用量重建（§3.6）→ 出重建前后对比 → 双方确认 |
| AMOUNT | 单价/阶梯/保底封顶计算错误 | 重跑计算器快照对比，错则调整 |
| CONTENT_SCOPE | 内容归属错误（不该计费/漏计） | 裁定 scope → 同步 supplier_content_item 映射 → 重生成 |
| CONTRACT_TERM | 合同条款解释分歧 | ESCALATED 法务 |
| OTHER | 其他 | 人工 |

**SLA：** NORMAL 3 个工作日受理、HIGH 1 个工作日、CRITICAL 4 小时；超时自动升级提醒主管。

**争议调整落账：**
```
resolve(dispute, decision):
  if decision.adjustAmount != 0:
     settlement_adjustment += DISPUTE_ADJUST(delta, related_dispute_id, reason=decision.remark)
     final_amount += delta → 重新走 G6 → CONFIRMED
  dispute.status = RESOLVED, resolution/adjusted_amount/resolved_by 落库
  outbox → SettlementDisputeResolved
```

### 6.5 防滥用

- 争议窗口：仅 PENDING_CONFIRM 且 dispute_deadline 前（§5.3 G4）；
- 同一结算单争议总数上限 5 条（超出提示合并提交，53906）；
- 争议描述 ≥ 20 字、证据必填（evidence_urls 至少 1 个）才允许提交 UNDER_REVIEW。

## 7. 付款集成与发票

### 7.1 付款流程（CONFIRMED → COMPLETED 段）

```
① 财务在工作台发起付款：POST /admin/api/v1/settlements/{id}/payments
   守卫 G7（账户完整、金额>0）→ settlement 置 PAYMENT_PENDING + 创建 supplier_payment_record(CREATED)
② 财务审批（双人复核：金额 ≥ ¥50,000 强制第二审批人）：payment APPROVED
③ 出款：v1.0 网银线下转账（pay_channel=BANK_TRANSFER），银企直连批量（EBANK_BATCH）为 v1.1；
   出款后工作台回填 bank_serial_no + voucher_url（付款回单扫描件）→ payment PAID + paid_at
④ 守卫 G8 校验 ΣPAID.amount = final_amount → settlement PAID
⑤ 发票登记（进项方向：供应商向我方开票）：发票服务登记发票号/金额/类型；
   守卫 G9：发票金额 = final_amount（±0.01）→ settlement COMPLETED
   发票缺失：PAID 后 30 天未登记 → 周报提醒财务（应付合规），不阻塞状态但入合规看板
```

**失败重试：** payment FAILED（退票/汇款失败）→ fail_reason 必填 → 新建 payment 记录 retry_of 指向原单重付；
金额不变，仅补差额场景走 MANUAL_ADJUST 调整行后按新 final_amount 重付。

**付款单状态机：** `CREATED → APPROVED → PAYING → PAID / FAILED；CREATED/APPROVED → CANCELLED`
同一结算单同时仅一条非终态付款记录（应用层 CAS：`UPDATE ... WHERE settlement_id=? AND id NOT IN (终态单)` 校验）。

### 7.2 付款日终对账

- 我方付款记录 vs 银行流水（银企对账单文件/CSV 导入）：金额+流水号双向匹配；
- 差异分类：A 我方已记银行无（凭证缺失/退票未回填）→ 财务确认；B 银行有我方无（线下直接汇款未走系统）→ 补录；
 C 金额不一致 → 告警 53908 工单；
- 与供应商侧：供应商确认金额 vs 实收金额差异由供应商发起争议（线下补充协议），平台侧只维护我方口径。

### 7.3 发票联动（对接《发票管理与电子发票开具服务》）

| 时机 | 动作 |
|------|------|
| settlement PAID | 触发「进项发票登记提醒」给供应商门户 + 邮件 |
| 发票登记完成 | 发票服务回调 /internal/api/v1/settlements/{id}/invoice-registered → G9 校验 → COMPLETED |
| 发票金额 ≠ final_amount | 拒绝完成，差异工单（红字发票/补开由财务处理） |
| invoice_type=NONE | 登记收据扫描件即可（金额一致才 COMPLETED） |

### 7.4 与《支付对账与资金清结算服务》的关系边界

- 支付对账服务管**收款侧**（用户→平台，渠道 T+1/T+3 对账，单号前缀 STTL）；
- 本引擎管**付款侧**（平台→供应商版权费，单号前缀 STL/PAY）；
- 唯一交点：`revenue_share_pool.source_summary_no` 引用其 `settlement_summary.settlement_no` 作为收入池来源，
  保证分成基数可追溯到渠道对账结果；两套单号体系严格区分，财务报表按前缀分列。

## 9. 异常处理与降级矩阵

版权费直接涉及资金结算，降级原则：**宁可延迟、不可多计**（少计可补，多计难以追回且损害供应商信任）。

| # | 故障场景 | 影响 | 处置策略 | 恢复动作 |
|---|----------|------|----------|----------|
| D1 | Kafka 消费中断/积压 | 用量缺失→少计费 | 消费者 pause 自动重连；事件在 Broker 保留 7 天（retention）；小时 flush 检查消费 watermark，缺失小时标记 PENDING 不落日表 | 恢复后按 eventId 幂等回放（§3.6），日终对账兜底（差异>2% 自动重建） |
| D2 | Redis 不可用 | 去重键与小时桶不可写；生成锁失效 | **暂停消费**（无去重条件下禁止计费）；手动生成入口熔断返回 53900；周期 Cron 跳过本轮 | 恢复后回放事件；Redis 有 AOF 持久化，小时桶数据可恢复 |
| D3 | 归属解析未命中（映射缺失） | 该事件无法计费 | 推入 `usage:orphan`（保留 7 天），不阻塞主流；非空 24h 告警 53920 | 映射补齐后管理端一键回放 |
| D4 | 计费规则匹配失败 | 该行用量无法计价 | **整行降级不计费**：仍写 settlement_detail（gross=0，metadata.degrade_reason=RULE_MISS），usage 计入 total_usage_count；fallback DEFAULT_RULE（unit_price=0）仅兜底防中断 | 出单后自动创建「补规则重算」工单，规则补齐后走重生成链（§5.5） |
| D5 | 规则优先级歧义（前两条 priority 相同且单价不同） | 计价口径不确定 | 按较高 priority 继续计算，metadata.ambiguous=true，告警 53909 | 人工 48h 内裁决，必要时争议/调整行修正 |
| D6 | 收入池未 LOCKED 或 Σ分摊≠net | 分成类合同无法计价 | 该合同结算生成推迟（每日重试最多 3 次）；非分成合同不受影响照常出单 | 3 次失败→P2 工单+通知财务人工核池 |
| D7 | 通知渠道失败（邮件+站内全失败） | 供应商未知晓→争议期限不应起算 | 保持 DRAFT（守卫 G1），每 30min 重试 6 次；门户列表可见作兜底渠道 | 仍失败→P2；sent_at 未写入前 dispute_deadline 不生效 |
| D8 | 付款退票/汇款失败 | 资金未达 | payment→FAILED（fail_reason 必填）→ 新建 retry_of 链重付 | 金额变化走 MANUAL_ADJUST 调整行后按新 final_amount 重付 |
| D9 | 发票 30 天未登记 | 进项合规 | 不阻塞状态机；进合规看板+财务周报 | 发票登记后回调走 G9 完成 |
| D10 | ClickHouse 不可用（对账/重建） | 日终对账缺位 | 对账 Job 当日标记 SKIPPED；重建接口熔断返回 53900 | 恢复后自动补跑；连续 3 天 SKIPPED→P2 |
| D11 | gRPC 预估超时（>200ms）或计算服务异常 | 推荐侧拿不到成本 | 返回最近成功结果缓存（TTL 24h，stale=true）；无缓存时返回明确错误 | 推荐侧按中性权重处理，**不得因预估失败屏蔽内容** |
| D12 | 门户服务异常 | 供应商无法确认 | 不影响主链：出单/自动确认/付款照常；线下邮件确认可由管理端代录（审计留痕） | 门户恢复后补线上确认记录 |

**熔断规则**：手动生成接口连续失败率 >50%（1min 窗口）→ 熔断 10min，防抖动雪崩。

### 11.2 资金恒等式审计 Job（每日 05:00）

```sql
-- 恒等式破坏即 P1：final_amount = Σ明细 + Σ调整
SELECT s.id, s.settlement_no, s.final_amount,
       COALESCE(d.sum_gross,0) AS detail_sum, COALESCE(a.sum_delta,0) AS adj_sum,
       s.final_amount - COALESCE(d.sum_gross,0) - COALESCE(a.sum_delta,0) AS diff
FROM settlement_order s
LEFT JOIN (SELECT settlement_id, SUM(gross_amount) sum_gross FROM settlement_detail GROUP BY settlement_id) d ON d.settlement_id = s.id
LEFT JOIN (SELECT settlement_id, SUM(delta_amount) sum_delta FROM settlement_adjustment GROUP BY settlement_id) a ON a.settlement_id = s.id
WHERE s.status <> 'CANCELLED'
  AND ABS(s.final_amount - COALESCE(d.sum_gross,0) - COALESCE(a.sum_delta,0)) > 0.01;
-- 结果集非空 → P1 告警 + 冻结相关结算单后续付款（守卫 G7 前置检查本标记）
```

## 13. 安全与合规红线

1. **敏感字段加密**：bank_account_no / id_card_no 信封加密存储（KMS，参照《服务端密钥管理与敏感配置安全策略》），任何界面仅展示尾 4 位；
2. **用户隐私**：content_usage_daily 与结算明细**禁止落明文 userId**（当前模型仅计数+HLL，天然满足；HLL 不可逆，禁止引入可逆的用户级枚举能力）；
3. **行级隔离**：门户所有查询强制 supplier_id 过滤（《统一数据权限控制框架》），跨供应商访问 53917 + 审计告警；
4. **资金双人原则**：付款审批人与发起人不得为同一账号；金额 ≥¥50,000 强制第二审批人；
5. **恒等式审计**：`final_amount = Σdetail + Σadjustment` 每日校验（§11.2），破坏即 P1 并冻结后续付款；
6. **操作审计**：管理端全部写操作（生成/重生成/取消/付款/裁定/调账）入《服务端审计日志与操作追溯系统》，合同与计费规则变更保留 diff 快照；
7. **税额口径**：价内税口径（§4.4）不得与价外税混用；舍入差异只能经 ROUND_DIFF 调整行吸收，**禁止直接修改明细金额**；
8. **自动确认边界**：仅当合同未开启 require_explicit_confirm 才允许沉默确认；年额>¥50 万合同强制显式确认（§5.4）；
9. **个人信息最小必要**：供应商联系人信息仅用于结算通知与门户登录，禁止透出给第三方或用于营销（PIPL）；
10. **未成年人保护**：争议处理/对账视图只提供聚合口径用量，任何情况下不得向供应商提供用户级（含未成年学生）行为明细；
11. **合同法务**：CONTRACT_TERM 类争议必须 ESCALATED 法务，产品与技术侧无权单方解释合同条款。
