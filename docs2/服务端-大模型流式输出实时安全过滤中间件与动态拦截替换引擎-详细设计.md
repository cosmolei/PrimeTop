# 服务端-大模型流式输出实时安全过滤中间件与动态拦截替换引擎-详细设计

## 1. 概述

### 1.1 模块定位

大模型流式输出实时安全过滤中间件（Streaming Output Safety Filter，简称 **SOSF**）是部署在 AI 服务层与客户端之间的流式内容安全网关。当大模型以 SSE（Server-Sent Events）或 WebSocket 方式流式输出回答时，SOSF 负责在每个 token chunk 到达客户端之前进行**毫秒级实时安全检测**，在不破坏用户流式阅读体验的前提下，拦截和替换不适宜内容。

### 1.2 核心挑战

| 挑战 | 说明 |
| --- | --- |
| **部分文本匹配** | 敏感词可能被拆分到多个 SSE chunk 中（如"考" + "试答案"），需要跨 chunk 滑动窗口 |
| **超低延迟要求** | 每个 chunk 的过滤延迟必须控制在 50ms 以内，否则影响流式阅读体验 |
| **语义级检测** | 单纯关键词无法识别变体表达、暗语、隐喻等语义层面的不当内容 |
| **优雅中断** | 检测到违规内容时需要平滑中断流并输出替换文本，不能让客户端出现明显断裂 |
| **上下文感知** | 同一表述在不同学段、学科场景下合规性不同（如高中生物 vs 小学对话） |
| **流恢复** | 中断或替换后，需要尽可能保持后续内容的连贯性 |

### 1.3 与现有模块的边界

| 现有模块 | 职责 | 与本模块关系 |
| --- | --- | --- |
| AI输入安全与教育对话护栏引擎 | 输入侧意图识别与 prompt 注入安全 | **上游**：输入安全通过后才进入模型推理 |
| 教育场景敏感词多层次过滤引擎 | 离线/批量内容的多层敏感词过滤 | **共享词库**：复用其敏感词库与分类体系 |
| AI对话安全审计与敏感内容自动上报 | 事后审计与上报 | **下游消费者**：SOSF 的拦截事件发送给它做审计 |
| AI回答后处理与智能优化管线 | 非流式场景的后处理 | **互补**：非流式场景由其处理，流式场景由 SOSF 处理 |
| AI幻觉检测与教育事实校验引擎 | 事实性校验 | **并行管道**：幻觉检测可以异步执行，不影响流式输出 |
| SSE流式响应与AI增量渲染引擎 | SSE 协议管理与客户端渲染 | **传输层**：SOSF 作为 SSE 管道中的中间件 |

### 2.2 三层过滤管道

SOSF 采用**三层级联过滤**架构，按延迟从低到高、精度从粗到细排列：

| 层级 | 名称 | 延迟 | 机制 | 拦截类型 |
| --- | --- | --- | --- | --- |
| **L1** | 关键词层 | < 1ms | AC 自动机多模式匹配 | 精确敏感词、变体词 |
| **L2** | 规则引擎层 | < 5ms | 正则 + 规则模板 + 上下文条件 | 格式化违规、答案直接泄露、联系方式 |
| **L3** | 语义分类层 | < 20ms (异步) | 轻量分类模型 + 置信度判断 | 隐喻、暗示、语义不当内容 |

**L3 异步设计**：由于语义分类可能偶尔超过 20ms，L3 采用**延迟判定 + 回溯拦截**策略：
- 正常情况下 L3 在 chunk 到达输出缓冲区之前完成
- 如果 L3 处理超时，chunk 暂不释放，等待 L3 结果（最多等 50ms）
- 如果 50ms 内 L3 仍未完成，放行当前 chunk，异步标记为"待复审"
- 后续如果 L3 判定违规，对后续 chunk 执行拦截并触发告警

```java
public interface StreamingSafetyFilter {

    /**
     * 初始化一个流式过滤会话
     * @param context 会话上下文（学段、学科、场景等）
     * @return 会话ID
     */
    String initSession(FilterContext context);

     * 对流入的 chunk 进行安全过滤

     * @param chunk 模型输出的文本片段
     * @return 过滤结果（通过/替换内容/中断信号）

    /**
     * 流结束时清理资源

    void closeSession(String sessionId);
```

## 4. 详细设计

### 4.1 L1：AC 自动机关键词匹配层

#### 4.1.1 核心算法：改进的 Aho-Corasick 多模式匹配

选择 AC 自动机的原因：
- **多模式同时匹配**：一次扫描可同时匹配 10 万+ 敏感词
- **O(n) 时间复杂度**：扫描耗时仅与文本长度相关，与词库大小无关
- **成熟可靠**：工业界广泛使用的字符串匹配算法

#### 4.1.2 变体处理策略

```java
public class KeywordVariantExpander {

    // 变体生成策略
    public Set<String> expandVariants(String keyword) {
        Set<String> variants = new HashSet<>();
        variants.add(keyword);

        // 1. 谐音变体（中文特有）
        variants.addAll(homophoneVariants(keyword));
        // 示例："答案" → "答暗", "哒案"

        // 2. 拆字变体
        variants.addAll(splitCharVariants(keyword));
        // 示例："考试" → "考  试", "考.试", "考-试"

        // 3. 拼音变体
        variants.addAll(pinyinVariants(keyword));
        // 示例："答案" → "da'an", "da an"

        // 4. 全角/半角混淆
        variants.addAll(fullWidthVariants(keyword));
        // 示例："abc" → "ａｂｃ"

        // 5. 星号/符号混淆
        variants.addAll(symbolObfuscationVariants(keyword));
        // 示例："微信号" → "微☆信号", "微*信号"

        // 6. 英文大小写变体（针对英文敏感词）
        variants.addAll(caseVariants(keyword));

        return variants;
    }

    private Set<String> homophoneVariants(String keyword) {
        // 基于预构建的谐音字典生成同音字替换
        // 字典示例：答→[答,哒,搭], 案→[案,暗,按]
        Set<String> result = new HashSet<>();
        char[] chars = keyword.toCharArray();
        generateHomophones(chars, 0, new StringBuilder(), result);
        return result;
    }
}
```

#### 4.1.3 跨 Chunk 滑动窗口

这是流式过滤的**核心技术难点**。敏感词可能被拆分到多个 SSE chunk 中：

```
Chunk 1: "这道题的正确答"
Chunk 2: "案是C，因为..."
                    ↑ "答案" 跨越了两个 chunk
```

**解决方案：滑动窗口缓冲器**

```java
public class SlidingWindowBuffer {

    private final int windowSize;           // 窗口大小（字节），默认 256
    private final StringBuilder buffer;     // 累积缓冲区
    private int flushedPosition;            // 已安全刷新的位置

    /**
     * 写入新 chunk，返回可以被安全输出的文本段
     * 
     * 策略：
     * 1. 将新 chunk 追加到 buffer
     * 2. 在 buffer 的 [flushedPosition, end] 范围内执行 AC 匹配
     * 3. 找到所有匹配后，确定可安全输出的范围：
     *    - 从 flushedPosition 到「最后一个匹配结束位置之后」或「buffer 尾部减窗口余量」
     *    - 保留尾部 windowSize 字节作为下一轮的窗口前缀
     * 4. 返回可安全输出的文本，更新 flushedPosition
     */
    public WindowFlushResult flush(String newChunk, ACTrieMatcher matcher) {
        buffer.append(newChunk);
        int totalLen = buffer.length();

        // 在未刷新区域执行匹配
        String unchecked = buffer.substring(flushedPosition);
        List<Match> matches = matcher.match(unchecked);

        // 计算安全可输出边界
        int safeEndOffset = calculateSafeBoundary(unchecked.length(), matches, windowSize);

        // 提取可输出内容
        String flushable = unchecked.substring(0, safeEndOffset);
        String remaining = unchecked.substring(safeEndOffset);

        // 更新状态
        flushedPosition += safeEndOffset;

        // 检查缓冲区是否需要压缩
        if (flushedPosition > 4096) {
            buffer.delete(0, flushedPosition);
            flushedPosition = 0;
        }

        return new WindowFlushResult(
            flushable,    // 可安全输出的文本
            remaining,    // 暂留窗口中的文本
            matches       // 在本次匹配中发现的违规项
        );
    }

    private int calculateSafeBoundary(int uncheckedLen, List<Match> matches, int windowSize) {
        if (matches.isEmpty()) {
            // 无匹配：可输出到「总长度 - 窗口保留区」
            return Math.max(0, uncheckedLen - windowSize);
        }

        // 有匹配：输出到「首个匹配起点」之前（v1.1 修复 F1：
        // v1.0 误取 lastMatch.getStart()，会先把首个命中的敏感词随 flushable
        // 原样下发再处理后续匹配——属漏拦截缺陷；首个匹配起点之前的
        // 内容才是确定安全的，匹配区交由仲裁器逐段替换/中断）
        Match firstMatch = matches.get(0);
        return firstMatch.getStart();
    }
}
```

#### 4.1.4 AC 自动机构建与热更新

```java
public class ACTrieManager {

    private volatile ACTrie trie;        // 当前生效的 Trie
    private volatile long version;       // 当前版本号
    private final ScheduledExecutorService scheduler;

    /**
     * 构建新的 AC 自动机（全量重建）
     * 触发条件：词库变更量超过阈值（新增/修改 ≥ 100 条）
     */
    public void rebuildTrie(List<SafetyKeyword> keywords) {
        // 1. 构建新的 Trie
        ACTrie newTrie = new ACTrie();
        for (SafetyKeyword kw : keywords) {
            if (kw.getStatus() != 1) continue;

            // 添加原始词
            newTrie.add(kw.getKeyword(), kw);

            // 添加变体
            if (kw.getVariants() != null) {
                for (String variant : kw.getVariants()) {
                    newTrie.add(variant, kw);
                }
            }
        }
        newTrie.buildFailureLinks(); // 构建 failure 链接

        // 2. 原子切换
        long newVersion = version + 1;
        // 序列化到 Redis
        redis.set("SOSF:ac_trie:v" + newVersion, serialize(newTrie));
        // 内存切换
        this.trie = newTrie;
        this.version = newVersion;
        // 更新缓存版本标记
        redis.set("SOSF:ac_trie:current_version", String.valueOf(newVersion));
    }

    /**
     * 增量更新（少量词变更时使用）
     * 注意：AC 自动机不支持真正的增量更新，这里的增量是指：
     * 1. 收集变更词列表
     * 2. 在低峰期异步重建
     * 3. 平滑切换
     */
    @Scheduled(fixedDelay = 60000) // 每分钟检查一次
    public void checkAndIncrementalUpdate() {
        try {
            String verStr = redis.get("SOSF:ac_trie:current_version");
            if (verStr == null) return; // Redis 未初始化：保持本地版本，M6 告警观测
            long lastVersion = Long.parseLong(verStr);
            if (lastVersion > this.version) {
                // 发现新版本，从 Redis 加载
                byte[] data = redis.get(("SOSF:ac_trie:v" + lastVersion)
                        .getBytes(StandardCharsets.UTF_8));
                if (data == null) {
                    // 版本标记在、载体丢失（Redis 淘汰/网络分区）→ 从 DB 兜底重建（G5）
                    rebuildFromDatabase();
                    return;
                }
                ACTrie loaded = deserialize(data);
                // 双重校验：加载期间可能又发布了更新版本，避免旧覆盖新
                long nowVer = Long.parseLong(redis.get("SOSF:ac_trie:current_version"));
                if (nowVer == lastVersion) {
                    this.trie = loaded;   // volatile 引用原子切换，读侧无锁（G4）
                    this.version = lastVersion;
                    metrics.gauge("sosf_trie_version", this.version);
                } else {
                    log.info("trie version advanced during load: {} -> {}, retry next tick",
                            lastVersion, nowVer);
                }
            }
        } catch (Exception e) {
            // 检查线程绝不抛出：更新失败保持旧版本继续服务（G5 红线）
            log.warn("ac trie incremental check failed, keep version {}", this.version, e);
            metrics.counter("sosf_trie_update_fail_total").increment();
        }
    }

    /**
     * 低峰期重建调度：变更词累计 ≥ 100 条或距上次全量重建 > 24h
     * 由词库变更事件（word.changed / rule.changed）驱动计数，异步执行
     */
    @Scheduled(cron = "0 30 3 * * ?") // 每日 03:30 低峰期
    public void scheduledRebuild() {
        if (pendingWordChanges.get() >= REBUILD_THRESHOLD
                || Instant.now().toEpochMilli() - lastRebuildAt > Duration.ofHours(24).toMillis()) {
            executor.submit(this::rebuildFromDatabase);
        }
    }

    /** DB 全量重建：与 rebuildTrie 共用构建逻辑，但序列化后写 Redis */
    private void rebuildFromDatabase() {
        List<SafetyKeyword> keywords = keywordRepo.findEnabledByScene("AI_OUTPUT"); // G8：词库权威投影
        rebuildTrie(keywords);
        pendingWordChanges.set(0);
        lastRebuildAt = Instant.now().toEpochMilli();
    }
}
```

#### 4.1.5 变体膨胀护栏与内存预估

变体扩展是双刃剑：10 万原始词接 5 类变体策略直接展开可能达到百万级 pattern，
内存与构建时间失控。SOSF 采用**分级变体策略**：

| 级别 | 适用词 | 变体策略 | 膨胀系数上限 |
| --- | --- | --- | --- |
| V0 | severity=4（危禁级）全量 | 六类变体全展开 | ≤ 8x |
| V1 | severity=3 | 谐音 + 拆字 + 符号混淆 | ≤ 4x |
| V2 | severity≤2 | 原词 + 全半角 + 大小写 | ≤ 1.5x |
| 定制 | 单词级 variants 字段显式指定 | 以 DB 配置为准 | 计入单词上限 32 |

- 单词变体数硬上限 32，超出部分丢弃并告警（防错误配置拖垮构建）；
- 全库 pattern 总量护栏 60 万，超出时拒绝新增（错误码 56824）并触发词库治理；
- 实测基线：10 万词 / 42 万 pattern 的 AC 自动机 ≈ 210MB 堆内，构建耗时 ≈ 11s，
  满足低峰重建窗口；
- 变体归一化双向约定：与《敏感词多层次过滤引擎》的归一化器（全半角/大小写/繁简）
  **同一份实现库**（contract 对齐 R4），避免两侧对同一文本判定不一致。

### 4.2 L2：规则引擎层

#### 4.2.1 规则分类与执行模型

| 规则类型 | 示例 | 执行方式 |
| --- | --- | --- |
| REGEX | 手机号/微信号/QQ 号引流格式、URL 外链 | 预编译 Pattern，窗口文本单遍执行 |
| TEMPLATE | “答案是X”“选X”类直接给答案句式 | 转译为 AC 词典 + 后置校验器组合 |
| COMPOSITE | 规则A命中且上下文条件成立才触发 | 条件求值器 + 子规则与门 |

规则按 `priority` 升序执行，首条 `INTERRUPT` 级规则命中即短路返回；
`REPLACE` 级规则全部执行后取 severity 最高者进入仲裁器。

#### 4.2.2 ReDoS 防护（规则安全准入）

管理端保存正则时强制走**三道准入校验**，任何一道失败拒绝入库（56811）：

```java
public class RegexRuleAdmission {

    private static final int MAX_PATTERN_LEN = 512;
    private static final long COMPILE_BUDGET_MS = 50;
    private static final long MATCH_BUDGET_MS = 5;
    private static final String[] FORBIDDEN_FRAGMENTS = {
        "(.*)*", "(.+)+", "(.*|.*).*", "\\w*+\\w*"  // 嵌套量词特征
    };

    public AdmissionResult admit(String pattern) {
        // ① 静态检查：长度、嵌套量词特征、反向引用禁用
        if (pattern.length() > MAX_PATTERN_LEN) return reject("TOO_LONG");
        for (String frag : FORBIDDEN_FRAGMENTS)
            if (pattern.contains(frag)) return reject("NESTED_QUANTIFIER");

        // ② 编译预算：预编译耗时超 50ms 视为高风险
        long t0 = System.nanoTime();
        Pattern compiled;
        try { compiled = Pattern.compile(pattern); }
        catch (PatternSyntaxException e) { return reject("SYNTAX"); }
        if ((System.nanoTime() - t0) / 1_000_000 > COMPILE_BUDGET_MS)
            return reject("COMPILE_TOO_SLOW");

        // ③ 回放压测：用 8 个对抗样本（全匹配/全不匹配/回溯陷阱串）各跑一遍
        for (String probe : adversarialProbes()) {
            if (matchWithBudget(compiled, probe, MATCH_BUDGET_MS) == TIMEOUT)
                return reject("BACKTRACK_RISK"); // 56812
        }
        return AdmissionResult.pass(compiled);
    }
}
```

运行期防护：规则执行带 5ms 硬预算（字符级限步计数器实现，不依赖线程中断）；
单条规则超预算即熔断该规则（自动置 `status=0` + P2 告警 + 复审工单），
**不阻塞其余规则**（G7）。

`conditions` JSON 在规则加载时预编译为 `ConditionEvaluator` 树，流式路径仅做

#### 4.2.4 答案管控联动规则（0401 场景）

**边界裁决（R7）**：题目级、会话级的答案管控权威归《答案管控与渐进式提示引擎》
（ACPH）；SOSF 的 0401 规则组仅是**文本形态兜底**——在 `answerControlEnabled=true`
的会话中拦截“直接公布答案”的表述句式，覆盖 ACPH 提示策略被模型忽略的残余风险。
`answerControlEnabled` 由 AI 辅导编排层从 ACPH 决策结果注入 FilterContext，
SOSF 不自行查询 ACPH。

0401 内置规则组（可运营配置）：

| 规则 | 句式模式 | 动作 |
| --- | --- | --- |
| ANS-DIRECT | “正确答案是 {X}”“应选 {X}”“答案：{X}”且命中题目选项字符集 | MASK（遮蔽选项符号） |
| ANS-FULL | 连续 ≥ N 题输出“题号+答案”序列（N≥3，批量泄答案） | INTERRUPT |
| ANS-PROMISE | “我把完整答案发给你”“剩下的答案都在这里” | REPLACE → 引导提示话术 |

MASK 模式仅遮蔽答案符号本身（如“答案是 **\*\*\*\***”），保留讲解结构，
避免整段替换损伤教学价值；用户仍可通过 ACPH 的渐进提示流程主动解锁。

#### 4.2.5 跨 Chunk 正则执行

正则在滑动窗口文本上执行，窗口大小必须 ≥ 最长规则匹配长度上限：

- `windowSize = max(256B, longestRuleMaxLength + 64B)`，构建期自动推导；
- 正则命中区若跨越已刷新边界（历史遗留尾部），由仲裁器回撤最近一次 flush
  中的重叠段（见 §4.5.3 句界回撤）；
- 执行次数护栏：单 chunk 规则执行总预算 5ms（L2 层整体），超预算放行当前
  chunk 并标记 `needsReview=true`（宁复审不阻塞流，G9）。

### 4.3 L3：语义分类层

#### 4.3.1 模型选型与部署形态

| 项 | 选型 | 说明 |
| --- | --- |
| 基座 | 蒸馏小模型（BERT-tiny 级，4 层 / 312 hidden） | 教育场景违规语料微调 |
| 运行时 | ONNX Runtime，INT8 量化，CPU 推理 | 免 GPU 依赖，单实例推理 P50 ≈ 6ms / P99 ≈ 18ms |
| 类别体系 | 与敏感词分类对齐的 8 大类 + `SAFE` | 单模型多标签 sigmoid |
| 部署 | 与 SOSF 同进程（嵌入式） | 避免网络跳数；模型文件 ~28MB |

#### 4.3.2 句界缓冲与检测粒度

L3 **不以裸 chunk 为单元**，以“句”为单元：chunk 文本先经句界切分器
（。！？；换行 + 0.9 分数置信中文句号模型兜底）累积成完整句，句完整才送模型。
句长超过 120 字符时强制截断送检（防止长句无限累积阻塞流）。
未成句的尾部文本随窗口滚动，最终在流结束时强制送检。

#### 4.3.3 延迟判定与回溯拦截

```
chunk 到达 ──► 句界缓冲 ──► 成句送模型（异步，预算 20ms）
                              │
              ┌───────────────┤
              ▼               ▼
        20ms 内出结果    20ms 未出 → 挂起当前句输出，等待窗再计时（上限 50ms）
              │               │
        正常参与仲裁      50ms 仍未出 → 放行该句 + 标记 pending_review
                              │
                    后续模型返回违规 → 回溯拦截：
                    ① 对当前句及后续 chunk 立即 INTERRUPT
                    ② SSE 下发 blocked 事件（客户端停止渲染并展示替代文案）
                    ③ 事件 safety.review.required + safety.blocked 双发
                    ④ P2 告警（回溯拦截属漏拦风险事件，必须观测）
```

回溯拦截时违规句可能已部分到达客户端——这是**已知且受控的权衡**：
- 概率受控：模型 P99 ≈ 18ms << 50ms 等待窗，回溯仅发生在长尾（< 0.1% 句）；
- 暴露受控：客户端收到 `blocked` 事件后立即停止增量渲染并整体替换为替代文案，
  违规片段在屏幕上的停留时间 = 一次 RTT；
- 兜底观测：所有回溯拦截句强制进入人工复审队列（不可配置关闭，C9）。

#### 4.3.4 置信度分档（阈值对齐 R2）

| 置信区间 | 判定 | 动作 |
| --- | --- | --- |
| p ≥ 0.95 | 违规 | 按类别进入仲裁器（等价 L1 命中 severity=3） |
| 0.80 ≤ p < 0.95 | 疑似 | 不拦截，标记 `needsReview` 入复审队列 |
| p < 0.80 | 安全 | 放行，不计事件 |

**阈值统一 0.8**：疑似下限 0.80 与 ARPP《AI回答后处理管线》约定的“SOSF 阈值
统一 0.8”保持同一数值锚点（R2），两侧阈值调整必须同步评审。

#### 4.3.5 面向非流式调用方的全文同步检测（反向服务）

ARPP 的非流式链路云端检测步骤**委托 SOSF**（ARPP §3.2 约定，150ms 超时降级
异步复检），SOSF 对外提供全文同步检测接口：

```
POST /api/internal/sosf/detect
{
  "text": "待检测全文",
  "context": { "phase": "JUNIOR", "subject": "MATH", "scene": "AI_OUTPUT",
                "answerControl": false },

→ 200
```

#### 4.3.6 模型热更新与灰度

模型版本随 Trie 版本号体系独立管理（`SOSF:l3_model:current_version`）：
- 新模型先在灰度节点加载，双跑对拍（新旧模型结果不一致率 > 2% 时阻断放量）；
- 切换同样走 volatile 原子引用，推理中的请求持有旧模型引用直至完成；
- 模型文件完整性：SHA-256 校验 + 本地缓存最近 2 个版本（回滚用）。

### 4.4 决策仲裁器

#### 4.4.1 合并规则

1. **动作优先级**：INTERRUPT > REPLACE > MASK > PASS（多层同时命中取最高）；
2. **severity 合成**：取各层命中的最大 severity；L1+L2 同时命中同一类别时
   severity +1（多重证据强化，上限 4）；
3. **类别仲裁**：多类别命中时按 `POLITICAL > PORN_VULGAR > VIOLENCE(含 0302 危机) >
   EDUCATION_SPECIFIC > PRIVACY > COMMERCIAL > PSYCHOLOGICAL > PHASE_SPECIFIC`
   的处置优先序选择主类别，其余类别记入 `matchedRules` 一并落日志；
4. **CRITICAL 快速通道**：命中 0302（自残自杀诱导）/0701 危机类且 severity=4 时
   跳过常规仲裁，直接 INTERRUPT + `safety.escalated` 事件直连《学生AI对话心理危机
   信号检测与分级预警干预编排引擎》（R6），同时冻结会话（后续 chunk 全部丢弃）。

#### 4.4.2 连续违规升级

| 会话内违规计数 | 升级动作 |
| --- | --- |
| 1–2 次（MEDIUM 以下） | 正常 REPLACE/MASK |
| 3 次 | 提示软化 + 话术升级（“我们换个话题吧”） |
| 4 次或单次 CRITICAL | INTERRUPT 终止流 + 会话标记 BLOCKED |
| 5 次/小时（用户级，跨会话） | 触发用户级频控：后续会话降级为“先全文后放行”模式（牺牲流式体验）+ 事件上报风控 |

用户级计数用 `SOSF:user_violation:{userId}`（1h 窗口），与 Redis 数据结构约定一致。

#### 4.5.2 平滑衔接处理

REPLACE 不只是字符串替换，需保证与已输出前文的衔接自然：
1. 替换段以“接续词”开头（按上文句尾标点选择：“不过/另外/我们继续”）；
2. 若命中点在句中，替换段补全该句剩余 grammatical 骨架（句级模板）；
3. 若命中点处于 Markdown 结构内（代码块/公式块），先闭合结构再注入替换文案，
  防止客户端渲染器进入未闭合状态（与《客户端-AI对话消息 Markdown 流式渲染引擎》
  的 hold-buffer 补齐协议对齐，R5）。

#### 4.5.3 句界回撤（Sentence Rollback）

当违规命中点距上次 flush 边界过近（替换无法在本轮窗口内完成）时，执行回撤：
仲裁器向 SSE 引擎发送 `rollback_to` 控制帧，客户端按 `index` 回退已渲染的
尾部 N 个 text_delta（N 由 rollback_to 携带），再接收替换段。回撤窗口上限
= 最近 3 个 text_delta 事件；超过上限则放弃回撤、直接 INTERRUPT（保证复杂度
有界）。该控制帧登记为《SSE 流式响应与 AI 增量渲染引擎》v1.1 扩展需求（R5）。

---

### 4.6 中断与流终止语义

INTERRUPT 的完整时序（与 ARPP §4.2 拦截时序对齐，R1）：

```
仲裁器判定 INTERRUPT
  │
  ├─① 输出缓冲区立即冻结：未下发的 flushable 全部丢弃
  ├─② 丢弃对 LLM 上游的剩余订阅（cancel subscription，停止 token 消费）
  ├─③ 注入替代文案（经 ARPP FORMAT 规范化后由 SSE 引擎下发）
  ├─④ SSE 下发 event: blocked（协议见 R5）:
  │     event: blocked
  │     data: {"conversation_id":"...","finish_reason":"safety_block",
  │            "category":"0202","message":"这部分内容不适合展示…"}
  ├─⑤ SSE 下发 event: session_end {"finish_reason":"safety_block"}
  ├─⑥ Outbox 事件 safety.blocked（同事务落库，G11）
  └─⑦ closeSession：窗口/句缓冲/句队列资源释放

客户端约定（消费 blocked 事件）:
  - 停止增量渲染，保留已渲染前文（已通过安全层的正常内容）
  - 用替代文案替换“正在打字的未完成段”
  - 流状态机进入终态，不重试（重试由用户显式发起新请求）
```

`finish_reason=safety_block` 枚举值登记到 SSE 引擎 session_end 协议（R5）。

### 4.7 会话生命周期管理

```
initSession ──► ACTIVE ──┬──filter(chunk)×N（TTL 滑动续期）──┐
     │                   │                              │
     │ 校验失败           ├── 5min 无 chunk（空闲超时扫描） ──► EXPIRED
     ▼                   ├── 10min 硬超时（绝对时长） ─────► EXPIRED
  (56802/56805)          ├── INTERRUPT 仲裁 ─────────────► INTERRUPTED
                         └── closeSession / LLM 流正常结束 ─► CLOSED
```

- **单写者模型（G3）**：每个会话的过滤串行执行（对话流本身有序），跨会话并行；
  会话内并发调用 filter 返回 56803（chunkIndex 乱序防御）；
- **空闲超时扫描**：ZSET `SOSF:session:idle_zset`（score=lastActiveAt）每 30s
  扫描，避免依赖逐 key TTL 过期后才发现会话泄漏；
- **异常断开**：SSE 引擎断连回调触发 closeSession；漏调时由空闲超时兜底；
- **内存有界**：单会话窗口 ≤ 4KB + 句缓冲 ≤ 8KB + 事件队列 ≤ 64 条，超限
  直接 INTERRUPT（56806，防御恶意超长流）。

### 4.8 性能工程

#### 4.8.1 单 chunk 延迟预算分解

| 阶段 | P50 | P99 | 备注 |
| --- | --- | --- | --- |
| 窗口追加与切片 | 0.05ms | 0.2ms | StringBuilder 预分配 |
| L1 AC 匹配 | 0.3ms | 1.0ms | 42 万 pattern 基线 |
| L2 规则执行 | 0.4ms | 5.0ms | 含预算熔断护栏 |
| L3 句级模型（异步路径） | 6ms | 18ms | 不占用同步预算 |
| 同步仲裁合计 | 1.0ms | 6.5ms | 目标 <20ms 达成 |
| 端到端 SSE 增量（含传输层） | — | <50ms | 对齐全链路预算 |

#### 4.8.2 工程手段

- **零拷贝匹配**：窗口文本转 `char[]` 复用（池化），避免 substring 临时对象；
- **对象池**：MatchResult / FilterResult 池化（Netty Recycler），降低 GC 压力；
- **无锁读**：Trie / 规则 / 模型三者的热更新均为 volatile 引用切换，读路径零锁；
- **GC 调优**：G1，Young 区 2G；匹配热路径零分配设计下单节点 GC 暂停 P99 < 10ms；
- **基准验收**：每次发版跑固定基准集（10 万词 Trie + 200 规则 + 10 万 chunks
  回放），单 chunk P99 > 20ms 或吞吐 < 10k chunks/s 阻断发布（CI 门禁）。

#### 4.8.3 容量与节点规划（DAU 50 万）

| 项 | 估算 |
| --- | --- |
| 日 AI 对话/拍题流式回答 | 15 万次 × 平均 120 chunks ≈ 1,800 万 chunks/日 |
| 峰值 chunks/s（20% 集中在 1h，×1.5 拍题等场景系数） | ≈ 4,500/s |
| 节点数（单节点 10k chunks/s，N+2 冗余） | 3 节点（常态负载 15%，发布/故障时余量充足） |
| 单节点内存 | Trie 210MB + 模型 28MB + 会话运行时 <100MB ≈ 350MB（预算 512MB 内） |
| Redis 会话存储 | 峰值并发流 5,000 × ~12KB ≈ 60MB |

### 4.9 多节点部署与版本一致性

- **无状态过滤节点**：会话状态全在 Redis，任意节点可处理任意 chunk；
  但为降低窗口跨节点搬移成本，SSE 长连接与过滤会话同节点亲和（网关按
  conversation_id 一致性路由）；
- **词库版本一致性（G6）**：节点每 60s 对齐版本，集群内版本差 > 2 个版本
  持续 5min 触发 P3 告警（56823）；不一致期间各节点按本地版本独立判定
  （安全策略短暂不一致可容忍，方向必须是“新版本更严”时优先放量）；
- **滚动升级**：先升级非亲和节点 → 观察 15min（拦截率漂移 < 0.5%）→ 再
  逐节点排空升级；升级期间该节点会话由空闲超时自然收割，不主动迁移。

## 5. API 接口设计

### 5.1 内部 gRPC（流式主链路，AI 编排层调用）

```protobuf
service StreamingSafetyFilter {
  // 建会话：返回 session_id；上下文缺失返回 INVALID_ARGUMENT(56802)
  rpc InitSession(FilterContext) returns (SessionHandle);

  // 双向流：编排层推 ChunkIn，SOSF 回 ChunkOut（flushable/控制信号）
  rpc FilterStream(stream ChunkIn) returns (stream ChunkOut);

  // 主动关流（正常结束/用户取消）
  rpc CloseSession(SessionHandle) returns (CloseResult);

  // 全文同步检测（ARPP 等非流式调用方，见 §4.3.5）
  rpc Detect(DetectRequest) returns (DetectResponse);
}

message ChunkIn  { string session_id = 1; int32 chunk_index = 2; string text = 3; }
message ChunkOut {
  string session_id = 1;
  FilterAction action = 2;      // PASS/REPLACE/INTERRUPT/BUFFER
  string content = 3;           // 可下发内容（含替换段）
  string replacement = 4;       // REPLACE 时的替换文案
  int32  rollback_delta = 5;    // 句界回撤的 text_delta 条数（>0 时生效）
  string blocked_reason = 6;    // INTERRUPT 时的对外文案
  bool   needs_review = 7;
}
```

## 6. 关键流程时序

### 6.1 流式过滤主链路（正常放行）

```
LLM编排层      SOSF                                   Redis/DB
    │  InitSession(ctx) │                                │
    │──────────────────►│ 校验上下文/写 session Hash      │
    │◄──session_id──────│ (TTL 600s 滑动)                │
    │                   │                                │
    │  ChunkIn(i,text)  │                                │
    │──────────────────►│ ①窗口追加 ②L1 AC ③L2 规则      │
    │                   │ ④成句→L3 异步(20ms预算)        │
    │◄─PASS+flushable───│ ⑤仲裁=PASS ⑥EXPIRE 续期       │
    │      ...          │                                │
    │  CloseSession     │                                │
    │──────────────────►│ 尾句强制送检→释放资源→会话EXPIRED/CLOSED
```

### 6.2 REPLACE（命中可替换违规）

```
    │ ChunkIn(i)        │                                │
    │──────────────────►│ L1 命中 0602 外链引流(sev=2)    │
    │                   │ 仲裁=REPLACE ②句界回撤判定     │
    │◄─REPLACE──────────│ content=替换文案, rollback=1    │
    │                   │ 拦截日志落库(异步批量)          │
    │                   │ Outbox: safety.replaced        │
```

### 6.3 INTERRUPT（高危/连续违规/危机）

见 §4.6 完整时序；危机类额外走 ④' `safety.escalated` 直连危机引擎（R6）。

### 6.4 L3 回溯拦截

```
句S送检(超20ms) ─► 挂起等待(≤50ms) ─► 超时放行+pending_review
                                            │ 模型结果迟到: 违规(p≥0.95)
                                            ▼
                          当前及后续 chunk INTERRUPT + blocked 事件
                          + safety.blocked & safety.review.required 双发 + P2 告警
```

### 6.5 词库热更新

```
敏感词引擎管理端 ─► word.changed 事件(Kafka) ─► SOSF 订阅: pendingWordChanges++
                                                     │ 累计≥100 或 03:30 定时
                                                     ▼
                                    DB 全量读取(scene=AI_OUTPUT) ─► 构建新 Trie
                                    ─► 写 Redis vN+1 ─► 原子切换 ─► 版本对齐(G6)
```

## 7. 状态机与守卫

### 7.1 会话状态机

`INIT → ACTIVE → {INTERRUPTED | EXPIRED | CLOSED}`（终态不可逆；终态后
FilterStream 返回 56804）。

### 7.2 复审条目状态机

`PENDING → {CONFIRMED | FALSE_POSITIVE | IGNORED}`（终态；FALSE_POSITIVE
回流：命中规则加入豁免观察名单，同规则 7 日误报 ≥ 3 次自动生成规则复审工单）。

### 7.3 Trie 版本状态机

`BUILDING → ACTIVE → DEPRECATED`（DEPRECATED 保留 2 个版本供回滚；回滚
操作双人审批）。

### 7.4 守卫总表 G1–G14

| 守卫 | 规则 |
| --- | --- |
| G1 | 每个 chunk 必须经过 L1+L2 同步检测后才可下发，无任何绕过路径 |
| G2 | L3 超时放行的句必须标记 pending_review 且强制入复审队列（不可配置关闭） |
| G3 | 会话内 filter 串行（单写者），乱序/并发 chunk 返回 56803 |
| G4 | Trie/规则/模型热更新均为 volatile 原子切换，构建期对象对外不可见 |
| G5 | 词库更新失败保持旧版本服务，绝不半量切换或清空在用词库 |
| G6 | 集群词库版本差 >2 持续 5min 触发告警；节点以本地最新版本判定 |
| G7 | 单条规则超预算仅熔断该规则，不得阻塞 L2 其余规则与整条流 |
| G8 | 词库写入口唯一（敏感词引擎管理端），SOSF 侧只读投影，禁止双写 |
| G9 | L2 总预算超限时放行 + 复审标记，不得无限阻塞流（宁复审不卡流） |
| G10 | CRITICAL 危机类（0302/0701）跳过常规仲裁直连危机引擎并冻结会话 |
| G11 | safety.blocked/replaced 事件与拦截日志经 Outbox 同事务持久化后发布 |
| G12 | 会话内存三上限（窗口 4KB/句缓冲 8KB/队列 64 条），超限 INTERRUPT |
| G13 | INTERRUPT 后对上游 LLM 订阅必须显式 cancel，杜绝后台 token 空转计费 |
| G14 | 未成年人会话的 SOSF 故障降级终点是“拒绝服务”，不是“无过滤放行” |

## 8. 幂等与并发控制

| 场景 | 机制 |
| --- | --- |
| chunk 重复投递 | (session_id, chunk_index) 单调校验，重复或回退返回 56803 并丢弃 |
| 会话重复 Init | 同 conversation_id 幂等返回既有 session_id（uk，Redis SETNX） |
| closeSession 重复调用 | 幂等，终态保持不变 |

| 文案并发发布 | version 乐观锁，409 冲突返回最新版本由管理端合并重提 |
| Detect 并发同文 | 内容+上下文 hash 缓存（5min）命中直接回放缓存结果 |

## 11. 错误码（56800–56899，内部段）

> 客户端**不可见**本段错误码：流内异常一律表现为 SSE `blocked`/`error` 事件或
> 编排层降级行为；业务码仅供内部 gRPC、管理端与观测使用。

| 码 | 含义 | 处置 |
| --- | --- | --- |
| 56801 | 会话不存在/已过期 | 编排层重新 InitSession（对话续流语义由其裁决） |
| 56802 | 会话上下文非法（学段/场景缺失） | 拒绝建会话，编排层修复上下文 |
| 56803 | chunk 乱序/重复 | 丢弃并计数，>3 次告警 |
| 56804 | 会话已终态 | 忽略后续 chunk |

## 12. 降级矩阵 D1–D10

**总红线（C1/G14）**：SOSF 不可用时的降级终点是**拒绝流式输出**或**整段缓冲
后非流式检测再下发**，对未成年人流量绝不存在“无过滤直接放行”路径。

| 编号 | 故障 | 降级动作 |
| --- | --- |
| D1 | Trie 加载失败 | 本地磁盘最近版本快照加载；仍失败则拒绝接流（readiness=false） |
| D2 | Redis 不可用 | 会话退化为进程内本地 Map（牺牲跨节点亲和，网关哈希路由兜底）；词库用本地快照 |
| D3 | DB 不可用 | 词库保持当前版本运行；重建任务挂起并告警（不影响在线过滤） |
| D4 | Kafka 不可用 | Outbox 积压本地（status=0），恢复后补发；事件可延迟不可丢（G11） |
| D5 | L3 模型不可用 | L1/L2 照常 + 放行句按 5% 采样入复审（宁复审不阻塞流） |
| D6 | L2 规则引擎异常 | L1 照常 + 全量 needsReview 标记；连续失败熔断后按 D10 兜底 |
| D7 | 替换文案服务不可用 | 使用内置默认文案（进程内常量，永不依赖远端） |
| D8 | 审计/复审下游不可用 | 事件滞留 Outbox；复审队列写本地暂存表，恢复后回灌 |
| D9 | 上游 LLM 流本身异常中断 | 正常 closeSession，已通过内容不受影响，错误语义归 SSE 引擎 |
| D10 | SOSF 整体不可用 | 编排层切换“整段缓冲 + 非流式 Detect(FULL_L3) + 一次性下发”模式；
    Detect 也不可用时未成年人会话直接拒绝服务（fail-close），成人会话可配置降级放行（默认拒绝） |

## 16. 验收场景（18 条）

1. 敏感词跨 chunk 拆分（“答”+“案”）被 L1 滑动窗口命中并替换，客户端无断裂感；
2. 变体词（谐音/拆字/符号混淆）各取样例命中，膨胀护栏下单词变体 ≤32；
3. 答案管控会话输出“答案是C”被 MASK，且 ACPH 提示流程可正常解锁；
4. 诱导加微信（含变体“微☆信”）触发 REPLACE，替换文案与前文衔接自然；
5. 批量泄答案序列（3 题“题号+答案”）触发 ANS-FULL INTERRUPT，SSE 收到 blocked + session_end(safety_block)；
6. L3 检出隐喻不当内容（p=0.96）在成句后 ≤50ms 内拦截；
7. L3 超时放行后回溯拦截：违规句短暂显示后客户端收到 blocked 并整体替换，事件双发 + P2 告警 + 强制复审；
8. 0302 危机类输出：立即 INTERRUPT + safety.escalated 事件在 1s 内到达危机引擎；
9. 词库热更新：新增词后 60s 内集群全部节点生效，进行中的会话不中断；
10. Redis 宕机演练：D2 生效，过滤不中断，会话退本地 Map，恢复后自动回归；
11. SOSF 整体宕机演练：编排层切换整段缓冲模式；未成年人会话拒绝服务而非无过滤放行；
12. ReDoS 恶意规则（嵌套量词）在管理端保存时被拒绝（56811）；
13. 单 chunk P99 延迟压测（10k chunks/s 持续 10min）< 20ms；
14. 复审标记 FALSE_POSITIVE 后同规则 7 日误报 ≥3 次自动生成规则复审工单；
15. 日终对账：拦截日志数 = blocked∪replaced∪escalated 事件数，偏差为 0；
16. 会话空闲 5min 后被扫描器收割为 EXPIRED，资源释放，无内存泄漏；
17. 全文 Detect 接口：ARPP 以 150ms 预算调用，超时收到 degraded=true 并自行异步复检；
18. 集群滚动升级期间拦截率漂移 <0.5%，无会话被强制中断。
