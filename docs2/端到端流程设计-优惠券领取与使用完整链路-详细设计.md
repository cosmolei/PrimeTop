## 1. 概述

### 1.1 范围

本文档覆盖优惠券从 **运营创建** → **多渠道分发** → **用户领取** → **支付时使用/核销** → **过期/退款处理** 的完整端到端链路。重点关注各子系统间的协作时序、数据流转、异常分支和幂等保障，使开发人员能清晰理解优惠券在全链路中的生命周期。

### 1.2 优惠券在业务中的定位

优惠券是连接"定价策略"与"用户转化"的核心促销工具，覆盖以下业务场景：

| 场景 | 优惠券类型 | 触发方式 |
|------|-----------|---------|
| 新用户注册激励 | 折扣券（8折） | 系统自动发放 |
| 会员续费挽回 | 满减券（满100减20） | 系统定向发放 |
| 运营活动促销 | 折扣券/满减券 | 用户主动领取 |
| 积分商城兑换 | 满减券/体验券 | 积分兑换 |
| 裂变邀请奖励 | 兑换券/折扣券 | 邀请成功自动发放 |
| 线下合作推广 | 兑换码（PRIME-XXXX） | 兑换码领取 |

### 3.3 关键校验规则

| 校验项 | 规则 | 失败处理 |
|--------|------|---------|
| 折扣上限 | 最高不超过5折（即 `discountValue ≥ 50`） | 返回 `COUPON_DISCOUNT_EXCEEDS_LIMIT`，需主管审批 |
| 有效期合理性 | 固定时间段 `valid_until > NOW()` | 返回 `COUPON_INVALID_VALIDITY` |
| 面额合理性 | `discountValue > 0`，满减券 `minPurchaseAmount ≥ discountValue` | 返回参数错误 |
| 编码唯一性 | `code` 全局唯一 | 返回 `COUPON_CODE_DUPLICATE` |

### 3.4 兑换码生成（可选）

若 `distributeType = CODE_REDEEM`，上线后可批量生成兑换码：

```
POST /api/v1/admin/coupon-templates/{templateId}/redeem-codes/generate
{ "quantity": 1000, "codePrefix": "PRIME-" }
```

服务端生成 `PRIME-{4位随机}-{4位随机}` 格式的兑换码，批量写入 `coupon_redeem_code` 表。通过 CSV 下载链接返回给运营人员，用于线下分发。

#### 4.2.2 关键逻辑

**有效期计算**：

```typescript
function calculateValidity(template: CouponTemplate): { validFrom: Date; validUntil: Date } {
  const now = new Date();
  if (template.validityType === 'FIXED_RANGE') {
    // 固定时间段：直接使用模板配置
    return { validFrom: template.validFrom, validUntil: template.validUntil };
  } else {
    // 相对有效期：领取后N天
    return {
      validFrom: now,
      validUntil: new Date(now.getTime() + template.validDaysAfterClaim * 86400000)
    };
  }
}
```

**库存扣减 Lua 脚本**（保障原子性，防止超发）：

```lua
local stock = redis.call('GET', KEYS[1])
if stock == false then return -1 end     -- 需初始化
if tonumber(stock) <= 0 then return 0 end -- 已售罄
return redis.call('DECR', KEYS[1])        -- 扣减成功，返回剩余量
```

#### 4.2.3 客户端交互

1. 用户进入优惠券中心 → 展示可领取列表（带剩余数量、倒计时）
2. 点击"立即领取" → 按钮变为 loading 状态 → 防止重复点击
3. 领取成功 → 按钮变为"去使用" → 卡片移入"未使用"Tab
4. 领取失败 → Toast 提示具体原因（"已领完" / "您已领取过" / "不在活动范围内"）

### 5.2.1 时序步骤说明（7-20 步）

| 步骤 | 关键点 | 失败分支 |
|------|--------|---------|
| 7 | `SET coupon:lock:{id} = orderId NX EX 600`；锁值为 orderId，用于后续归属裁决 | NX 失败=已被其他订单锁定 → 返回 `COUPON_LOCK_FAILED`，订单创建中断 |
| 7a | 服务端以 `user_coupon` 上的**金额快照**重算优惠，不信任客户端传入金额 | 状态非 CLAIMED / 已过期 / 范围不匹配 → 返回对应错误码并撤销锁 |
| 8 | 返回 `{locked, discountAmount, finalAmount}`，支付服务以此金额创建订单 | — |
| 10 | 订单落库时冗余存储 `coupon_discount` 快照（对账依据） | 订单写库失败 → 本地事务回滚 + 调 release 撤锁 |
| 12/13 | 预支付金额必须等于 `finalAmount`；客户端只拿支付参数，不传金额 | — |
| 14/15 | 回调验签后**金额强校验**：渠道实付金额 ≠ finalAmount → 告警 + 人工处理，不自动核销 | 金额不符禁止自动 confirm（防篡改） |
| 16a-18a | confirm 三步同 DB 事务：`UPDATE status=USED` + `INSERT coupon_usage_log` + Outbox；`DEL lock` 在事务提交后执行，失败由锁 TTL 兜底 | 锁归属不匹配 → 拒绝并告警（见 §5.3.2 乱序） |
| 16b-17b | release 仅删锁，status 保持 CLAIMED 可继续使用 | — |
| 20 | `coupon.used` 事件经 Outbox 扇出：权益开通（会员/增值）、积分返利、消息通知、BI | 扇出失败由 Outbox 重试，不影响主链路 |

> **锁与状态分离**：Redis 锁是轻量临时态（600s TTL），`user_coupon.status` 不引入 `LOCKED` 落库态，与[优惠券与促销活动引擎-详细设计](优惠券与促销活动引擎-详细设计.md) §3.2 状态机保持一致。锁泄漏（订单已终态但锁仍在）由锁 TTL 自动过期 + §9 对账任务双重兜底。

### 5.3 核销关键逻辑

#### 5.3.1 锁定（lock）

**幂等与并发规则**：

| 场景 | 行为 |
|------|------|
| 同一 `(userCouponId, orderId)` 重复 lock | 幂等成功，返回首次计算的金额 |
| 不同 orderId 且锁存在 | `COUPON_LOCK_FAILED`（409） |
| 锁存在但 TTL 剩余 < 60s 且订单已终态 | 对账任务提前清理（不等待 TTL） |

**Lua 锁归属原子校验**（confirm/release 共用，防止 TOCTOU）：

```lua
-- KEYS[1]=coupon:lock:{id}, ARGV[1]=orderId
local holder = redis.call('GET', KEYS[1])
if holder == ARGV[1] then
  return 1                    -- 归属匹配，允许 confirm/release
end
if holder == false then
  return 0                    -- 锁不存在（已过期/已释放）
end
return -1                     -- 已被其他订单持有
```

#### 5.3.2 确认核销（confirm）

**守卫条件**（全部满足才执行）：

1. `status = CLAIMED` 且 `NOW() ≤ valid_until`（临界券以 confirm 到达服务端时间为准）
2. 锁归属校验返回 `1`；若返回 `0`（锁已过期）但订单已 `PAID` 且携带支付流水号 → 允许**无锁确认**，`usage_log.lock_expired = 1` 并打点告警（支付回调延迟超过锁 TTL 的兜底路径）
3. 金额复核：重算优惠 == lock 时返回值 == 订单快照 `coupon_discount`，三方一致；不一致 → `COUPON_AMOUNT_MISMATCH` 告警，转人工

**事务与幂等**：

```sql
BEGIN;
  -- 幂等闸门：uk_usage(user_coupon_id, order_id) 唯一键
  INSERT INTO coupon_usage_log
    (user_coupon_id, order_id, original_amount, discount_amount,
     final_amount, used_at, lock_expired)
  VALUES (#{ucId}, #{orderId}, #{original}, #{discount},
          #{final}, NOW(), #{lockExpired});      -- 重复插入报唯一键冲突 → 读回首次记录直接返回成功

  UPDATE user_coupon
     SET status = 'USED', used_order_id = #{orderId}, used_at = NOW()
   WHERE id = #{ucId} AND status = 'CLAIMED';     -- 受影响行数=0 → 状态被并发改变，回滚抛 COUPON_CONFIRM_CONFLICT

  INSERT INTO coupon_outbox (event_id, event_type, payload, next_retry_at)
  VALUES (UUID(), 'coupon.used', #{payloadJson}, NOW());
COMMIT;
-- 事务提交后删除锁；DEL 失败不影响正确性（TTL 兜底）
DEL coupon:lock:{ucId};
```

#### 5.3.3 释放（release）

| 场景 | 行为 |
|------|------|
| 锁归属匹配，status=CLAIMED | `DEL lock`，返回成功 |
| 锁不存在，status=CLAIMED | 幂等成功（视为已释放/已过期） |
| status=USED | 拒绝：`RELEASE_ON_USED`，提示调用方走退款链路（§6） |
| 锁归属不匹配（-1） | 拒绝：`RELEASE_LOCK_MISMATCH`，说明已有新订单持有 |

**取消与支付成功竞态**：用户点取消的同时支付回调到达。裁决规则：关单走 CAS（`UPDATE orders SET status='CLOSED' WHERE order_id=? AND status='PAY_PENDING'`），受影响行数=0 说明订单已 PAID → 不再 release，改走 confirm；反之回调侧 confirm 失败（锁已被 release 删除）时以订单状态为准：订单 CLOSED 则忽略回调仅记账，订单 PAID 则走 §5.3.2 无锁确认。

#### 5.3.4 0 元单（兑换券全额抵扣）

`finalAmount = 0`（EXCHANGE 券抵扣全部价款）时：

1. lock 正常执行（占用券与锁，防止重复使用）
2. 支付服务跳过支付渠道，直接将订单置 `PAID`（支付方式=COUPON_FULL，虚拟流水号 `CPN-{orderId}`）
3. 同步调用 confirm 完成核销；失败由 Outbox + 对账扫描兜底（§9 E9）
4. 0 元单占比异常升高（>阈值）触发风控告警（兑换码渠道刷单信号）

### 5.4 优惠金额计算与叠加规则

**计算顺序**（多券叠加时）：按 `stackPriority` 升序逐张扣减，每扣一张后用**剩余金额**评估下一张的满减门槛；同 `stackGroup` 内互斥只可选一张。

| 规则 | 公式/约束 |
|------|-----------|
| 满减券 | `discount = faceValue`，前置条件 `amount ≥ minPurchaseAmount` |
| 折扣券 | `discount = round(amount × (1 - discountValue/100))`，封顶 `min(maxDiscountAmount, discount)` |
| 兑换券 | `discount = amount`（全额抵扣，0 元单） |
| 下限保护 | 每步扣减后 `amount ≥ 0`；`finalAmount = originalAmount − ΣdiscountAmount ≥ 0` |
| 精度 | 全链路以**分**为单位整数运算；折扣率换算 `ROUND_HALF_UP` |

**算例**（年度会员 19800 分）：

| 组合 | 计算 | 结果 |
|------|------|------|
| 单张 8 折券（封顶 5000） | 19800×0.2 = 3960 ≤ 5000 | discount=3960，final=15840 |
| 单张满 100 减 20 | 19800 ≥ 10000 满足门槛 | discount=2000，final=17800 |
| 满减(优先级1) + 8折券(优先级2) 叠加 | 先减 2000 → 17800；再 8 折 17800×0.2=3560 | Σdiscount=5560，final=14240 |

**最优券推荐（bestCouponId）**：单变量场景取 `discount` 最大者并列时优先先到期者；多券组合推荐为 V1.5 能力（引用引擎文档 §11.3）。

**金额篡改防线**：客户端 checkout 仅上送 `userCouponId` 列表；一切金额（original/discount/final）均由服务端计算并在 lock/confirm/订单三处快照一致。

### 5.5 订单取消/超时与锁联动

```
用户主动取消                      定时关单 Job（每分钟）
     │                                  │
     ▼                                  ▼
POST /orders/{id}/cancel          扫描 PAY_PENDING 且 created_at < NOW()-15min
     │                                  │
     └──────────┬───────────────────────┘
                ▼
     CAS: UPDATE orders SET status='CLOSED'
          WHERE order_id=? AND status='PAY_PENDING'
                │
        ┌───────┴────────┐
   受影响行数=1      受影响行数=0
        │                │
        ▼                ▼
   调 release 撤锁   订单已 PAID（竞态）
   （幂等，可重试）   忽略关单，等待/补发 confirm
```

- 关单后 release 失败：锁 TTL（600s）自动过期；§9 对账任务扫描「订单 CLOSED 且券 status=USED」的脏数据并人工裁决
- 15 分钟关单窗口与锁 TTL 匹配：锁 10 分钟 < 关单 15 分钟，保证锁先于订单超时释放，避免「订单仍可支付但券锁已过期被另单锁定」的长尾窗口

### 6.3 幂等与防套券风控

- **幂等**：`usage_log.refund_order_id` 非空则拒绝重复退券（返回首次结果）；退款事件消费方以 `(user_coupon_id, refund_order_id)` 幂等
- **复活规则**：退券时若 `valid_until` 已过（EXPIRED），先复活为 CLAIMED 再顺延 3 天；超过 30 天的深度过期券不复活，改为按面值补偿积分（防止长期套利）
- **套券风控**：同张券「退回→再核销→再退款」循环 ≥ 2 次触发风控冻结该券并转人工；监控指标见 §10.2
- **EXPIRED 状态守卫**：引擎文档 §3.2 声明 EXPIRED 不可逆——本链路退款复活是**唯一例外**，须带 `reason=REFUND_RELIVE` 审计标记，与引擎文档的 REVOKED/退款场景条款一致

## 7. 阶段五：过期处理与运营后处理

### 7.1 过期扫描与到期提醒

| 任务 | 频率 | 逻辑 |
|------|------|------|
| 全量过期扫描 | 每日 02:00 | `UPDATE user_coupon SET status='EXPIRED' WHERE status='CLAIMED' AND valid_until < NOW()`，500 条/批分页推进，避免大事务 |
| 临界提醒 T-3 / T-1 | 每日 10:00 | 扫描 3/1 天后到期的 CLAIMED 券 → 投递 `coupon.expire.remind` 事件给消息服务（走统一频控：同一用户每日最多 1 条券提醒，多券合并为一条聚合通知） |
| 到期当天 D-0 | 每小时 | 仅扫「今天 24:00 前到期」券，最后一次提醒 |

### 7.2 模板暂停/下线与已发券的关系

- 模板 `PAUSED`：仅关闭**领取入口**（领券中心/自动发放/兑换码暂停核销入口），已领的 CLAIMED 券在有效期内**照常可用**
- 模板 `EXPIRED`/`ARCHIVED`：清理 `coupon:stock:{id}` 与 `coupon:tpl:{id}` 缓存；库存不回收（未领取的量作废）
- 紧急事故（如价格配错）：走运营 `REVOKED` 批量撤销（见 §7.3），不依赖模板下线

### 7.3 运营撤销（REVOKED）

- 守卫：仅 `status=CLAIMED` 且**无 Redis 锁**的券可撤销；锁存在（正在支付）→ 跳过并加入重试队列，避免支付中撤券导致 confirm 冲突
- 批量撤销按模板维度操作，二次确认 + 审计留痕（操作人/原因/影响面）
- 已 USED 的券不可撤销，只能通过「运营退款」链路退回

### 7.4 数据归档

`coupon_usage_log` 保留 12 个月在线，超期归档至冷存储（对齐[服务端数据归档与生命周期管理策略](服务端数据归档与生命周期管理策略-详细设计.md)）；归档不影响 §9 对账（对账窗口仅 T+1～T+7）。

### 9.1 补偿矩阵

| # | 异常场景 | 检测方 | 补偿动作 | 兜底 |
|---|---------|--------|---------|------|
| E1 | lock 成功但订单创建失败 | 支付服务本地事务 | 同步调 release | release 失败→锁 TTL 过期 |
| E2 | 支付回调丢失（渠道未通知） | 客户端轮询/主动查单 Job | 查单补偿 → confirm | [会员订阅 E2E](端到端流程设计-会员订阅与增值服务购买完整链路-详细设计.md) 掉单三重补偿 |
| E3 | confirm 超时/失败 | 支付服务重试（指数退避 ×5） | 重试 | 对账任务 E11 修复 |
| E4 | release 失败（关单后） | 订单服务重试 | 重试 ×3 | 锁 TTL；对账扫描 CLOSED+锁残留 |
| E5 | 回调乱序：release 先于 confirm 到达 | 优惠券服务锁归属裁决 | 订单 PAID → 无锁确认（G4 兜底） | 人工裁决队列 |
| E6 | 金额不符（渠道实付 ≠ finalAmount） | 支付服务强校验 | 挂起 + 告警，不自动核销 | 人工处理工单 |
| E7 | 积分兑换：发券成功但扣积分失败 | Saga 协调器 | 调 release 撤券 | 对账任务 E12 |
| E8 | 兑换码已置 CLAIMED 但 user_coupon 插入失败 | 同库事务回滚 | 码回滚 AVAILABLE | 跨库时补偿队列反向回滚 |
| E9 | 0 元单 PAID 但 confirm 失败 | 定时扫描（5min） | 补发 confirm | 告警 + 人工 |
| E10 | 发券成功但推送通知失败 | Outbox 重试 | 异步重发推送 | 不影响主流程，仅记日志 |
| E11 | 对账发现 PAID 订单但券仍 CLAIMED | 日终对账 | 自动补 confirm（带对账标记） | 差异工单 |
| E12 | 对账发现 CLOSED 订单但券 USED | 日终对账 | 自动退回 CLAIMED + 告警 | 差异工单（疑似 E5 残留） |
| E13 | 库存缓存与 DB 漂移（超发/少发） | 领取量 vs 库存对账 | 以 DB `issued_quantity` 为准重建缓存 | [引擎文档 §7.2](优惠券与促销活动引擎-详细设计.md) |

### 9.2 日终三方对账

对账窗口 T+1，比对 `coupon_usage_log` ↔ `orders` ↔ `payment`：

```sql
-- ① 券已核销但订单未支付（E12：疑似关单竞态残留）
SELECT u.order_id, u.user_coupon_id
  FROM coupon_usage_log u
  JOIN orders o ON o.order_id = u.order_id
 WHERE o.status IN ('CLOSED','PAY_PENDING')
   AND u.created_at < :today AND u.refund_order_id IS NULL;

-- ② 订单已支付但券未核销（E11：confirm 丢失）
SELECT o.order_id, o.coupon_user_id
  FROM orders o
  LEFT JOIN coupon_usage_log u
         ON u.order_id = o.order_id AND u.user_coupon_id = o.coupon_user_id
 WHERE o.status = 'PAID' AND o.coupon_user_id IS NOT NULL
   AND o.paid_at < :today AND u.id IS NULL;

-- ③ 金额恒等式审计：订单快照 vs 核销明细
SELECT o.order_id
  FROM orders o
  JOIN coupon_usage_log u ON u.order_id = o.order_id
 WHERE o.coupon_discount <> u.discount_amount
    OR o.pay_amount <> u.final_amount;
```

差异处理：①② 自动修复（E11/E12）并告警；③ 一律人工（金额错误属资损级）。

## 11. 安全与合规红线

1. **未成年人营销隔离**：营销类券（运营促销/裂变奖励）默认不投递未成年人账号，与[青少年模式风控引擎](服务端-教育平台青少年模式风控与内容访问分级策略引擎-详细设计.md)的人群过滤联动；新客礼包按实名年龄分档发放
2. **折扣上限**：教育类商品最高 5 折（§3.3），服务端硬校验，绕过即 `COUPON_DISCOUNT_EXCEEDS_LIMIT`
3. **兑换码非资产**：兑换码/优惠券不可转让、不可提现、不构成虚拟货币、无现金价值——用户协议明示，且兑换码不支持找回挂失
4. **防暴力破解**：兑换接口 IP 连续 10 次失败触发人机验证 + 封禁 30 分钟（§4.4），联动作风控服务
5. **防刷**：同设备/同 IP 限领、领取行为前置风控评分，引用[引擎文档 §10.1](优惠券与促销活动引擎-详细设计.md) 防刷策略
6. **审计**：模板创建/修改/上线、批量撤销、退券、深度过期积分补偿全部写入审计日志（操作人、before/after、原因）
7. **资损红线**：金额恒等式（§9.2 ③）violated 即 P1 告警；confirm 金额不符绝不自动放行
