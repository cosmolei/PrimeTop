> **文档版本**: v1.1

## 1. 概述

### 1.1 设计目标

学生在使用 PrimeTop 过程中，会同时面对来自多个子系统产生的学习任务：

| 任务来源 | 产出方 | 典型示例 |
|----------|--------|----------|
| 学习规划系统 | 每日计划引擎 | "复习数学第三章 - 函数" |
| 教师作业 | 教师端发布 | "完成数学练习册 P45-46" |
| 错题复习 | 间隔重复算法 | "复习 12 道错题（今日到期）" |
| 薄弱点补强 | 诊断测评引擎 | "强化训练：二次函数图像变换" |
| 考试冲刺 | 备考计划引擎 | "刷 10 道高频考点选择题" |
| 家长任务 | 家长中心 | "完成 30 分钟英语阅读" |
| 系统推荐 | 个性化推荐 | "推荐阅读：物理受力分析专题" |

**多源学习任务统一调度与优先级仲裁引擎**（以下简称"任务调度引擎"或"引擎"）负责：

1. **聚合**：从所有任务源实时收集待执行任务
2. **去重合并**：检测内容重叠的任务并智能合并
3. **优先级仲裁**：根据截止时间、来源权重、认知负荷等维度排序
4. **认知负荷控制**：控制每日总任务量在合理范围内
5. **统一输出**：生成结构化的"今日优先队列"供客户端渲染

### 1.2 设计原则

- **来源解耦**：各任务源独立生产任务，通过标准接口投递，互不依赖
- **实时响应**：任务队列在新增、完成、取消时近实时更新
- **学生友好**：优先呈现最紧急、最重要的任务，避免任务过载焦虑
- **可解释性**：每个任务的优先级理由可追溯、可解释
- **渐进增强**：MVP 阶段支持基本聚合排序，后续迭代增加智能合并与负荷控制

### 1.3 与现有模块的关系

| 模块 | 关系 |
|------|------|
| 每日任务智能生成服务 | **上游**：产生学习计划任务，投递到调度引擎 |
| 学习计划动态调整服务 | **上游**：计划变更时通知调度引擎重新排程 |
| 间隔重复算法引擎 | **上游**：每日生成的错题复习任务投递到调度引擎 |
| 教师班级管理与作业发布服务 | **上游**：教师发布作业时投递到调度引擎 |
| 家长中心 | **上游**：家长设置任务时投递到调度引擎 |
| 学科能力诊断测评引擎 | **上游**：诊断后生成补强任务投递到调度引擎 |
| 首页内容卡片推荐服务 | **下游**：消费调度引擎输出的统一任务队列 |
| 学习场景意图识别引擎 | **协同**：根据学生当前意图动态调整任务推荐 |

### 2.2 核心组件

| 组件 | 职责 | 实现 |
|------|------|------|
| Task Ingestion API | 接收各源任务投递，校验格式 | REST API + MQ Consumer |
| Task Aggregator | 聚合指定时间范围内的全部待执行任务 | 定时计算 + 实时增量 |
| Task Merger | 检测重叠/相似任务并智能合并 | 规则引擎 + 知识点匹配 |
| Priority Arbiter | 多维度评分排序 | 加权评分模型 |
| Cognitive Load Balancer | 控制总量、学科分布、难度梯度 | 负荷模型 + 约束优化 |
| Unified Task Queue | 存储并维护统一任务队列 | Redis ZSet + RDB 持久 |
| Task Query API | 对外提供任务查询接口 | REST API + SSE 推送 |

## 3. 数据结构设计

### 3.1 任务源注册表 `task_source_registry`

记录所有合法的任务来源及其配置。

```sql
CREATE TABLE task_source_registry (
    source_id          VARCHAR(32)   PRIMARY KEY,          -- 任务来源唯一标识
    source_name        VARCHAR(64)   NOT NULL,             -- 来源名称
    source_type        VARCHAR(32)   NOT NULL,             -- STUDY_PLAN / HOMEWORK / ERROR_REVIEW / WEAKNESS / EXAM_PREP / PARENT / SYSTEM_RECOMMEND
    base_priority      SMALLINT      NOT NULL DEFAULT 50,  -- 基础优先级权重 (1-100)
    can_be_merged      BOOLEAN       NOT NULL DEFAULT TRUE,-- 该来源的任务是否允许被合并
    can_be_deferred    BOOLEAN       NOT NULL DEFAULT TRUE,-- 是否允许推迟
    max_daily_count    INT           DEFAULT 10,           -- 每日最大产出任务数
    max_daily_minutes  INT           DEFAULT 120,          -- 每日最大预估总时长（分钟）
    cooldown_minutes   INT           DEFAULT 0,            -- 连续投递冷却时间
    is_active          BOOLEAN       NOT NULL DEFAULT TRUE,
    created_at         TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    updated_at         TIMESTAMPTZ   NOT NULL DEFAULT NOW()
);
```

### 3.2 原始任务表 `unified_task`

存储从所有来源投递的原始任务。

```sql
CREATE TABLE unified_task (
    task_id            BIGSERIAL     PRIMARY KEY,
    uuid               UUID          NOT NULL UNIQUE DEFAULT gen_random_uuid(),
    user_id            BIGINT        NOT NULL,                -- 归属学生ID
    source_id          VARCHAR(32)   NOT NULL,                -- 任务来源ID（FK → task_source_registry）
    external_ref       VARCHAR(128),                          -- 来源系统的外部引用ID（如作业ID、计划ID等）
    
    -- 任务基本信息
    title              VARCHAR(200)  NOT NULL,                -- 任务标题
    description        TEXT,                                  -- 任务描述
    task_type          VARCHAR(32)   NOT NULL,                -- PRACTICE / REVIEW / READ / WATCH / WRITE / QUIZ / CUSTOM
    subject_code       VARCHAR(16),                           -- 学科代码（MATH / CHINESE / ENGLISH / ...）
    chapter_ids        BIGINT[],                              -- 关联章节ID列表
    knowledge_point_ids BIGINT[],                             -- 关联知识点ID列表
    
    -- 时间属性
    suggested_start    TIMESTAMPTZ,                           -- 建议开始时间
    suggested_end      TIMESTAMPTZ,                           -- 建议结束时间
    deadline           TIMESTAMPTZ,                           -- 截止时间（如果有）
    estimated_minutes  INT           NOT NULL DEFAULT 30,     -- 预估耗时（分钟）
    
    -- 难度与认知负荷
    difficulty_level   SMALLINT      NOT NULL DEFAULT 3,      -- 难度等级 1-5
    cognitive_load     SMALLINT      NOT NULL DEFAULT 3,      -- 认知负荷 1-5（不完全等同于难度）
    
    -- 状态
    status             VARCHAR(20)   NOT NULL DEFAULT 'PENDING', -- PENDING / ACTIVE / COMPLETED / SKIPPED / EXPIRED / MERGED
    merged_into_task_id BIGINT,                               -- 如果被合并，指向合并后的任务ID
    
    -- 优先级计算缓存
    priority_score     DECIMAL(6,2),                          -- 最终优先级得分（由仲裁器计算）
    priority_reason    JSONB,                                 -- 优先级得分明细
    
    -- 关联资源
    resource_url       VARCHAR(512),                          -- 任务关联资源URL
    metadata           JSONB,                                 -- 扩展元数据
    
    created_at         TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    updated_at         TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    completed_at       TIMESTAMPTZ,
    
    CONSTRAINT chk_status CHECK (status IN ('PENDING', 'ACTIVE', 'COMPLETED', 'SKIPPED', 'EXPIRED', 'MERGED')),
    CONSTRAINT chk_difficulty CHECK (difficulty_level BETWEEN 1 AND 5),
    CONSTRAINT chk_cognitive_load CHECK (cognitive_load BETWEEN 1 AND 5)
);

-- 核心索引
CREATE INDEX idx_unified_task_user_date ON unified_task (user_id, suggested_start, status);
CREATE INDEX idx_unified_task_user_status ON unified_task (user_id, status, deadline);
CREATE INDEX idx_unified_task_source_ref ON unified_task (source_id, external_ref);
CREATE INDEX idx_unified_task_kp ON unified_task USING GIN (knowledge_point_ids);
CREATE INDEX idx_unified_task_priority ON unified_task (user_id, priority_score DESC) WHERE status = 'PENDING';
```

### 3.3 任务合并记录表 `task_merge_log`

记录任务合并操作，用于审计和撤销。

```sql
CREATE TABLE task_merge_log (
    id                 BIGSERIAL     PRIMARY KEY,
    merged_task_id     BIGINT        NOT NULL,   -- 合并后的目标任务ID
    source_task_id     BIGINT        NOT NULL,   -- 被合并的源任务ID
    merge_strategy     VARCHAR(32)   NOT NULL,   -- DEDUPLICATE / COMBINE / SUPerset
    merge_reason       VARCHAR(256),
    merge_confidence   DECIMAL(3,2),              -- 合并置信度 0.00-1.00
    created_at         TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    
    CONSTRAINT fk_merged FOREIGN KEY (merged_task_id) REFERENCES unified_task(task_id),
    CONSTRAINT fk_source FOREIGN KEY (source_task_id) REFERENCES unified_task(task_id)
);

CREATE INDEX idx_merge_log_merged ON task_merge_log (merged_task_id);
```

### 3.4 每日任务快照表 `daily_task_snapshot`

记录每天的最终调度结果，用于趋势分析和历史回溯。

```sql
CREATE TABLE daily_task_snapshot (
    id                 BIGSERIAL     PRIMARY KEY,
    user_id            BIGINT        NOT NULL,
    snapshot_date      DATE          NOT NULL,
    task_ids           BIGINT[]      NOT NULL,              -- 当日最终排定的任务ID有序列表
    total_count        INT           NOT NULL,
    total_minutes      INT           NOT NULL,
    avg_difficulty     DECIMAL(3,2),
    subject_distribution JSONB,                             -- {"MATH": 3, "ENGLISH": 2, ...}
    created_at         TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    
    UNIQUE (user_id, snapshot_date)
);
```

### 3.5 任务状态枚举与流转

```
                        ┌──────────┐
        投递任务 ──→     │ PENDING  │
                        └────┬─────┘
                             │
               ┌─────────────┼─────────────┐
               │             │              │
               ▼             ▼              ▼
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ ACTIVE   │  │ MERGED   │  │ EXPIRED  │
        │(学生开始) │  │(被合并)   │  │(过期)    │
        └────┬─────┘  └──────────┘  └──────────┘
             │
      ┌──────┴──────┐
      │             │
      ▼             ▼
┌──────────┐  ┌──────────┐
│COMPLETED │  │ SKIPPED  │
│(完成)     │  │(跳过)    │
└──────────┘  └──────────┘
```

| 状态 | 含义 | 触发条件 |
|------|------|----------|
| `PENDING` | 待执行 | 任务投递后初始状态 |
| `ACTIVE` | 进行中 | 学生点击"开始"或客户端上报开始信号 |
| `COMPLETED` | 已完成 | 学生完成任务，或外部系统回报完成 |
| `SKIPPED` | 已跳过 | 学生主动跳过、或被负荷控制裁剪 |
| `EXPIRED` | 已过期 | 超过 deadline 且未被完成 |
| `MERGED` | 已合并 | 被去重合并器合并到另一个任务中 |

## 4. 任务投递接口（Task Ingestion API）

### 4.1 投递单个任务

```
POST /api/v1/task-scheduler/tasks
```

**请求体：**
```json
{
  "sourceId": "HOMEWORK",
  "externalRef": "HW_20260615_MATH_001",
  "userId": 10086,
  "title": "完成数学第三章函数练习（P45-46）",
  "description": "教师王老师布置的课后作业",
  "taskType": "PRACTICE",

  "chapterIds": [3012, 3013],
  "knowledgePointIds": [5012, 5013, 5014],
  "suggestedStart": "2026-06-15T10:00:00Z",
  "suggestedEnd": "2026-06-15T10:45:00Z",

  "estimatedMinutes": 45,
```

## 6. 核心算法设计

### 6.1 任务聚合器（Task Aggregator）

#### 6.1.1 触发时机

| 触发方式 | 场景 | 延迟 |
|----------|------|------|
| 定时触发 | 每日凌晨 6:00 生成当日任务队列 | 批量计算 |
| 增量触发 | 新任务投递时 | ≤ 2秒 |
| 事件触发 | 任务完成/跳过/过期时重排 | ≤ 2秒 |
| 手动触发 | 学生刷新首页 | 即时 |

#### 6.1.2 聚合逻辑

```java
/**
 * 聚合指定用户指定日期的所有待执行任务
 */
public List<UnifiedTask> aggregateTasks(Long userId, LocalDate date) {
    // 1. 查询时间范围内的所有 PENDING 任务
    LocalDateTime dayStart = date.atStartOfDay();
    LocalDateTime dayEnd = date.plusDays(1).atStartOfDay();
    
    List<UnifiedTask> tasks = unifiedTaskMapper.selectByUserAndDateRange(
        userId, 
        dayStart, 
        dayEnd,
        List.of("PENDING", "ACTIVE")
    );
    
    // 2. 拉取逾期任务（status=PENDING 且 deadline < now）
    List<UnifiedTask> overdueTasks = unifiedTaskMapper.selectOverdueTasks(userId, date);
    
    // 3. 合并去重
    tasks.addAll(overdueTasks);
    
    // 4. 过滤已合并任务
    tasks = tasks.stream()
        .filter(t -> !"MERGED".equals(t.getStatus()))
        .collect(Collectors.toList());
    
    return tasks;
}
```

### 6.2 去重合并器（Task Merger）

#### 6.2.1 合并规则

当两个任务满足以下条件之一时，触发合并评估：

| 规则 | 条件 | 合并策略 |
|------|------|----------|
| **完全重复** | 同用户 + 同 `externalRef` + 同 `sourceId` | 保留最新一条，旧标记 `MERGED` |
| **知识点重叠** | 同用户 + 同学科 + `knowledgePoint_ids` 交集 ≥ 60% | 合并为一个"综合学习"任务 |
| **章节重叠** | 同用户 + 同学科 + `chapter_ids` 交集 ≥ 70% | 合并为章节级任务 |
| **错题+薄弱点重叠** | `ERROR_REVIEW` 与 `WEAKNESS_FIX` 指向相同知识点 | 合并为"错题强化"任务 |

#### 6.2.2 合并实现

```java
/**
 * 检测并合并重复/重叠任务
 * @return 合并后的任务列表 + 合并记录
 */
public MergeResult mergeTasks(List<UnifiedTask> tasks, Long userId) {
    List<TaskMergeRecord> mergeLogs = new ArrayList<>();
    Set<Long> mergedIds = new HashSet<>();
    
    // 按学科分组，同学科内检测重叠
    Map<String, List<UnifiedTask>> bySubject = tasks.stream()
        .filter(t -> t.getSubjectCode() != null)
        .collect(Collectors.groupingBy(UnifiedTask::getSubjectCode));
    
    for (Map.Entry<String, List<UnifiedTask>> entry : bySubject.entrySet()) {
        List<UnifiedTask> subjectTasks = entry.getValue();
        
        for (int i = 0; i < subjectTasks.size(); i++) {
            UnifiedTask t1 = subjectTasks.get(i);
            if (mergedIds.contains(t1.getTaskId())) continue;
            
            for (int j = i + 1; j < subjectTasks.size(); j++) {
                UnifiedTask t2 = subjectTasks.get(j);
                if (mergedIds.contains(t2.getTaskId())) continue;
                
                MergeDecision decision = evaluateMerge(t1, t2);
                if (decision.shouldMerge()) {
                    UnifiedTask merged = performMerge(t1, t2, decision);
                    mergedIds.add(decision.getAbsorbedTaskId());
                    mergeLogs.add(new TaskMergeRecord(
                        merged.getTaskId(),
                        decision.getAbsorbedTaskId(),
                        decision.getStrategy(),
                        decision.getReason(),
                        decision.getConfidence()
                    ));
                }
            }
        }
    }
    
    // 过滤掉被合并的任务
    List<UnifiedTask> result = tasks.stream()
        .filter(t -> !mergedIds.contains(t.getTaskId()))
        .collect(Collectors.toList());
    
    return new MergeResult(result, mergeLogs);
}

/**
 * 评估两个任务是否应该合并
 */
private MergeDecision evaluateMerge(UnifiedTask t1, UnifiedTask t2) {
    // 规则1: 完全重复（同来源同外部引用）
    if (Objects.equals(t1.getSourceId(), t2.getSourceId()) 
        && Objects.equals(t1.getExternalRef(), t2.getExternalRef())) {
        return MergeDecision.merge(t1.getTaskId(), t2.getTaskId(), 
            "DEDUPLICATE", "相同来源重复投递", 1.00);
    }
    
    // 规则2: 知识点重叠
    double kpOverlap = calculateSetOverlap(
        t1.getKnowledgePointIds(), 
        t2.getKnowledgePointIds()
    );
    if (kpOverlap >= 0.6) {
        // 保留优先级更高的任务作为主任务
        Long primaryId = comparePriority(t1, t2) >= 0 ? t1.getTaskId() : t2.getTaskId();
        Long absorbedId = primaryId.equals(t1.getTaskId()) ? t2.getTaskId() : t1.getTaskId();
        return MergeDecision.merge(primaryId, absorbedId,
            "COMBINE", 
            String.format("知识点重叠率 %.0f%%，合并为综合学习任务", kpOverlap * 100),
            kpOverlap);
    }
    
    // 规则3: 特殊规则 - 错题复习 + 薄弱点补强
    if ("ERROR_REVIEW".equals(t1.getSourceId()) && "WEAKNESS_FIX".equals(t2.getSourceId())
        && hasCommonKnowledgePoints(t1, t2)) {
        return MergeDecision.merge(t1.getTaskId(), t2.getTaskId(),
            "SUPERSET", "错题复习与薄弱点补强指向相同知识点，合并为强化训练",
            0.85);
    }
    
    return MergeDecision.noMerge();
}
```

### 6.3 优先级仲裁器（Priority Arbiter）

#### 6.3.1 评分模型

每个任务的最终优先级得分由以下因素加权计算：

```
finalScore = basePriority
           + deadlineBonus
           + overdueBonus
           + subjectBalanceAdjust
           + userPreferenceBonus
           - cognitiveLoadPenalty
           - redundancyPenalty
```

| 因子 | 公式 | 说明 |
|------|------|------|
| `basePriority` | 任务来源的基础权重 (1-100) | 见 `task_source_registry.base_priority` |
| `deadlineBonus` | `min(30, max(0, 30 × (1 - hoursUntilDeadline / 24)))` | 越接近截止时间加成越高，24h内最高+30 |
| `overdueBonus` | `min(20, overdueDays × 5)` | 逾期任务每天+5，最多+20 |
| `subjectBalanceAdjust` | 见 6.3.2 学科平衡策略 | 避免某一学科任务过多 |
| `userPreferenceBonus` | 学生偏好学科 +5，弱势学科 +3 | 根据学情画像动态调整 |
| `cognitiveLoadPenalty` | 连续高负荷任务的惩罚项 | 见 6.3.3 认知负荷控制 |
| `redundancyPenalty` | 与已完成任务的内容重叠惩罚 | 避免重复学习 |

#### 6.3.2 学科平衡策略

```java
/**
 * 计算学科平衡调整分
 * 目标：避免队列中某一学科任务占比过高
 */
private double calculateSubjectBalanceAdjust(
    UnifiedTask task, 
    List<UnifiedTask> allTasks,
    UserLearningProfile profile
) {
    String subject = task.getSubjectCode();
    if (subject == null) return 0;
    
    // 统计当前队列中各学科任务数
    Map<String, Long> subjectCounts = allTasks.stream()
        .filter(t -> t.getSubjectCode() != null)
        .collect(Collectors.groupingBy(
            UnifiedTask::getSubjectCode, 
            Collectors.counting()
        ));
    
    long totalTasks = allTasks.size();
    long subjectCount = subjectCounts.getOrDefault(subject, 0L);
    double subjectRatio = (double) subjectCount / totalTasks;
    
    // 如果该学科占比已超过 50%，降低优先级
    if (subjectRatio > 0.5) {
        return -8.0;
    } else if (subjectRatio > 0.4) {
        return -4.0;
    }
    
    // 如果学生该学科较弱，适当提高
    Double masteryLevel = profile.getSubjectMastery(subject);
    if (masteryLevel != null && masteryLevel < 0.5) {
        return +5.0;  // 弱势学科加成
    }
    
    return 0;
}
```

#### 6.3.3 认知负荷控制（Cognitive Load Balancer）

```java
/**
 * 控制每日认知负荷总量，避免任务过载
 */
public List<UnifiedTask> balanceCognitiveLoad(
    List<UnifiedTask> rankedTasks, 
    Long userId,
    UserPreference preference
) {
    // 1. 获取用户每日最大学习时长偏好
    int maxDailyMinutes = preference.getMaxDailyStudyMinutes(); // 默认 180
    
    // 2. 获取已完成的今日学习时长
    int completedMinutes = taskService.getTodayCompletedMinutes(userId);
    
    // 3. 计算可用时长
    int availableMinutes = maxDailyMinutes - completedMinutes;
    
    // 4. 贪心填充：按优先级从高到低，填充直到达到时长上限
    List<UnifiedTask> result = new ArrayList<>();
    int accumulatedMinutes = 0;
    int consecutiveHighLoadCount = 0;
    
    for (UnifiedTask task : rankedTasks) {
        if (accumulatedMinutes + task.getEstimatedMinutes() <= availableMinutes) {
            // 检查连续高认知负荷任务限制
            if (task.getCognitiveLoad() >= 4) {
                if (consecutiveHighLoadCount >= 2) {
                    // 插入一个低负荷任务作为缓冲
                    UnifiedTask buffer = findLowLoadTask(rankedTasks, result);
                    if (buffer != null) {
                        result.add(buffer);
                        accumulatedMinutes += buffer.getEstimatedMinutes();
                    }
                    consecutiveHighLoadCount = 0;
                }
                consecutiveHighLoadCount++;
            } else {
                consecutiveHighLoadCount = 0;
            }
            
            result.add(task);
            accumulatedMinutes += task.getEstimatedMinutes();
        } else if (result.isEmpty()) {
            // 至少保留第一个任务（即使超时）
            result.add(task);
            accumulatedMinutes += task.getEstimatedMinutes();
        } else {
            // 剩余任务标记为推迟
            task.setSkipReason("COGNITIVE_LOAD_LIMIT");
            log.info("任务 {} 因认知负荷限制被推迟到明日", task.getTaskId());
        }
    }
    
    return result;
}
```

#### 6.3.4 完整仲裁流程

```java
/**
 * 完整的优先级仲裁流程
 */
public SchedulingResult schedule(Long userId, LocalDate date) {
    // Step 1: 聚合任务
    List<UnifiedTask> tasks = aggregator.aggregateTasks(userId, date);
    
    if (tasks.isEmpty()) {
        return SchedulingResult.empty();
    }
    
    // Step 2: 去重合并
    MergeResult mergeResult = merger.mergeTasks(tasks, userId);
    List<UnifiedTask> mergedTasks = mergeResult.getTasks();
    
    // Step 3: 加载用户画像
    UserLearningProfile profile = profileService.getProfile(userId);
    UserPreference preference = preferenceService.getPreference(userId);
    
    // Step 4: 计算每个任务的优先级得分
    for (UnifiedTask task : mergedTasks) {
        double score = calculatePriorityScore(task, mergedTasks, profile);
        task.setPriorityScore(BigDecimal.valueOf(score));
    }
    
    // Step 5: 按优先级排序
    mergedTasks.sort(Comparator.comparing(UnifiedTask::getPriorityScore).reversed());
    
    // Step 6: 认知负荷控制
    List<UnifiedTask> finalTasks = balancer.balanceCognitiveLoad(mergedTasks, userId, preference);
    
    // Step 7: 持久化结果
    persistSchedulingResult(userId, date, finalTasks, mergeResult);
    
    // Step 8: 发布 SSE 通知
    eventPublisher.publishEvent(new TaskQueueUpdatedEvent(userId, date, finalTasks));
    
    return new SchedulingResult(finalTasks, mergeResult);
}
```

### 6.4 优先级得分计算完整实现

```java
/**
 * 计算单个任务的最终优先级得分
 */
private double calculatePriorityScore(
    UnifiedTask task, 
    List<UnifiedTask> allTasks,
    UserLearningProfile profile
) {
    PriorityReason.PriorityReasonBuilder reasonBuilder = PriorityReason.builder();
    
    // 1. 基础优先级
    TaskSourceRegistry sourceReg = sourceRegistryCache.get(task.getSourceId());
    double base = sourceReg.getBasePriority();
    reasonBuilder.basePriority(base);
    
    // 2. 截止时间加成
    double deadlineBonus = 0;
    if (task.getDeadline() != null) {
        long hoursUntilDeadline = Duration.between(
            LocalDateTime.now(), 
            task.getDeadline().toLocalDateTime()
        ).toHours();
        
        if (hoursUntilDeadline <= 0) {
            // 已逾期
            long overdueDays = Math.abs(hoursUntilDeadline) / 24;
            deadlineBonus = 30;
            deadlineBonus += Math.min(20, overdueDays * 5);
        } else if (hoursUntilDeadline <= 24) {
            deadlineBonus = 30 * (1 - hoursUntilDeadline / 24.0);
        }
    }
    reasonBuilder.deadlineBonus(deadlineBonus);
    
    // 3. 学科平衡调整
    double subjectAdjust = calculateSubjectBalanceAdjust(task, allTasks, profile);
    reasonBuilder.subjectBalanceAdjust(subjectAdjust);
    
    // 4. 用户偏好加成
    double preferenceBonus = calculateUserPreferenceBonus(task, profile);
    reasonBuilder.userPreferenceBonus(preferenceBonus);
    
    // 5. 认知负荷惩罚
    double loadPenalty = calculateCognitiveLoadPenalty(task, allTasks);
    reasonBuilder.cognitiveLoadPenalty(loadPenalty);
    
    // 6. 冗余惩罚（与已完成任务的内容重叠惩罚，避免重复学习）
    double redundancyPenalty = 0;
    Set<Long> taskKps = toSet(task.getKnowledgePointIds());
    if (!taskKps.isEmpty()) {
        // 查询该学生近 7 天内已 COMPLETED 任务的知识点集合（带本地缓存）
        Set<Long> recentCompletedKps = taskService.getRecentCompletedKnowledgePoints(userId, 7);
        if (!recentCompletedKps.isEmpty()) {
            Set<Long> intersection = new HashSet<>(taskKps);
            intersection.retainAll(recentCompletedKps);
            double overlap = (double) intersection.size() / taskKps.size();
            if (overlap >= 0.7) {
                redundancyPenalty = -10.0 * overlap;   // 最高 -10，全重复时基本沉底
            }
        }
    }
    reasonBuilder.redundancyPenalty(redundancyPenalty);
    
    // 7. 汇总并落库得分明细（可解释性）
    double finalScore = base + deadlineBonus + overdueBonus
            + subjectAdjust + preferenceBonus + loadPenalty + redundancyPenalty;
    // 得值域收敛到 [0, 100]，保留两位小数
    finalScore = Math.round(Math.max(0, Math.min(100, finalScore)) * 100) / 100.0;
    
    return finalScore;
}
```

> **得分公式与 §6.3.1 一致性说明**：`overdueBonus` 在 v1.0 的公式表中独立列出，但代码实现上已并入 `deadlineBonus` 的"已逾期"分支（`deadlineBonus = 30 + min(20, overdueDays × 5)`），对外展示的 `priorityReason` 中仍拆分为两个字段输出，保证与公式表一致，便于学生端"为什么这个任务排第一"的解释气泡渲染。

### 6.5 仲裁辅助函数实现

#### 6.5.1 用户偏好加成

```java
/**
 * 用户偏好加成：偏好学科 +5，弱势学科 +3（与画像 mastery 联动）
 * 画像不可用时返回 0（降级 D1，见 §14）
 */
private double calculateUserPreferenceBonus(UnifiedTask task, UserLearningProfile profile) {
    if (task.getSubjectCode() == null || profile == null) {
        return 0;
    }
    double bonus = 0;
    // 1. 学生显式偏好学科（兴趣建模引擎写入 profile.preferredSubjects）
    if (profile.getPreferredSubjects() != null
            && profile.getPreferredSubjects().contains(task.getSubjectCode())) {
        bonus += 5.0;
    }
    // 2. 弱势学科（掌握度 < 0.4）：+3，与学科平衡策略的 +5 弱势加成二选一取大者，不叠加
    Double mastery = profile.getSubjectMastery(task.getSubjectCode());
    if (mastery != null && mastery < 0.4) {
        bonus = Math.max(bonus, 3.0);
    }
    return bonus;
}
```

#### 6.5.2 认知负荷惩罚

```java
/**
 * 认知负荷惩罚：单个任务本身负荷过高、或排在多个高负荷任务之后时施加惩罚
 * 注意：这是排序阶段的"软惩罚"；总量硬控制由 §6.3.3 贪心填充完成
 */
private double calculateCognitiveLoadPenalty(UnifiedTask task, List<UnifiedTask> allTasks) {
    double penalty = 0;
    // 1. 任务本身负荷 5 → -3，负荷 4 → -1.5
    if (task.getCognitiveLoad() >= 5) {
        penalty += -3.0;
    } else if (task.getCognitiveLoad() == 4) {
        penalty += -1.5;
    }
    // 2. 当日队列中高负荷任务（load>=4）占比 >= 60% 时，对高负荷任务统一追加 -4
    long highLoadCount = allTasks.stream()
            .filter(t -> t.getCognitiveLoad() >= 4).count();
    if (!allTasks.isEmpty()
            && (double) highLoadCount / allTasks.size() >= 0.6
            && task.getCognitiveLoad() >= 4) {
        penalty += -4.0;
    }
    return penalty;
}
```

#### 6.5.3 集合工具函数

```java
/** 计算两个集合的重叠率：intersection / min(size1, size2)，分母取小集合防误伤 */
private double calculateSetOverlap(List<Long> a, List<Long> b) {
    if (a == null || b == null || a.isEmpty() || b.isEmpty()) {
        return 0;
    }
    Set<Long> sa = new HashSet<>(a);
    Set<Long> sb = new HashSet<>(b);
    sa.retainAll(sb);
    return (double) sa.size() / Math.min(a.size(), b.size());
}

private boolean hasCommonKnowledgePoints(UnifiedTask t1, UnifiedTask t2) {
    return calculateSetOverlap(t1.getKnowledgePointIds(),
            t2.getKnowledgePointIds()) > 0;
}

/** 合并方向裁决：来源 base_priority 高者为主任务；同权时 taskId 小者（先投递）为主 */
private int comparePriority(UnifiedTask t1, UnifiedTask t2) {
    int p1 = sourceRegistryCache.get(t1.getSourceId()).getBasePriority();
    int p2 = sourceRegistryCache.get(t2.getSourceId()).getBasePriority();
    if (p1 != p2) return Integer.compare(p1, p2);
    return Long.compare(t2.getTaskId(), t1.getTaskId());
}

/**
 * 寻找低负荷缓冲任务（load <= 2、非紧急、未被选入），用于打断连续高负荷序列
 * v1.1 修复：传入 excludeIds 防止同一缓冲任务被重复插入
 */
private UnifiedTask findLowLoadTask(List<UnifiedTask> ranked, List<UnifiedTask> selected) {
    Set<Long> exclude = selected.stream()
            .map(UnifiedTask::getTaskId).collect(Collectors.toSet());
    return ranked.stream()
            .filter(t -> !exclude.contains(t.getTaskId()))
            .filter(t -> t.getCognitiveLoad() <= 2)
            .filter(t -> t.getDeadline() == null
                    || Duration.between(LocalDateTime.now(),
                        t.getDeadline().toLocalDateTime()).toHours() > 24)
            .findFirst().orElse(null);
}
```

## 7. 存储与缓存设计

### 7.1 存储分工原则

**PostgreSQL（`unified_task` 等表）为唯一权威数据源**；Redis 仅作为"当日队列的展示层缓存与实时通道"，任何情况下允许丢失后由 DB 重建（重建方向恒为 DB → Redis，禁止反向回写，与《服务端-统一计费账单中心》对账红线同一原则）。

### 7.2 Redis Key 设计总表

| Key | 类型 | Score/Value | TTL | 用途 |
|-----|------|-------------|-----|------|
| `task:queue:{userId}:{yyyyMMdd}` | ZSet | score=priority_score, member=taskId | 当日 23:59 + 2h | 当日排定队列（展示顺序源） |
| `task:detail:{taskId}` | Hash | 任务展示字段快照 | 26h | 队列页免回源渲染 |
| `task:summary:{userId}:{yyyyMMdd}` | Hash | totalCount/completedCount/totalMinutes/subjectJson | 26h | 今日汇总（首页卡与工作台头图） |
| `task:qver:{userId}` | String | queueVersion（单调递增整数） | 7d | 队列版本号，多端增量同步 |
| `task:sched:lock:{userId}:{yyyyMMdd}` | String（NX） | 调度实例ID | 10s | 单用户调度互斥锁 |
| `task:debounce:{userId}` | String（NX） | 1 | 500ms | 增量调度去抖合并窗口 |
| `task:srcquota:{sourceId}:{yyyyMMdd}` | String 计数 | INCR | 48h | 来源日投递量/时长限额检查 |
| `task:recentkps:{userId}` | Set | 知识点ID | 7d | 冗余惩罚的已完成 KP 缓存 |

### 7.3 队列版本与多端一致性

1. 每次成功调度（批量/增量/事件重排）完成后 `INCR task:qver:{userId}`；
2. 客户端今日队列响应携带 `queueVersion`，下次请求带 `If-Match` 头；
3. 版本不一致时服务端返回全量 + 新版本（55716 的语义见 §13）；
4. SSE 推送事件统一携带 `queueVersion`，客户端按版本单调性丢弃乱序旧事件。

### 7.4 缓存失效与重建

| 场景 | 处理 |
|------|------|
| 队列 Key 丢失（Redis 重启/驱逐） | 查询路径回源 DB 按 `priority_score DESC` 重建 ZSet，重建加 `task:sched:lock` 防并发 |
| 调度完成 | 同事务提交 DB 后删除 `task:summary`、更新 ZSet、`INCR qver`（顺序：先 DB 后缓存） |
| 详情修改（完成/跳过） | 删除 `task:detail:{taskId}` + 更新 ZSet 分数或移除 member |
| 汇总查询 | 先读 `task:summary`，miss 时 DB 聚合回填（锁定 `NX EX 30s` 防击穿） |

## 8. 调度触发与批处理设计

### 8.1 触发矩阵

| 触发方式 | 时机 | 范围 | 延迟目标 |
|----------|------|------|----------|
| 日终批量 | 每日 06:00（用户所在时区，分 15min 滚动窗口分片） | 全量活跃用户 | 06:30 前完成 |
| 增量触发 | 任务投递成功后 | 单用户 | 投递 → 可查询 ≤ 2s |
| 事件触发 | 任务完成/跳过/撤销、画像更新事件 | 单用户 | ≤ 2s |
| 手动触发 | 学生下拉刷新首页/任务中心 | 单用户 | 即时（读缓存，必要时重排） |
| 过期扫描 | 每 5 分钟 | 全局 PENDING/ACTIVE 且 deadline 已过 | 5min 粒度 |
| 首开兜底 | 用户当日首次打开 App（06:00 批量遗漏或失败时） | 单用户 | 即时同步调度 |

### 8.2 日终批量任务（BatchScheduler）

```java
/**
 * 每日 06:00（按用户时区分 15 分钟滚动窗口）批量预排当日队列
 * 分片游标 + 幂等：任务可安全中断重跑
 */
@Scheduled(cron = "0 */15 6 * * ?", zone = "Asia/Shanghai")
public void dailyBatchSchedule() {
    // 1. 取调度分片游标（Redis: task:batch:cursor:{yyyyMMdd}，DB 兜底）
    // 2. 分片拉取本窗口应调度用户（按 user_id % 16 分片，每片 500 用户/批）
    // 3. 逐用户执行 schedule(userId, today)，每个用户独立 try-catch，
    //    单用户失败计入批次失败率，不中断整片
    // 4. 写 daily_task_snapshot（uk(user_id, snapshot_date) 冲突则 version+1 覆盖）
    // 5. 批次完成后发布 task.scheduled 批事件（供学习提醒服务生成当日提醒计划）
    // 6. 推进游标；06:30 未完成的分片触发 P2 告警，由首开兜底路径接手
}
```

**与上游生成时序的契约**：错题复习任务（间隔重复引擎）与学习计划任务（每日任务生成服务）必须在每日 05:30 前完成当日投递（对齐《间隔重复算法与遗忘曲线复习调度引擎》§投递时序与《服务端-每日任务智能生成与学习计划执行追踪服务》§4.1）；06:00 批量调度只做"聚合-合并-仲裁-负荷控制"，不生成任务。投递晚于 06:00 的任务走增量触发路径，不丢失。

### 8.3 增量调度（去抖合并）

新任务投递后不立即全量重排，而是：

1. 投递落库（同步）→ 写 `task:debounce:{userId}`（NX EX 500ms）；
2. 去抖键写入成功的一方（同一用户 500ms 窗口内多次投递只触发一次）投递延迟消息（15s）；
3. 消费延迟消息时执行 `schedule(userId, today)` 增量重排（含新任务合并评估）；
4. 重排完成后 SSE 推送 `TASK_ADDED` / `TASK_REPRIORITIZED`。

投递接口的响应语义不变（"将在下一次调度周期中计算优先级"），客户端在 SSE 收到 `TASK_ADDED` 前可先以本地占位渲染（乐观更新，30s 内被服务端校准，对齐《客户端-首页与学习工作台》§6.2.5）。

### 8.4 过期扫描器（ExpireScanner）

```java
/** 每 5 分钟扫描：PENDING/ACTIVE 且 deadline < now 的任务转 EXPIRED */
@Scheduled(fixedDelay = 300_000)
public void scanExpired() {
    // UPDATE unified_task SET status='EXPIRED', updated_at=NOW()
    //  WHERE status IN ('PENDING','ACTIVE') AND deadline < NOW()
    //    AND expired_scanned = FALSE            -- 防重标记列（v1.1 增补，见 §9.1）
    // 逐行发布 task.expired 事件（Outbox）；
    // 特例：HOMEWORK 来源过期不生成新事件（由作业服务自己的催交引擎负责提醒），
    //       调度引擎仅收敛展示状态，避免双重提醒。
}
```

**顺延语义边界（重要）**：调度引擎**不自动顺延**过期任务到次日——任务实体归属来源系统，是否重投由来源决策（学习计划服务会在次日生成新计划任务；错题引擎的 SM-2 调度天然会在下一周期重排到期）。调度引擎只负责把"今日仍 PENDING 且来源允许跨日（`can_be_deferred=TRUE`）"的任务在次日聚合时作为 overdue 任务带回队列（见 §6.1.2 第 2 步），并施加 `overdueBonus` 提权。

### 8.5 首开兜底

用户当日首次打开 App 请求 `/today` 时：若 `task:queue:{userId}:{today}` 不存在且当日无快照记录，则同步执行一次 `schedule(userId, today)`（预计 P99 ≤ 800ms，超时则返回 DB 直查的未排序兜底列表并标记 `sorted=false`，客户端按 deadline 升序本地排序）。

| 守卫 | 规则 | 违反错误码 |

| G9 | 合并方向：base_priority 高者为主任务；`can_be_merged=FALSE` 的任务只可作主任务、不可被吸收（教师作业永远不被合并吸收） | — |
| G10 | 快照写入幂等：uk(user_id, snapshot_date) 冲突时 version+1 覆盖，保留最后两次版本供回溯 | — |
| G11 | ACTIVE 无心跳超时回收：开始后 120min 无完成/跳过回报且无学习会话心跳 → 回退 PENDING（`deferred_count` 不变），防僵尸任务占用当日负荷预算 | — |

## 10. 幂等与并发控制

### 10.1 投递幂等

- 唯一键 `uk_task_source_ref_user(source_id, external_ref, user_id)`；
- 重复投递返回原任务（`code=0`，响应附 `"idempotent": true`），不产生新任务、不触发重排；
- 批量投递逐条独立幂等，部分失败返回 `partialResults`（对齐《服务端-统一响应封装与分页查询规范》部分成功结构）。

### 10.2 状态回调幂等（CAS）

```sql
UPDATE unified_task
   SET status = :newStatus, completed_at = :completedAt, updated_at = NOW()
 WHERE uuid = :uuid
   AND status IN (:allowedFromStates);   -- 由 G1 流转表决定
-- affected = 0 时读当前状态判定：同状态 → 幂等成功；否则按 G2/G3 返回 55711/55712
```

### 10.3 调度互斥

- 单用户调度串行化：`SET task:sched:lock:{userId}:{date} {instanceId} NX EX 10`；
- 拿锁失败且锁持有 >10s（锁过期竞争）→ 直接读现有队列返回（调度结果短暂陈旧可接受，下一次触发收敛）；
- DB 侧兜底：`daily_task_snapshot` uk 冲突时放弃写入（以先完成者为准）。

### 10.4 事件消费幂等

调度引擎自身作为消费方（订阅画像更新、计划变更事件）时，以 `(event_id, consumer='task-scheduler')` 在事件总线的消费位点表中登记去重（对齐《服务端-事件驱动架构与统一事件总线》消费幂等约定）。

## 11. 统一事件设计（Outbox）

### 11.1 Outbox 表

```sql
CREATE TABLE task_outbox (
    id            BIGSERIAL PRIMARY KEY,
    event_id      VARCHAR(64)  NOT NULL,
    event_type    VARCHAR(64)  NOT NULL,
    aggregate_id  BIGINT       NOT NULL,        -- task_id 或 user_id
    user_id       BIGINT       NOT NULL,
    payload       JSONB        NOT NULL,
    occurred_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    relay_state   VARCHAR(16)  NOT NULL DEFAULT 'PENDING',  -- PENDING/SENT/DEAD
    retry_count   SMALLINT     NOT NULL DEFAULT 0,
    UNIQUE (event_id)
);
CREATE INDEX idx_task_outbox_relay ON task_outbox (relay_state, occurred_at);
```

事件信封（`event_id` / `eventType` / `occurredAt` / `payload`）对齐《服务端-事件驱动架构与统一事件总线》，Topic 复用 `learning-events`，`eventType` 前缀 `task.`。Relay 每 500ms 批量投递，失败 2^n 退避，`retry_count ≥ 8` 转 DEAD + P2 告警；日终 Relay 对账（outbox SENT 数 vs 总线 ACK 数）差异 > 0.1% 告警。

### 11.2 事件清单与消费方矩阵

| eventType | 触发 | payload 关键字段 | 主要消费方 |
|-----------|------|------------------|-----------|
| `task.scheduled` | 日终批量/手动重排完成 | userId, date, taskIds, totalMinutes, queueVersion | 学习提醒服务（生成当日提醒计划）、首页卡片服务（TODAY_TASK 卡失效重取） |
| `task.updated` | 增量重排后队列变化 | userId, changeType(ADD/REMOVE/RERANK), taskIds, queueVersion | 首页卡片服务、客户端 SSE 网关 |
| `task.completed` | 任务完成 | taskId, userId, sourceId, actualMinutes, result | 每日任务追踪服务（计划执行度）、画像特征平台（任务完成率特征）、用户学习激励中心（打卡判定）、学习时长归因引擎 |
| `task.skipped` | 学生跳过/负荷裁剪 | taskId, userId, skipReason, deferredTo | 家长中心（PARENT_TASK 跳过时通知家长）、每日任务追踪服务（负面信号） |
| `task.expired` | 过期扫描 | taskId, userId, deadline | 每日任务追踪服务（计划偏离预警） |
| `task.merged` | 合并执行 | primaryTaskId, absorbedTaskId, strategy, confidence | 每日任务追踪服务（externalRef 归一）、错题引擎（复习任务被合并时的完成回传路由） |
| `task.withdrawn` | 来源撤销 | taskId, userId, sourceId, reason | 首页卡片服务、学习提醒服务（撤销提醒） |
| `snapshot.created` | 日终快照落库 | userId, date, totalCount, subjectDistribution | 学习数据看板、成长报告引擎 |

**消费幂等键统一为 `(event_id, consumer)`**；`task.completed` 中 `actualMinutes` 仅作展示，学习时长权威归因以《服务端-学生学习时长跨模块统一归因与对账引擎》为准（本引擎不重复计时，避免双计红线）。

## 12. API 补全

### 12.1 学生侧任务操作接口

#### 开始任务

```
POST /api/v1/task-scheduler/tasks/{taskUuid}/start
```

```json
// 响应
{ "code": 0, "data": { "taskId": 200005, "status": "ACTIVE", "startedAt": "2026-06-15T10:02:11Z" } }
```

守卫：G1（仅 PENDING 可开始，ACTIVE 重复开始幂等成功）；开始信号同时联动《学习会话状态快照》建立学习上下文（任务作为会话 anchor，对齐《服务端-学生学习上下文全局管理》handoff 契约）。

#### 跳过任务

```
POST /api/v1/task-scheduler/tasks/{taskUuid}/skip
{ "reason": "TOO_HARD" }   // TOO_HARD / NO_TIME / NOT_INTERESTED / OTHER
```

守卫：G1；`can_be_deferred=FALSE` 且未过期的家长任务跳过时，事件 `task.skipped` 触发家长中心站内信通知家长（学生不可静默跳过家长任务）。

#### 推迟任务到明日

```
POST /api/v1/task-scheduler/tasks/{taskUuid}/defer
```

守卫：G6（不可推迟来源返回 55714）、G12（`deferred_count ≤ 3`，超出返回 55713）。实现为改写 `suggested_start` 至次日 06:00，并从当日 ZSet 移除。

### 12.2 队列增量拉取

```
GET /api/v1/task-scheduler/users/{userId}/today?version=42
If-Match: "42"
```

- 版本一致 → `304` 语义（`code=0, data.unchanged=true`，仅返回 summary）；
- 版本落后/领先 → 返回全量 + 新 `queueVersion`（55716 仅在客户端传入了过期 2 个版本以上且服务端已无增量日志时返回，客户端应丢弃本地状态全量刷新）。

## 14. 降级矩阵（D1-D10）

| 编号 | 故障 | 降级行为 | 影响 |
|------|------|----------|------|
| D1 | 画像服务不可用 | `UserLearningProfile` 用中性空画像：无偏好/弱势加成、无掌握度数据 | 排序质量下降，可用性不变 |
| D2 | 偏好服务不可用 | `maxDailyMinutes` 取分龄防沉迷上限（幼儿 40/小学 60/初中 90 分钟，高中 120 提示性） | 宁可少排不超排 |
| D3 | Redis 不可用 | 查询回源 DB（priority_score 索引覆盖）；SSE 断开，客户端 30s 轮询兜底 | P99 劣化至 ~300ms |
| D4 | MQ 不可用 | 投递 REST 通道不受影响（本来就是同步落库）；增量调度退化为 5min 定时全量重算 | 新任务可见延迟 ≤ 5min |
| D5 | 合并器异常 | 跳过合并直接排序（fail-open，容忍少量重复任务展示），合并器熔断 5min | 体验下降，无数据风险 |
| D6 | 知识点元数据不可用 | 合并仅保留 externalRef 精确去重，禁用 KP/章节重叠合并 | 合并率下降 |
| D7 | 快照写失败 | 不阻塞调度主链路；补偿任务（延迟队列 10min）重建当日快照 | 趋势报表缺口 |
| D8 | SSE 网关不可用 | 客户端降级轮询（对齐《客户端-网络请求治理与弱网适配》SSE 断线重连策略） | 实时性下降 |
| D9 | 事件总线不可用 | Outbox 积压自动重投；下游（提醒/卡片）短暂陈旧 | 提醒延迟 |
| D10 | 服务端时钟与来源系统偏差 | deadline 计算以调度引擎服务端权威时间为准（NTP 校准，偏差 >2s 告警）；来源投递时间仅作参考 | 逾期判定一致性 |

**红线**：D1-D10 任何降级不得导致任务**丢失**或**重复**（幂等键保证）；不得向未成年人超量排任务（D2 方向为收紧而非放宽）。

## 15. 监控与容量规划

### 15.1 监控指标（10 项）

| 指标 | 口径 | 告警阈值 |
|------|------|----------|
| 调度延迟 P99 | 投递成功 → `/today` 可见 | > 5s（P2）/ > 30s（P1） |
| 日终批量完成时间 | 06:00 起至全部分片完成 | > 06:30 P2；> 07:00 P1 |
| 批量失败率 | 失败用户数/应调度用户数 | > 1% P2 |
| 队列缓存命中率 | Redis 命中/今日队列读 | < 95% P3（容量预警） |
| 任务合并率 | 合并任务数/总任务数 | < 2%（合并失效）或 > 20%（上游重复投递嫌疑）P3 |
| 负荷裁剪率 | COGNITIVE_LOAD_LIMIT 裁剪数/当日任务数 | > 20% P2（任务过载信号，联动每日任务生成服务） |
| 任务过期率 | EXPIRED/当日排定总数 | > 15% P3（计划过载或执行障碍，联动学习计划执行障碍诊断） |
| 投递 QPS / 限额拒绝数 | task:srcquota 拒绝计数 | 突增 5 倍告警（上游异常重投） |
| SSE 在线连接数 | 网关上报 | 单节点 > 5 万告警（容量） |
| Outbox 积压 | PENDING 年龄 > 60s 数量 | > 1000 P2 |

### 15.2 容量估算（DAU 50 万基准）

- **写入**：日均投递 400 万条（人均 8 任务）+ 状态变更 200 万次 ≈ 峰值写 800 QPS（日终批量 06:00-06:30 窗口内集中调度读放大，按 16 分片 × 500/批滚动）；
- **存储**：`unified_task` 按月分区，月增约 1.2 亿行（含状态变更新版本不产生新行，仅 UPDATE）≈ 单月 ~40GB（含索引），在线保留 12 个月，归档 24 个月（画像长期特征需要）；
- **Redis**：50 万活跃队列 ZSet（人均 ~10 member × 100B）+ detail/summary ≈ ~500MB，26h TTL 滚动；
- **查询**：今日队列 + 首页 summary 峰值 ~5000 QPS，99% 由 Redis 承接，DB 回源 ≤ 50 QPS。

## 17. 合规红线（C1-C8）

- **C1 未成年人任务量硬上限**：当日排定总时长 ≤ min(用户偏好 maxDailyMinutes, 分龄防沉迷上限 − 当日已用 App 时长)。分龄上限以《防沉迷与未成年人保护机制》权威表为准（幼儿 40 / 小学 60 / 初中 90 分钟，高中提示性 120）；防沉迷上限是**硬约束**，用户偏好只能更小不能更大。触发上限时新任务拒收并返回 55718（来源为 HOMEWORK/PARENT_TASK 的任务不拒收、但标记 `overflowProtected=true` 次日优先排入）。
- **C2 双减与休息保护**：义务教育阶段学生 SYS_RECOMMEND 任务在校日 21:00 后不投递不展示（调度引擎在读路径按用户年龄段 + 时间过滤，双保险）；法定节假日/寒暑假不受此限但受 C1 约束。
- **C3 家长任务保护**：每日 ≤3 条、总时长 ≤60min（注册表限额）；学生跳过家长任务必须通知家长（§12.1），不可静默；家长任务不可被负荷裁剪（G6）。
- **C4 内容边界**：任务 title/description 投递时过敏感词（委托《服务端-教育场景敏感词多层次过滤》scene=TASK，fail-secure：不可用时段接投递进人工复核队列而非直接放行）；SYS_RECOMMEND 任务不得含营销导流素材（metadata.reviewed=1 才可投递）。
- **C5 家长可见性**：任务队列对学生本人全量可见；家长端可见性遵循《服务端-学生学习数据家庭共享可见度分级与隐私边界管控》分级配置（默认家长可见任务完成状态、不可见 SYS_RECOMMEND 明细）。
- **C6 无社交泄露面**：任务与优先级数据仅本人及授权监护人可见；priority_reason 对家长展示时**不得**包含同伴比较、班级排名类因子（本引擎因子集天然不含，禁止后续加入）。
- **C7 可解释性**：每个任务最终得分必须携带完整 `priorityReason` 明细（§6.4），客户端"为什么排第一"气泡直接渲染该明细，禁止黑盒分数。
- **C8 越权与审计**：投递/撤销接口仅限内网来源系统（服务间鉴权 mTLS + sourceId 白名单）；管理端诊断查询对任务标题脱敏、全量审计留痕。

## 19. 验收场景（18 条）

1. **多源聚合**：同日投递 7 类来源任务各 1 条，`/today` 返回 7 条且 `summary.subjectDistribution` 统计正确。
2. **投递幂等**：同一 `(sourceId, externalRef, userId)` 连续投递 3 次，仅产生 1 条任务，后 2 次响应 `idempotent=true` 且返回相同 taskId。
3. **重复投递限额**：SYS_RECOMMEND 单日第 6 条投递返回 55702；ERROR_REVIEW 30min 内第 2 次投递返回 55704。
4. **完全重复合并**：同 externalRef 不同 user_id（同班作业）不合并、各自成任务。
5. **知识点重叠合并**：STUDY_PLAN 与 WEAKNESS_FIX 任务 KP 重叠 70% → 合并为一条，`task_merge_log` 有 COMBINE 记录，被吸收任务状态 MERGED 且 `merged_into_task_id` 正确。
6. **作业不被吸收**：HOMEWORK 任务与 WEAKNESS_FIX 任务 KP 重叠 80%，合并方向为作业作主任务（G9），`task.updated` 中作业 taskId 不变。
7. **优先级排序**：无 deadline 的 SYS_RECOMMEND（base 30）排在 2h 内截止的 HOMEWORK（base 90 + deadlineBonus）之后；`priorityReason` 明细字段完整（C7）。
8. **逾期提权**：昨日到期未完成的 ERROR_REVIEW 任务今日仍出现在队列且 `overdueBonus ≥ 5`、rank 提升。
9. **负荷总量控制**：用户偏好 90min，当日待排任务总预估 150min → 裁剪后 ≤90min，被裁任务 SKIPPED+COGNITIVE_LOAD_LIMIT，HOMEWORK/PARENT_TASK 任务未被裁剪（G6/G7）。
10. **连续高负荷缓冲**：队列前 3 个任务 cognitive_load 均 ≥4 → 第 3 个前插入 load≤2 缓冲任务且缓冲任务不重复（§6.5.4）。
11. **未成年人保护**：小学用户当日已用 App 55min（防沉迷上限 60），偏好 120min → 实际可用 5min，新 SYS_RECOMMEND 投递返回 55718；HOMEWORK 任务不拒收但 `overflowProtected=true`（C1）。
12. **夜间推荐过滤**：义务教育用户 21:30 请求 `/today`，SYS_RECOMMEND 任务不出现在响应中（C2）。
13. **状态回调幂等**：COMPLETED 回调重放 2 次均返回成功且 `completed_at` 不变；COMPLETED 之后的 SKIPPED 回调返回 55712。
14. **过期扫描**：deadline 已过的 ACTIVE 任务 5min 内转 EXPIRED、`task.expired` 事件恰好一条；HOMEWORK 过期不触发提醒类事件（§8.4）。
15. **推迟链路**：STUDY_PLAN 任务推迟 3 次后第 4 次返回 55713；PARENT_TASK 推迟返回 55714。
16. **增量调度与 SSE**：任务投递后 ≤2s 客户端收到 `TASK_ADDED`（含 queueVersion），队列插入位置与重算优先级一致。
17. **缓存重建**：删除该用户当日 Redis 全部 Key 后请求 `/today`，自动回源 DB 重建队列，结果与重建前一致且无重复任务。
18. **合并撤销**：管理端撤销一条 7 天内的误合并记录，被吸收任务恢复 PENDING、重新进入队列且 `task.updated` 事件发布；超过 7 天的撤销被拒绝。
