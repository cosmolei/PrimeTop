# 学生学习状态建模与动态评估引擎 — 详细设计

> 版本：v1.0 | 创建日期：2026-05-24 | 状态：待评审

---

## 1. 概述

### 1.1 文档目的

本文档详细设计"学生学习状态建模与动态评估引擎"（Student Learning State Modeling & Dynamic Assessment Engine，简称 **StateEngine**）。StateEngine 是 PrimeTop 学习闭环中的核心基础设施，负责对每位学生的多维学习状态进行实时建模、持续追踪和动态评估，为个性化推荐、难度调节、学习规划、家长报告等上层服务提供统一的状态查询与事件推送能力。

### 1.2 问题背景

原始设计文档多处提到"动态判断学习状态"（§8.5.2、§12.3）、"能力画像"（§6.7）、"掌握度"（§12.3）等需求，当前已细化的文档分别从不同角度覆盖了一部分：

| 已有文档 | 覆盖范围 | 局限 |
|---------|---------|------|
| 用户学习画像与能力维度模型 | 静态/半静态的能力维度画像 | 更新频率低，偏向长期趋势 |
| 题目难度标定与能力评估模型 | 基于 IRT 的能力值 θ 估计 | 仅关注答题能力单一维度 |
| 学情分析 | 学习数据统计与报告 | 偏报表视角，非实时状态 |
| 自适应学习与个性化推荐引擎 | 内容推荐算法 | 依赖状态输入但未定义状态模型本身 |
| 护眼模式与视觉健康管理 | 视觉/用眼健康状态 | 仅覆盖健康维度 |

**缺失的核心能力**：没有一个统一的、实时运转的引擎来综合建模学生在任意时刻的多维学习状态（认知、情绪、疲劳、进度等），并将状态变化以事件形式推送给下游服务。

### 1.3 设计目标

1. **多维状态建模**：将学生学习状态拆解为 5 个核心维度，每维度独立评估、综合输出。
2. **实时更新**：核心状态在每次学习行为发生后 ≤ 3 秒内完成更新。
3. **事件驱动**：状态变更时产生结构化事件，下游服务可订阅消费。
4. **可扩展**：新增维度、指标、信号源不影响已有逻辑。
5. **隐私合规**：状态数据按最小必要原则采集，敏感维度（如情绪）需家长/用户授权。

## 2. 状态维度模型

### 2.1 五维模型总览

```
┌─────────────────────────────────────────────────┐
│              Student Learning State              │
│                                                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────┐ │
│  │ Cognitive│ │ Emotional│ │    Fatigue        │ │
│  │  State   │ │  State   │ │    State          │ │
│  │(知识掌握) │ │(学习情绪) │ │   (疲劳状态)      │ │
│  └──────────┘ └──────────┘ └──────────────────┘ │
│  ┌──────────┐ ┌──────────────────────────────┐  │
│  │Engagement│ │       Progress State          │  │
│  │  State   │ │        (进度状态)              │  │
│  │(参与投入) │ │                               │  │
│  └──────────┘ └──────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

| 维度 | 英文标识 | 核心问题 | 更新频率 |
|------|---------|---------|---------|
| 认知状态 | `cognitive` | 学生对各知识点的掌握程度如何？ | 每次答题/学习行为后 |
| 情绪状态 | `emotional` | 学生当前的情绪/动机状态如何？ | 每次交互后（低置信度） |
| 疲劳状态 | `fatigue` | 学生是否疲劳？需要休息吗？ | 每分钟采样 + 行为触发 |
| 参与状态 | `engagement` | 学生当前是否专注投入？ | 每30秒采样 + 行为触发 |
| 进度状态 | `progress` | 相对学习目标，进度是否正常？ | 每次任务完成/每日汇总 |

#### 3.1.2 掌握度估计算法

采用 **贝叶斯知识追踪（BKT）** 与 **IRT 项目反应理论** 的混合模型：

```
BKT 四参数模型：
  P(L0) — 初始掌握概率（先验）
  P(T)  — 学习转移概率（未掌握→掌握）
  P(G)  — 猜对概率
  P(S)  — 失误概率

每次答题后更新：
  P(Lt|correct)   = P(Lt) × (1-P(S)) / [P(Lt)×(1-P(S)) + (1-P(Lt))×P(G)]
  P(Lt|incorrect) = P(Lt) × P(S)     / [P(Lt)×P(S)     + (1-P(Lt))×(1-P(G)]
  P(Lt+1)         = P(Lt|answer) + (1 - P(Lt|answer)) × P(T)

参数初始值（按学段和知识点类型差异化）：
  小学基础知识点：P(L0)=0.3, P(T)=0.15, P(G)=0.2,  P(S)=0.1
  初中进阶知识点：P(L0)=0.2, P(T)=0.10, P(G)=0.15, P(S)=0.15
  高中复杂知识点：P(L0)=0.15,P(T)=0.08, P(G)=0.1,  P(S)=0.2
```

#### 3.1.3 信号来源与权重

| 信号 | 采集方式 | 权重 | 说明 |
|------|---------|------|------|
| 答题正确性 | 题目服务推送 | 0.35 | 最核心信号 |
| 答题响应时间 | 客户端上报 | 0.15 | 过快可能猜测，过慢可能不熟练 |
| 知识点关联深度 | RAG 检索上下文 | 0.10 | 问题涉及的知识点层级 |
| AI 辅导后的二次作答 | 辅导服务回调 | 0.20 | 辅导后是否答对 |
| 主动求助频率 | 对话服务统计 | 0.10 | 频繁求助暗示掌握不足 |
| 错题复习通过率 | 错题服务回调 | 0.10 | 复习后是否掌握 |

#### 3.1.4 更新触发时机

```
触发源                     延迟要求     处理方式
─────────────────────────────────────────────────
答题完成                   ≤ 1s         同步计算
AI 辅导会话结束            ≤ 3s         异步队列
错题复习完成               ≤ 3s         异步队列
每日学习汇总               T+1          批量计算
知识点标签变更             ≤ 5s         异步重算
```

#### 3.2.2 情绪推断策略

由于 PrimeTop 以文字/语音交互为主，且需遵守未成年人隐私保护原则，情绪推断采用**纯行为信号**方式，不使用面部表情识别：

```python
# 情绪推断规则引擎（伪代码）

def infer_emotion(student_id: str, recent_events: list[Event]) -> EmotionalState:
    features = extract_features(recent_events)
    
    # 特征向量
    # - 连续错误次数 (consecutive_errors)
    # - 最近5题正确率 (recent_accuracy)  
    # - 平均响应时间变化率 (response_time_delta)
    # - 主动求助频率 (help_seeking_rate)
    # - 会话放弃率 (session_abandon_rate)
    # - 正向反馈交互率（点赞/收藏）(positive_interaction_rate)
    
    # 规则层（高置信度快速判断）
    if features.consecutive_errors >= 5:
        return EmotionalState(
            valence='negative', 
            primaryEmotion=FRUSTRATED,
            frustrationIndex=80,
            confidence=0.85
        )
    
    if features.recent_accuracy >= 0.9 and features.positive_interaction_rate > 0.3:
        return EmotionalState(
            valence='positive',
            primaryEmotion=CONFIDENT,
            frustrationIndex=5,
            confidence=0.7
        )
    
    # 模型层（低置信度场景使用轻量分类模型）
    # 输入：6维特征向量
    # 模型：轻量决策树 (max_depth=5, 在线更新)
    # 输出：情绪标签 + 置信度
    
    prediction = emotion_classifier.predict(features.to_vector())
    
    return EmotionalState(
        valence=prediction.valence,
        primaryEmotion=prediction.label,
        frustrationIndex=prediction.frustration_score,
        confidence=prediction.confidence  # 通常 0.4~0.65
    )
```

#### 3.3.2 疲劳评分算法

```
疲劳评分计算公式：

  fatigue_score = W1 × time_factor 
                + W2 × behavior_factor 
                + W3 × accuracy_decay_factor
                + W4 × pattern_factor

其中：
  time_factor = min(1.0, continuous_minutes / max_continuous_minutes)
  
  behavior_factor = (
    0.3 × min(1.0, avg_response_time_recent / avg_response_time_baseline - 1) 
    + 0.3 × page_scroll_frequency_recent / page_scroll_frequency_baseline
    + 0.2 × session_pause_count / session_duration_minutes  
    + 0.2 × input_retry_count / total_input_count
  )
  
  accuracy_decay_factor = max(0, baseline_accuracy - recent_accuracy) / baseline_accuracy
  
  pattern_factor = detect_anomalous_time(student_id) ? 0.8 : 0.0
    // 检测是否在异常时段学习（如深夜），是则大幅提升疲劳分

权重：
  W1=0.35, W2=0.25, W3=0.25, W4=0.15
  
结果映射：
  fatigue_score ∈ [0, 1] → 映射到 0~100
```

```typescript
// 参与度信号采集（客户端 → 服务端）

interface EngagementSignal {
  studentId: string;
  sessionId: string;
  timestamp: ISO8601;
  
  // 高频信号（每30秒采样）
  activeScreenTimeSec: number;      // 屏幕活跃时间（排除后台/锁屏）
  scrollDistance: number;            // 滚动距离（像素）
  tapCount: number;                  // 点击次数
  
  // 事件驱动信号
  aiConversationTurns: number;       // AI对话轮次
  questionAttempts: number;          // 尝试答题次数
  noteActions: number;               // 笔记/收藏操作次数
  videoWatchProgress: number;        // 视频观看进度（0~1）
  
  // 反向信号（降低参与度）
  appBackgroundCount: number;        // APP 切后台次数
  idleDurationSec: number;           // 空闲时长
  rapidSkipCount: number;            // 快速跳过内容次数（<3秒）
}

// 参与度评分公式
function calculateEngagement(signal: EngagementSignal, window: TimeWindow): number {
  const positiveSignals = (
    0.20 * normalize(signal.aiConversationTurns, 0, 10) +
    0.15 * normalize(signal.questionAttempts, 0, 8) +
    0.10 * normalize(signal.noteActions, 0, 5) +
    0.10 * normalize(signal.videoWatchProgress, 0, 1) +
    0.15 * normalize(signal.activeScreenTimeSec, 0, 1800) +
    0.10 * normalize(signal.tapCount, 0, 50)
  );
  
  const negativeSignals = (
    0.10 * normalize(signal.appBackgroundCount, 0, 5) +
    0.05 * normalize(signal.idleDurationSec, 0, 300) +
    0.05 * normalize(signal.rapidSkipCount, 0, 10)
  );
  
  return clamp((positiveSignals - negativeSignals) * 100, 0, 100);
}

function normalize(value: number, min: number, max: number): number {
  return Math.min(1.0, Math.max(0.0, (value - min) / (max - min)));
}
```

#### 3.5.2 进度评估逻辑

```python
def assess_progress(student_id: str) -> ProgressState:
    plan = get_active_plan(student_id)
    if not plan:
        return default_progress_state()
    
    # 1. 计算时间进度 vs 任务进度
    time_elapsed_ratio = (now - plan.start_date) / (plan.end_date - plan.start_date)
    task_completion_ratio = plan.completed_tasks / plan.total_tasks
    
    # 2. 计算偏差
    deviation = (task_completion_ratio - time_elapsed_ratio) * plan.total_days
    
    # 3. 基于掌握度的知识进度
    knowledge_progress = mastered_kps / total_kps_in_scope
    
    # 4. 综合进度（加权）
    overall_progress = 0.6 * task_completion_ratio + 0.4 * knowledge_progress
    
    # 5. 预估完成日期（基于当前速率）
    if plan.completed_tasks > 0:
        avg_task_duration = elapsed_days / plan.completed_tasks
        remaining_tasks = plan.total_tasks - plan.completed_tasks
        estimated_end = now + remaining_tasks * avg_task_duration
    else:
        estimated_end = plan.end_date  # 无数据，使用计划日期
    
    # 6. 状态判定
    status = determine_status(deviation, overall_progress, estimated_end, plan)
    
    return ProgressState(
        scheduleDeviation=deviation,
        goalCompletionRate=overall_progress,
        status=status,
        estimatedCompletionDate=estimated_end,
        # ... 其他字段
    )

def determine_status(deviation, progress, estimated_end, plan):
    if deviation > 3:
        return 'ahead'
    if deviation >= -2:
        return 'on_track'
    if deviation >= -7:
        return 'slightly_behind'
    if deviation >= -14 or estimated_end <= plan.end_date + timedelta(days=7):
        return 'behind'
    return 'at_risk'
```

### 6.3 风险干预流程

```typescript
// 风险干预编排器

class InterventionOrchestrator {
  
  async handleRiskDetected(event: RiskDetectedEvent): Promise<void> {
    const { studentId, riskFlag, recommendedAction } = event;
    
    // 1. 检查冷却期（避免短时间内重复干预）
    const cooldownKey = `intervention_cooldown:${studentId}:${riskFlag.type}`;
    const inCooldown = await redis.get(cooldownKey);
    if (inCooldown) return;
    
    // 2. 查询当前完整状态
    const state = await this.stateQueryApi.getFullState(studentId);
    
    // 3. 根据风险类型和严重度选择干预策略
    const strategy = this.selectStrategy(riskFlag, state);
    
    // 4. 执行干预
    switch (strategy.type) {
      case 'client_reminder':
        // 通过消息推送服务向客户端发送提醒
        await this.pushService.send(studentId, {
          type: 'learning_reminder',
          title: strategy.title,
          body: strategy.body,
          priority: strategy.priority,
          action: strategy.action,
        });
        break;
        
      case 'parent_notification':
        // 向家长推送通知
        const parentId = await this.getBoundParent(studentId);
        if (parentId) {
          await this.pushService.send(parentId, {
            type: 'child_status_alert',
            title: `${studentName}学习状态提醒`,
            body: strategy.parentMessage,
          });
        }
        break;
        
      case 'content_adjustment':
        // 通知自适应学习引擎调整难度
        await this.eventBus.publish('state-engine.intervention-triggered', {
          studentId,
          interventionType: 'difficulty_adjustment',
          direction: strategy.adjustDirection, // 'easier' | 'harder'
          reason: riskFlag.type,
        });
        break;
        
      case 'plan_adjustment':
        // 通知学习规划服务调整计划
        await this.eventBus.publish('state-engine.intervention-triggered', {
          studentId,
          interventionType: 'plan_reschedule',
          reason: riskFlag.type,
          currentState: state,
        });
        break;
    }
    
    // 5. 设置冷却期
    await redis.set(cooldownKey, '1', 'EX', strategy.cooldownSeconds);
    
    // 6. 记录干预日志
    await this.logIntervention(studentId, riskFlag, strategy);
  }
}
```

## 8. 性能与容量设计

### 8.1 性能目标

| 指标 | 目标值 | 说明 |
|------|-------|------|
| 状态查询 P99 延迟 | ≤ 50ms | Redis 热数据直读 |
| 答题触发状态更新延迟 | ≤ 1s | 从事件接收到 Redis 更新 |
| AI 会话结束触发更新延迟 | ≤ 3s | 异步处理 |
| 参与度采样计算延迟 | ≤ 500ms | 每 30 秒窗口 |
| 每日批量汇总单学生耗时 | ≤ 2s | 含全维度重算 |
| 系统吞吐 | 10,000 events/s | 峰值（如考前集中练习） |

### 8.2 容量估算

```
假设：
  - 日活学生数：100,000
  - 每学生日均学习行为事件：50~200 条
  - 日均事件总量：5M ~ 20M
  - 状态快照保留：90 天（PostgreSQL）
  - 行为事件保留：180 天（ClickHouse）

存储估算：
  PostgreSQL 快照：
    100K 学生 × 90 天 × ~1KB/快照 ≈ 9GB
    
  ClickHouse 事件：
    20M 事件/天 × 180 天 × ~0.5KB/事件 ≈ 1.8TB
    
  Redis 热数据：
    100K 学生 × ~5KB/快照 ≈ 500MB
```

### 8.3 扩展策略

| 场景 | 策略 |
|------|------|
| 学生数增长 10x | Kafka 增加分区，state-calculator 水平扩容 |
| 状态查询热点 | Redis 读副本 + 客户端本地缓存（TTL 30s） |
| ClickHouse 存储压力 | 冷热分层，180 天后归档到对象存储 |
| 批量汇总耗时过长 | 按 student_id 哈希分片并行处理 |

## 9. 错误处理

### 9.1 错误码定义

| 错误码 | HTTP 状态 | 说明 | 客户端处理 |
|-------|----------|------|-----------|
| `STATE_001` | 404 | 学生不存在 | 提示检查账号 |
| `STATE_002` | 404 | 状态快照不存在（新用户） | 引导开始首次学习 |
| `STATE_003` | 429 | 事件上报频率超限 | 客户端合并后重试 |
| `STATE_004` | 503 | 状态引擎暂时不可用 | 使用客户端本地缓存状态 |
| `STATE_005` | 403 | 无权限查看该学生状态 | 家长绑定校验 |
| `STATE_006` | 422 | 事件格式校验失败 | 丢弃并记录日志 |

## 11. 安全与合规

### 11.1 数据安全

| 措施 | 说明 |
|------|------|
| 传输加密 | 所有 API 使用 TLS 1.3 |
| 存储加密 | PostgreSQL 字段级加密（情绪数据） |

### 11.2 未成年人保护

| 规则 | 说明 |
|------|------|
| 情绪推断不用于强制干预 | 情绪维度置信度 < 0.5 时不触发任何自动化操作 |
| 疲劳干预优先保护学生 | 高疲劳时优先提醒休息，而非推送更多内容 |
| 家长可关闭情绪推断 | 家长中心可关闭情绪维度的数据采集 |
| 不向学生展示原始情绪标签 | 仅展示"状态良好"/"继续加油"等正向表述 |

### 12.1 核心指标

| 指标 | 采集方式 | 告警阈值 |
|------|---------|---------|
| `state_update_latency_p99` | Prometheus Histogram | > 3s |
| `state_query_latency_p99` | Prometheus Histogram | > 100ms |
| `event_processing_lag` | Kafka Consumer Lag | > 10,000 |
| `snapshot_generation_rate` | Prometheus Counter | < 100/min (异常低) |
| `risk_detection_rate` | Prometheus Counter | 无阈值（仪表盘观察） |
| `stale_snapshot_ratio` | 自定义指标 | > 5%（过期快照比例） |
| `bkt_mastery_anomaly` | 定时检测 | 掌握度 > 1.0 或 < 0 异常值 |

### 12.2 告警规则

```yaml
# Prometheus 告警规则
groups:
  - name: state-engine
    rules:
      - alert: StateUpdateLatencyHigh
        expr: histogram_quantile(0.99, rate(state_update_latency_seconds_bucket[5m])) > 3
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "状态更新延迟过高"
          
      - alert: KafkaConsumerLagHigh
        expr: kafka_consumer_lag{group="state-calculator"} > 10000
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "状态引擎消费延迟过大"
          
      - alert: StaleSnapshotRatioHigh
        expr: stale_snapshot_ratio > 0.05

          severity: warning
```

### 14.3 名词解释

| 术语 | 说明 |
|------|------|
| BKT | 贝叶斯知识追踪（Bayesian Knowledge Tracing） |
| IRT | 项目反应理论（Item Response Theory） |
| 快照（Snapshot） | 某一时刻学生完整学习状态的序列化记录 |
| 信号（Signal） | 影响状态计算的单次数据输入 |
| 维度（Dimension） | 状态模型中的一个独立评估方向 |
| 干预（Intervention） | 基于状态评估触发的自动化操作 |
| 冷却期（Cooldown） | 同类型干预之间的最小时间间隔 |
