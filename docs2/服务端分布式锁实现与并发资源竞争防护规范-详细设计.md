# 服务端分布式锁实现与并发资源竞争防护规范 - 详细设计

## 1. 文档概述

### 1.1 目的

本规范定义 PrimeTop 服务端分布式锁的实现方式、使用场景、接口约定和运维策略，确保在多节点、多服务并发环境下对共享资源的互斥访问安全、高效、可观测。

### 1.2 适用范围

- 所有需要跨节点互斥访问的业务场景
- 微服务拆分后的服务间协调
- 定时任务防重复执行
- 高并发写操作的幂等性保障

### 1.3 与现有文档的关系

| 文档 | 关系 |
|------|------|
| 服务端数据库事务管理与并发控制策略 | 本文档是其补充，聚焦**跨节点/跨服务**的并发控制，而非单库事务 |
| 接口幂等性与防重提交机制 | 幂等性可借助分布式锁实现，但二者为互补方案 |
| 服务端统一限流熔断与流量防护体系 | 限流是流量层防护，分布式锁是资源层互斥 |
| 异步任务与事件驱动架构 | 定时任务和异步消费场景常需分布式锁护航 |

## 2. 核心概念与设计原则

### 2.1 何时需要分布式锁

```
┌─────────────────────────────────────────────────────┐
│                  是否需要分布式锁？                      │
├─────────────────────────────────────────────────────┤
│                                                     │
│  1. 是否涉及跨进程/跨节点的共享资源？                      │
│     └─ 否 → 使用本地锁（synchronized / ReentrantLock） │
│     └─ 是 → 继续                                      │
│                                                     │
│  2. 是否可以用数据库乐观锁/唯一约束解决？                  │
│     └─ 可以 → 优先用数据库方案                           │
│     └─ 不可以 → 继续                                   │
│                                                     │
│  3. 是否可以用消息队列串行化？                           │
│     └─ 可以 → 优先用 MQ                               │
│     └─ 不可以 → 使用分布式锁                            │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 2.2 设计原则

| 原则 | 说明 |
|------|------|
| **最小持有时间** | 锁的持有时间应尽量短，临界区内只做必要的互斥操作 |
| **必须有超时** | 所有锁必须设置合理的过期时间，防止死锁 |
| **幂等兜底** | 分布式锁不是银弹，业务层仍需幂等设计 |
| **锁粒度适中** | 过粗降低并发度，过细增加管理复杂度和死锁风险 |
| **可观测可告警** | 锁竞争、等待超时、异常释放均需监控 |
| **降级预案** | Redis 不可用时要有降级策略（本地锁 + 乐观兜底） |

## 3. 技术选型

### 3.1 方案对比

| 维度 | Redis (Redisson) | Zookeeper | etcd | 数据库悲观锁 |
|------|------------------|-----------|------|------------|
| 性能 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ |
| 可靠性 | ⭐⭐⭐⭐ (RedLock) | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 运维复杂度 | 低（已有 Redis） | 高（新增组件） | 中 | 最低 |
| 自动续期 | ✅ (watchdog) | ✅ (临时节点) | ✅ (lease) | ❌ |
| 公平锁 | ✅ | ✅ | ✅ | ❌ |
| 读写锁 | ✅ | ✅ | ✅ | ❌ |
| 适用场景 | 通用场景 | 强一致性要求 | K8s 环境 | 低并发简单场景 |

### 3.2 选型结论

**主方案：Redis + Redisson**

理由：
1. 项目已部署 Redis 集群（见"服务端服务架构与部署设计"），零额外运维成本
2. Redisson 提供了成熟的分布式锁实现，支持自动续期（watchdog）
3. 性能优异，满足学习平台高并发场景
4. API 简洁，学习成本低

**强一致场景备选：数据库乐观锁 / 唯一约束**

当业务涉及金钱、会员权益等强一致性需求时，以数据库为最终兜底。

## 4. 核心抽象设计

### 4.1 锁Key命名规范

```
锁Key格式：primetop:lock:{业务域}:{资源类型}:{资源标识}

示例：
primetop:lock:question:generate:{questionId}       # 题目生成
primetop:lock:mistake:collect:{userId}:{questionId} # 错题收录
primetop:lock:plan:adjust:{userId}                  # 学习计划调整
primetop:lock:membership:upgrade:{userId}           # 会员升级
primetop:lock:task:daily:{taskId}                   # 定时任务执行
primetop:lock:content:publish:{contentId}           # 内容发布
```

**命名规则：**
- 使用冒号 `:` 分隔层级
- 业务域对应微服务名或业务模块
- 资源标识使用业务主键（userId、questionId 等）
- 禁止使用动态拼接的非受控字符串（防 Key 爆炸）

### 4.2 锁超时时间参考表

| 场景分类 | 建议持有时间 | 建议等待时间 | 说明 |
|---------|------------|------------|------|
| 轻量操作（状态更新、标记） | 3s | 3s | 大多数 CRUD |
| 中等操作（AI调用编排、内容生成） | 15s | 5s | 涉及外部调用 |
| 重量操作（批量导入、报告生成） | 60s | 10s | 可考虑异步 |
| 定时任务（全量同步、数据归档） | 300s | 0s（非阻塞） | 必须防重入 |

### 4.3 核心接口定义

```java
/**
 * 分布式锁服务接口
 * 所有分布式锁操作统一通过此接口，禁止直接使用 Redisson 原生 API
 */
public interface DistributedLockService {

    /**
     * 执行带锁的操作（最常用方式 —— 模板方法模式）
     *
     * @param lockKey      锁的完整Key
     * @param waitTime     等待获取锁的最大时间
     * @param leaseTime    锁自动释放时间（-1 表示启用 watchdog 自动续期）
     * @param timeUnit     时间单位
     * @param action       获取锁后执行的业务逻辑
     * @param <T>          返回值类型
     * @return 业务执行结果
     * @throws LockAcquireException 获取锁失败
     * @throws LockExecutionException 业务执行异常
     */
    <T> T executeWithLock(String lockKey, long waitTime, long leaseTime,
                          TimeUnit timeUnit, Supplier<T> action);

    /**
     * 无返回值的带锁操作
     */
    default void executeWithLock(String lockKey, long waitTime, long leaseTime,
                                 TimeUnit timeUnit, Runnable action) {
        executeWithLock(lockKey, waitTime, leaseTime, timeUnit, () -> {
            action.run();
            return null;
        });
    }

    /**
     * 使用默认超时的带锁操作
     * 默认 waitTime=5s, leaseTime=-1(watchdog)
     */
    default <T> T executeWithLock(String lockKey, Supplier<T> action) {
        return executeWithLock(lockKey, 5, -1, TimeUnit.SECONDS, action);
    }

    default void executeWithLock(String lockKey, Runnable action) {
        executeWithLock(lockKey, 5, -1, TimeUnit.SECONDS, action);
    }

    /**
     * 尝试获取锁（非阻塞）
     * @return 获取成功返回锁句柄，失败返回 empty
     */
    Optional<LockHandle> tryAcquire(String lockKey, long leaseTime, TimeUnit timeUnit);

    /**
     * 读写锁 - 读操作
     */
    <T> T executeWithReadLock(String lockKey, long waitTime, long leaseTime,
                              TimeUnit timeUnit, Supplier<T> action);

    /**
     * 读写锁 - 写操作
     */
    <T> T executeWithWriteLock(String lockKey, long waitTime, long leaseTime,
                               TimeUnit timeUnit, Supplier<T> action);
}

/**
 * 锁句柄（AutoCloseable，支持 try-with-resources）
 */
public interface LockHandle extends AutoCloseable {
    String getLockKey();
    long getAcquiredAt();
    @Override
    void close(); // 释放锁
}
```

### 4.4 异常定义

```java
/**
 * 锁获取失败异常
 */
public class LockAcquireException extends RuntimeException {
    private final String lockKey;
    private final long waitTimeMs;

    public LockAcquireException(String lockKey, long waitTimeMs) {
        super(String.format("获取分布式锁失败: key=%s, waitTime=%dms", lockKey, waitTimeMs));
        this.lockKey = lockKey;
        this.waitTimeMs = waitTimeMs;
    }

    public LockAcquireException(String lockKey, long waitTimeMs, Throwable cause) {
        super(String.format("获取分布式锁异常: key=%s, waitTime=%dms", lockKey, waitTimeMs), cause);
        this.lockKey = lockKey;
        this.waitTimeMs = waitTimeMs;
    }
}

/**
 * 锁内业务执行异常
 */
public class LockExecutionException extends RuntimeException {
    private final String lockKey;

    public LockExecutionException(String lockKey, Throwable cause) {
        super(String.format("锁内业务执行异常: key=%s", lockKey), cause);
        this.lockKey = lockKey;
    }
}
```

### 4.5 核心实现

```java
@Slf4j
@Service
public class RedissonDistributedLockService implements DistributedLockService {

    private final RedissonClient redissonClient;
    private final LockMetricsCollector metricsCollector;

    public RedissonDistributedLockService(RedissonClient redissonClient,
                                          LockMetricsCollector metricsCollector) {
        this.redissonClient = redissonClient;
        this.metricsCollector = metricsCollector;
    }

    @Override
    public <T> T executeWithLock(String lockKey, long waitTime, long leaseTime,
                                 TimeUnit timeUnit, Supplier<T> action) {
        RLock lock = redissonClient.getLock(lockKey);
        long startTime = System.currentTimeMillis();
        boolean acquired = false;

        try {
            acquired = lock.tryLock(waitTime, leaseTime, timeUnit);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            metricsCollector.recordAcquireFailed(lockKey, "INTERRUPTED");
            throw new LockAcquireException(lockKey,
                    timeUnit.toMillis(waitTime), e);
        }

        if (!acquired) {
            long waited = System.currentTimeMillis() - startTime;
            metricsCollector.recordAcquireFailed(lockKey, "TIMEOUT");
            log.warn("分布式锁获取超时: key={}, waitMs={}", lockKey, waited);
            throw new LockAcquireException(lockKey, timeUnit.toMillis(waitTime));
        }

        long acquireCost = System.currentTimeMillis() - startTime;
        metricsCollector.recordAcquired(lockKey, acquireCost);

        try {
            T result = action.get();
            metricsCollector.recordSuccess(lockKey);
            return result;
        } catch (Exception e) {
            metricsCollector.recordExecutionFailed(lockKey);
            throw new LockExecutionException(lockKey, e);
        } finally {
            try {
                if (lock.isHeldByCurrentThread()) {
                    lock.unlock();
                }
            } catch (IllegalMonitorStateException e) {
                log.warn("锁已过期或被释放: key={}", lockKey, e);
            }
            long totalCost = System.currentTimeMillis() - startTime;
            metricsCollector.recordReleased(lockKey, totalCost);
        }
    }

    @Override
    public Optional<LockHandle> tryAcquire(String lockKey, long leaseTime,
                                           TimeUnit timeUnit) {
        RLock lock = redissonClient.getLock(lockKey);
        try {
            boolean acquired = lock.tryLock(0, leaseTime, timeUnit);
            if (acquired) {
                return Optional.of(new RedissonLockHandle(lockKey, lock));
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return Optional.empty();
    }

    @Override
    public <T> T executeWithReadLock(String lockKey, long waitTime, long leaseTime,
                                     TimeUnit timeUnit, Supplier<T> action) {
        RReadWriteLock rwLock = redissonClient.getReadWriteLock(lockKey);
        RLock readLock = rwLock.readLock();
        return executeWithRLock(readLock, lockKey + ":read", waitTime,
                leaseTime, timeUnit, action);
    }

    @Override
    public <T> T executeWithWriteLock(String lockKey, long waitTime, long leaseTime,
                                      TimeUnit timeUnit, Supplier<T> action) {
        RReadWriteLock rwLock = redissonClient.getReadWriteLock(lockKey);
        RLock writeLock = rwLock.writeLock();
        return executeWithRLock(writeLock, lockKey + ":write", waitTime,
                leaseTime, timeUnit, action);
    }

    private <T> T executeWithRLock(RLock lock, String metricKey,
                                   long waitTime, long leaseTime,
                                   TimeUnit timeUnit, Supplier<T> action) {
        long startTime = System.currentTimeMillis();
        boolean acquired;
        try {
            acquired = lock.tryLock(waitTime, leaseTime, timeUnit);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new LockAcquireException(metricKey,
                    timeUnit.toMillis(waitTime), e);
        }

        if (!acquired) {
            metricsCollector.recordAcquireFailed(metricKey, "TIMEOUT");
            throw new LockAcquireException(metricKey, timeUnit.toMillis(waitTime));
        }

        metricsCollector.recordAcquired(metricKey,
                System.currentTimeMillis() - startTime);

        try {
            T result = action.get();
            metricsCollector.recordSuccess(metricKey);
            return result;
        } catch (Exception e) {
            throw new LockExecutionException(metricKey, e);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }

    /**
     * Redisson 锁句柄实现
     */
    @RequiredArgsConstructor
    private class RedissonLockHandle implements LockHandle {
        private final String lockKey;
        private final RLock lock;
        private final long acquiredAt = System.currentTimeMillis();

        @Override
        public String getLockKey() { return lockKey; }

        @Override
        public long getAcquiredAt() { return acquiredAt; }

        @Override
        public void close() {
            try {
                if (lock.isHeldByCurrentThread()) {
                    lock.unlock();
                }
            } catch (IllegalMonitorStateException e) {
                log.warn("锁句柄释放时锁已失效: key={}", lockKey, e);
            }
        }
    }
}
```

## 5. PrimeTop 业务场景应用

### 5.1 场景一：定时任务防重入

**问题：** 多节点部署时，每日学习任务生成、数据归档等定时任务可能在多个节点同时触发。

```java
@Service
@Slf4j
public class DailyTaskGenerateJob {

    private final DistributedLockService lockService;
    private final TaskGenerateService taskGenerateService;

    private static final String LOCK_KEY = "primetop:lock:task:daily:generate";
    private static final long LEASE_TIME = 300; // 最多持有 5 分钟

    /**
     * 每天凌晨 6:00 执行，生成所有活跃用户的每日学习任务
     * Cron: 0 0 6 * * ?
     */
    @Scheduled(cron = "0 0 6 * * ?")
    public void generateDailyTasks() {
        // 非阻塞获取锁，获取不到说明其他节点在执行
        Optional<LockHandle> lockHandle = lockService.tryAcquire(
                LOCK_KEY, LEASE_TIME, TimeUnit.SECONDS);

        if (lockHandle.isEmpty()) {
            log.info("每日任务生成锁获取失败，可能其他节点正在执行");
            return;
        }

        try (LockHandle handle = lockHandle.get()) {
            log.info("开始生成每日学习任务");
            taskGenerateService.generateAllActiveUsersDailyTasks();
            log.info("每日学习任务生成完成");
        } catch (Exception e) {
            log.error("每日任务生成异常", e);
            // 上报告警
        }
    }
}
```

**关键点：**
- `tryAcquire` 非阻塞，不会阻塞节点线程
- 使用 `try-with-resources` 确保锁释放
- 300s 超时兜底，即使节点宕机也不会死锁

### 5.2 场景二：会员权益变更

**问题：** 用户升级/续费会员时，需防止并发请求导致权益重复发放或状态不一致。

```java
@Service
@Slf4j
public class MembershipUpgradeService {

    private final DistributedLockService lockService;
    private final MembershipRepository membershipRepo;
    private final OrderRepository orderRepo;
    private final BenefitGrantService benefitGrantService;

    /**
     * 处理会员升级
     * 使用 userId 作为锁粒度，同一用户的升级请求串行化
     */
    public MembershipUpgradeResult upgrade(Long userId, String orderNo,
                                           MembershipPlan targetPlan) {
        String lockKey = "primetop:lock:membership:upgrade:" + userId;

        return lockService.executeWithLock(lockKey, 5, 15, TimeUnit.SECONDS, () -> {
            // 1. 幂等校验：检查订单是否已处理
            Order order = orderRepo.findByOrderNo(orderNo)
                    .orElseThrow(() -> new BizException(ErrorCode.ORDER_NOT_FOUND));

            if (order.getStatus() == OrderStatus.COMPLETED) {
                log.info("订单已处理，跳过: orderNo={}", orderNo);
                return MembershipUpgradeResult.alreadyProcessed(orderNo);
            }

            // 2. 查询当前会员状态
            Membership current = membershipRepo.findByUserId(userId)
                    .orElseGet(() -> Membership.free(userId));

            // 3. 校验是否可升级（不可降级）
            if (current.getLevel().ordinal() >= targetPlan.getLevel().ordinal()) {
                throw new BizException(ErrorCode.MEMBERSHIP_CANNOT_DOWNGRADE);
            }

            // 4. 更新会员状态
            Membership upgraded = current.upgradeTo(targetPlan, order.getExpiredAt());
            membershipRepo.save(upgraded);

            // 5. 更新订单状态
            order.complete();
            orderRepo.save(order);

            // 6. 发放权益
            benefitGrantService.grantUpgradeBenefits(userId, targetPlan);

            log.info("会员升级成功: userId={}, plan={}, orderNo={}",
                    userId, targetPlan, orderNo);
            return MembershipUpgradeResult.success(upgraded);
        });
    }
}
```

**关键点：**
- 锁粒度精确到 userId，不同用户互不影响
- 锁内仍做幂等校验（订单状态检查），双重保障
- 15s 持有时间足够完成数据库操作 + 权益发放

### 5.3 场景三：错题收录去重

**问题：** 学生在快速答题时可能多次点击"加入错题本"，或同一题目被不同渠道重复收录。

```java
@Service
public class MistakeCollectService {

    private final DistributedLockService lockService;
    private final MistakeRecordRepository mistakeRepo;

    /**
     * 收录错题
     * 锁粒度: userId + questionId，同一用户同一题目不重复收录
     */
    public MistakeCollectResult collect(Long userId, Long questionId,
                                        MistakeSource source, String wrongAnswer) {
        String lockKey = String.format(
                "primetop:lock:mistake:collect:%d:%d", userId, questionId);

        return lockService.executeWithLock(lockKey, 3, 3, TimeUnit.SECONDS, () -> {
            // 检查是否已存在
            if (mistakeRepo.existsByUserIdAndQuestionId(userId, questionId)) {
                // 已存在则更新状态（如错误次数 +1）
                MistakeRecord existing = mistakeRepo
                        .findByUserIdAndQuestionId(userId, questionId)
                        .orElseThrow();
                existing.incrementErrorCount(source, wrongAnswer);
                existing.updateLastReviewedAt();
                mistakeRepo.save(existing);
                return MistakeCollectResult.updated(existing);
            }

            // 新增错题记录
            MistakeRecord record = MistakeRecord.builder()
                    .userId(userId)
                    .questionId(questionId)
                    .source(source)
                    .wrongAnswer(wrongAnswer)
                    .status(MistakeStatus.PENDING_REVIEW)
                    .errorCount(1)
                    .collectedAt(Instant.now())
                    .build();
            mistakeRepo.save(record);

            return MistakeCollectResult.created(record);
        });
    }
}
```

### 5.4 场景四：学习计划并发调整

**问题：** AI 推荐调整 + 用户手动调整 + 定时自动调整可能同时修改学习计划。

```java
@Service
public class StudyPlanAdjustService {

    private final DistributedLockService lockService;
    private final StudyPlanRepository planRepo;
    private final PlanAdjustHistoryRepository historyRepo;

    /**
     * 调整学习计划
     * 使用读写锁：多个读操作（查看计划）可并发，写操作（调整计划）互斥
     */
    public StudyPlan adjustPlan(Long userId, PlanAdjustRequest request,
                                String adjustSource) {
        String lockKey = "primetop:lock:plan:adjust:" + userId;

        return lockService.executeWithWriteLock(lockKey, 5, 10, TimeUnit.SECONDS, () -> {
            StudyPlan currentPlan = planRepo.findActiveByUserId(userId)
                    .orElseThrow(() -> new BizException(ErrorCode.PLAN_NOT_FOUND));

            // 记录调整历史
            PlanAdjustHistory history = PlanAdjustHistory.builder()
                    .userId(userId)
                    .planId(currentPlan.getId())
                    .adjustSource(adjustSource)
                    .snapshotBefore(currentPlan.toJsonSnapshot())
                    .reason(request.getReason())
                    .build();

            // 执行调整
            currentPlan.adjust(request);
            planRepo.save(currentPlan);

            // 保存调整后快照
            history.setSnapshotAfter(currentPlan.toJsonSnapshot());
            historyRepo.save(history);

            return currentPlan;
        });
    }

    /**
     * 查看当前学习计划（读锁，允许并发读取）
     */
    public StudyPlanView getCurrentPlan(Long userId) {

### 5.5 场景五：AI 题目生成防重复

**问题：** 智能组卷或同类题生成时，可能对同一题目并发触发多次 AI 生成。

```java
@Service
public class AIGenerationService {

    private final DistributedLockService lockService;
    private final QuestionGenerationTaskRepository taskRepo;
    private final AIModelService aiModelService;

    /**
     * AI 生成题目（带结果缓存）
     * 如果同一任务正在生成中，等待其结果而非重复调用 AI
     */
    public Question generateQuestion(GenerationSpec spec) {
        String lockKey = "primetop:lock:question:generate:" + spec.specHash();

        return lockService.executeWithLock(lockKey, 30, 30, TimeUnit.SECONDS, () -> {
            // 检查是否已有生成结果（其他线程可能刚完成）
            Optional<Question> existing = taskRepo.findCompletedBySpecHash(spec.specHash());
            if (existing.isPresent()) {
                log.info("题目已生成，直接复用: specHash={}", spec.specHash());
                return existing.get();
            }

            // 检查是否有正在进行的任务
            Optional<QuestionGenerationTask> running = taskRepo
                    .findRunningBySpecHash(spec.specHash());
            if (running.isPresent()) {
                // 等待任务完成（自旋或事件通知）
                return waitForCompletion(running.get(), 25_000);
            }

            // 创建任务并执行 AI 生成
            QuestionGenerationTask task = QuestionGenerationTask.running(spec);
            taskRepo.save(task);

            try {
                Question question = aiModelService.generateQuestion(spec);
                task.complete(question);
                taskRepo.save(task);
                return question;
            } catch (Exception e) {
                task.fail(e.getMessage());
                taskRepo.save(task);
                throw e;
            }
        });
    }

    private Question waitForCompletion(QuestionGenerationTask task, long timeoutMs) {
        long deadline = System.currentTimeMillis() + timeoutMs;
        while (System.currentTimeMillis() < deadline) {
            task = taskRepo.findById(task.getId()).orElseThrow();
            if (task.isCompleted()) {
                return task.getGeneratedQuestion();
            }
            if (task.isFailed()) {
                throw new BizException(ErrorCode.AI_GENERATION_FAILED);
            }
            try {
                Thread.sleep(500);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                throw new BizException(ErrorCode.OPERATION_INTERRUPTED);
            }
        }
        throw new BizException(ErrorCode.AI_GENERATION_TIMEOUT);
    }
}

                .register(meterRegistry);

    public void recordAcquired(String lockKey, long acquireCostMs) {

        acquireTimeSummary.record(acquireCostMs);

        meterRegistry.counter("primetop.lock.acquire.success.bydomain", tags)
                .increment();
    }

    public void recordAcquireFailed(String lockKey, String reason) {
        acquireFailedCounter.increment();
        Tags tags = Tags.of("lockKey", extractBizDomain(lockKey), "reason", reason);
        meterRegistry.counter("primetop.lock.acquire.failed.detail", tags)
                .increment();
    }

    public void recordSuccess(String lockKey) {
        // 成功完成（无异常）
    }

    public void recordExecutionFailed(String lockKey) {
        executionFailedCounter.increment();
    }

    public void recordReleased(String lockKey, long totalCostMs) {
        releaseCounter.increment();
        holdTimeSummary.record(totalCostMs);
    }

    private String extractBizDomain(String lockKey) {
        // primetop:lock:{domain}:{type}:{id} → 提取 domain
        String[] parts = lockKey.split(":");
        return parts.length >= 3 ? parts[2] : "unknown";
    }

## 7. 降级与容灾策略

### 7.1 Redis 不可用时的降级

```java
/**
 * 降级策略：Redis 不可用时回退到本地锁 + 数据库乐观锁
 */
@Service
@Slf4j
public class FallbackLockService implements DistributedLockService {

    private final DistributedLockService primary;   // Redis 实现
    private final DistributedLockService fallback;   // 本地锁实现
    private final CircuitBreaker circuitBreaker;

    public FallbackLockService(@Qualifier("redisson") DistributedLockService primary,
                               @Qualifier("local") DistributedLockService fallback) {
        this.primary = primary;
        this.fallback = fallback;
        this.circuitBreaker = CircuitBreaker.ofDefaults("distributedLock");
    }

    @Override
    public <T> T executeWithLock(String lockKey, long waitTime, long leaseTime,
                                 TimeUnit timeUnit, Supplier<T> action) {
        try {
            return circuitBreaker.executeSupplier(() ->
                    primary.executeWithLock(lockKey, waitTime, leaseTime, timeUnit, action));
        } catch (CallNotPermittedException e) {
            // 熔断器打开，Redis 可能不可用
            log.warn("分布式锁降级到本地锁: key={}, reason=circuit_breaker_open", lockKey);
            return fallback.executeWithLock(lockKey, waitTime, leaseTime, timeUnit, action);
        } catch (Exception e) {
            log.error("分布式锁异常，降级到本地锁: key={}", lockKey, e);
            return fallback.executeWithLock(lockKey, waitTime, leaseTime, timeUnit, action);
        }
    }

    // 其他方法同理...
}
```

### 7.2 本地锁降级实现

```java
/**
 * 本地锁实现（仅作降级方案，不保证跨节点互斥）
 * 搭配数据库乐观锁使用
 */
@Service("local")
public class LocalDistributedLockService implements DistributedLockService {

    private final ConcurrentMap<String, ReentrantLock> localLocks = new ConcurrentHashMap<>();

    @Override
    public <T> T executeWithLock(String lockKey, long waitTime, long leaseTime,
                                 TimeUnit timeUnit, Supplier<T> action) {
        ReentrantLock lock = localLocks.computeIfAbsent(lockKey,
                k -> new ReentrantLock());

        try {
            boolean acquired = lock.tryLock(waitTime, timeUnit);
            if (!acquired) {
                throw new LockAcquireException(lockKey, timeUnit.toMillis(waitTime));
            }
            return action.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new LockAcquireException(lockKey, timeUnit.toMillis(waitTime), e);
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
            // 清理未使用的锁对象，防止内存泄漏
            if (!lock.isLocked()) {
                localLocks.remove(lockKey, lock);
            }
        }
    }

    // tryAcquire、读写锁等方法省略，结构类似
}
```

## 8. 最佳实践与反模式

### 8.1 最佳实践清单

| # | 实践 | 说明 |
|---|------|------|
| 1 | **锁Key必须含业务标识** | 禁止使用全局锁Key，如 `primetop:lock:global` |
| 2 | **使用模板方法而非手动加解锁** | `executeWithLock` 自动处理异常释放 |
| 3 | **临界区内禁止外部调用** | 临界区内只做数据库操作，不调用外部 API |
| 4 | **设置合理的超时时间** | 参考 4.2 超时表，禁止无限等待 |
| 5 | **锁内操作必须幂等** | 锁只解决并发，不解决网络重试 |
| 6 | **优先使用 try-with-resources** | 手动加锁时必须用 try-finally 释放 |
| 7 | **读写分离场景用读写锁** | 读多写少时提升并发度 |
| 8 | **定时任务用非阻塞获取** | `tryAcquire` 而非 `executeWithLock` |

### 8.2 常见反模式

#### ❌ 反模式1：临界区内调用外部 API

```java
// 错误：AI 调用可能耗时 30s+，锁早就超时了
lockService.executeWithLock(lockKey, 5, 10, SECONDS, () -> {
    String aiResult = aiModelService.callModel(prompt); // 可能耗时很长！
    saveResult(aiResult);
});
```

**正确做法：** 先获取锁做状态标记，然后释放锁，再调用外部 API

```java
// 正确：锁内只做状态标记
String taskId = lockService.executeWithLock(lockKey, 5, 3, SECONDS, () -> {
    // 标记任务为进行中（防重入）
    GenerationTask task = taskRepo.findBySpecHash(specHash);
    if (task != null && task.isRunning()) {
        throw new BizException(ErrorCode.GENERATION_IN_PROGRESS);
    }
    task = new GenerationTask(specHash, RUNNING);
    taskRepo.save(task);
    return task.getId();
});

// 锁外调用 AI（不持有锁）
String aiResult = aiModelService.callModel(prompt);

// 更新结果（乐观锁兜底）
updateGenerationResult(taskId, aiResult);
```

#### ❌ 反模式2：嵌套锁

```java
// 错误：嵌套锁容易死锁
lockService.executeWithLock(lockA, () -> {
    lockService.executeWithLock(lockB, () -> {
        doSomething();
    });
});
```

**如果确实需要多资源互斥：** 使用 Redisson 的 `MultiLock`

```java
RLock lock1 = redissonClient.getLock(lockKeyA);
RLock lock2 = redissonClient.getLock(lockKeyB);
RLock multiLock = redissonClient.getMultiLock(lock1, lock2);

try {
    if (multiLock.tryLock(5, 15, SECONDS)) {
        try {
            doSomething();
        } finally {
            multiLock.unlock();
        }
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

#### ❌ 反模式3：锁粒度过粗

```java
// 错误：整个题库模块共用一把锁
String lockKey = "primetop:lock:question:global";
```

**正确：** 细化到具体资源

```java
// 正确：每个题目独立锁
String lockKey = "primetop:lock:question:generate:" + questionId;
```

### 8.3 锁使用 Checklist

每个需要分布式锁的业务场景，开发前需确认：

``n`` [ ] 1. 是否真的需要分布式锁？（参考 2.1 决策树）
- [ ] 2. 锁 Key 是否包含业务标识？是否够细粒度？
- [ ] 3. 是否使用了模板方法 `executeWithLock`？
- [ ] 4. 持有时间和等待时间是否合理？
- [ ] 5. 锁内是否有外部 API 调用？（应该没有）
- [ ] 6. 业务是否有幂等兜底？
- [ ] 7. 是否需要读写锁分离？
- [ ] 8. 是否有降级预案（乐观锁/MQ）？
- [ ] 9. 是否添加了监控埋点？（模板方法已内置）
- [ ] 10. 是否在 Code Review 中重点关注了锁的正确性？

| 正常获取锁 | tryLock 返回 true | 执行业务，正常释放 |
| 锁获取超时 | tryLock 返回 false | 抛出 LockAcquireException |
| 业务执行异常 | action 抛出异常 | 锁仍被释放，异常包装为 LockExecutionException |
| 锁已过期释放 | unlock 时锁已不存在 | 不抛异常，仅 warn 日志 |
| 线程中断 | tryLock 被中断 | 抛出 LockAcquireException，恢复中断标志 |
| 读写锁并发 | 多线程读 + 1 个写 | 读可并发，写互斥 |
| 并发竞态 | 100 线程竞争同一锁 | 串行化执行，无数据不一致 |
| 降级到本地锁 | Redis 不可用 | 自动降级，业务仍可执行 |

## 10. 运维指南

### 10.1 Redis 锁 Key 管理

```bash
# 查看当前所有活跃锁
redis-cli KEYS "primetop:lock:*"

# 查看特定锁的剩余 TTL
redis-cli TTL "primetop:lock:membership:upgrade:12345"

# 紧急手动释放锁（仅在确认安全后使用）
redis-cli DEL "primetop:lock:membership:upgrade:12345"

# 批量清理过期锁 Key（TTL <= 0 的已自动过期，无需手动清理）
# 注意：不要批量 DEL 活跃锁！
```

### 10.2 紧急操作手册

| 场景 | 操作 | 影响范围 |
|------|------|----------|
| 锁未释放（Redis Key 存在但业务已结束） | 1. 确认无节点持有该锁<br>2. `DEL` 该 Key | 仅影响该资源 |
| 大量锁获取超时 | 1. 检查 Redis 延迟和内存<br>2. 检查是否有长事务持有锁<br>3. 必要时重启问题节点 | 可能影响对应业务域 |
| Redis 集群故障 | 1. 自动降级到本地锁<br>2. 检查数据一致性<br>3. 恢复后验证分布式锁功能 | 全局 |
| 锁 Key 数量爆炸 | 1. 检查是否有动态拼接的非法 Key<br>2. 设置 Key 过期策略 | 内存相关 |

### 10.3 Redis 配置建议

```yaml
# Redis 配置（与分布式锁相关）
redis:
  maxmemory-policy: allkeys-lru  # 内存不足时 LRU 淘汰
  maxmemory: 4gb
  timeout: 300                    # 客户端空闲 300s 断开

# 注意事项：
# 1. 锁 Key 自带 TTL，不需要额外淘汰策略
# 2. 锁 Key 不应被 LRU 淘汰（TTL 内不会过期）
# 3. 监控 Redis 内存使用率，超过 80% 告警
```
