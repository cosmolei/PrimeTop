# 服务端-教材修订内容变更检测与平台内容影响评估引擎-详细设计

## 1. 模块概述

### 1.1 功能定位

本引擎负责在教材新版本发布时，自动完成以下核心任务：

1. **结构化对比**：对新旧版教材进行章节、知识点、考点的细粒度差异比对
2. **变更分类**：将差异归类为新增、删除、修改、调序、重命名等变更类型
3. **影响评估**：扫描全平台与旧版教材关联的所有内容（题目、课程、解析、考点梳理等），评估受影响范围
4. **任务生成**：自动生成内容更新工单，推送至内容运营团队

### 1.2 与现有模块的边界

| 现有模块 | 覆盖范围 | 本引擎差异 |
| --- | --- | --- |
| 教育内容版本管理与教材同步更新引擎 | 版本元数据管理、发布同步 | 不做内容级别的差异检测和影响分析 |
| 教材内容生命周期与版本管理引擎 | 内容从创建到下架的全生命周期 | 不处理版本间内容变更对比 |
| 服务端-教材版本间知识点映射与学生进度迁移引擎 | **跨出版社**版本间的知识点映射（如人教版↔苏教版） | 本引擎处理**同一出版社**新旧版次间的变更检测 |
| 服务端-教材课标对齐度分析与内容覆盖率统计服务 | 教材与课程标准的对齐度 | 不处理版次间的增量变更 |

### 1.3 设计目标

| 目标 | 指标 |
| --- | --- |
| 变更检测准确率 | 章节结构变更 ≥ 98%，知识点变更 ≥ 90% |
| 单教材对比耗时 | ≤ 5 分钟（一本完整教材约 200-400 页） |
| 影响评估扫描范围 | 覆盖全平台所有与该教材版本绑定的内容资源 |
| 影响报告生成耗时 | ≤ 15 分钟 |
| 自动任务生成覆盖率 | 高优先级变更（知识点删除/修改）自动生成任务 ≥ 95% |

### 1.4 核心使用场景

```
场景1：教材年度修订
人教版数学七年级上册 2024版 → 2025版
→ 自动检测新增/删除/修改的知识点
→ 评估平台已有题目、课程、解析的影响
→ 生成内容更新工单

场景2：课标改革导致教材改版
义务教育数学课程标准更新
→ 多家出版社同步修订
→ 批量检测所有受影响教材
→ 生成跨教材的影响评估报告

场景3：区域教材版本切换
某省份更换教材版本
→ 对比新旧版本的差异
→ 评估学生历史学习数据的影响
→ 协调学生进度迁移
```

## 4. 核心引擎设计

### 4.1 教材结构对比器 (StructureDiffComparator)

#### 4.1.1 算法设计

教材结构对比采用 **改进的树编辑距离 (Tree Edit Distance)** 算法，结合语义相似度进行节点匹配。

```
输入:
  oldTree: 旧版教材目录树 (Chapter → Section → Subsection)
  newTree: 新版教材目录树

步骤:
  1. 对两棵树进行层级展开，提取每个节点
  2. 计算节点间的语义相似度矩阵 (使用章节标题的编辑距离 + 语义向量余弦相似度)
  3. 使用动态规划求最优匹配 (匈牙利算法)
  4. 对匹配节点递归对比子节点
  5. 未匹配的旧节点 → REMOVED
  6. 未匹配的新节点 → ADDED
  7. 匹配但序号变化的节点 → REORDERED
  8. 匹配但标题变化的节点 → RENAMED 或 MODIFIED

输出:
  List<ChangeDetail> 结构变更列表
```

#### 4.1.2 语义相似度计算

```java
/**
 * 计算两个章节标题的相似度
 * 综合编辑距离和语义向量相似度
 *
 * @param title1 旧版标题
 * @param title2 新版标题
 * @return 相似度 [0, 1]
 */
public double calculateTitleSimilarity(String title1, String title2) {
    if (title1 == null || title2 == null) return 0.0;
    if (title1.equals(title2)) return 1.0;

    // 1. 编辑距离相似度 (权重 0.4)
    double editDistSim = calculateEditDistanceSimilarity(title1, title2);

    // 2. 语义向量余弦相似度 (权重 0.4)
    double semanticSim = calculateSemanticSimilarity(title1, title2);

    // 3. 关键词重合度 (权重 0.2)
    double keywordOverlap = calculateKeywordOverlap(title1, title2);

    return 0.4 * editDistSim + 0.4 * semanticSim + 0.2 * keywordOverlap;
}

/**
 * 匹配阈值判定
 */
private static final double MATCH_THRESHOLD = 0.75;

/**
 * 判定两个节点是否为同一实体
 */
public boolean isSameEntity(double similarity) {
    return similarity >= MATCH_THRESHOLD;
}
```

#### 4.1.3 树对比核心逻辑

```java
/**
 * 对比两棵教材目录树
 */
public List<ChangeDetail> diffChapterTrees(
        List<ChapterNode> oldChapters,
        List<ChapterNode> newChapters) {

    List<ChangeDetail> changes = new ArrayList<>();

    // 1. 构建相似度矩阵
    int oldSize = oldChapters.size();
    int newSize = newChapters.size();
    double[][] simMatrix = new double[oldSize][newSize];

    for (int i = 0; i < oldSize; i++) {
        for (int j = 0; j < newSize; j++) {
            simMatrix[i][j] = calculateChapterSimilarity(
                oldChapters.get(i), newChapters.get(j));
        }
    }

    // 2. 匈牙利算法求最优匹配
    int[] oldToNewMatch = hungarianAlgorithm.findMaxWeightMatching(simMatrix);

    // 3. 生成变更明细
    Set<Integer> matchedNew = new HashSet<>();

    for (int i = 0; i < oldSize; i++) {
        int j = oldToNewMatch[i];
        if (j >= 0 && simMatrix[i][j] >= MATCH_THRESHOLD) {
            // 匹配成功
            matchedNew.add(j);
            ChapterNode oldCh = oldChapters.get(i);
            ChapterNode newCh = newChapters.get(j);

            // 检查标题变更
            if (!oldCh.getTitle().equals(newCh.getTitle())) {
                changes.add(buildRenameChange(oldCh, newCh));
            }

            // 检查位置变更
            if (i != j) {
                changes.add(buildReorderChange(oldCh, newCh, i, j));
            }

            // 递归对比子章节
            changes.addAll(diffChapterTrees(
                oldCh.getChildren(), newCh.getChildren()));

            // 对比关联的知识点
            changes.addAll(diffKnowledgePoints(
                oldCh.getKnowledgePoints(),
                newCh.getKnowledgePoints()));

        } else {
            // 旧节点在新版中被删除
            changes.add(buildRemovedChange(oldChapters.get(i)));
        }
    }

    // 检查新增节点
    for (int j = 0; j < newSize; j++) {
        if (!matchedNew.contains(j)) {
            changes.add(buildAddedChange(newChapters.get(j)));
        }
    }

    return changes;
}
```

### 4.2 知识点对比器 (KnowledgeDiffComparator)

#### 4.2.1 对比策略

知识点对比比章节结构对比更复杂，因为知识点可能：
- 内容修改但名称不变
- 名称修改但内容不变
- 被拆分为多个知识点
- 多个知识点被合并为一个
- 从一个章节移动到另一个章节

```java
/**
 * 知识点对比核心逻辑
 */
public List<ChangeDetail> diffKnowledgePoints(
        List<KnowledgePoint> oldPoints,
        List<KnowledgePoint> newPoints) {

    List<ChangeDetail> changes = new ArrayList<>();

    // 1. 构建知识点相似度矩阵
    //    综合考虑：名称相似度 + 描述相似度 + 关联章节相似度
    double[][] simMatrix = buildKnowledgeSimMatrix(oldPoints, newPoints);

    // 2. 最优匹配
    int[] matches = hungarianAlgorithm.findMaxWeightMatching(simMatrix);

    // 3. 分类处理
    Set<Integer> matchedNew = new HashSet<>();
    Map<Integer, List<Integer>> potentialSplits = new HashMap<>(); // 旧知识点可能被拆分
    Map<Integer, List<Integer>> potentialMerges = new HashMap<>();  // 多个旧知识点可能被合并

    for (int i = 0; i < oldPoints.size(); i++) {
        int j = matches[i];
        if (j >= 0 && simMatrix[i][j] >= KNOWLEDGE_MATCH_THRESHOLD) {
            // 匹配成功 — 检查是否为修改
            matchedNew.add(j);
            KnowledgePoint oldKp = oldPoints.get(i);
            KnowledgePoint newKp = newPoints.get(j);

            if (!oldKp.getContent().equals(newKp.getContent())) {
                double contentSim = calculateContentSimilarity(
                    oldKp.getContent(), newKp.getContent());
                if (contentSim < 0.95) {
                    changes.add(buildModifiedChange(oldKp, newKp, contentSim));
                }
            }

            // 检查所属章节是否变化
            if (!oldKp.getChapterId().equals(newKp.getChapterId())) {
                changes.add(buildMoveChange(oldKp, newKp));
            }

        } else {
            // 检查是否被拆分：一个旧知识点匹配多个新知识点
            List<Integer> splitCandidates = findMultiMatches(
                i, simMatrix, KNOWLEDGE_WEAK_THRESHOLD);
            if (splitCandidates.size() > 1) {
                potentialSplits.put(i, splitCandidates);
                matchedNew.addAll(splitCandidates);
                changes.add(buildSplitChange(
                    oldPoints.get(i),
                    splitCandidates.stream().map(newPoints::get).toList()));
            }
        }
    }

    // 检查合并：多个旧知识点匹配同一个新知识点
    for (int j = 0; j < newPoints.size(); j++) {
        if (matchedNew.contains(j)) continue;
        List<Integer> mergeCandidates = new ArrayList<>();
        for (int i = 0; i < oldPoints.size(); i++) {
            if (matches[i] < 0 && simMatrix[i][j] >= KNOWLEDGE_WEAK_THRESHOLD) {
                mergeCandidates.add(i);
            }
        }
        if (mergeCandidates.size() > 1) {
            changes.add(buildMergeChange(
                mergeCandidates.stream().map(oldPoints::get).toList(),
                newPoints.get(j)));
            matchedNew.add(j);
        }
    }

    // 未匹配的旧知识点 → 删除
    for (int i = 0; i < oldPoints.size(); i++) {
        if (matches[i] < 0 && !potentialSplits.containsKey(i)) {
            changes.add(buildRemovedChange(oldPoints.get(i)));
        }
    }

    // 未匹配的新知识点 → 新增
    for (int j = 0; j < newPoints.size(); j++) {
        if (!matchedNew.contains(j)) {
            changes.add(buildAddedChange(newPoints.get(j)));
        }
    }

    return changes;
}

private static final double KNOWLEDGE_MATCH_THRESHOLD = 0.70;
private static final double KNOWLEDGE_WEAK_THRESHOLD = 0.50;

// 辅助方法实现说明：
// buildModifiedChange  — 生成 MODIFIED 变更，old_value/new_value 存知识点快照，similarity_score=内容相似度
// buildMoveChange      — 生成 REORDERED 变更（跨章节移动），metadata 记录 old_chapter_id/new_chapter_id
// findMultiMatches     — 在相似度矩阵第 i 行中找所有 ≥ weakThreshold 的列，用于拆分检测
// buildSplitChange     — 生成 SPLIT 变更，metadata.old_kp_id 指向被拆分的旧知识点
// buildMergeChange     — 生成 MERGED 变更，metadata.merged_from_kp_ids 记录被合并的旧知识点列表
// buildRemovedChange   — 生成 REMOVED 变更，target_id 为旧版实体 ID（新版无对应）
// buildAddedChange     — 生成 ADDED 变更，target_id 为新版实体 ID
}
```

#### 4.2.2 知识点相似度矩阵构建

```java
/**
 * 构建知识点相似度矩阵
 * 三因子加权：名称相似度 0.35 / 描述内容相似度 0.45 / 同章节归属加成 0.20
 */
public double[][] buildKnowledgeSimMatrix(
        List<KnowledgePoint> oldPoints,
        List<KnowledgePoint> newPoints) {
    int oldSize = oldPoints.size();
    int newSize = newPoints.size();
    double[][] matrix = new double[oldSize][newSize];

    for (int i = 0; i < oldSize; i++) {
        KnowledgePoint oldKp = oldPoints.get(i);
        for (int j = 0; j < newSize; j++) {
            KnowledgePoint newKp = newPoints.get(j);

            double nameSim = calculateTitleSimilarity(
                oldKp.getName(), newKp.getName());
            double contentSim = oldKp.getContent() == null ? 0.0
                : calculateContentSimilarity(oldKp.getContent(), newKp.getContent());
            double chapterBonus = oldKp.getChapterId().equals(newKp.getChapterId())
                ? 1.0 : 0.0;

            matrix[i][j] = 0.35 * nameSim + 0.45 * contentSim + 0.20 * chapterBonus;
        }
    }
    return matrix;
}
```

### 4.3 内容影响评估器 (ImpactAssessmentEngine)

#### 4.3.1 评估原则

影响评估以 `change_detail` 为输入，扫描全平台绑定了受影响实体的内容资源，逐条生成 `content_impact_record`。

**权威边界（R4）**：本引擎是"影响面"的 SSOT（哪些内容受影响、影响多严重、建议怎么处理），但不直接修改任何内容、不直接生成生产工单——工单调制委托《服务端-教育内容生产任务编排与产能智能调度引擎》的 `production_task`。

#### 4.3.2 影响等级判定规则

| 变更类别 | 目标类型 | 影响等级 | 建议动作 | 判定依据 |
| --- | --- | --- | --- | --- |
| REMOVED | KNOWLEDGE_POINT | CRITICAL | REMAP / DELETE | 知识点被删除，绑定该知识点的题目/解析将失效 |
| REMOVED | EXAM_POINT | CRITICAL | DELETE / REVIEW | 考点被删除，专题/冲刺内容需下架或重做 |
| MODIFIED | KNOWLEDGE_POINT | HIGH | UPDATE | 知识点内容实质修改（相似度 < 0.95），关联解析可能出错 |
| SPLIT / MERGED | KNOWLEDGE_POINT | HIGH | REMAP | 知识点拆分/合并，关联内容需重新映射 |
| REORDERED（跨章移动） | KNOWLEDGE_POINT | MEDIUM | UPDATE | 知识点换章，需更新章节归属 |
| RENAMED | CHAPTER / SECTION | MEDIUM | UPDATE | 章节改名，引用名称需同步 |
| REORDERED（章内调序） | CHAPTER / SECTION | LOW | UPDATE | 仅顺序变化 |
| ADDED | KNOWLEDGE_POINT | LOW | MANUAL_CHECK | 新增知识点，平台内容缺口的信号，转生产需求预测 |
| MODIFIED（措辞微调，相似度 ≥ 0.95） | 任意 | LOW | MANUAL_CHECK | 无实质影响，抽样人工确认即可 |

#### 4.3.3 内容资源扫描策略

```java
/**
 * 影响评估主流程
 * 输入：一条 change_detail
 * 输出：0..N 条 content_impact_record
 */
public List<ContentImpactRecord> assess(ChangeDetail change) {
    List<ContentImpactRecord> impacts = new ArrayList<>();

    // 1. 确定需要扫描的内容类型
    //    知识点删除/修改 → QUESTION / COURSE / ANALYSIS / LESSON / EXAM_PAPER
    //    考点删除/修改   → EXAM_PAPER / COURSE(专题) / NOTE
    //    章节结构变更    → COURSE / LESSON / QUESTION（按章节归属检索）
    List<ScanTarget> targets = resolveScanTargets(change);

    // 2. 分批扫描，单批 500 条，避免长事务与大内存占用
    for (ScanTarget target : targets) {
        long lastId = 0;
        while (true) {
            List<ContentRef> refs = contentQueryGateway
                .findByEntityId(target, lastId, 500);
            if (refs.isEmpty()) break;

            for (ContentRef ref : refs) {
                // 3. 幂等防重：同一 (change_detail_id, content_type, content_id) 仅一条活跃记录
                if (impactRecordRepository.existsActive(
                        change.getId(), ref.getContentType(), ref.getContentId())) {
                    continue;
                }
                impacts.add(buildImpactRecord(change, ref));
            }
            impactRecordRepository.batchInsert(impacts);
            impacts.clear();
            lastId = refs.get(refs.size() - 1).getId();
        }
    }
    return impacts;
}
```

### 4.5 更新任务生成器 (UpdateTaskGenerator)

#### 4.5.1 生成规则

```java
/**
 * 将 impact 记录按"内容聚合"转生产工单：
 * 同一 content_id 的多条 impact 合并为一个工单，避免重复派单；
 * 工单优先级 = min(impact_level.severity)（最严重的一条决定）。
 */
public List<ProductionTaskHandoff> generateTasks(Long revisionId) {
    List<ContentImpactRecord> pending = impactRecordRepository
        .findByRevisionIdAndStatus(revisionId, "PENDING");

    // 按内容聚合
    Map<ContentKey, List<ContentImpactRecord>> grouped = pending.stream()
        .collect(Collectors.groupingBy(r ->
            new ContentKey(r.getContentType(), r.getContentId())));

    return grouped.entrySet().stream().map(entry -> {
        ContentKey key = entry.getKey();
        List<ContentImpactRecord> group = entry.getValue();
        ImpactLevel level = group.stream()
            .map(ContentImpactRecord::getImpactLevel)
            .min(Comparator.comparingInt(ImpactLevel::getSeverity))
            .orElse(ImpactLevel.MEDIUM);

        return ProductionTaskHandoff.builder()
            .source("REVISION_DIFF")
            .sourceRef(revisionId.toString())
            .contentType(key.getContentType())
            .contentId(key.getContentId())
            .priority(level.toTaskPriority())   // CRITICAL→P1, HIGH→P2, MEDIUM→P3, LOW→P4
            .title(buildTaskTitle(key, group))
            .detailRefs(group.stream().map(ContentImpactRecord::getId).toList())
            .build();
    }).toList();
}
```

#### 4.5.2 防重复派单

- 幂等键：`(source='REVISION_DIFF', source_ref=revision_id, content_type, content_id)`，下游生产任务引擎以该组合键去重（R4）。
- 同一修订任务重复执行影响评估时，`existsActive` 检查 + 下游组合键双重防重，保证重复触发不产生重复工单。
- CRITICAL 影响在工单创建成功后，同步在管理后台站内信通知内容运营负责人。

## 7. 状态机与守卫

### 7.1 修订任务状态机

```
PENDING ──(worker抢占,CAS)──► RUNNING ──(diff全部完成)──► ANALYZING ──(报告生成完成)──► COMPLETED
   │                            │                                │
   │                            └──(任一环节不可恢复异常)───────► FAILED ──(retry)──► PENDING
   └──(创建即失败:版本不存在等参数错误)──► FAILED
```

### 7.2 diff 记录状态机

```
PENDING ──► RUNNING ──► COMPLETED
              │            │
              └──► FAILED  └──► SKIPPED（该维度不适用，如纯章节教材无考点层）
```

### 7.3 影响记录状态机

```
PENDING ──(assign)──► ASSIGNED ──(start)──► IN_PROGRESS ──(resolve)──► RESOLVED
                                                            │
                                                            └──(wont-fix)──► WONT_FIX
```

### 7.4 守卫规则

| 编号 | 规则 |
| --- | --- |
| G1 | 同一 (textbook_id, old_edition_id, new_edition_id) 仅允许一个非终态任务，DB 函数唯一索引强制（见 §8.1） |
| G2 | 状态迁移一律 CAS（UPDATE ... WHERE status = #{expected}），抢占失败即放弃本轮执行 |
| G3 | 影响记录全生命周期只允许本引擎与指派处理人写 status，生产任务引擎不得回写（R4 单向边界） |
| G4 | CRITICAL 级 impact 的 WONT_FIX 必须双人审批，审批记录写审计日志 |
| G5 | change_detail / impact_record 只增不删；评估重跑产生新记录，旧记录保留供审计 |
| G6 | 教材版本元数据（edition 存在性、生效状态）以版本同步引擎为 SSOT，本引擎只读校验，不本地冗余状态 |
| G7 | REMAP 类建议不得由本引擎直接执行知识点重映射——handoff 委托跨版本映射引擎（R2） |
| G8 | 报告生成失败不阻塞任务进入 COMPLETED，report_url 允许为空并在监控中告警（报告可重生成） |
| G9 | 本引擎全部写操作走 Outbox 同事务，禁止跨服务同步调用（扫描查询除外） |
| G10 | 触发源为 EXTERNAL 时校验事件签名，防伪造教材发布事件刷任务 |
| G11 | 扫描内容资源只读，严禁在评估流程中写任何下游业务表 |
| G12 | impact 指派/解决接口做教材-运营数据范围校验（多租户/行级权限委托统一数据权限框架） |
| G13 | 任务重试清空 error_detail 前必须保留上一次失败快照到 error_history（JSON 列追加） |
| G14 | 定时巡检批量建任务单批 ≤ 20，防课标改版季瞬时风暴 |

## 8. 幂等与并发

### 8.1 幂等机制总表

| 场景 | 幂等键 | 机制 |
| --- | --- | --- |
| 创建对比任务 | (textbook_id, old_edition_id, new_edition_id) | DB 函数唯一索引，冲突返回已存在任务 |
| 事件触发 NotifyEditionPublished | event_id | Redis SETNX 24h + DB 去重表双保险 |
| worker 抢占 | revision.id + status 前置条件 | CAS 抢占，同一时刻仅一个执行器 |
| 影响记录生成 | (change_detail_id, content_type, content_id) | existsActive 检查 + 部分唯一索引 |
| 工单 handoff | (source, source_ref, content_type, content_id) | 下游生产任务引擎组合键去重（R4） |
| resolve / wont-fix | impact.id + status 前置条件 | CAS；重复提交返回首次结果 |

```sql
-- G1 函数唯一索引：非终态任务唯一（终态释放槽位，允许对同版本对再次发起对比）
ALTER TABLE textbook_revision
  ADD UNIQUE KEY uk_active_revision
  (textbook_id, old_edition_id, new_edition_id,
   (IF(status IN ('COMPLETED','FAILED'), NULL, status)));

-- 影响记录活跃唯一索引
ALTER TABLE content_impact_record
  ADD UNIQUE KEY uk_active_impact
  (change_detail_id, content_type, content_id,
   (IF(status IN ('RESOLVED','WONT_FIX'), NULL, status)));

-- 任务乐观锁
ALTER TABLE textbook_revision ADD COLUMN version INT NOT NULL DEFAULT 0 COMMENT '乐观锁';
```

### 8.2 并发场景裁决

1. **手动创建 vs 定时巡检并发**：唯一索引裁决，后到请求返回已有任务（duplicate=true）。
2. **重试 vs 正在执行**：retry 仅 FAILED 可发起，CAS 抢占失败的 worker 直接退出。
3. **评估中重复触发评估**：existsActive 幂等检查吞没重复；已完成部分不再生成。
4. **resolve 与 wont-fix 并发**：先到者胜，后到者因状态前置条件不满足返回 53506。
5. **报告生成与详情查询并发**：report_url 为空时详情接口返回 reportStatus=GENERATING，前端轮询。

## 9. 事件设计（Outbox）

### 9.1 revision_outbox 表

```sql
CREATE TABLE revision_outbox (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_id        VARCHAR(64) NOT NULL COMMENT '事件ID，幂等键',
    event_type      VARCHAR(64) NOT NULL COMMENT '事件类型',
    revision_id     BIGINT NOT NULL,
    payload         JSON NOT NULL,
    status          VARCHAR(16) NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/SENT/FAILED',
    retry_count     INT NOT NULL DEFAULT 0,
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    sent_at         DATETIME,
    UNIQUE KEY uk_event (event_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='教材修订域Outbox';
```

所有事件与业务表写入同事务；Relay 异步投递，失败指数退避（2^n 分钟，上限 30 分钟，8 次后转死信并 P2 告警）。

### 9.2 发布事件与消费方矩阵

| 事件 | 触发时机 | 关键载荷 | 消费方 | 消费方幂等键 |
| --- | --- | --- | --- | --- |
| revision.completed | 任务 COMPLETED | revision_id, textbook_id, old/new_edition_id, 变更统计 | 版本同步引擎（刷新版本对齐度/教材内容管理后台） | event_id |
| revision.failed | 任务 FAILED | revision_id, error_code, error_detail（脱敏） | 管理后台告警中心 | event_id |
| impact.assigned | impact 指派 | impact_id, assignee_id, impact_level | 管理后台站内信/通知服务 | event_id |
| impact.resolved | impact 解决 | impact_id, content_type, content_id, resolution_note | 审计日志服务、运营看板（处理时效统计） | event_id |
| remap.handoff.created | 产生 REMAP 建议 | revision_id, old_kp_id, candidate_new_kp_ids, similarity | 跨版本映射引擎（创建映射候选） | handoff_id |
| task.handoff.created | 产生工单 | revision_id, content_type, content_id, priority | 生产任务编排引擎（建 production_task） | handoff_id（组合键去重 R4） |
| revision.report.ready | 报告上传 OSS 完成 | revision_id, report_url | 管理后台通知发起人 | event_id |

### 9.3 上游订阅

| 来源事件 | 消费动作 |
| --- | --- |
| content.events: textbook.edition.published（版本同步引擎） | NotifyEditionPublished → 校验后自动建任务（trigger_source=EXTERNAL，校验签名 G10） |

### 9.4 对账

每日 04:40 对账任务：`textbook_revision` 终态任务数 = Outbox 中 revision.completed + revision.failed 事件数；偏差 > 0 即告警并补发缺失事件（幂等键防重复投递）。

## 11. 降级矩阵

| 编号 | 故障场景 | 降级策略 | 红线 |
| --- | --- | --- | --- |
| D1 | 语义向量服务不可用 | 标题相似度退化为编辑距离+关键词重合两因子（阈值上调至 0.80） | 评估可以继续，准确率下降须在报告中标注 degraded |
| D2 | 某个内容服务扫描超时 | 该 content_type 跳过并标记 partial=true，任务照常完成 | 不得将整个任务置 FAILED |
| D3 | OSS 上传失败 | report_url 留空，告警，提供管理端手动重新生成入口 | 不得阻塞 COMPLETED（G8） |
| D4 | 事件总线不可用 | Outbox 堆积，恢复后按幂等键补投 | 事件不得丢失（对账兜底） |
| D5 | 下游生产任务引擎不可用 | handoff 保留在 Outbox 重试，8 次后进死信队列并人工介入 | 不得直接写 production_task 表 |
| D6 | DB 只读/主从切换 | 全部写接口返回 53500，读接口走从库 | 评估 worker 暂停而非报错继续 |
| D7 | 定时巡检过载 | 单批上限 20 本（G14），超出顺延 | 不得跳过幂等直接建任务 |
| D8 | AI 辅助分析接口超时 | ai_analysis 字段留空，不影响变更检测主结果 | AI 分析为增强项，禁止阻塞主链路 |
| D9 | Redis 不可用 | event_id 去重退化为 DB 唯一键单保险 | 不得重复消费产生重复任务 |
| D10 | 匈牙利算法超大矩阵（>2000×2000） | 先按章分块再块内匹配，避免 O(n³) 失控 | 不得因此超时杀任务，须分块完成 |

| # | 场景 | 预期 |

| 1 | 手动创建对比任务 | 返回 revisionId，状态 PENDING→RUNNING→ANALYZING→COMPLETED |

| 13 | 报告下载 | 302 跳转 OSS 签名 URL，10 分钟后链接失效 |
| 14 | CRITICAL wont-fix 未审批 | 53512 拒绝；双人审批后成功 |
| 15 | retry 失败任务 | CAS 抢占成功，error_history 保留上次失败快照（G13） |
| 16 | 重复 resolve | 幂等返回首次结果，不报错 |
