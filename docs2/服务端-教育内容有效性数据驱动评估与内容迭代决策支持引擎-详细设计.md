# 服务端-教育内容有效性数据驱动评估与内容迭代决策支持引擎-详细设计

## 1. 模块概述

### 1.1 功能定位

教育内容有效性数据驱动评估引擎（Content Effectiveness Evaluation & Decision Engine，简称 CEE）是 PrimeTop 内容运营体系的核心分析中枢。与已有的「教育内容质量自动评估」模块不同——后者关注 **内容本身的静态质量**（格式是否规范、知识点是否准确、语言是否通顺），本引擎聚焦于 **内容投放后的实际效果**：

- 学生看完这个知识点讲解后，相关题目正确率提升了多少？
- 这套微课视频的完播率是多少？在哪个时间点集中流失？
- 哪些内容的消费显著推动了会员转化？
- 哪些内容长期无人问津，应该下线或重制？

本引擎从 **内容视角**（而非用户视角）出发，建立"内容曝光 → 用户消费 → 学习行为变化 → 业务价值产出"的全链路评估闭环，为内容团队的生产排期、迭代优化、上下架决策提供量化依据。

### 1.2 与已有模块的边界

| 已有模块 | 关注点 | 本模块差异 |
| --- | --- | --- |
| 教育内容质量自动评估与低质内容智能检测 | AI 对内容本身进行格式/准确性/适龄性评分 | 本模块基于 **真实用户消费数据** 评估，而非内容本身的静态属性 |
| 学习效果量化追踪与教育价值归因分析 | 追踪 **用户** 的学习效果和归因 | 本模块追踪 **内容** 的效果，回答"这个内容对多少学生有效" |
| 练习答题行为数据采集与学习过程分析引擎 | 采集和分析 **答题行为** | 本模块关联内容消费到答题效果变化 |
| 管理后台数据分析看板与运营驾驶舱服务 | 全局运营数据可视化 | 本模块提供 **内容维度的深度分析引擎**，为看板提供数据源 |
| 教学内容用户纠错反馈与内容质量持续迭代引擎 | 基于 **用户纠错反馈** 迭代内容 | 本模块基于 **全量消费行为数据** 评估，覆盖无反馈提交的沉默大多数 |

### 1.3 核心能力总览

```
┌─────────────────────────────────────────────────────────────┐
│                  内容有效性评估引擎 (CEE)                      │
├─────────────┬──────────────┬──────────────┬─────────────────┤
│  数据采集层  │  效果分析层    │  决策支持层    │   服务输出层     │
├─────────────┼──────────────┼──────────────┼─────────────────┤
│ 消费事件追踪 │ 内容吸引力评分│ 内容ROI分析   │ RESTful API     │
│ 学习增量度量 │ 内容理解度评分│ 内容缺口检测  │ GraphQL 查询    │

│ 外部数据接入 │ 内容转化评分  │ 生产排期建议  │ 批量报告导出     │
└─────────────┴──────────────┴──────────────┴─────────────────┘
```

## 2. 核心数据模型

### 2.1 内容消费事件表 `content_consumption_events`

记录每次用户与内容的交互行为，是所有效果分析的基础数据。

```sql
CREATE TABLE content_consumption_events (
    id              BIGINT       PRIMARY KEY AUTO_INCREMENT,
    event_id        VARCHAR(64)  NOT NULL COMMENT '事件唯一ID（防重）',
    user_id         BIGINT       NOT NULL COMMENT '用户ID',
    content_id      BIGINT       NOT NULL COMMENT '内容ID',
    content_type    VARCHAR(32)  NOT NULL COMMENT '内容类型: LESSON/EXERCISE/EXPLANATION/VIDEO/AUDIO/FLASHCARD/MICRO_COURSE',
    subject_code    VARCHAR(16)  NOT NULL COMMENT '学科编码',
    chapter_id      BIGINT       NULL     COMMENT '章节ID',
    knowledge_point_ids JSON     NULL     COMMENT '关联知识点ID列表',
    
    -- 消费行为字段
    event_type      VARCHAR(32)  NOT NULL COMMENT 'VIEW/START/PROGRESS/COMPLETE/ABANDON/REPLAY/BOOKMARK/SHARE',
    progress_pct    DECIMAL(5,2) NULL     COMMENT '消费进度百分比 0-100',
    duration_ms     INT          NULL     COMMENT '本次消费停留时长(毫秒)',
    total_duration_ms INT        NULL     COMMENT '该内容累计消费时长(毫秒)',
    replay_count    INT          DEFAULT 0 COMMENT '重播次数',
    abandon_point   VARCHAR(64)  NULL     COMMENT '放弃位置标记(如视频时间点/章节段落号)',
    
    -- 上下文字段
    source          VARCHAR(32)  NULL     COMMENT '来源: RECOMMEND/SEARCH/CHAPTER/ERROR_REVIEW/PLAN/AI_SUGGEST',
    session_id      VARCHAR(64)  NULL     COMMENT '学习会话ID',
    device_type     VARCHAR(16)  NULL     COMMENT '设备类型',
    app_version     VARCHAR(32)  NULL     COMMENT 'APP版本',
    
    -- 效果标记字段（异步回填）
    has_assessment  TINYINT      DEFAULT 0 COMMENT '是否有后续测评 0/1',
    assessment_score_delta DECIMAL(5,2) NULL COMMENT '消费前后测评得分变化',
    assessment_time_delta INT   NULL     COMMENT '消费后到测评的时间间隔(秒)',
    
    created_at      DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    
    UNIQUE KEY uk_event_id (event_id),
    KEY idx_user_content (user_id, content_id),
    KEY idx_content_type_date (content_id, content_type, created_at),
    KEY idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='内容消费事件表';
```

**分表策略（v1.1 修正 F1）**：按月水平分表 `content_consumption_events_YYYYMM` 再按 content_id hash 16 桶；MySQL 仅保留 3 个月热数据（效果回填窗口最长 7 天 + 对账重算窗口 30 天 + 冗余），全量事件经 Kafka 同步 ClickHouse 保留 13 个月，超期转 OSS Parquet 冷归档（G14）。v1.0 原定 MySQL 保留 13 个月在 DAU 50 万（日 750 万事件）下约 39 亿行不可行。

## 3. 效果评估指标体系

### 3.1 指标分层架构

```
                    ┌─────────────────┐
                    │  综合有效性评分  │  overall_cee_score (0-100)
                    │   一级指标       │
                    └────────┬────────┘
           ┌───────────────┼───────────────┐
     ┌─────┴─────┐   ┌─────┴─────┐   ┌─────┴─────┐   ┌──────────┐
     │ 吸引力评分 │   │ 理解促进  │   │ 记忆留存  │   │ 转化贡献  │
     │  二级指标  │   │  二级指标  │   │  二级指标  │   │  二级指标  │
     └─────┬─────┘   └─────┬─────┘   └─────┬─────┘   └─────┬────┘
           │                │                │                │
      三级原子指标      三级原子指标      三级原子指标      三级原子指标
```

### 3.2 详细指标定义

#### 3.2.1 吸引力评分（Attractiveness Score）

衡量内容吸引用户消费的能力。

| 三级指标 | 计算方式 | 权重 |
| --- | --- | --- |
| 消费转化率 | 消费启动数 / 曝光数 | 0.30 |
| 完播/完成率 | 完成消费数 / 消费启动数 | 0.25 |
| 均消费时长比 | 实际平均时长 / 预期消费时长 | 0.20 |
| 重播率 | 有重播行为用户数 / 消费用户数 | 0.10 |
| 分享率 | 分享次数 / 消费用户数 | 0.10 |
| 收藏率 | 收藏次数 / 消费用户数 | 0.05 |

**计算公式**：

```text
attractiveness_score = (
    normalize(consumption_conversion_rate) * 0.30 +
    normalize(completion_rate) * 0.25 +
    normalize(duration_ratio) * 0.20 +
    normalize(replay_rate) * 0.10 +
    normalize(share_rate) * 0.10 +
    normalize(favorite_rate) * 0.05
) * 100
```

`normalize()` 采用 **相对基线法**（v1.1 修正 F3）：`min(value / baseline, 1.0)`，基线取同类内容（同类型+同学科+同年级）近 90 天该指标的 P75 分位数（计算与双缓冲切换见 §4.7）；cohort 样本 < 30 时回退全局基线（G12）。达到同类 P75 即得满分 1.0，超过不再累加。

#### 3.2.2 理解促进评分（Comprehension Score）

衡量内容对学生理解知识点的帮助程度。

| 三级指标 | 计算方式 | 权重 |
| --- | --- | --- |
| 平均测评增量 | 消费后测评得分 - 消费前测评得分 | 0.35 |
| 正向提升比例 | 得分提升>5分人数 / 总测评人数 | 0.25 |
| 知识点掌握度增量 | 消费后掌握度 - 消费前掌握度 | 0.25 |
| 同类题正确率变化 | 消费后同类题正确率 - 消费前 | 0.15 |

**前置条件**：需要有足够的样本量（≥30 人同时有消费前和消费后测评数据）。

#### 3.2.3 记忆留存评分（Retention Score）

衡量内容帮助学生长期记忆的效果。

| 三级指标 | 计算方式 | 权重 |
| --- | --- | --- |
| 7日复访率 | 7日内重新消费/复习该内容的用户比例 | 0.30 |
| 14日知识保持率 | 14日后同类题正确率 / 首次正确率 | 0.35 |
| 错题重做通过率 | 关联错题在该内容消费后重做通过的比例 | 0.20 |
| 间隔复习完成率 | 消费该内容后触发的复习任务完成率 | 0.15 |

#### 3.2.4 转化贡献评分（Conversion Score）

衡量内容对业务价值的贡献。

| 三级指标 | 计算方式 | 权重 |
| --- | --- | --- |
| 会员转化率 | 消费后7日会员转化人数 / 消费人数 | 0.35 |
| 正面反馈比 | (点赞数 - 差评数) / 总反馈数 | 0.25 |
| 推荐触发率 | 被用户主动推荐/分享给其他用户的次数 | 0.20 |
| 续费提升度 | 消费组续费率 - 未消费对照组续费率（lift，v1.1 修正 F4：原“续费用户中消费过该内容的比例”无因果方向） | 0.20 |

### 3.3 综合有效性评分

```text
overall_cee_score = 
    attractiveness_score * 0.20 +
    comprehension_score * 0.35 +
    retention_score     * 0.25 +
    conversion_score    * 0.20
```

> 理解促进评分权重最高（0.35），因为教育产品的核心价值在于学习效果。

### 3.4 评分等级与建议

| CEE Score | 等级 | 含义 | 建议动作 |
| --- | --- | --- | --- |
| 85-100 | S | 卓越效果 | 标杆内容，推荐为参考模板，加大分发 |
| 70-84 | A | 优秀效果 | 继续保持，可考虑作为推荐素材 |
| 55-69 | B | 中等效果 | 局部优化（提升完播率/补充练习等） |
| 40-54 | C | 偏弱效果 | 需要修订，分析薄弱维度并改进 |
| 0-39 | D | 低效内容 | 建议重制或下线 |

## 4. 核心流程设计

### 4.1 消费事件采集流程

```
客户端                           服务端                        数据层
  │                                │                             │
  │  1. 用户消费内容               │                             │
  │  (观看视频/阅读讲解/做练习)     │                             │
  │                                │                             │
  │  2. 上报消费事件               │                             │
```

**关键设计要点**：

1. **事件批量上报**：客户端每 30 秒或离开内容页面时批量上报消费事件，减少请求频率
2. **幂等保障**：`event_id` 由客户端生成（`userId + contentId + timestamp + random`），服务端去重

4. **效果回填**：测评得分变化通过异步任务关联回填，不阻塞主链路

```java
            metrics.setAvgKnowledgeMasteryDelta(BigDecimal.valueOf(avgMasteryDelta));
            metrics.setAssessmentSampleSize(pairs.size());
        } else {
            metrics.setDataQualityFlag("LOW_SAMPLE");
        }

        metrics.setFavoriteCount(bs.getFavoriteCount());
        metrics.setFeedbackCount(bs.getFeedbackCount());
```

> **v1.1 口径修正（缺陷 F2）**：`abandonment_rate` 废弃 v1.0 的 `1 - completion_rate` 兜底公式，统一为 **`ABANDON 事件数 / 消费启动数`**。三者关系：`completion_rate + abandonment_rate + in_progress_ratio ≈ 1`（in_progress = 启动后既无 COMPLETE 也无 ABANDON 的占比，通常为跨天暂停会话）。原公式会把“暂停未完”误计为放弃，导致短内容放弃率虚高。

```java
/**
 * 四维评分合成任务
 * 读取 Step2 产出的日指标 + §4.7 基线快照，合成 attractiveness/comprehension/
 * retention/conversion 四维评分与 overall_cee_score。
 */
@Scheduled(cron = "0 30 2 * * ?")
public void composeEffectivenessScores() {
    LocalDate statDate = LocalDate.now().minusDays(1);
    BaselineSnapshot baseline = baselineService.loadActiveSnapshot(); // 双缓冲快照，见 §4.7

    List<ContentEffectivenessMetrics> daily = metricsMapper.findByDate(statDate);

    for (ContentEffectivenessMetrics m : daily) {
        // G9：刷量内容不评分（保留原始指标供人工核查）
        if ("ANOMALY".equals(m.getDataQualityFlag())) {
            m.setOverallCeeScore(null);
            continue;
        }

        double attr = composeAttractiveness(m, baseline); // §3.2.1 六项三级指标
        double conv = composeConversion(m, baseline);      // §3.2.4
        Double comp = composeComprehension(m, baseline);   // §3.2.2，LOW_SAMPLE 返回 null
        Double ret  = composeRetention(m, baseline);       // §3.2.3

        // 缺失维度权重再归一化：可用维度权重 / Σ可用权重（G3）
        Map<String, Double> dims = new LinkedHashMap<>();
        dims.put("ATTR", attr);
        if (comp != null) dims.put("COMP", comp);
        if (ret  != null) dims.put("RET",  ret);
        dims.put("CONV", conv);

        if (dims.size() < 2) {
            // 证据不足：置空防“0 分误伤”，连续 7 日置空转 LOW_SAMPLE 并停发决策（G3）
            m.setOverallCeeScore(null);
            m.setDataQualityFlag("LOW_SAMPLE");
        } else {
            double wSum = dims.keySet().stream().mapToDouble(DIM_WEIGHT::get).sum();
            double overall = dims.entrySet().stream()
                .mapToDouble(e -> e.getValue() * DIM_WEIGHT.get(e.getKey()) / wSum)
                .sum();
            m.setOverallCeeScore(BigDecimal.valueOf(overall).setScale(2, RoundingMode.HALF_UP));
            m.setAttractivenessScore(scale100(attr));
            if (comp != null) m.setComprehensionScore(scale100(comp));
            if (ret  != null) m.setRetentionScore(scale100(ret));
            m.setConversionScore(scale100(conv));
        }
        m.setPerformanceTrend(calcTrend(m.getContentId(), m.getOverallCeeScore()));
    }
    metricsMapper.batchUpdateScores(daily);
    log.info("Step3 评分合成完成: date={}, scored={}", statDate, daily.size());
}

/** 相对基线归一化：value / 同类 P75，封顶 1.0（v1.1 修正 F3，替代 Min-Max 描述） */
static double normalize(double value, double p75Baseline) {
    if (p75Baseline <= 0) return value > 0 ? 1.0 : 0.0;
    return Math.min(value / p75Baseline, 1.0);
}

/** 趋势判定：近 7 日滚动均值 vs 前 7 日，±5% 阈值；上线不足 7 天标记 NEW */
private String calcTrend(Long contentId, Double todayScore) {
    TrendWindow tw = metricsMapper.loadRollingWindow(contentId, 14);
    if (tw.getValidDays() < 7) return "NEW";
    double delta = (tw.getLast7Avg() - tw.getPrev7Avg()) / Math.max(tw.getPrev7Avg(), 1e-6);
    if (delta > 0.05)  return "UP";
    if (delta < -0.05) return "DOWN";
    return "STABLE";
}
```

**权重再归一化说明**：当理解促进（COMP）因样本不足缺失时，其 0.35 权重按剩余维度原权重比例分摊（ATTR 0.20→0.308、RET 0.25→0.385、CONV 0.20→0.308）。该策略仅允许 **单向降级**：日级评分可缺维，但 §3.4 等级判定与 §4.2 Step4 自动决策必须使用 **完整四维** 的 14 天滚动均值（G3），缺维日不参与等级判定。

**显著性判定**（比例类主指标，双样本双侧检验）：

```text
z = (p_variant - p_control) / sqrt( p_pool × (1 - p_pool) × (1/n₁ + 1/n₂) )
p_pool = (x₁ + x₂) / (n₁ + n₂)
|z| > z_{α/2}（默认 α=0.05 → 1.96）→ 显著；符号决定方向
```

- 均值类指标（如 avg_score_delta）使用 Welch t 检验（不假设方差齐性）。
- `success_metrics[0]` 为主指标，其余为 **护栏指标**（guardrail）：变体主指标获胜但任一护栏指标劣化超阈值（默认 -5%），判 `WIN_WITH_GUARDRAIL_BREACH`，只允许人工 finalize。
- 不满足 G5（样本量不足或不显著）时 finalize 被拒绝（错误码 58123），结果记录为 INCONCLUSIVE，`winning_variant = NULL`。

要点：
1. 决策 DONE 必须携带 `executed_ref`（内容服务/题库操作凭证）或 `resolution_notes`（拒绝理由）之一（G7）。
2. 内容新版本上线后，该内容的 CEE 观察窗口重置（14 天重新累计），且变体评分与新版本评分在指标表以 `calculation_version` 区分，不混算。
3. 回看任务：resolve 后 +7 天自动比较 overall 与 trigger_metrics 快照，改善 < +3 分的 REVISE/REPRODUCE 决策生成二次复盘工单（每内容最多 2 次，防无限循环）。

### 4.7 归一化基线计算（每日 00:30）

```sql
CREATE TABLE content_score_baselines (
    id            BIGINT       PRIMARY KEY AUTO_INCREMENT,
    cohort_key    VARCHAR(64)  NOT NULL COMMENT '组合键 contentType:subject:grade；回退键 GLOBAL:type',
    metric_name   VARCHAR(64)  NOT NULL COMMENT '三级指标名（completion_rate/share_rate 等）',
    p75_value     DECIMAL(10,4) NOT NULL,
    sample_size   INT          NOT NULL COMMENT '参与计算的同类内容数',
    window_days   INT          NOT NULL DEFAULT 90,
    snapshot_date DATE         NOT NULL,
    is_active     TINYINT      DEFAULT 0 COMMENT '当前生效快照（同 cohort 仅一份，双缓冲切换）',
    created_at    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_cohort_metric_date (cohort_key, metric_name, snapshot_date),
    KEY idx_active (is_active, snapshot_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='评分归一化基线快照';
```

- 队列（cohort）= 同 contentType + subject + grade，统计近 90 天有消费内容各三级指标的 P75。
- **G12**：cohort 内容数 < 30 时回退 `GLOBAL:{contentType}` 全局基线，`baseline_source` 记录回退标记（回退占比 > 20% 触发 M8 告警）。
- 双缓冲切换：新快照全量写入 `is_active=0` → 校验行数 → 单事务翻转 `is_active`，评分任务只读 active 快照，杜绝半更新状态。

### 4.8 刷量防护与异常检测

| 层级 | 机制 | 说明 |
| --- | --- | --- |
| L1 事件层 | `event_id` 唯一键 + 同 user 同 content 10s 内重复 START 折叠 | 原始事件保留，折叠仅影响聚合口径 |
| L2 用户层 | 风控标记用户剔除 | 每日从《统一风控决策中心》拉取 risk_level ≥ HIGH 名单（Redis Set），聚合前过滤，原始事件保留（G10） |
| L3 设备层 | 设备指纹哈希去重 | unique_consumers / unique_exposed_users 按设备指纹去重，防多账号刷量 |
| L4 内容层 | P95×5 异常检测 | 单日指标超同类基线 P75 × 5 → ANOMALY 标记 + `cee.content.anomaly.flagged` 事件；ANOMALY→NORMAL 仅允许人工恢复 |
| L5 转化层 | 归因去重 | 同一 (user, content) 7 天窗口内会员转化只计一次（G11） |

ANOMALY 内容的处置走《服务端-教育内容供应商交付质量多维评估与智能分级动态管理引擎》争议流程，本引擎只标记不处罚（C7）。

## 6. 状态机与守卫规则

### 6.1 A/B 实验状态机

```text
DRAFT ──(创建成功且平台注册通过)──> RUNNING ──(pause)──> PAUSED
  │                                   │  ^                    │
  │                                   │  └──(resume)──────────┘
  │                                   ├──(finalize, G5)──> COMPLETED
  └──(任意非终态 cancel)──────────────┤                    └──(cancel)──> CANCELLED
                                      └──(cancel)──> CANCELLED
```

| 转移 | 守卫 |
| --- | --- |
| DRAFT→RUNNING | 平台注册成功返回 platform_experiment_id；注册失败回 DRAFT 并报 58120 |
| 创建时 | 同内容仅允许一个 RUNNING/PAUSED 实验（G4，58121） |
| →COMPLETED | min_sample_size 达标且主指标显著；不显著时 finalize 拒绝（58123），仅允许人工以 INCONCLUSIVE 备注结案（winning_variant=NULL） |
| COMPLETED/CANCELLED | 终态不可再流转；变体内容快照保留供回溯 |

### 6.2 决策工单状态机

```text
PENDING ──(assign)──> IN_PROGRESS ──(resolve:DONE/REJECTED)──> 终态
   │                        │
   └──(reject)──────────────┘
```

| 转移 | 守卫 |
| --- | --- |
| 创建 | 同 content + decision_type 活跃单唯一（函数唯一索引，§7）；自动决策仅建 PENDING（G6） |
| →DONE | executed_ref（内容服务/题库操作凭证）或 resolution_notes 必填其一（G7） |
| SLA | due_date +14 天未处理 → 升级通知内容负责人；+21 天 → 通知运营负责人（委托延迟任务引擎，R15） |
| 回看 | DONE 后 +7 天自动回看任务，结论回填；REVISE/REPRODUCE 改善 <+3 分生成二次复盘（每内容 ≤ 2 次） |

### 6.3 数据质量标记流转

```text
NORMAL ⇄ LOW_SAMPLE   （样本量波动自动双向）
NORMAL → STALE        （评分链路失败沿用旧值，恢复后自动回 NORMAL）
NORMAL → ANOMALY      （P95×5 异常自动）
ANOMALY → NORMAL      （仅人工恢复，需填写理由并审计）
```

### 6.4 守卫规则总表 G1-G14

| ID | 规则 |
| --- | --- |
| G1 | 消费事件 `event_id` 唯一键去重，重复上报不报错计入 deduped |
| G2 | 效果回填仅限 COMPLETE 后 7 天窗口内的消费事件 |
| G3 | LOW_SAMPLE/缺维日不参与等级判定与自动决策；评分连续 7 日缺失 overall 置 NULL |
| G4 | 同一内容同时仅一个 RUNNING/PAUSED 实验 |
| G5 | 实验定稿需样本量达标且主指标显著；护栏劣化只允许人工结案 |
| G6 | 自动决策仅创建 PENDING 工单与快照，不直接变更内容线上状态 |
| G7 | 决策 DONE 必须携带 executed_ref 或 resolution_notes；终态不可再流转 |
| G8 | 缺口分析 (date,kp,grade) 幂等；推送生产任务幂等键 `gap:{date}:{kp}:{grade}` |
| G9 | 推荐正加权仅限 S/A 级且 flag=NORMAL；ANOMALY 一律不评分不加权 |
| G10 | 风控标记用户仅聚合层剔除，原始事件保留；ANOMALY 处置走供应商争议流程 |
| G11 | 会员转化归因同 (user,content) 7 天窗口仅计一次 |
| G12 | 基线 cohort < 30 内容回退全局基线并标记；回退占比 > 20% 告警 |
| G13 | 回补重算不得覆盖已确认决策的 trigger_metrics 快照 |
| G14 | MySQL 滚动保留 3 个月 / ClickHouse 13 个月，删除前双向对账（R 系容量见 §11） |

## 7. 幂等与并发控制

| 场景 | 机制 |
| --- | --- |
| 客户端重试上报 | `uk_event_id` 唯一键 + 客户端本地 SQLite 缓存补报（断网恢复） |
| 日批任务重跑/断点续跑 | 任务分片游标（content_id hash 16 片）记录于 Redis，重启从断点继续；`uk_content_date` upsert 幂等，calculation_version 递增防旧覆盖新 |
| 效果回填并发 | `has_assessment = 0` 条件更新（CAS），仅 NULL→值一次生效 |
| 决策单创建 | 活跃单函数唯一索引：`is_active` 生成列（status IN PENDING,IN_PROGRESS 时为 content_id+decision_type，否则 NULL） |
| 基线切换 | 双缓冲：新快照全量写 is_active=0 → 校验 → 单事务翻转，评分任务只读 active |
| 实验分流一致性 | 委托 AB 平台 Hash 分桶，CEE 不缓存分桶结果，仅透传 experiment_code |
| 回补重算 | 回补任务单实例分布式锁（lock key `cee:backfill:{contentId}`）；与日任务窗口重叠时回补延后至日任务完成后执行 |
| 多消费组重复消费 | Outbox Relay 至少一次投递 + 消费方按 event_id 幂等（§8） |

| ID | 故障 | 降级策略 |
| --- | --- | --- |
| D1 | Kafka 不可用 | 客户端本地 SQLite 缓存，恢复后补报；服务端写入路径直写 MySQL，指标链路不依赖实时消费 |
| D2 | ClickHouse 查询失败 | 日任务退化为 MySQL 分表聚合（仅近 3 个月可算，更早日数据沿用旧值并标 STALE） |
| D3 | 掌握度融合引擎不可用 | MASTERY_PROXY 配对暂停，理解度评分沿用最近一次可用值 + STALE |
| D4 | 会员域事件延迟 | 转化评分沿用最近可用值 + STALE；恢复后回补重算 |
| D5 | 搜索量数据缺失 | 缺口分析降级为 AI 提问量单指标，判定矩阵阈值自动收紧一档 |
| D6 | AB 平台分流服务降级 | 实验自动 PAUSED，全量回退 CONTROL 版本；恢复后继续累计样本 |
| D7 | 评分计算失败 | 沿用前一日评分 + STALE，连续 3 日失败 P2 告警 |
| D8 | 融合层取分超时 | Redis 周级评分缓存兑底（TTL 7 天）；缓存也未命中则不加权而非报错 |
| D9 | Webhook 推送失败 | 重试 3 次（1m/5m/30m）转站内通知 |
| D10 | 风控名单拉取失败 | 照常聚合但整体标记 `ANOMALY_RISK`，名单恢复后重算当日指标（不双向覆盖 calculation_version 更高者） |

总红线：采集与评分链路任何故障 **不阻塞学生学习主链路**（上报失败静默缓存）；ANOMALY 标记不影响内容在线可用性。

## 12. 数据安全与合规红线 C1-C10

| ID | 红线 |
| --- | --- |
| C1 | 评估对象是内容不是学生：所有输出禁止生成学生个体负面标签或排名 |
| C2 | 消费明细仅用于效果计算；个体明细不提供对外查询/导出，仅限内部分析权限；看板仅展示聚合 |
| C3 | 会员转化归因结果仅限运营后台，不得出现在学生端/家长端任何界面 |
| C4 | A/B 实验若涉及教学策略差异（影响学习路径/效果），需教育合规评审，不得对实验组明显不利 |
| C5 | 评估数据不得用于未成年人画像营销定向（对齐掌握度融合引擎合规红线） |
| C6 | 导出报告仅聚合维度；确需个体样本时 user_id 脱敏哈希且双人审批 |
| C7 | ANOMALY 仅内部可见，不向供应商自动公示处罚；争议走交付质量评估流程 |
| C8 | 埋点最小化：不采集学习输入内容/笔记文本，仅进度、时长、位置标记 |
| C9 | 供应商结算联动数据可追溯：trigger_metrics 快照与基线快照保留 3 年 |
| C10 | 注销用户：消费事件匿名化（user_id→0）以维持聚合口径稳定，在数据导出与注销链路 180 天延迟删除前完成当日聚合重算 |

## 14. 验收场景（18 条）

1. 客户端单批上报 50 条含 3 条重复 event_id → accepted=47、deduped=3，重复不报错（G1）。
2. 断网 2 小时后恢复 → 本地缓存补报成功，client_ts 正常回灌，48h 外事件被拒（58102）。
3. 同一用户 START→PROGRESS×n→COMPLETE → 次日 completion_rate 正确，PROGRESS 已客户端聚合。
4. 视频中途退出 → ABANDON 事件带 abandon_point，abandonment_rate 按 ABANDON/START 口径计算（F2 修正后）。
5. 消费后 3 天完成关联 KP 测评 → 回填 score_delta；COMPLETE 后第 8 天的测评不回填（G2）。
6. 无前测用户 → MASTERY_PROXY 配对生效，权重 ×0.5，pair_type 标记正确。
7. 某内容 14 天 overall 持续 50 → 自动创建 REVISE 决策单 PENDING，内容线上状态不变（G6）。
8. 同内容同规则再次触发 → 不产生重复活跃单（函数唯一索引幂等）。
9. 内容 overall 88 且样本达标 → PROMOTE 决策 + cee.score.calculated 事件，融合层可见可正加权（G9）。
10. 风控标记 500 账号集中消费同一内容 → 聚合剔除（G10），指标突增超 P75×5 → ANOMALY 标记 + flagged 事件。
11. 实验样本不足时 finalize → 拒绝（58123）；补齐样本且显著 → winning_variant 回填 + finalized 事件（G5）。
12. 同内容第二个 RUNNING 实验创建 → 拒绝（58121，G4）；CANCELLED 后可新建。
13. 缺口 CRITICAL → push-production 成功；重复推送返回既有任务（58140，G8）。
14. LOW_SAMPLE 内容 → 不进入 S/A 判定，融合层 has_score=false 不加权（G3/G9）。
15. ClickHouse 不可用 → 日任务退化 MySQL 聚合 + STALE，前一日评分沿用（D2/D7），任务不中断。
16. 注销用户 → 历史事件匿名化后聚合指标无回跳（C10）。
17. 回补 30 天重算 → uk upsert 幂等，已确认决策 trigger_metrics 快照不变（G13）。
18. 决策 DONE 后 7 天回看 → 指标改善 < +3 分生成二次复盘工单，每内容最多 2 次（§4.6）。
