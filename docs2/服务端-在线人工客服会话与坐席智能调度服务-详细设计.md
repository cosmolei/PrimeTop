# 服务端 - 在线人工客服会话与坐席智能调度服务 详细设计

## 0. 文档定位与缺口说明

本服务是客服域的**实时会话基础设施**，补齐一个被多份文档引用但从未设计的执行层：

| 引用方 | 引用内容 | 现状 |
| --- | --- | --- |
| 服务端-AI智能客服对话与工单自动分流解决引擎 §11.4 | `escalate` 接口返回 `queue_position / estimated_wait_minutes / target_group`，排队引擎无设计 | 仅契约 |
| 服务端-学生AI对话心理危机信号检测与分级预警干预编排引擎 §L3 | `takeoverService.requestTakeover(userId, conversationId, TakeoverPriority.HIGH, riskCategories)` "人工客服接管，对话流切换" | 接口签名存在，实现零设计 |
| 端到端流程设计-会员退订与权益降级完整链路 | 高危退订 "需要人工客服介入" | 无承载通道 |
| 管理后台-客户服务与工单管理工作台 §3.1 | 顶部指标 "在线客服数 / 当前排队数" | 无数据源 |
| 客服与工单系统 | 工单异步流转、SLA、FAQ 拦截 | 纯异步工单制，无实时会话实体 |
| 原设计文档 §12.4 | "建立用户反馈、客服、工单和 AI 纠错机制" | 客服实时通道未细化 |

**关键结论**：全库检索 `坐席端`、`客服坐席`、`chat_session`（客服语境）均为零命中；现有四份客服域文档（工单系统、AI 智能客服、自助支持中心、管理工作台）均不覆盖"用户 ↔ 人工坐席实时 IM 会话"。本服务补齐：会话实体、坐席状态机、排队调度引擎、消息投递与补偿、危机接管绿色通道、质检与满意度闭环。

## 1. 概述

### 1.1 定位

在线人工客服会话与坐席智能调度服务（Customer Contact Service，简称 **CC 服务**）为 PrimeTop 提供用户与人工客服坐席之间的**实时双向 IM 会话能力**，是 AI 客服无法解决时的兜底人工通道。服务范围：

1. **会话生命周期管理**：发起、排队、分配、进行中、转接、结束、满意度评价。
2. **坐席管理**：坐席账号、技能组、状态（在线/忙碌/小休）、最大并发会话数。
3. **智能调度**：技能组匹配、优先级仲裁、负载均衡、粘性会话（回访优先原坐席）。
4. **消息投递**：实时投递、ACK 与已读、断线重连补偿、离线转推送、撤回。
5. **特殊通道**：心理危机 L3 接管绿色通道、高危支付/退款直达组。
6. **质量闭环**：会话质检抽检、满意度评价（CSAT）、坐席行为红线检测。

### 1.2 设计目标

| 目标 | 指标 |
| --- | --- |
| 排队等待 P95 | 普通会话 ≤ 180s，会员 ≤ 90s |
| 危机绿色通道首响 | 100% ≤ 30s（硬性，超时自动升级 OnCall） |
| 坐席首次响应 P95 | ≤ 40s（会话分配后至坐席首条消息） |
| 消息投递成功率 | ≥ 99.99%（含补偿链路） |
| 会话解决率（不转工单） | ≥ 85% |
| 可用性 | 99.9%（降级时自动回落工单制，不可用时直接转工单） |

### 1.3 边界（不做什么）

- **不做** AI 对话（由 AI 智能客服 ICS 负责，本服务通过 escalate 接口承接其转人工流量）。
- **不做** 异步工单流转（由客服与工单系统负责，本服务超时会话自动转工单并双向关联）。
- **不做** 底层 WebSocket 连接管理（复用《WebSocket长连接管理与实时双向通信引擎》的连接/心跳/注册中心，本服务仅定义业务通道与帧协议）。
- **不做** 客服知识库与话术推荐生成（复用 ICS §11.5 agent-assist，本服务只记录采纳标记）。

### 3.2 通道与帧协议（建立在 WebSocket 引擎之上）

复用《WebSocket长连接管理与实时双向通信引擎》的 `/ws/connect` 握手、30s/90s 双层心跳与连接注册中心。CC 服务注册两个业务通道：

| 通道 | 订阅者 | 说明 |
| --- | --- | --- |
| `cc.user` | 发起会话的学生/家长端 | 单用户同一时刻最多 1 个活跃会话 |
| `cc.agent` | 客服工作台坐席端 | 一个连接可承载该坐席全部会话 |

**帧类型总表**（JSON，统一信封 `{type, sessionId, seq, ts, data}`）：

| type | 方向 | 说明 |
| --- | --- | --- |
| `queue_update` | S→U | 排队位次/预计等待变化（节流 5s 一次） |
| `agent_assigned` | S→U | 分配坐席（含坐席昵称、头像、技能组） |
| `msg` | 双向 | 聊天消息，`seq` 会话内单调递增 |
| `msg_ack` | S→发送方 | 服务端已持久化确认（携带 seq） |
| `read` | 双向 | 对端已读（携带 lastReadSeq） |
| `typing` | 双向 | 正在输入（60s 超时自动失效，不落库） |
| `session_ended` | S→双向 | 会话结束（原因：resolved/user_left/timeout/fallback_ticket） |
| `csat_request` | S→U | 请求满意度评价 |
| `takeover_alert` | S→A | 危机绿色通道抢答广播（仅危机组坐席收到） |
| `recall` | S→双向 | 消息撤回通知 |
| `route_changed` | S→U | 转接生效，新坐席信息 |

### 3.3 会话建立全链路（AI 转人工场景）

```text
用户(AI会话中) ──"转人工"──→ ICS escalate API
    ICS ──① POST cc-internal/sessions (source=AI_ESCALATION, skill=支付组, aiConversationId)──→ CC
    CC ──② 创建 Session(QUEUED) + QueueEntry(ZSET) ──→ 返回 sessionNo
    ICS ──③ 组装 queue_position/estimated_wait_minutes 返回给客户端（契约不变）
    CC ──④ AssignmentEngine 异步撮合 → agent_assigned 帧（双向）
    用户/坐席 IM …（msg/msg_ack/read/typing）
    ──⑤ 任一方 5 分钟无消息 → 系统提示 → 仍无 → 会话 PENDING_RESOLVE
    坐席 resolve → session_ended + csat_request → CSAT 落库 → Outbox 事件
```

### 4.2 Redis 结构

| Key | 类型 | 说明 |
| --- | --- | --- |
| `cc:queue:{group}` | ZSET | member=sessionId，score=priority×10¹⁰+epochMs（高优先级先出，同级 FIFO） |
| `cc:agent:load:{group}` | ZSET | member=agentId，score=当前会话数×1000/maxConcurrent（分配候选按负载升序） |
| `cc:agent:status:{agentId}` | HASH | status / concurrent / maxConcurrent / connId |
| `cc:session:route:{sessionId}` | STRING | 当前受理坐席ID（TTL = 会话时长 + 1h） |
| `cc:user:lastagent:{userId}` | STRING | 24h 粘性坐席（TTL 24h） |
| `cc:seq:{sessionId}` | STRING(INCR) | 消息序号发生器 |
| `cc:sticky:hold:{agentId}` | STRING | 粘性预留锁（30s，防分配竞态） |
| `cc:stats:realtime` | HASH | onlineAgents/queuing/activeSessions/servingByGroup（工作台指标源，5s 刷新） |
| `cc:green:pending` | ZSET | 危机待抢答会话（score=入队时间，30s 巡检超时升级） |

## 6. 状态机设计

### 6.1 会话状态机

```text
                    ┌──────────── 300s 队列超时 ────────────┐
                    ↓                                        │
QUEUED ──分配──→ ASSIGNED ──坐席首条消息──→ ACTIVE ──坐席resolve──→ PENDING_RESOLVE ──CSAT/24h──→ CLOSED
  │                  │                        │                                           ↑
  │用户取消           │30s坐席未接入(掉线)      │5min双方无消息                              │
  ↓                  ↓回队列                   ↓                                          │
CANCELLED        REQUEUED(计数+1)         IDLE_TIMEOUT ──提示后用户回复──→ ACTIVE          │
                                             └──仍无回复──→ PENDING_RESOLVE ─────────────→┘
TRANSFERRED：ACTIVE 状态内子标记（route_changed 帧），不作为独立主状态
TICKET_FALLBACK：QUEUE_TIMEOUT 的终态别名（end_reason=FALLBACK_TICKET，关联工单号）
```

**守卫表：**

| 当前态 | 事件 | 目标态 | 守卫条件 |
| --- | --- | --- | --- |
| (null) | enqueue | QUEUED | 同用户无活跃会话；source 合法 |
| QUEUED | assign | ASSIGNED | 坐席 status=ONLINE 且 concurrent<max |
| QUEUED | cancel | CANCELLED | 仅发起用户本人 |
| QUEUED | expire(300s) | CLOSED(FALLBACK_TICKET) | 自动创建工单并关联 |
| ASSIGNED | first_agent_msg | ACTIVE | — |
| ASSIGNED | agent_lost(30s) | QUEUED | requeue 次数 ≤ 2，超过转工单 |
| ACTIVE | resolve | PENDING_RESOLVE | 仅受理坐席/主管 |
| ACTIVE | idle(5min) | IDLE_TIMEOUT | 提示帧发出后再计时 2min |
| ACTIVE | user_reenter | ACTIVE | 断线重连不改变状态 |
| ACTIVE | transfer | ACTIVE | transferCount ≤ 3；跨组需二次确认 |
| PENDING_RESOLVE | csat / timeout(24h) | CLOSED | CSAT 幂等（uk_session） |

### 6.2 坐席状态机

```text
OFFLINE ──登录工作台──→ ONLINE ──接满并发──→ BUSY ──会话释放──→ ONLINE
                         │                    │
                         ├──手动小休──→ BREAK ──归位──→ ONLINE
                         └──强制下线/心跳超90s──→ OFFLINE（其会话全部 REQUEUED）
```

- BUSY 自动切换：`concurrent == maxConcurrent` 时写入；释放会话后若 `concurrent < max` 回 ONLINE。
- BREAK 期间不参与分配；队列积压 > 50 且组内 ONLINE 不足时，主管可发送"请求归位"通知（不强制）。
- 危机组坐席 BREAK 需二次确认（绿色通道人力红线）。

### 6.3 优先级公式

```text
priority = clamp(0, 100,
    base(source)          // CRISIS_TAKEOVER=100, AI_ESCALATION(退款/支付)=70,
                          // AI_ESCALATION(会员)=60, ORDER_CALLBACK=60,
                          // TICKET_CHAT=55, DIRECT_ENTRY=40
  + memberBoost           // 年度会员+10 / 月度+5（读会员权益缓存）
  + riskBoost             // riskFlags 含 COMPLAINT +10
  + waitBoost             // min(20, floor(waitSeconds / 30))  排队每30秒+1，封顶20
)
```

ZSET score = `priority × 10^10 + epochMs`：保证高优先级永远先出，同优先级按入队时间 FIFO；`waitBoost` 通过每 10s 的巡检任务对队列重打分实现"越等越优先"。

## 7. 关键代码示例（Java 17 / Spring Boot 3.x）

### 7.1 AssignmentEngine：原子分配（Redis Lua）

分配三步合一个 Lua 保证原子性：①校验坐席可接；②从队列弹出该坐席所匹配的最优条目；③写入路由并累加负载。避免"两个坐席同时抢到同一会话"与"会话分给已满坐席"两类竞态。

```java
private static final String ASSIGN_LUA = """
    -- KEYS[1]=queue ZSET  KEYS[2]=agentLoad ZSET  KEYS[3]=cc:agent:status:{agentId}
    -- KEYS[4]=cc:session:route:{sessionId占位} 由调用方逐候选执行
    -- ARGV[1]=agentId ARGV[2]=maxConcurrent ARGV[3]=now
    local st = redis.call('HGETALL', KEYS[3])
    local status, concurrent = st['status'], tonumber(st['concurrent'] or '0')
    if status ~= 'ONLINE' or concurrent >= tonumber(ARGV[2]) then return 0 end
    -- 取队列最高优先级（score 最大）
    local entries = redis.call('ZREVRANGE', KEYS[1], 0, 0, 'WITHSCORES')
    if #entries == 0 then return -1 end           -- 队列空
    local sessionId = entries[1]
    redis.call('ZREM', KEYS[1], sessionId)
    redis.call('HINCRBY', KEYS[3], 'concurrent', 1)
    redis.call('SET', 'cc:session:route:' .. sessionId, ARGV[1])
    redis.call('ZADD', KEYS[2], (concurrent + 1) * 1000 / tonumber(ARGV[2]), ARGV[1])
    return sessionId
    """;

/** 分配主流程：粘性优先 → 负载升序候选 → 逐个 Lua 尝试 */
public Optional<Long> tryAssign(Long sessionId, String group) {
    // ① 粘性会话：30s 预留锁防竞态
    Long sticky = stickyService.holdOrGetPrevAgent(sessionId);
    if (sticky != null && tryAssignTo(sticky, group)) return Optional.of(sticky);
    // ② 候选 = 组内 ONLINE 且负载未满，按 (current/max, lastAssignedAt) 升序
    List<Long> candidates = agentRegistry.candidatesOfGroup(group);
    for (Long agentId : candidates) {
        if (tryAssignTo(agentId, group)) return Optional.of(agentId);
    }
    return Optional.empty();   // 触发队列广播/超时降级逻辑（§7.3）
}
```

### 7.2 MessagePipeline：seq 单调、两级 ACK、补偿

```java
/** 用户/坐席发消息：INCR 分配 seq → 落库 → 双向投递 → ack；对端离线走通知补偿 */
@Transactional
public MsgAck publish(long sessionId, Direction dir, WsMsgFrame frame) {
    long seq = redis.increment("cc:seq:" + sessionId);
    // 敏感词：minor_flag 会话双向强制过滤；拦截则写 safe_status=BLOCKED 的占位消息
    SafeResult safe = contentGuard.check(frame.content(), session.isMinorFlag(), dir);
    ccMessageDao.insert(Message.builder()
        .sessionId(sessionId).seq((int) seq).direction(dir.name())
        .msgType(frame.type()).content(safe.masked()).safeStatus(safe.status()).build());

    String userChannel = "cc.user:" + session.getUserId();
    if (wsEngine.isOnline(userChannel)) {
        wsEngine.send(userChannel, frame.withSeq(seq));            // 实时帧
    } else if (dir == Direction.AGENT) {
        notifyCenter.push(session.getUserId(), NotifyTemplate.CC_AGENT_REPLIED, // 离线补偿
            Map.of("sessionNo", session.getSessionNo()));          // App推送+站内信
    }
    if (dir == Direction.USER) sessionDao.touchLastMsg(sessionId);
    return new MsgAck(seq, safe.status());
}
```

### 7.3 队列巡检与超时降级（每 10s，分布式锁 `cc:lock:patrol`）

```java
public void patrol() {
    for (String group : SkillGroups.ALL) {
        Set<Long> waiting = queue.entries(group);
        for (Long sid : waiting) {
            Session s = sessionDao.find(sid);
            long wait = elapsed(s.getQueuedAt());
            reprioritize(group, sid, s);                       // waitBoost 重打分
            if (wait >= 60_000 && !s.isBroadcastHelp())        // T+60s 组内广播求助
                wsEngine.broadcast("cc.agent:group:" + group, Frame.helpWanted(sid));
            if (wait >= 180_000 && !s.isUserNotified())        // T+180s 提示可留言
                wsEngine.send(userChannel(sid), Frame.suggestLeaveMessage());
            if (wait >= 300_000)                               // T+300s 转工单
                fallbackToTicket(sid, "QUEUE_TIMEOUT");
        }
    }
}
```

```java
public TakeoverResult requestTakeover(TakeoverRequest req) {

/** 30s 巡检：绿色通道超时 → 升级：短信通知值班主管 + 复用 OnCall 值班表拉人 + 工单加急 */
public void greenChannelGuard() {
    for (Long sid : redis.zrange("cc:green:pending", 0, -1)) {
        if (elapsedSinceEnqueue(sid) >= 30_000) {
            oncallService.escalate(OnCallTopic.PSYCH_CRISIS, sid);   // 生产事故OnCall体系联动
            smsGateway.send(dutySupervisor(), SmsTemplate.CRISIS_NO_CLAIM, sid);
            redis.zrem("cc:green:pending", sid);
            metrics.increment("cc_green_timeout_total");             // 目标恒为0，非0即告警
        }
    }
}
```

### 9.2 降级与容灾策略

| 故障 | 行为 |
| --- | --- |
| Redis 不可用 | 分配停摆；新会话直接走 `CC_SERVICE_DEGRADED` 转工单；存量 ACTIVE 会话仅走 DB 消息（seq 用 DB `MAX(seq)+1` + 唯一键兜底） |
| WS 集群不可用 | 用户端提示"网络波动"；消息落库不丢，恢复后增量拉取；坐席端同 |
| CC 服务整体不可用 | ICS escalate 直接建工单（其文档已含该兜底语义）；危机引擎 L3 走短信+OnCall 直呼 |
| MySQL 主库故障 | 只读副本维持历史查询；新会话拒绝（503）→ 转工单；消息暂存本地队列恢复后回放 |
| 消息投递失败重试 | 推送通知链路 3 次退避；仍失败记 `cc_event_outbox` 死信 + 告警 |

### 10.2 未成年人合规（红线）

1. `minor_flag=1` 会话：双向消息强制敏感词过滤（复用教育场景敏感词多层次过滤引擎，含自伤词汇组实时联动危机引擎打分）。
2. **家长可见性分级**（对齐《学生学习数据家庭共享可见度分级》约定）：绑定的家长端收到"孩子发起了客服会话"通知；会话内容默认 **16 岁以下可见摘要+可申请全文**、16 岁及以上仅通知不展示内容（保护青少年隐私自主），家长中心可配置。
3. 会话记录留存 **3 年**（未成年人纠纷举证窗口），到期按归档策略处理；任何导出必须走审计日志接口并留痕（复用审计日志系统）。
4. 危机类会话内容仅危机组坐席+质检员可见，普通坐席不可检索。

强制下线、质检结论 FAIL、红线命中、会话导出、坐席创建/停用 —— 全部写操作审计日志（操作人/对象/前后状态）。

| `cc_active_sessions` / `cc_queuing` | Gauge | 排队 > 50 且在线坐席 0 → P2 |
| `cc_msg_delivery_fail_total` | Counter | 5min > 10 → P2 |
| `cc_fallback_ticket_ratio` | Gauge | 日累计 > 15% → 容量告警（加坐席/扩技能组） |
| `cc_agent_utilization{agent}` | Gauge | 组均值 > 85% 持续 30min → 排班提醒 |
| `cc_csat_avg{group}` 日聚合 | Gauge | < 4.0 → 质检加抽 |

埋点事件（客户端复用统一埋点平台）：`cc_session_start / cc_queue_cancel / cc_agent_assigned / cc_msg_send / cc_csat_submit`，附 sessionNo/source/skillGroup 维度。

工作台顶栏 `GET /api/v1/admin/cc/realtime/stats` 数据源即 `cc:stats:realtime`（5s 定时聚合：在线坐席数、排队数、进行中会话数、分组明细）。

## 12. 容量估算与性能要点

**假设**：DAU 50 万，1.2% 用户/日发起人工会话（≈6000 会话/日，高峰 400 会话/小时），平均会话 12 分钟、15 条消息。坐席 60 人（并发 3），危机组 6 人 7×24 轮班。

- 消息写入峰值 ≈ 400×15/3600×2 ≈ 3.3 QPS（含双向）——单库轻松承载；消息表按月分区，月增量 ≈ 270 万行。
- 排队 ZSET 单组 < 500 成员，巡检 10s 周期 O(N) 扫描无压力。
- WS 并发：用户在线会话 ≤ 60×3=180 + 排队用户 ≈ 千级连接，远低于引擎容量。
- 热点：`uk_session_seq` 范围拉取 + `(session_id, id)` 索引覆盖断线补偿；seq 发生器单 key INCR 无争用（单会话内串行写入由 DB 唯一键兜底）。
- 读写分离：历史会话检索/质检读取走只读副本。

## 13. 测试与验收场景（15 条）

1. 用户在 AI 会话点"转人工" → ICS escalate 返回的 queue_position 随 CC 真实队列变化，两端一致。
2. 同一用户重复发起 → 幂等返回同一 sessionNo，队列中只有一条。
3. 优先级抢占：排队中退款会话（70）后于普通咨询（40）入队，先被分配。
4. waitBoost：普通会话等待 90s 后 priority +3，越等越靠前（ZSET 重打分生效）。
5. 粘性会话：24h 内二次进入且原坐席在线有空位 → 直接分配原坐席；原坐席 BUSY → 正常排队不阻塞。
6. 坐席并发满 → 自动 BUSY 不再被分配；会话结束后回 ONLINE 并立即参与分配。
7. 分配后坐席 30s 未发首条消息（模拟掉线）→ 会话 REQUEUED，requeue 计数 +1；累计 3 次转工单。
8. 危机 L3 触发 → requestTakeover 建绿色通道会话，AI 尾部 20 条消息以 CONTEXT_INJECT 注入，危机组全员收到 takeover_alert，某坐席 claim 成功、第二人 claim 收到 53412。
9. 绿色通道 30s 无人抢答 → OnCall 升级 + 值班主管短信，`cc_green_timeout_total` 计数并 P1 告警。
10. 用户排队 180s 收到"可留言"提示，300s 自动转工单，工单号回写 session.ticket_id，用户端收到 FALLBACK_TICKET 帧。
11. 用户杀进程 2 分钟后重进 → last_seq 增量拉取无丢消息、无重复渲染（seq 幂等）。
12. 用户离线时坐席发消息 → 收到 App 推送"客服回复了你"，点击深链直达会话。
13. 未成年人会话发送涉自伤词 → 双向过滤生效（53410 或 MASKED），并联动危机引擎打分入 risk_flags。
14. 坐席发送含微信号消息 → 消息送达但红线待办生成、组长收到告警，次日质检批次可见 REDLINE_HIT 抽样。
15. 会话结束 → csat_request 送达，评分落库幂等；24h 未评自动 CLOSED；CC.SESSION.ENDED 事件驱动工单同步结单。
