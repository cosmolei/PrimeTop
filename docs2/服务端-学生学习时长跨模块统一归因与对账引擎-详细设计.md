> 版本：v1.0　　创建日期：2026-08-09　　负责人：后端架构组

---

## 1. 概述

### 1.1 背景

PrimeTop 平台包含多个学习模块：AI 辅导对话、拍照搜题、同步课堂、练习测评、错题复习、作文辅导、文科背诵等。每个模块都会产生"学习时长"，但各模块对时长的定义、采集方式、上报口径各不相同，导致同一个学生同一天的学习时长在不同报表中可能出现不一致：

| 问题场景 | 表现 |
|----------|------|
| **口径不一致** | AI 辅导按对话轮次时间段累加，同步课堂按页面停留计算，练习按提交时间计算 — 三者叠加后出现"24小时学习15小时" |
| **重叠未去重** | 学生在同步课堂中打开浮动 AI 助手提问，两个模块同时计时，导致双倍计算 |
| **跨模块空白** | 学生从 AI 辅导切换到练习页面，中间 3 秒的页面跳转无人认领，形成"时长黑洞" |
| **报表打架** | 家长端显示当日学习 2 小时，学情分析显示 1.5 小时，打卡系统显示 1.8 小时 — 各自取数来源不同 |
| **离线时间归属** | 学生离线做了一套试卷，重新上线后同步成绩，但这段时间从未被任何模块上报 |

现有的 **学习时长统计与有效性判定引擎** 解决了"前台时间是否为有效学习"的问题（心跳检测、空闲判定、防作弊），并提供了 `scene_breakdown` 按场景拆分。但它假定单一会话线性流转，**未覆盖多模块并行计时、模块间口径差异、以及对账纠偏**的需求。

### 1.2 本引擎定位

本引擎是 **学习时长统计与有效性判定引擎** 的上层补充，专注于：

1. **统一口径定义**：为所有业务模块制定标准化的"模块学习时长"上报规范。
2. **跨模块归因**：当多个模块同时活跃时，按优先级规则将时间归属到唯一主模块，消除重复计时。
3. **对账纠偏**：定期比对"心跳推导时长"与"模块自报时长"，标记差异并自动修正。
4. **统一查询服务**：为学情分析、家长端、打卡系统、运营看板等消费方提供一致的时长查询 API。

### 1.3 系统边界

| 职责 | 归属 |
|------|------|
| 心跳采集、空闲检测、防作弊 | 学习时长统计与有效性判定引擎（已有） |
| **模块时长上报 SDK 规范** | **本引擎** |
| **多模块时间重叠去重** | **本引擎** |
| **心跳时长 vs 模块时长对账** | **本引擎** |
| **统一时长查询 API** | **本引擎** |
| 防沉迷限额管控 | 防沉迷与未成年人保护机制（已有） |
| 学习计划完成度判定 | 学习规划服务（已有） |

### 1.4 设计目标

1. **一致性**：全平台任何入口查到的同一学生同一天学习时长完全一致。
2. **可追溯**：每秒学习时长都能追溯到来源模块、时间段、计算方式。
3. **低延迟**：当日时长查询 P99 ≤ 50ms（Redis 缓存），T+1 对账批处理在 30 分钟内完成。
4. **容错**：模块上报失败或延迟不影响心跳时长的基础统计。
5. **可扩展**：新增业务模块时，只需按 SDK 规范接入，无需修改本引擎核心逻辑。

## 3. 核心概念与口径定义

### 3.1 时长层次模型

```
Layer 4: 展示时长 (Displayed Duration)
         ▲ - 经过归因去重后的最终展示值
         │
Layer 3: 归因时长 (Attributed Duration)
         ▲ - 重叠时段按优先级归属到唯一模块后的值
         │
Layer 2: 模块自报时长 (Module-Reported Duration)
         ▲ - 各业务模块通过 SDK 上报的原始时长
         │
Layer 1: 心跳推导时长 (Heartbeat-Derived Duration)
           - 由心跳事件 + 活跃判定推导的有效前台时长
```

### 3.2 模块编码注册表

每个业务模块在接入前需在平台注册，获得唯一编码和优先级：

| 模块编码 | 名称 | 优先级 | 场景类型 | 说明 |
|----------|------|--------|----------|------|
| `ai_chat` | AI 辅导对话 | 30 | interactive | 文字/语音对话 |
| `photo_search` | 拍照搜题 | 40 | interactive | 拍题→解析 |
| `textbook_read` | 同步课堂阅读 | 20 | content_consume | 教材章节学习 |
| `practice` | 练习测评 | 35 | interactive | 答题、考试模拟 |
| `mistake_review` | 错题复习 | 25 | interactive | 错题订正、复习 |
| `essay_writing` | 作文辅导 | 35 | productive | 作文撰写、批改 |
| `recitation` | 文科背诵 | 25 | interactive | 背诵检测 |
| `phonics` | 拼音识字 | 25 | interactive | 启蒙学习 |
| `knowledge_map` | 知识图谱浏览 | 15 | content_consume | 图谱探索 |
| `study_plan` | 学习规划 | 10 | management | 计划管理 |
| `parent_center` | 家长中心 | 5 | management | 家长查看 |
| `settings` | 设置页面 | 1 | non_learning | 非学习页面 |

**优先级规则**：
- 数值越大优先级越高，重叠时段归属到优先级高的模块。
- `interactive`（交互类）优先级一般高于 `content_consume`（内容消费类）。
- `non_learning` 类不产生学习时长。

### 3.3 时间槽 (Time Slot) 模型

将一天划分为 **30 秒粒度的时间槽**（2880 个/天），每个时间槽只能归属到一个模块：

```
00:00:00 ─────── 00:00:30 ─────── 00:01:00 ─────── 00:01:30 ─── ...
  Slot 0             Slot 1            Slot 2           Slot 3
  [empty]        [ai_chat]         [ai_chat]       [practice]
```

选择 30 秒粒度的理由：
1. 与心跳间隔（30 秒）对齐，一个心跳周期对应一个时间槽。
2. 2880 个槽/天的数据量适中，可用 Bitmap 或 ZSet 高效存储。
3. 足够精细，不会因粒度过粗丢失短时切换信息。

## 4. 数据结构定义

### 4.1 模块时长原始事件表 `module_time_raw_events`

各模块通过 SDK 上报的时长事件，每条记录代表一个模块在某个时间段内活跃。

```sql
CREATE TABLE module_time_raw_events (
    id              BIGINT UNSIGNED   NOT NULL AUTO_INCREMENT COMMENT '事件ID',
    user_id         BIGINT UNSIGNED   NOT NULL COMMENT '用户ID',
    session_id      BIGINT UNSIGNED   NOT NULL COMMENT '学习会话ID(关联learning_sessions)',

    -- 模块信息
    module_code     VARCHAR(32)       NOT NULL COMMENT '模块编码(ai_chat/practice/...)',
    module_session  VARCHAR(64)       NOT NULL COMMENT '模块内会话标识(如对话ID/练习批次ID)',

    -- 时间段
    start_ts        DATETIME(3)       NOT NULL COMMENT '模块活跃开始时间',
    end_ts          DATETIME(3)       NOT NULL COMMENT '模块活跃结束时间',
    duration_ms     INT UNSIGNED      NOT NULL COMMENT '持续时长(毫秒) = end_ts - start_ts',

    -- 上下文
    subject         VARCHAR(32)       NOT NULL DEFAULT '' COMMENT '学科(math/chinese/english/...)',
    chapter_id      VARCHAR(64)       NULL     COMMENT '关联章节ID',
    knowledge_point_ids JSON          NULL     COMMENT '关联知识点ID列表',

    -- 客户端信息
    device_id       VARCHAR(64)       NOT NULL COMMENT '设备指纹',
    app_version     VARCHAR(32)       NOT NULL,
    platform        TINYINT UNSIGNED  NOT NULL COMMENT '1=iOS 2=Android',

    -- 上报元信息
    client_report_ts DATETIME(3)      NOT NULL COMMENT '客户端上报时间',
    server_recv_ts   DATETIME(3)      NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '服务端接收时间',
    report_source   TINYINT UNSIGNED  NOT NULL DEFAULT 1 COMMENT '1=实时上报 2=补报(离线缓存) 3=对账修正',

    -- 归因状态
    attribution_status TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0=待归因 1=已归因 2=被去重(重叠) 3=被丢弃',

    created_at      DATETIME          NOT NULL DEFAULT CURRENT_TIMESTAMP,

    PRIMARY KEY (id),
    INDEX idx_user_time (user_id, start_ts, end_ts),
    INDEX idx_session_module (session_id, module_code),
    INDEX idx_module_date (module_code, start_ts),
```

### 4.3 时间槽归属表 `time_slot_attribution` (ClickHouse/Redis)

记录每个时间槽归属到哪个模块，用于精细分析和审计。数据量大，推荐 ClickHouse 或用 Redis Bitmap。

#### ClickHouse 版本：

```sql
CREATE TABLE time_slot_attribution (
    user_id         UInt64,
    date            Date,
    slot_index      UInt16 COMMENT '时间槽序号(0~2879), 每30秒一个槽',

    module_code     LowCardinality(String) COMMENT '归属模块编码',
    subject         LowCardinality(String) DEFAULT '' COMMENT '学科',
    session_id      UInt64 COMMENT '学习会话ID',

    -- 该槽内各模块的活跃情况(JSON)
    overlapping_modules String COMMENT '["ai_chat","practice"] 表示该槽内两模块同时活跃',

    created_at      DateTime DEFAULT now()
)
ENGINE = MergeTree()
PARTITION BY toYYYYMMDD(date)
ORDER BY (user_id, date, slot_index)
TTL date + INTERVAL 90 DAY COMMENT '保留90天';
```

#### Redis 版本（实时查询用）：

```
Key:   attribution:{user_id}:{YYYYMMDD}
Type:  ZSet
Score: slot_index (0~2879)
Value: "{module_code}:{subject}:{session_id}"

# 查询某用户某天的归属时间槽:
ZRANGE attribution:10086:20260809 0 -1 WITHSCORES
```

## 5. 模块时长上报 SDK 规范

### 5.1 客户端 SDK 接口

所有业务模块必须集成 `ModuleTimeAgent`，通过它上报活跃时间段。

#### Dart (Flutter) 示例：

```dart
/// 模块时长采集器 — 全局单例
class ModuleTimeAgent {
  static final ModuleTimeAgent _instance = ModuleTimeAgent._();
  factory ModuleTimeAgent() => _instance;
  ModuleTimeAgent._();

  final String _endpoint = '/api/v1/module-time/report';
  final Queue<ModuleTimeEvent> _buffer = Queue();
  final StreamController<ModuleTimeEvent> _controller = StreamController.broadcast();

  /// 模块进入前台时调用
  ///
  /// [moduleCode]  模块编码（见注册表）
  /// [moduleSession] 模块内会话标识（如对话ID、练习批次ID）
  /// [subject]     学科
  /// [context]     附加上下文（章节ID、知识点ID等）
  ModuleTimeHandle enter({
    required String moduleCode,
    required String moduleSession,
    String subject = '',
    Map<String, dynamic>? context,
  }) {
    final handle = ModuleTimeHandle._(
      agent: this,
      moduleCode: moduleCode,
      moduleSession: moduleSession,
      subject: subject,
      context: context ?? {},
      startTs: DateTime.now(),
    );
    return handle;
  }

  /// 模块退出前台时调用（由 Handle 自动触发，通常不需手动调用）
  void _emit(ModuleTimeEvent event) {
    _buffer.add(event);
    _controller.add(event);
    _flushIfNeeded();
  }

  /// 批量刷新缓冲区
  Future<void> flush() async {
    if (_buffer.isEmpty) return;
    final batch = _buffer.toList();
    _buffer.clear();
    try {
      await _httpPost(_endpoint, body: jsonEncode(batch));
    } catch (_) {
      // 失败重回缓冲区，等待下次重试
      _buffer.addAll(batch);
    }
  }

  void _flushIfNeeded() {
    if (_buffer.length >= 10) {
      flush();
    }
  }
}

/// 模块时长句柄 — 控制 enable/disable 期间
class ModuleTimeHandle {
  final ModuleTimeAgent _agent;
  final String moduleCode;
  final String moduleSession;
  final String subject;
  final Map<String, dynamic> context;
  final DateTime startTs;

  bool _paused = false;
  DateTime? _pauseTs;

  ModuleTimeHandle._({
    required ModuleTimeAgent agent,
    required this.moduleCode,
    required this.moduleSession,
    required this.subject,
    required this.context,
    required this.startTs,
  }) : _agent = agent;

  /// 暂停计时（模块进入后台但未完全退出）
  void pause() {
    if (_paused) return;
    _paused = true;
    _pauseTs = DateTime.now();
    _emitSegment(startTs, _pauseTs!);
  }

  /// 恢复计时
  void resume() {
    if (!_paused) return;
    _paused = false;
    // pause 到 resume 之间的时间不计入
    // 新的 segment 从现在开始
  }

  /// 退出模块，提交最终时长
  void exit() {
    final endTs = _paused ? _pauseTs! : DateTime.now();
    if (!_paused) {
      _emitSegment(startTs, endTs);
    } else {
      // 已在 pause 时 emit 过
    }
  }

  void _emitSegment(DateTime from, DateTime to) {
    if (to.difference(from).inMilliseconds < 1000) return; // <1s 不上报
    _agent._emit(ModuleTimeEvent(
      moduleCode: moduleCode,
      moduleSession: moduleSession,
      subject: subject,
      startTs: from,
      endTs: to,
      context: context,
    ));
  }
}

class ModuleTimeEvent {
  final String moduleCode;
  final String moduleSession;
  final String subject;
  final DateTime startTs;
  final DateTime endTs;
```

```dart
      'retry_count': 0,
    });

    final rows = await db.query(
      _tableName,
      where: 'retry_count < 3',
      orderBy: 'created_at ASC',
      limit: 50,
    );

    if (rows.isEmpty) return;

    final events = rows.map((r) => ModuleTimeEvent(
      moduleCode: r['module_code'] as String,
      moduleSession: r['module_session'] as String,
      subject: r['subject'] as String,
```

## 7. 核心算法

### 7.1 重叠检测与归因算法

当多个模块在同一时间槽内活跃时，按以下步骤决策归属：

```python
from dataclasses import dataclass
from typing import List, Optional
from enum import IntEnum

class SceneType(IntEnum):
    NON_LEARNING = 0
    MANAGEMENT = 5
    CONTENT_CONSUME = 10
    INTERACTIVE = 20
    PRODUCTIVE = 20

@dataclass
class ModuleSegment:
    """一个模块的时间段"""
    module_code: str
    module_session: str
    subject: str
    session_id: int
    start_ts: float        # epoch seconds
    end_ts: float
    priority: int          # 来自模块注册表

    @property
    def duration_s(self) -> float:
        return self.end_ts - self.start_ts

@dataclass
class TimeSlot:
    """一个 30 秒时间槽的归属结果"""
    slot_index: int
    start_ts: float
    end_ts: float
    attributed_module: str
    attributed_subject: str
    attributed_session: int
    overlapping_modules: List[str]
    resolution_rule: str   # priority / foreground / exclusive / random


SLOT_DURATION = 30  # 秒

def resolve_overlaps(segments: List[ModuleSegment],
                    heartbeat_slots: set,
                    user_id: int,
                    date_str: str) -> List[TimeSlot]:
    """
    主归因函数：将多个模块的重叠时间段归因到唯一时间槽。

    算法步骤:
    1. 将所有时间段对齐到 30 秒时间槽
    2. 逐槽检查有哪些模块活跃
    3. 按优先级规则决定归属
    4. 生成 TimeSlot 列表
    """
    if not segments:
        return []

    # 按 start_ts 排序
    segments.sort(key=lambda s: s.start_ts)

    day_start = min(s.start_ts for s in segments)
    day_start = (day_start // 86400) * 86400  # 对齐到 UTC 当天 00:00

    # 构建每个槽的活跃模块列表
    # slot_modules[slot_index] = List[ModuleSegment]
    slot_modules: dict[int, List[ModuleSegment]] = {}

    for seg in segments:
        start_slot = int((seg.start_ts - day_start) // SLOT_DURATION)
        end_slot = int((seg.end_ts - day_start) // SLOT_DURATION + 0.999)  # 向上取整

        for slot_idx in range(start_slot, end_slot):
            if slot_idx not in slot_modules:
                slot_modules[slot_idx] = []
            slot_modules[slot_idx].append(seg)

    # 逐槽归因
    results: List[TimeSlot] = []
    for slot_idx in sorted(slot_modules.keys()):
        active = slot_modules[slot_idx]
        slot_start = day_start + slot_idx * SLOT_DURATION
        slot_end = slot_start + SLOT_DURATION

        if slot_idx not in heartbeat_slots:
            # 心跳显示该槽不活跃，跳过（不计入学习时长）
            continue

        if len(active) == 1:
            # 只有一个模块活跃，直接归属
            seg = active[0]
            results.append(TimeSlot(
                slot_index=slot_idx,
                start_ts=slot_start,
                end_ts=slot_end,
                attributed_module=seg.module_code,
                attributed_subject=seg.subject,
                attributed_session=seg.session_id,
                overlapping_modules=[seg.module_code],
                resolution_rule="exclusive"
            ))
        else:
            # 多模块重叠 — 按优先级决策
            winner = resolve_conflict(active, slot_idx)
            results.append(TimeSlot(
                slot_index=slot_idx,
                start_ts=slot_start,
                end_ts=slot_end,
                attributed_module=winner.module_code,
                attributed_subject=winner.subject,
                attributed_session=winner.session_id,
                overlapping_modules=[s.module_code for s in active],
                resolution_rule="priority"
            ))

    return results


def resolve_conflict(segments: List[ModuleSegment], slot_idx: int) -> ModuleSegment:
    """
    多模块重叠时的冲突解决策略。

    优先级规则 (按顺序判断):
    1. 交互类(interactive) > 内容消费类(content_consume) > 管理类(management)
    2. 同类型中，优先级数值更高的优先
    3. 同优先级时，更晚进入的模块优先（用户当前注意力焦点）
    4. 完全相同时，取 module_session 字典序最小的（保证幂等性）
    """
    # 规则 1+2: 按 priority 降序
    sorted_segs = sorted(segments, key=lambda s: (-s.priority, s.module_code))

    # 检查最高优先级组
    top_priority = sorted_segs[0].priority
    top_group = [s for s in sorted_segs if s.priority == top_priority]

    if len(top_group) == 1:
        return top_group[0]

    # 规则 3: 同优先级取 start_ts 更大的（更晚进入）
    top_group.sort(key=lambda s: -s.start_ts)
    if top_group[0].start_ts != top_group[1].start_ts:
        return top_group[0]

    # 规则 4: 取 module_session 字典序最小的
    top_group.sort(key=lambda s: s.module_session)
    return top_group[0]
```

### 7.2 对账算法

每日 T+1 执行，比对心跳推导时长与模块自报时长：

```python
from datetime import date, timedelta
from typing import Tuple

class ReconciliationEngine:
    """时长对账引擎 — T+1 批处理"""

    # 对账阈值配置
    THRESHOLD_WARN_S = 60          # 差异 ≥ 60 秒标记警告
    THRESHOLD_FLAG_S = 300         # 差异 ≥ 300 秒标记异常
    THRESHOLD_RATIO = 0.1          # 差异比例 ≥ 10% 标记异常
    THRESHOLD_TRUST = 0.95         # 一致性 ≥ 95% 判定为可信

    def reconcile_user_day(self, user_id: int, target_date: date) -> dict:
        """
        对单个用户单日进行对账。

        Returns:
            {
                'heartbeat_total_s': int,
                'module_total_s': int,
                'attributed_total_s': int,
                'displayed_total_s': int,
                'diff_s': int,
                'diff_ratio': float,
                'reason': str,
                'action': str,
                'adjustment_s': int,
            }
        """
        # 1. 获取心跳推导有效时长
        heartbeat_total = self._get_heartbeat_duration(user_id, target_date)

        # 2. 获取模块自报总时长（去重前）
        module_raw_total = self._get_module_raw_duration(user_id, target_date)

        # 3. 获取归因后总时长（去重后）
        attributed_total = self._get_attributed_duration(user_id, target_date)

        # 4. 判断差异类型
        diff = attributed_total - heartbeat_total
        diff_ratio = diff / heartbeat_total if heartbeat_total > 0 else 0.0

        reason, action, adjustment = self._classify_diff(
            heartbeat_total, module_raw_total, attributed_total,
            diff, diff_ratio, user_id, target_date
        )

        # 5. 计算最终展示时长
        displayed_total = attributed_total + adjustment

        # 6. 写入对账日志
        self._write_log(user_id, target_date,
                        heartbeat_total, module_raw_total,
                        attributed_total, displayed_total,
                        diff, diff_ratio, reason, action, adjustment)

        # 7. 更新每日汇总表的 reconciliation_status
        self._update_daily_summary(user_id, target_date,
                                   displayed_total, action, adjustment)

        return {
            'heartbeat_total_s': heartbeat_total,
            'module_total_s': module_raw_total,
            'attributed_total_s': attributed_total,
            'displayed_total_s': displayed_total,
            'diff_s': diff,
            'diff_ratio': round(diff_ratio, 4),
            'reason': reason,
            'action': action,
            'adjustment_s': adjustment,
        }

    def _classify_diff(self, hb_total, mod_raw, attr_total,
                       diff, diff_ratio, user_id, target_date):
        """
        差异分类与决策。

        场景分析:
        A. 模块时长 > 心跳时长（模块在后台或息屏时仍在计时）
        B. 心跳时长 > 模块时长（有页面未接入SDK或心跳判活跃但模块未上报）
        C. 基本一致（差异在阈值内）
        """
        abs_diff = abs(diff)

        # 场景 C: 基本一致
        if abs_diff < self.THRESHOLD_WARN_S or abs(diff_ratio) < self.THRESHOLD_TRUST - 1 + 1:
            if abs_diff < self.THRESHOLD_WARN_S:
                return 'consistent', 'none', 0

        # 场景 A: 归因后模块时长 > 心跳时长
        if diff > self.THRESHOLD_WARN_S:
            if diff_ratio > self.THRESHOLD_RATIO:
                # 差异较大，可能模块在后台计时
                # 策略: 信任心跳（前台时间），将展示时长调整为心跳值
                return ('module_exceeds_heartbeat',
                        'trusted_heartbeat',
                        -(diff))  # 负调整，缩减到心跳值
            else:
                # 差异在可接受范围，信任模块（更精细）
                return ('module_slightly_exceeds',
                        'trusted_module', 0)

        # 场景 B: 心跳时长 > 模块时长
        if diff < -self.THRESHOLD_WARN_S:
            # 检查哪些槽有心跳但无模块上报
            missing_slots = self._find_missing_module_slots(
                user_id, target_date)

            if len(missing_slots) > 0:
                # 有未接入SDK的页面
                # 策略: 用心跳值补齐，将差额归属到 primary_scene
                primary_scene = self._get_primary_scene(
                    user_id, target_date, missing_slots)
                return ('missing_module_report',
                        'trusted_heartbeat',
                        -(diff))  # 正调整，补齐到心跳值
            else:
                # 心跳可能有误判（如心跳延迟导致）
                return ('heartbeat_may_overcount',
                        'trusted_module', 0)

        # 默认: 一致
        return 'consistent', 'none', 0

    def _find_missing_module_slots(self, user_id, target_date):
        """找到有心跳活跃但无任何模块上报的时间槽"""
        heartbeat_slots = self._get_heartbeat_active_slots(user_id, target_date)
        module_slots = self._get_module_occupied_slots(user_id, target_date)
        return heartbeat_slots - module_slots

    def run_daily_batch(self, target_date: date):
        """
        T+1 批量对账。
        每天 02:00 执行，处理前一天的全量数据。
        """
        users = self._get_active_users(target_date)
        stats = {'total': 0, 'consistent': 0, 'diff': 0, 'flagged': 0}

        for user_id in users:
            result = self.reconcile_user_day(user_id, target_date)
            stats['total'] += 1
            if result['reason'] == 'consistent':
                stats['consistent'] += 1
            elif abs(result['diff_s']) > self.THRESHOLD_FLAG_S:
                stats['flagged'] += 1
            else:
                stats['diff'] += 1

        # 标记终算完成
        self._finalize_daily_summaries(target_date)

        # 发送告警（异常率过高时）
        if stats['total'] > 0:
            anomaly_rate = (stats['diff'] + stats['flagged']) / stats['total']
            if anomaly_rate > 0.05:  # 超过 5% 异常
                self._send_alert(target_date, stats)

        return stats
```

### 7.3 实时归因处理流程

模块上报事件到达后，实时更新 Redis 中的归属数据：

```python
import redis
import json
from datetime import datetime

class RealtimeAttributionUpdater:
    """实时归因更新器 — 消费模块上报事件，更新 Redis 归属数据"""

    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        self.module_registry = ModuleRegistry()

    def on_module_event(self, event: dict):
        """
        消费 module_time_raw_events 的 Kafka/消息队列事件。
        实时更新 Redis 中的当天归属数据。
        """
        user_id = event['user_id']
        date_str = event['start_ts'][:10].replace('-', '')  # YYYYMMDD
        module_code = event['module_code']
        subject = event.get('subject', '')
        session_id = event['session_id']
        priority = self.module_registry.get_priority(module_code)

        # 计算涉及的槽位范围
        start_ts = datetime.fromisoformat(event['start_ts'].replace('Z', '+00:00'))
        end_ts = datetime.fromisoformat(event['end_ts'].replace('Z', '+00:00'))
        day_start = start_ts.replace(hour=0, minute=0, second=0, microsecond=0)

        start_slot = int((start_ts - day_start).total_seconds() // SLOT_DURATION)
        end_slot = int((end_ts - day_start).total_seconds() // SLOT_DURATION + 0.999)

        attribution_key = f"attribution:{user_id}:{date_str}"
        daily_key = f"module_time:{user_id}:{date_str}"

        pipe = self.redis.pipeline()

        for slot_idx in range(start_slot, end_slot):
            slot_value = f"{module_code}:{subject}:{session_id}"
            score = slot_idx

            # 检查该槽是否已有归属
            existing = pipe.zscore(attribution_key, slot_idx)
            # 用 ZADD NX 语义：只在槽位未被占用时写入
            # 但我们需要优先级比较，所以先读取已有的
            pipe.execute()

            existing_member = self.redis.zrangebyscore(
                attribution_key, slot_idx, slot_idx
            )
            if not existing_member:
                # 槽位空闲，直接写入
                pipe.zadd(attribution_key, {slot_value: slot_idx})
            else:
                # 槽位已被占用，比较优先级
                existing_module = existing_member[0].decode().split(':')[0]
                existing_priority = self.module_registry.get_priority(existing_module)
                if priority > existing_priority:
                    # 新模块优先级更高，替换
                    pipe.zremrangebyscore(attribution_key, slot_idx, slot_idx)
                    pipe.zadd(attribution_key, {slot_value: slot_idx})

            pipe.execute()

        # 更新模块日累计（增量）
        duration_s = int(event['duration_ms'] / 1000)
        pipe.hincrby(daily_key, module_code, duration_s)
        pipe.hincrby(daily_key, '_total_attributed', 0)  # 占位，总量在对账后更新
        pipe.execute()

    def get_today_duration(self, user_id: int) -> dict:
        """获取当日各模块时长（实时）"""
        date_str = datetime.now().strftime('%Y%m%d')
        daily_key = f"module_time:{user_id}:{date_str}"

        raw = self.redis.hgetall(daily_key)
        result = {}
        total = 0
        for k, v in raw.items():
            module_code = k.decode()
            seconds = int(v)
            result[module_code] = seconds
            if module_code != '_total_attributed':
                total += seconds

        result['_total'] = total
        return result
```

## 8. 重叠去重场景详解

### 8.1 场景一：浮动 AI 助手 + 同步课堂

**时间线：**

```
10:00 ─────────── 10:05 ─────────── 10:10 ─────────── 10:15
  │ textbook_read   │ textbook_read    │ textbook_read  │
  │                 │ + ai_chat(浮动)   │                 │
```

**处理：**
- 10:00-10:05：只有 `textbook_read`，归属 `textbook_read`，10 个槽
- 10:05-10:10：`textbook_read`(priority=20) 与 `ai_chat`(priority=30) 重叠 → 归属 `ai_chat`，10 个槽
- 10:10-10:15：只有 `textbook_read`，归属 `textbook_read`，10 个槽

**结果：**
- `textbook_read`：20 个槽 = 600 秒
- `ai_chat`：10 个槽 = 300 秒
- 总计：30 个槽 = 900 秒（无重复计时）

### 8.2 场景二：练习 + 错题复习（练习中查看错题）

**时间线：**

```
14:00 ──── 14:05 ──── 14:10 ──── 14:15 ──── 14:20
  │ practice  │ practice   │ practice  │ practice  │
  │           │ + mistake_ │           │           │
  │           │  review    │           │           │
```

**处理：**
- `practice` priority=35，`mistake_review` priority=25
- 14:05-14:10 的重叠段归属 `practice`（优先级更高）
- 注意：虽然学生确实在"看错题"，但主要活动上下文仍是练习，错题查看是辅助行为

**结果：**
- `practice`：40 个槽 = 1200 秒
- `mistake_review`：0 个槽（被完全去重）
- 但 `mistake_review` 的 `raw_reported_duration_s` 仍记录 300 秒，`overlap_deducted_s` 记录 300 秒

### 8.3 场景三：同优先级模块重叠

**场景：** 学生在 `ai_chat`(priority=30) 中提问，同时 `essay_writing`(priority=35) 的自动保存触发了一个后台计时事件。

**处理：**
- `essay_writing` 优先级 35 > `ai_chat` 优先级 30 → 归属 `essay_writing`
- 但这不合理 — 学生当前注意力在 AI 对话上，作文只是后台保活

**修正规则**：后台触发的模块事件需标记 `is_background=true`，后台事件优先级降为 0：

```python
if event.get('is_background'):
    effective_priority = 0  # 后台事件总是最低优先级
```

## 9. 状态流转

### 9.1 模块时长事件状态机

```
                    ┌──────────┐
    SDK 上报 ──────▶│ PENDING  │
                    │  (待归因)  │
                    └────┬─────┘
                         │
                    归因处理
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ATTRIBUTED│ │ OVERLAP  │ │ DISCARDED│
        │ (已归因)  │ │ (去重)    │ │ (已丢弃)  │
        └──────────┘ └──────────┘ └──────────┘
              │
         T+1 对账
              │
         ┌────┴────┐
         ▼         ▼
    ┌─────────┐ ┌──────────┐
    │RECONCILED│ │ FLAGGED  │
    │(对账完成) │ │(待人工)   │
    └─────────┘ └──────────┘
```

| 状态 | 含义 | 触发条件 |
|------|------|----------|
| `PENDING` | 刚接收，等待归因 | SDK 上报成功 |
| `ATTRIBUTED` | 已归属到本模块 | 无重叠或本模块优先级最高 |
| `OVERLAP` | 被去重 | 有更高优先级的模块同时活跃 |
| `DISCARDED` | 丢弃 | 心跳显示该时段不活跃（模块可能在后台计时但学生已离开） |
| `RECONCILED` | T+1 对账完成且一致 | 对账差异 < 阈值 |
| `FLAGGED` | 对账异常，待人工 | 对账差异 ≥ 阈值 |

### 9.2 每日汇总终算流程

```
每天 02:00 触发:

  1. 收集昨日所有 module_time_raw_events (status=PENDING)
     → 执行归因算法
     → 更新 attribution_status = ATTRIBUTED / OVERLAP / DISCARDED

  2. 计算每日模块汇总 module_time_daily
     → 从 time_slot_attribution 聚合
     → 写入 attributed_duration_s, raw_reported_duration_s, overlap_deducted_s

  3. 执行对账 reconciliation
     → 比对 attributed_duration_s vs heartbeat_duration_s
     → 计算差异并分类
     → 写入 time_reconciliation_logs
     → 按策略调整 displayed_duration_s

  4. 标记终算完成 is_finalized=1
     → 推送最终数据到数据仓库/BI
```

## 10. 错误处理与异常场景

### 10.1 上报异常

| 异常场景 | 处理策略 |
|----------|----------|
| 网络超时 | 客户端本地缓存，指数退避重试（1s, 3s, 10s, 30s），最多 3 次 |
| 服务端 5xx | 同上重试；超限后写入本地 SQLite 等待下次 APP 启动同步 |
| 服务端 4xx（参数错误） | 不重试，记录本地日志上报到异常监控 |
| 模块编码未注册 | 返回 400 + 错误码 `MODULE_NOT_REGISTERED`，丢弃事件 |
| 时间段非法 (end ≤ start) | 返回 400 + 错误码 `INVALID_TIME_RANGE`，丢弃事件 |
| duration_ms 超过 2 小时 | 截断到 2 小时，标记 `truncated=true` |
| 重复上报（相同 module_session + start_ts） | 幂等处理，返回成功但不重复写入 |

### 10.2 归因异常

| 异常场景 | 处理策略 |
|----------|----------|
| 同一槽位 ≥ 5 个模块重叠 | 记录告警，仍按优先级处理；标记 `multi_overlap=true` 供运营分析 |
| 模块上报时间跨天（如 23:50 - 00:10） | 拆分为两条事件，分别归属到两天的槽位 |
| 时区差异（客户端时区与服务端不一致） | 统一使用客户端 `start_ts` 的 UTC 时间进行槽位计算 |
| 心跳缺失但模块有上报 | 信任模块上报（心跳服务可能短暂故障），对账时标记 `heartbeat_missing=true` |

### 10.3 对账异常

| 异常场景 | 处理策略 |
|----------|----------|
| 模块时长 > 心跳时长 50%+ | 自动缩减为心跳值，记录 `action=trusted_heartbeat`，`reason=module_overcount` |
| 心跳时长 > 模块时长 50%+ | 用心跳值补齐，差额归属到 `primary_scene`，记录 `action=trusted_heartbeat` |
| 完全无心跳数据 | 使用模块归因值，标记 `heartbeat_missing=true`，不自动调整 |
| 完全无模块上报 | 使用心跳推导值，按 `scene` 字段拆分，标记 `module_missing=true` |
| 异常率 > 5% | 发送钉钉/飞书告警给架构组，附带异常用户列表 |

### 10.4 错误码定义

| 错误码 | HTTP | 含义 |
|--------|------|------|
| `MODULE_TIME_001` | 400 | 模块编码未注册 |
| `MODULE_TIME_002` | 400 | 时间段非法（end ≤ start） |
| `MODULE_TIME_003` | 400 | duration_ms 超出限制 |
| `MODULE_TIME_004` | 400 | 单批上报条数超限 |
| `MODULE_TIME_005` | 400 | module_session 与时间段重叠 |
| `MODULE_TIME_006` | 403 | 用户 ID 与当前认证用户不匹配 |
| `MODULE_TIME_007` | 429 | 上报频率超限（同用户每分钟 ≤ 30 条） |
| `MODULE_TIME_008` | 500 | 归因处理内部错误 |
| `MODULE_TIME_009` | 500 | 对账服务内部错误 |

## 11. 性能优化

### 11.1 写入优化

1. **批量写入**：模块上报事件先写入 Redis Stream 做缓冲，每 5 秒批量落库。
2. **分区表**：`module_time_raw_events` 按 `start_ts` 做月度分区，单月约 3000 万条（10万 DAU × 30条/天）。
3. **异步归因**：实时只做 Redis 更新，MySQL 的 `time_slot_attribution` 通过异步任务从 Redis 同步。

### 11.2 查询优化

1. **缓存策略**：
   ```
   Redis Key: module_time:{user_id}:{YYYYMMDD}
   TTL: 当天数据 7 天，历史数据不缓存
   ```

2. **预计算**：`module_time_daily` 表在 T+1 终算后固化，查询直接走索引。

3. **ClickHouse 加速**：时间槽级别查询走 ClickHouse，支持毫秒级范围扫描。

### 11.3 容量估算

| 数据表 | 日增量 | 月增量 | 年增量 |
|--------|--------|--------|--------|
| `module_time_raw_events` | ~300万 (10万DAU×30条) | ~9000万 | ~11亿 |
| `module_time_daily` | ~50万 (10万用户×5模块) | ~1500万 | ~1.8亿 |
| `time_slot_attribution` (ClickHouse) | ~1.4亿 (10万×2880×50%占用率) | ~42亿 | -- |
| `time_reconciliation_logs` | ~10万 | ~300万 | ~3600万 |

**建议**：
- `module_time_raw_events`：MySQL 月分区 + 3 个月后归档到 OSS
- `time_slot_attribution`：ClickHouse，TTL 90 天
- `module_time_daily`：MySQL 长期保留 + 按年归档

```sql
    sdk_version     VARCHAR(16)       NOT NULL DEFAULT '1.0' COMMENT '最低SDK版本要求',
    description     TEXT              NULL,
    created_at      DATETIME          NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME          NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (module_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='模块注册表';
```
