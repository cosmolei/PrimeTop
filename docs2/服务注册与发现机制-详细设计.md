# 服务注册与发现机制 - 详细设计

> 模块版本：v1.0 | 最后更新：2026-07-13
> 原始需求来源：`docs/design/启硕-PrimeTop-全学段AI辅助学习软件项目设计文档.md` §8.4 服务端架构
> 关联模块：服务端服务架构与部署设计、服务端分布式链路追踪与全链路可观测体系、服务端统一限流熔断与流量防护体系

## 1. 概述

### 1.1 背景与目标

PrimeTop 项目初期采用模块化单体架构，随着业务规模增长和团队扩大，系统将逐步演进为微服务架构。在微服务架构下，服务实例数量动态变化（自动扩缩容、发布重启），服务间调用（HTTP/RPC）需要依赖动态服务发现机制来获取目标服务的实例列表。

本设计旨在建立一套统一、高可用的服务注册与发现机制，解决以下问题：
1.  **服务寻址**：服务消费者无需硬编码服务提供者地址，通过服务名动态获取可用实例。
2.  **健康检查**：自动剔除不健康或下线的实例，确保流量只分发到正常节点。
3.  **负载均衡**：支持基于权重的负载均衡策略，结合灰度发布实现流量控制。
4.  **跨环境隔离**：支持开发、测试、预发、生产环境的命名空间隔离。
5.  **平滑演进**：支持从模块化单体到微服务的平滑过渡（单体模式下可仅作为配置中心或简单注册）。

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| 高可用 | 注册中心集群化部署，避免单点故障，具备故障自愈能力 |
| 最终一致性 | CAP 理论中选择 AP 或 CP 根据场景权衡，保证数据最终一致 |
| 低延迟 | 服务发现请求耗时控制在毫秒级，客户端具备本地缓存能力 |
| 灵活扩展 | 支持多种注册协议（Nacos, Consul, Eureka等），通过适配层隔离 |
| 安全可控 | 支持服务注册鉴权、访问控制，防止恶意注册 |

### 1.3 适用范围

- **服务端微服务**：用户服务、学习服务、AI服务、题目服务、支付服务等 Java/Kotlin 服务。
- **网关层**：API Gateway 需要根据路由规则动态发现后端服务实例。
- **异步任务**：需要感知服务状态的调度器或消费者。

## 2. 技术选型

### 2.1 选型对比

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| **Nacos** | 阿里开源，AP/CP模式切换，支持DNS与RPC，集成配置管理，国内生态活跃 | 社区维护力度较Consul略逊 | **推荐**：Spring Cloud 生态，国内云环境 |
| **Consul** | 强一致性(CP)，支持健康检查，Service Mesh集成好，Go语言高性能 | 不支持AP模式，配置管理功能相对较弱 | 对强一致性要求极高的场景 |
| **Eureka** | Spring Cloud 旧版默认，成熟稳定 | 已闭源(维护版)，仅支持AP，不支持CP模式 | 老旧项目维护，不推荐新项目使用 |
| **Kubernetes Service** | 原生支持，与容器编排深度集成，无需额外组件 | 依赖 K8s 环境，非容器化部署场景不适用 | 完全容器化部署，无跨平台调用需求 |
| **CoreDNS** | 云原生标准，基于 DNS 协议，通用性强 | 实时性不如 SDK，不支持复杂负载均衡策略 | 简单场景，跨语言异构系统 |

### 2.2 推荐方案

本系统推荐采用 **Nacos** 作为服务注册与发现中心。

**理由**：
1.  **AP/CP 切换**：对于内部服务调用，可接受短暂的不一致（AP模式）；对于配置中心类强一致性需求，可切换 CP 模式。
2.  **配置管理集成**：PrimeTop 已有“配置中心与动态配置管理”需求，Nacos 同时具备注册与配置能力，减少组件维护成本。
3.  **生态友好**：与 Spring Cloud Alibaba 完美集成，Dubbo 生态支持良好。
4.  **国内运维**：文档中文，国内大厂广泛使用，遇到问题社区支持充足。

## 3. 数据模型

### 3.1 核心实体

#### 3.1.1 服务 (Service)

服务标识的逻辑集合。

| 字段 | 类型 | 说明 |
|------|------|------|
| namespace | String | 命名空间 (如: public, dev, prod) |
| group | String | 分组名 (如: PRIMETOP_GROUP) |
| name | String | 服务名 (如: user-service, ai-service) |
| protectThreshold | Float | 保护阈值 (0~1)，当健康实例占比低于此值时触发保护模式 |

#### 3.1.2 实例 (Instance)

服务的具体运行节点。

| 字段 | 类型 | 说明 |
|------|------|------|
| instanceId | String | 实例唯一标识 (通常是 ip:port) |
| ip | String | 服务 IP 地址 |
| port | Integer | 服务端口 |
| weight | Double | 实例权重 (用于负载均衡) |
| healthy | Boolean | 健康状态 |
| enabled | Boolean | 是否启用 (人为下线) |
| ephemeral | Boolean | 是否临时实例 (临时实例丢失心跳即删除) |
| clusterName | String | 集群名称 (如: DEFAULT, HANGZHOU) |
| serviceName | String | 所属服务名 |
| metadata | Map<String, String> | 元数据 (版本、环境、灰度标签等) |

#### 3.1.3 元数据 (Metadata) 规范

元数据用于服务治理和灰度控制。

| Key | Value示例 | 说明 |
|-----|-----------|------|
| version | v1.0.0 | 服务版本号 |
| env | prod | 运行环境 |
| preserved.register.source | SPRING_CLOUD | 注册来源 |
| gray | true | 是否为灰度实例 |
| zone | cn-hangzhou | 可用区 |

## 4. 核心流程设计

### 4.1 服务注册

**流程**：
1.  服务启动时，读取配置（服务名、分组、命名空间、IP、端口）。
2.  构建 `Instance` 对象，添加元数据（版本、启动时间等）。
3.  调用 Nacos SDK 发送注册请求 (`POST /nacos/v1/ns/instance`)。
4.  Nacos Server 将实例信息写入内存，并持久化到数据库（若为持久化实例）。
5.  返回注册成功。

**关键代码示例 (Spring Cloud)**：

```java
@SpringBootApplication
@EnableDiscoveryClient
public class UserServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(UserServiceApplication.class, args);
    }
}

# application.yml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_ADDR:127.0.0.1:8848}
        namespace: ${NACOS_NAMESPACE:prod}
        group: PRIMETOP_GROUP
        metadata:
          version: @project.version@
          env: prod
```

### 4.2 服务发现

**流程**：
1.  服务消费者发起调用（如 `user-service`）。
2.  客户端 SDK 优先查询**本地缓存**的服务列表。
3.  若缓存过期或不存在，向 Nacos Server 发起查询请求 (`GET /nacos/v1/ns/instance/list`)。
4.  Nacos Server 返回该服务下所有健康的实例列表。
5.  客户端更新本地缓存，并执行负载均衡算法（如加权随机）选择一个实例。
6.  发起实际调用。

**负载均衡策略**：
- **随机** (Random)：默认。
- **轮询** (Round Robin)：适用于实例性能相近场景。
- **加权响应时间** (Weighted Response Time)：响应时间越短权重越高。
- **同Zone优先**：优先调用同可用区实例，降低延迟。

### 4.3 健康检查

Nacos 支持两种模式：
1.  **临时实例 (Ephemeral)** - **推荐**
    -   **机制**：客户端主动上报心跳。
    -   **间隔**：默认 5s。
    -   **超时**：默认 15s 未收到心跳则剔除。
    -   **适用**：绝大多数业务服务。
2.  **持久化实例**
    -   **机制**：Nacos Server 主动探测 (TCP/HTTP)。
    -   **适用**：需要由 Nacos 主动管理生命周期的服务（如数据库）。

**配置示例**：
```yaml
spring:
  cloud:
    nacos:
      discovery:
        ephemeral: true # 开启临时实例模式
```

### 4.4 服务下线

**主动下线**：
-   服务正常关闭（SIGTERM）时，SDK 发送下线请求 (`DELETE /nacos/v1/ns/instance`)。
-   Spring Boot 支持 `@PreDestroy` 钩子自动触发。

**被动下线**：
-   临时实例心跳超时，Server 自动剔除。
-   健康检查失败，Server 标记为不健康。

### 4.5 故障保护

当服务注册中心不可用（网络分区、宕机）时，为防止雪崩，开启**保护模式**。

-   **触发条件**：健康实例占比 < 保护阈值 (默认 0.0)。
-   **保护行为**：
    1.  不再剔除过期实例。
    2.  客户端尝试使用本地缓存中的列表进行调用，即使可能包含已下线实例。
    3.  配合客户端重试机制和熔断器，保证基本可用性。

## 5. 客户端集成

### 5.1 Spring Cloud 集成

**依赖**：
```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

**RestTemplate 调用**：
```java
@LoadBalanced
@Bean
public RestTemplate restTemplate() {
    return new RestTemplate();
}

// 调用
String result = restTemplate.getForObject("http://ai-service/chat", String.class);
```

**Feign 调用**：
```java
@FeignClient(name = "ai-service")
public interface AiServiceClient {
    @GetMapping("/chat")
    String chat(@RequestParam String question);
}
```

### 5.2 Dubbo 集成

**依赖**：
```xml
<dependency>
    <groupId>org.apache.dubbo</groupId>
    <artifactId>dubbo-registry-nacos</artifactId>
</dependency>
```

**配置**：
```yaml
dubbo:
  registry:
    address: nacos://${NACOS_ADDR:127.0.0.1:8848}
```

### 5.3 纯 HTTP/非 Java 客户端

对于非 Java 服务（如 Python 数据分析服务，Go 中间件），使用 Nacos **Open API**。

**获取实例列表**：
```bash
curl -X GET 'http://127.0.0.1:8848/nacos/v1/ns/instance/list?serviceName=ai-service&namespaceId=prod'
```

**响应示例**：
```json
{
  "doms": [
    {
      "instanceId": "10.0.0.1:8080",
      "ip": "10.0.0.1",
      "port": 8080,
      "healthy": true,
      "weight": 1.0,
      "metadata": { "version": "v1.0.0" }
    }
  ]
}
```

客户端需实现：
1.  定时轮询 (Polling) 或长轮询获取服务列表。
2.  本地缓存。
3.  简单的负载均衡（如随机）。

## 6. 灰度发布支持

利用 `metadata` 和负载均衡策略实现灰度。

### 6.1 场景

新版本 `v2.0` 的 `user-service` 需灰度 10% 流量。

### 6.2 实现

1.  **注册实例**：
    -   老版本实例：`metadata: { version: v1.0.0, gray: false }`
    -   新版本实例：`metadata: { version: v2.0.0, gray: true }`

2.  **路由策略**：
    -   实现自定义 `LoadBalancer` (基于 Spring Cloud LoadBalancer)。
    -   解析请求上下文（如 Header `x-user-id`）。
    -   若用户 ID 哈希值落在灰度范围内，优先选择 `gray=true` 的实例。
    -   否则选择 `gray=false` 的实例。

**伪代码**：
```java
public class GrayLoadBalancer implements ReactorServiceInstanceLoadBalancer {
    @Override
    public Mono<Response<ServiceInstance>> choose(Request request) {
        String userId = request.getContext().getHint("userId");
        boolean isGrayUser = HashUtil.md5(userId).endsWith("0"); // 简单模拟 10% 灰度

        List<ServiceInstance> instances = discoveryClient.getInstances("user-service");
        List<ServiceInstance> candidates = instances.stream()
            .filter(inst -> isGrayUser == "true".equals(inst.getMetadata().get("gray")))
            .collect(Collectors.toList());

        // 若没有灰度实例或匹配实例，回退到默认实例
        if (candidates.isEmpty()) candidates = instances;

        ServiceInstance chosen = candidates.get(ThreadLocalRandom.current().nextInt(candidates.size()));
        return Mono.just(new DefaultResponse(chosen));
    }
}
```

## 7. 运维与监控

### 7.1 控制台管理

Nacos 提供内置控制台 (`http://nacos-server:8848/nacos`)，用于：
-   查看服务列表和实例状态。
-   上下线实例（手动运维）。
-   配置权重（用于流量调整）。
-   查看服务详情和元数据。

### 7.2 监控指标

需接入 Prometheus 监控 Nacos 及客户端 SDK 指标：

| 指标 | 含义 | 告警阈值 |
|------|------|----------|
| nacos_monitor{type="serviceCount"} | 注册服务数量 | 突变告警 |
| nacos_monitor{type="instanceCount"} | 注册实例数量 | 突变告警 |
| nacos_monitor{type="pushCount"} | 服务变更推送次数 | 异常波动 |
| sdk_subscribe_fail | 订阅失败次数 | > 0 |
| sdk_query_timeout | 查询超时次数 | > 5/min |

### 7.3 日志规范

**客户端日志**：
-   注册成功/失败。
-   心跳发送异常。
-   拉取服务列表变更。

**服务端日志**：
-   实例注册/注销请求。
-   心跳超时剔除事件。
-   保护模式触发/恢复事件。

## 8. 安全设计

### 8.1 访问控制

Nacos 2.x+ 开启鉴权。

1.  **服务端配置**：
    ```yaml
    nacos.core.auth.enabled=true
    nacos.core.auth.server.identity.key=primetop
    nacos.core.auth.server.identity.value=primetop_secret
    ```

2.  **客户端配置**：
    ```yaml
    spring:
      cloud:
        nacos:
          discovery:
            username: nacos
            password: nacos
    ```

### 8.2 通信加密

生产环境建议在 Nacos 前部署 TLS 终结（如 Nginx Ingress），或配置 Nacos Server HTTPS。

## 9. 异常处理与容灾

### 9.1 注册中心不可用

-   **现象**：所有服务无法获取新实例列表，无法注册新服务。
-   **对策**：
    1.  **客户端容错**：SDK 读取本地缓存（`/home/user/nacos/naming/...`），即使断网也能维持已建立连接的调用。
    2.  **运维预案**：保留最近一次的服务列表快照，紧急情况下可手动配置 DNS 解析或 Hosts 文件（仅限极端故障）。

### 9.2 网络分区

-   **现象**：部分 Server 与 Client 失联。
-   **对策**：
    -   AP 模式下，分区期间各分区数据不一致。
    -   网络恢复后，Nacos 通过 Raft 协议或同步机制进行数据对齐。

## 10. 版本演进计划

### 阶段一：单体应用期 (MVP)
-   仅引入 Nacos 作为**配置中心**。
-   服务内模块通信直接调用，无需服务发现。

### 阶段二：微服务拆分期 (V1.0+)
-   引入 Nacos **服务发现**。
-   API Gateway 集成 Nacos 实现动态路由。
-   Spring Cloud Boot 服务全部接入。

### 阶段三：多语言/云原生期 (V2.0)
-   Go/Python 服务通过 Open API 或 gRPC 接入。
-   结合 Kubernetes Service Mesh (Istio)，Nacos 仅用于控制面元数据管理。
