# 服务端-体育体测训练引擎 详细设计

## 1. 模块概述

### 1.1 功能定位

体育体测训练引擎(Fitness Training Engine, 下文简称 FTE)面向全学段学生,围绕《国家学生体质健康标准》体测项目,提供:

1. **体测项目标准查询**:按学段/年级/性别/项目返回国家标准评分表(分数、等级、及格线)。
2. **AI 视觉计数训练**:跳绳、仰卧起坐、俯卧撑、深蹲、高抬腿、坐位体前屈辅助等可视觉计数项目,端侧姿态估计实时计数,服务端抽样复核与质量分校准。
3. **手动/设备录入项目**:50米跑、800/1000米跑(计时)、肺活量(峰流量/肺活量计读数)、立定跳远(距离),支持手动录入与蓝牙体测设备数据对接。
4. **体测模拟考**:按真实体测流程组考(项目顺序、间隔休息、规则约束),生成与标准对齐的成绩单。
5. **体测档案与纵向追踪**:历次成绩入库,计算趋势、预测达标风险,联动「学生电子成长档案与综合素质评价服务」写入体测维度。
6. **训练计划编排**:基于薄弱项目生成周期性训练计划,联动「每日任务智能生成与学习计划执行追踪服务」派发每日训练任务。

### 1.2 覆盖范围

| 维度 | 覆盖 | 不覆盖 |
| --- | --- | --- |
| 学段 | 小学/初中/高中 | 幼儿(仅趣味运动游戏,不在本引擎) |
| 项目 | 国家标准体测全项目 + 家庭训练动作库 | 专业运动员训练、医疗康复运动处方 |
| 端 | Android/iOS 端侧视觉计数,服务端校准 | 纯硬件体测站全流程(仅预留设备接入) |
| 数据 | 成绩、评分、趋势、风险预警 | 原始视频/图像(隐私红线,见 §12) |

### 1.3 设计原则

- **端侧优先**:姿态估计、实时计数全部在端侧完成,服务端只接收计数结果与抽样骨架关键点,不上传原始影像。
- **标准对齐**:所有评分换算以国家标准评分表为准,表数据版本化管理,可随政策更新。
- **结果可信**:单端计数可能作弊(如摇手机模拟跳绳),引入动作质量分 + 服务端一致性校验 + 异常模式识别三级防作弊。
- **弱网可用**:训练计数完全离线可行,仅在会话结束时一次性上报,弱网队列补偿。

### 1.4 权威边界

| 职责 | 权威方 |
| --- | --- |
| 体测标准表(分数/等级) | FTE(本引擎) |
| 姿态估计与实时计数 | 客户端(端侧引擎,见《客户端-…》,本引擎只约定上报协议) |
| 骨架关键点复核、质量分校准 | FTE |
| 成长档案体测维度写入 | 学生电子成长档案服务(FTE 仅发事件) |
| 每日训练任务派发 | 每日任务服务(FTE 仅发事件) |
| 视力/屈光检查 | 不承接,只做用眼健康科普跳转 |

## 2. 整体架构

### 2.1 引擎架构图

```
┌─────────────────────────── 客户端 ───────────────────────────┐
│ 端侧姿态估计引擎(Pose)  实时计数器  离线缓存队列  设备BLE接入    │
└──────┬───────────────────────────┬───────────────────────────┘
       │ 计数事件流(skeleton KP)   │ 会话结果上报(HTTPS)
       ▼                           ▼
┌─────────────────────────── 服务端 FTE ───────────────────────┐
│ 接入层: 计数事件接收器(高频, Kafka)  / 会话API(BFF, HTTPS)      │
│ 领域层: 计数校准器 │ 质量分评估 │ 评分换算器 │ 防作弊校验 │ 计划编排 │
│ 存储层: MySQL(成绩/会话) │ Redis(实时计数/锁) │ OSS(关键点抽样)  │
│ 事件层: fitness_outbox → 成长档案 / 每日任务 / 消息通知          │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 模块职责

| 模块 | 职责 |
| --- | --- |
| CounterIngestService | 接收端侧高频计数事件(骨架关键点 + 计数),写入 Redis 实时流并抽样落 OSS |
| CountCalibrator | 服务端抽样复核端侧计数(重放关键点序列二次计数),偏差超阈值触发校准系数修正 |
| ScoreConverter | 按标准表将原始成绩(个/秒/毫升/厘米)换算为分数与等级 |
| AntiCheatGuard | 作弊模式识别:计数频率分布异常、关键点轨迹异常、设备静止但计数增长等 |
| ExamOrchestrator | 体测模拟考编排:项目顺序、休息间隔、规则守卫、成绩汇总 |
| PlanScheduler | 基于薄弱项目生成训练计划,事件驱动派发每日任务 |
| ArchiveWriter | 成绩归档、趋势计算、达标风险预测 |


### 3.3 Redis 键设计

```
fte:count:{sessionId}            HASH  实时计数状态 {count, lastSeq, startedAt}  TTL=2h
fte:lock:session:{sessionId}     SET   会话操作锁 NX EX=30
fte:lock:archive:{userId}:{proj} SET   档案更新锁 NX EX=10
fte:exam:{examId}:progress       HASH  模拟考进度 {currentIndex, restUntil}  TTL=6h
fte:anticheat:{userId}:cnt       STRING 可疑计数窗口(滑动) TTL=24h
fte:standard:{ver}:{project}     STRING 评分表缓存(JSON压缩) 常读,变更主动失效
```

### 3.4 端侧上报协议(骨架关键点)

约定端侧引擎每完成一个动作周期(或每 5 秒兜底)上报一次计数事件:

```json
{
  "sessionId": "182300000001",
  "seq": 137,
  "count": 136,
  "cycleMs": 580,
  "qualityHint": 0.93,
  "kpSample": {
    "frames": 3,
    "points": "BASE64(ZSTD(骨架关键点数组))",
    "note": "仅33个关键点x/y/z/visibility, 不含任何像素数据"
  }
}
```

> 红线:`kpSample` 只包含姿态关键点坐标,端侧 SDK 在上报前剥离全部图像帧,服务端网关层再加一道 schema 校验,尺寸超阈(>64KB/事件)直接拒绝并记安全事件。

### 4.2 POST /sessions 创建训练会话

```
POST /api/v1/fitness/sessions
{ "project": "rope_skipping", "mode": "TRAIN", "targetSeconds": 60 }
→ 201
{ "sessionId": "182300000001", "sessionNo": "FS20261122000001",
```

幂等:`Idempotency-Key` 重复返回首个会话(同 project+mode+5分钟窗口内),避免断网重建。守卫:防沉迷在线时长校验失败返回 48010。

### 4.3 POST /sessions/{id}/count-events 计数事件上报

```
POST /api/v1/fitness/sessions/{id}/count-events
Header: X-Count-Token: cst_xxx
Body: 见 §3.4
→ 202 Accepted { "serverCount": 136, "calibrated": false }
→ 409  序列号乱序(seq <= lastSeq)
→ 48031 关键点载荷超限(安全事件上报)
```

高频路径:单会话峰值约 2 事件/秒,直接走 Kafka 异步落盘,API 层只做鉴权+校验+seq 去重(Redis `fte:count:{sessionId}` CAS)。

### 4.4 POST /sessions/{id}/finish 结束会话并评分

```

  "status": "SCORED",
  "clientCount": 136, "calibratedCount": 134, "qualityScore": 88.5,
```

## 5. 核心流程

### 5.1 视觉计数训练主链路

```
端侧                 网关              FTE 领域服务                    存储/事件
 │ 创建会话           │                 │                              │
 ├──────────────────→├────────────────→│ 守卫G1(在线时长)             │
 │← 202 sessionId ───├←────────────────┤ 写 fte:count                 │
 │ Pose实时计数        │                 │                              │
 ├─ count-events ───→├─ Kafka ────────→│ 校验seq/载荷                 │→ Redis实时流
 │  (异步, 无阻塞)     │   (202立即返回)  │ 抽样10%落OSS                  │→ OSS骨架样本
 │ 用户停止            │                 │                              │
 ├─ finish ─────────→├────────────────→│ 校准(抽样重放)               │
 │                    │                 │ 防作弊三级校验               │
 │                    │                 │ 评分换算(标准表)             │
 │← SCORED结果 ──────├←────────────────┤ 档案 upsert + 趋势/风险       │→ MySQL
 │                    │                 │ fitness_outbox               │→ 事件总线
 │                    │                 │  → FitnessSessionScored      │
```

### 5.2 服务端计数校准链路

1. finish 时取该会话抽样段(默认 10%,至少 2 段),从 OSS 读关键点序列。
2. 重放计数:对关键点序列跑与端侧同构的服务端计数算法(轻量版 BlazePose 复现),得到 `serverCount`。
3. 偏差率 `|client-server|/max(server,1)`:≤3% 采信端侧;3%-10% 取两者均值并记录校准系数;>10% 标记 `calibrated=false`,进入人工抽查队列。
4. 校准系数按(端侧引擎版本 × 项目)聚合,供运营配置端侧系数热更新。

### 5.3 体测模拟考链路

```
组考(顺序+规则) → 逐项目执行(复用训练会话,mode=MOCK_EXAM)
  → 守卫G6 项目顺序守卫: index 必须等于当前进度
  → 守卫G7 休息间隔守卫: now >= restUntil
  → 全部完成 → 汇总评分 → 生成薄弱项 → 事件 FitnessExamFinished
  → PlanScheduler 消费事件生成周期训练计划 → 事件 DailyTaskRequested
```

## 6. 状态机与守卫

### 6.1 状态机迁移表

| 当前状态 | 事件 | 目标状态 | 守卫 |
| --- | --- | --- | --- |
| - | 创建会话 | CREATED | G1 防沉迷/权限 |
| CREATED | 首个计数事件 | COUNTING | G2 会话归属 |
| COUNTING | pause | PAUSED | G3 暂停次数<5 |
| PAUSED | resume | COUNTING | G4 未超总会话时长 |
| COUNTING/PAUSED | finish | FINISHED | G5 最小时长(≥10s) |
| FINISHED | 校准完成 | CALIBRATING→SCORED | - |
| SCORED | 归档 | ARCHIVED | 幂等 |
| 任意(非ARCHIVED) | 判作弊 | REVOKED | 管理端权限 |

非法迁移一律返回 48040,不做静默纠正。

### 6.2 守卫定义

| 守卫 | 规则 | 失败码 |
| --- | --- | --- |
| G1 | 防沉迷剩余时长 ≥ 项目预算时长;家长端未禁用体育训练 | 48010 / 48011 |
| G2 | count-token 与会话绑定,用户一致 | 48012 |
| G3 | 单会话暂停 ≤ 5 次 | 48013 |
| G4 | CREATED 起 24h 内必须 finish,否则自动过期 | 48014 |
| G5 | 训练时长 ≥ 10s 才允许 finish | 48015 |
| G6 | 模拟考项目按 schedule 顺序提交 | 48022 |
| G7 | 休息间隔未到禁止提交下一项 | 48021 |
| G8 | 标准表版本必须存在且为当前生效版本 | 48023 |
| G9 | 同一项目 60s 内不可重复 finish(防重复上报) | 48024 |
| G10 | 手动录入成绩超出该项目世界纪录/常识上限即拒绝 | 48025 |

### 6.3 竞态裁决

- **并发 finish**:Redis 锁 + DB `version` 乐观锁,后到请求返回 48024 幂等提示并携带首个结果。
- **计数事件与 finish 乱序**:事件 seq 持久化,finish 时以 `lastSeq` 为准回放补偿,补偿窗口 ≤5s,超时标记 `calibrated=false`。
- **档案并发更新**:按 (userId, project) 分片锁串行化,趋势计算异步化(事件驱动),不在 finish 关键路径。

## 7. 幂等与并发

- 所有写接口强制 `Idempotency-Key`(24h 去重窗口,Redis + DB 双保险)。
- `session_no` 全局唯一生成:号段服务按日发放,格式 `FS+yyyyMMdd+6位序号`(对齐《服务端-分布式唯一ID生成与序号管理服务》)。
- finish 与评分结果以会话为幂等粒度:重复 finish 返回首个评分结果,不做二次扣分/二次发事件。
- 模拟考汇总采用 Saga:分项成绩各自入库,汇总失败可重试,重试以 examId 幂等。

## 10. 降级矩阵

| 故障 | 降级行为 | 恢复动作 |
| --- | --- | --- |
| 计数校准超时 | 采信端侧计数,标记 calibrated=false,事后异步校准 | 校准结果差异>10% 发人工抽查 |
| Kafka 不可用 | 计数事件本地落盘队列,恢复后按 seq 补传(≤24h) | 补传完成自动触发重评 |
| 标准表缓存失效 | 回源 DB 读表,DB 故障时拒绝评分(48023),训练计数不受影响 | 缓存重建 |
| 端侧引擎在低配机不可用 | 客户端降级为「节拍引导+手动计数」模式,服务端质量分记 N/A | 引擎热更新 |
| 防作弊模型不可用 | 仅做规则级校验(频率分布/设备静止),可疑阈值收紧 | 模型恢复后回放补检 |
| OSS 关键点写入失败 | 跳过抽样落盘,校准链路旁路,标记无样本 | 补写任务 |

## 12. 合规

- **影像红线**:全链路禁止上传原始视频/图像,仅骨架关键点;客户端 SDK 输出层做物理剥离,服务端网关做载荷校验,违规事件上报安全中心。
- **未成年人保护**:体测成绩属健康敏感数据,家长端默认可见;对外分享需二次授权;B 端数据输出走脱敏(对齐《服务端-数据脱敏规则引擎与敏感信息动态遮蔽服务》)。
- **数据留存**:骨架样本 30 天后物理删除;成绩档案随账号注销流程删除(对齐《端到端流程设计-数据导出与账户注销完整链路》)。
- **标准引用**:评分表引用国家标准的版本号须标注于成绩单展示页(「依据 GB-2026-01 标准」)。

## 13. 契约对齐

- 计数上报协议与端侧引擎版本绑定,协议变更走 API 版本管理(对齐《服务端API版本管理与接口兼容性策略》),新旧协议并存 ≥2 个客户端大版本。

- 会话与成绩的数据权限走统一行级隔离(对齐《服务端-统一数据权限控制框架与行级数据范围隔离引擎》)。
