### 0.2 范围界定

**本文档覆盖（In Scope）：**

1. 教研组 / 备课组的组织管理（创建、成员、角色、组长交接）。
2. 集体备课活动全流程（发起 → 议程 → 研讨 → 共识 → 产出归档）。
3. 组内共享资源池（上传、共享范围、采纳统计、质量评分）。

7. 教研统计看板数据源与画像事件发布。

**本文档不覆盖（Out of Scope）：**

- 单份教案的多人协作编辑与冲突解决（见《服务端-教师智能备课辅助》§4.5/§5.3）。

- 教师培训课程/继续教育学时（training 域，仅消费其结果）。
- 教师能力画像计算本身（本文档仅作为事件生产方对接）。
- 教师端客户端页面交互（后续客户端文档另行细化）。

## 1. 概述

### 1.1 模块定位

`tr-service` 是 PrimeTop 教师域与 B 端合作场景下的**教研协作基础设施**，为学校提供"组织（教研组/备课组）— 活动（集体备课/听评课）— 沉淀（共享资源池）— 成长（同行评议/师徒带教）"的完整教研数字化闭环，并向教师专业发展画像持续输出协作行为事件。

### 1.2 核心职责

| 职责 | 说明 | 关键指标 |
| --- | --- | --- |
| 教研组织管理 | 教研组/备课组的创建、成员增删、组长角色与交接 | 组织信息查询 P99 < 100ms |
| 集体备课活动 | 按章节/主题组织集体备课，沉淀结论与教案产出 | 活动完结后产出关联率 ≥ 70% |
| 共享资源池 | 组内/校内共享教案、课件、题组，统计采纳与评分 | `shared_resources_count` 日增量准确率 100% |
| 同行评议 | 教案/蓝图/资源的同行评审流程与量表评分 | 评议按时完成率 ≥ 75% |
| 师徒带教 | 结对关系管理、带教记录双向确认、时长累计 | `mentorship_hours` 与确认记录一致率 100% |
| 听评课 | 听课预约、课堂观察量表评分、改进建议留档 | 听评课记录归属正确率 100% |
| 画像事件发布 | 向 `teacher.behavior.events` 发布教师协作行为事件 | 事件投递 At-Least-Once + 幂等消费 |

### 1.3 依赖关系

```text
上游依赖：
├── 用户服务/多角色统一身份（教师身份、teacher_id 校验）
├── 学校教务系统对接适配器（school_id、教师任教科目/年级来源）
├── 教材版本与章节管理服务（chapter_id、textbook_version_id）
├── 备课辅助引擎（lesson_plan 关联、协作编辑锁）
├── 命题蓝图引擎（blueprint 关联、教研组长审核回调）
├── 统一数据权限控制框架（教研组长数据范围扩展）
├── 统一延迟任务调度引擎（评议超时过期、活动提醒）
├── 统一通知消息模板引擎（教研通知触达）
└── 内容审核管线（共享资源 AI 初筛 + 人工复审）

下游消费：
├── 教师专业发展画像（PEER_REVIEW_DONE / MENTORSHIP_LOGGED）
├── 管理后台数据分析看板（教研活跃度指标）
├── B 端合作机构看板（学校教研能力评估）
└── 通知中心（站内信 + 教师端推送）
```

### 1.4 设计原则

1. **聚合优先，隐私红线**：教研域所有数据默认只触达**教师行为与聚合统计**，不触达学生个人身份数据；班级学情仅以聚合形式被组长查询（经数据权限框架鉴权）。
2. **事件驱动**：所有跨域影响通过事件（Outbox）传播，避免服务间同步长链路。
3. **幂等与补偿**：邀约/确认/事件发布均幂等，延迟任务驱动超时状态流转。
4. **组织即权限**：教研组角色（组长/干事/成员）是教师域数据权限的一等公民，与统一数据权限框架对接。

### 3.2 与统一数据权限框架的对接

教研组长是教师域新增的**数据范围类型**（`DataScopeType = TEACHING_RESEARCH`）：

```java
// 向统一数据权限框架注册的范围解析器（部署于 tr-service 内）
@Component
public class TeachingResearchScopeResolver implements DataScopeResolver {

    @Override
    public DataScopeType supports() {
        return DataScopeType.TEACHING_RESEARCH;
    }

    /**
     * 组长可查询范围 = 其担任 LEADER 的教研组所覆盖的
     * (school_id, stage, subject_id) 下全部任教班级的【聚合】数据。
     * 框架据此注入 SQL 行级过滤条件，个人明细仍按班级权限收敛。
     */
    @Override
    public Set<DataScope> resolve(long teacherId) {
        List<TrGroup> leadingGroups = groupRepository
                .findLeaderGroups(teacherId);          // status = ACTIVE
        return leadingGroups.stream()
                .map(g -> DataScope.builder()
                        .schoolId(g.getSchoolId())
                        .stage(g.getStage())
                        .subjectId(g.getSubjectId())
                        .aggregateOnly(true)            // 聚合红线
                        .build())
                .collect(Collectors.toSet());
    }
}
```

命题蓝图引擎 / 班级管理服务的"教研组长"审核与跨班查询，统一通过该范围解析器获得数据边界，**不各自硬编码角色判断**。

## 4. 数据模型设计

### 4.1 ER 关系总览

```text
tr_group 1 ─── n tr_group_member（teacher 维度视图）
tr_group 1 ─── n tr_prep_group 1 ─── n tr_collective_prep 1 ─── n tr_prep_attendance
                                        tr_collective_prep 1 ─── n tr_prep_discussion
teacher 1 ─── n tr_shared_resource 1 ─── n tr_resource_usage
tr_peer_review n ─── 1 目标（lesson_plan / blueprint / shared_resource / observation）
tr_mentorship 1 ─── n tr_mentorship_log
teacher(观察者) 1 ─── n tr_observation n ─── 1 teacher(被观察者) / class
```

### 4.2 表结构（MySQL 8.0，utf8mb4）


## 5. API 接口设计

统一前缀：`/api/v1/tr`。响应格式、分页参数、错误体遵循《服务端统一响应封装与分页查询规范》；鉴权走网关 JWT，角色校验见 §10。以下给出核心接口契约。

### 5.1 组织管理

#### POST /api/v1/tr/groups —— 创建教研组（校级管理员/教务）

```json
// Request
{
  "schoolId": 20001,
  "name": "高中数学教研组",
  "stage": "SENIOR",
  "subjectId": 3,
  "code": "MATH-SENIOR",
  "leaderTeacherId": 88001,
  "secretaryTeacherIds": [88002],
  "memberTeacherIds": [88003, 88004]
}
// Response
{
  "code": 0,
  "data": { "groupId": 1001, "status": "ACTIVE" },
  "traceId": "..."
}
```

约束：同校同学段同学科仅一个 ACTIVE 教研组（唯一键兜底 + 预检）；组长必须为该校在职教师（调用户服务校验）。

#### PUT /api/v1/tr/groups/{groupId}/leader —— 组长交接

```json
// Request
{ "newLeaderTeacherId": 88002, "reason": "换届" }
```

事务内：旧组长 → `MEMBER`，新组长角色写入 `tr_group_member`，`tr_group.leader_teacher_id` 更新，发布 `tr.group.leader_changed`（数据权限框架订阅刷新缓存）。

#### GET /api/v1/tr/schools/{schoolId}/groups?stage=&subjectId=&page=&size=

分页返回组列表（含 memberCount、leader 概要）。其余成员增删接口（`POST /groups/{id}/members`、`DELETE /groups/{id}/members/{teacherId}`）为常规 CRUD，从略。

## 6. 状态机设计

### 6.1 集体备课 `tr_collective_prep.status`

```text
DRAFT ──publish──> SCHEDULED ──start──> IN_PROGRESS ──end──> SUMMARIZING ──conclude──> COMPLETED ──archive(30d)──> ARCHIVED
  │                    │                     │                                       
  │                    ├──cancel──> CANCELLED<┘（SCHEDULED/IN_PROGRESS 可取消）      
  └──discard──> (删除)
```

| 当前态 | 目标态 | 动作 | 守卫条件 |
| --- | --- | --- | --- |
| DRAFT | SCHEDULED | publish | 主持人/干事发起；议程非空；scheduleTime 未来 |
| SCHEDULED | IN_PROGRESS | start | 主持人/干事；到达 scheduleTime±30min 或人工提前开始 |
| IN_PROGRESS | SUMMARIZING | end | 主持人/干事；出勤已登记 |
| SUMMARIZING | COMPLETED | conclude | conclusion.consensus 非空；记录人签署 |
| COMPLETED | ARCHIVED | archive | 完成后 30 天定时任务自动归档 |
| SCHEDULED / IN_PROGRESS | CANCELLED | cancel | 组长/发起人；必填 cancel_reason；通知全部出勤对象 |

### 6.2 同行评议 `tr_peer_review.status`

```text
INVITED ──accept──> ACCEPTED ──submit──> SUBMITTED ──resolve──> RESOLVED
   │                    │                                          ▲
   ├──decline──> DECLINED│                                          │
   │                    └──(超时)──> EXPIRED                        │
   └──(超时未响应)──> EXPIRED ──reassign──> INVITED(新评议人) ─────┘
```

- 量表模板：`rubric_template` 编码化，V1 内置 4 套（`LESSON_PLAN_RUBRIC_V2` / `BLUEPRINT_RUBRIC_V2` / `RESOURCE_RUBRIC_V1` / `COURSE_DEMO_RUBRIC_V1`），维度定义存配置中心（键：`tr.review.rubric.{code}`），允许运营扩展而无需发版。
- 超时过期由统一延迟任务调度引擎在 `deadline_at` 触发回调 `POST /internal/tr/peer-reviews/expire`（批量安全接口）。

### 6.3 师徒带教 `tr_mentorship.status`

| 当前态 | 目标态 | 动作 | 守卫 |
| --- | --- | --- | --- |
| PENDING | ACTIVE | 双方确认 | mentor 与 mentee 均已 confirm |
| ACTIVE | PAUSED | pause | 任一方或组长申请，另一方可异议（工单） |
| PAUSED | ACTIVE | resume | 组长操作 |
| ACTIVE / PAUSED | COMPLETED | complete | 到达 end_date 自动转（延迟任务）或组长手动；仍有未确认 log 时先冻结转 `SUMMARIZING_`（V1 简化为：提示存在 PENDING_CONFIRM 记录，强制先处理） |
| 任意未完结 | TERMINATED | terminate | 组长/教务，必填原因 |

`tr_mentorship_log.status`：`DRAFT → PENDING_CONFIRM → CONFIRMED / REJECTED`（驳回后可修改重提，`event_published` 仅在 CONFIRMED 事务中置 1）。

### 7.2 评议邀约配额（Redis Lua，防摊派）

```lua
-- review_quota.lua：KEYS[1]=tr:review:quota:{teacherId}:{yyyyMM}
--                   ARGV[1]=本次新增数量, ARGV[2]=上限(默认8)
local cur = tonumber(redis.call('GET', KEYS[1]) or '0')
if cur + tonumber(ARGV[1]) > tonumber(ARGV[2]) then
    return -1
end
redis.call('INCRBY', KEYS[1], ARGV[1])
redis.call('EXPIRE', KEYS[1], 2678400)  -- 31d
return cur + tonumber(ARGV[1])
```

### 7.3 带教记录确认与 `MENTORSHIP_LOGGED` 事件（Outbox 同事务）

```java
@Service
@RequiredArgsConstructor
public class MentorshipLogService {

    private final MentorshipLogRepository logRepo;
    private final MentorshipRepository mentorshipRepo;
    private final OutboxRepository outboxRepo;

    @Transactional
    public void confirm(long logId, long operatorId, ConfirmActionRequest req) {
        MentorshipLog log = logRepo.findByIdForUpdate(logId)
                .orElseThrow(() -> new TrException(TrErrorCode.LOG_NOT_FOUND));

        // 1. 守卫：只有"另一方"能确认，且状态必须 PENDING_CONFIRM
        Mentorship ms = mentorshipRepo.findById(log.getMentorshipId())
                .orElseThrow(() -> new TrException(TrErrorCode.MENTORSHIP_NOT_FOUND));
        long counterpart = log.getLoggerTeacherId() == ms.getMentorTeacherId()
                ? ms.getMenteeTeacherId() : ms.getMentorTeacherId();
        if (operatorId != counterpart) throw new TrException(TrErrorCode.LOG_CONFIRM_FORBIDDEN);
        if (log.getStatus() != LogStatus.PENDING_CONFIRM)
            throw new TrException(TrErrorCode.LOG_STATE_CONFLICT); // 幂等：重复确认直接冲突码

        if (req.getAction() == ConfirmAction.REJECT) {
            log.reject(operatorId, req.getReason());
            logRepo.save(log);
            return;
        }

        // 2. 状态推进 + 关系时长累计（乐观锁重试见 §9.3）
        log.confirm(operatorId);
        logRepo.save(log);
        int retries = mentorshipRepo.accumulateHours(
                ms.getId(), log.getDurationMinutes());   // UPDATE ... total_hours=?, version=version+1 WHERE version=?

        // 3. Outbox 写入（与业务同事务，At-Least-Once 投递）
        TeacherBehaviorEvent event = TeacherBehaviorEvent.newBuilder()
                .setEventId("mlog-" + log.getId())
                .setTeacherId(ms.getMentorTeacherId())          // 师傅获得 peer_collaboration 计分
                .setSchoolId(ms.getSchoolId())
                .setEventType("MENTORSHIP_LOGGED")
                .setEvent_subtype(log.getLogType())
                .setTimestamp(Instant.now().toEpochMilli())
                .putDimensions("hours", String.valueOf(log.getDurationMinutes() / 60.0))
                .putDimensions("log_id", String.valueOf(log.getId()))
                .putDimensions("mentee_id", String.valueOf(ms.getMenteeTeacherId()))
                .setSource_service("tr-service")
                .build();
        outboxRepo.append("MENTORSHIP_LOG", log.getId(),
                "MENTORSHIP_LOGGED", JsonFormat.printer().print(event),
                "mlog-" + log.getId());                          // 幂等键
    }
}
```

### 7.4 画像子指标日终对账 SQL（与画像引擎口径对齐）

```sql
-- peer_collaboration 三子指标（画像引擎日终拉取或本服务推送物化视图）
-- shared_resources_count：周期内"被他人采纳"的资源条数（去重）
SELECT u.teacher_id            AS owner_teacher_id,
       COUNT(DISTINCT u.resource_id) AS shared_resources_count
FROM tr_resource_usage u
JOIN tr_shared_resource r ON r.id = u.resource_id
WHERE u.action = 'ADOPT'
  AND u.teacher_id != r.owner_teacher_id
  AND u.created_at >= :from AND u.created_at < :to
GROUP BY u.teacher_id;

-- peer_review_participation：周期内完成评议次数
SELECT reviewer_teacher_id, COUNT(*) AS peer_review_participation
FROM tr_peer_review
WHERE status = 'RESOLVED'
  AND resolved_at >= :from AND resolved_at < :to
GROUP BY reviewer_teacher_id;

-- mentorship_hours：周期内已确认带教小时
SELECT ms.mentor_teacher_id, SUM(l.duration_minutes)/60.0 AS mentorship_hours
FROM tr_mentorship_log l
JOIN tr_mentorship ms ON ms.id = l.mentorship_id
WHERE l.status = 'CONFIRMED'
  AND l.confirmed_at >= :from AND l.confirmed_at < :to
GROUP BY ms.mentor_teacher_id;
```

### 7.5 Outbox 投递器（Kafka 双 Topic）

```java
@Component
@RequiredArgsConstructor
public class TrOutboxRelay implements Runnable {

    private final OutboxRepository outboxRepo;
    private final KafkaTemplate<String, String> kafka;
    private volatile boolean running = true;

    @Scheduled(fixedDelay = 2000)
    public void relay() {
        List<TrEventOutbox> batch = outboxRepo.lockPendingBatch(200); // FOR UPDATE SKIP LOCKED
        for (TrEventOutbox ob : batch) {
            try {
                String topic = ob.getEventType().startsWith("PEER_REVIEW_DONE")
                        || ob.getEventType().startsWith("MENTORSHIP_LOGGED")
                        ? "teacher.behavior.events"     // 复用画像消费 Topic
                        : "tr.domain.events";           // 域内事件（通知/看板）
                kafka.send(topic, ob.getIdempotencyKey(), ob.getPayload()).get(5, TimeUnit.SECONDS);
                outboxRepo.markSent(ob.getId());
            } catch (Exception e) {
                outboxRepo.scheduleRetry(ob.getId(), backoff(ob.getRetryCount()));
                if (ob.getRetryCount() + 1 >= 12) outboxRepo.markDead(ob.getId()); // 告警人工介入
            }
        }
    }
}
```

### 9.2 幂等策略

| 操作 | 幂等手段 |
| --- | --- |
| 提交带教记录 | `idempotency_key` 唯一约束；重复提交返回原 logId |
| 确认/驳回 | 状态机守卫 + `LOG_STATE_CONFLICT`（语义为"已处理"） |
| 事件发布 | Outbox `uk_idem`；消费端按 `event_id` 幂等 |
| 出勤登记 | `uk_prep_teacher` upsert |
| 评议提交 | `version` 乐观锁 + 状态守卫 |

### 9.3 乐观锁重试与降级

- `accumulateHours` 等累计字段走 `version` 条件更新，失败自旋重试 3 次（50ms 退避），仍失败抛 `47690`。
- 教研域为**非核心链路**：依赖的备课辅助/审核管线异常时，资源共享降级为"暂存待审"；画像事件投递失败不阻塞业务（Outbox 兜底）；整体故障时网关层对 `/api/v1/tr/**` 返回 `47602` 只读降级页（详见《错误处理与服务降级策略》）。

### 10.2 隔离与红线

1. **学校隔离**：所有查询强制 `school_id` 过滤（租户上下文 + Repository 基类模板方法）。
2. **学生数据红线**：教研域 API 不返回任何学生个人身份数据；组长跨班数据仅经数据权限框架的聚合视图（`aggregateOnly=true`）。
3. **审计**：组长交接、成员变更、评议归档、结对终止、听评课代确认写入审计日志（对接《服务端审计日志与操作追溯系统》）。
4. **内容安全**：共享资源与研讨发言过教育场景敏感词过滤（AI 初筛），命中转人工复审；带教佐证图片走对象存储私有读 + 审核回调。

## 13. 测试与验收场景（15 条）

1. 创建同学段同学科重复教研组 → `47611`。
2. 组长交接后，旧组长访问蓝图审核入口 → 403；新组长范围数据可查（数据权限缓存 ≤ 1min 生效）。
3. 集体备课无议程发布 → `47621`；带议程发布成功并产生教师端提醒。
4. `TO_COMPLETED` 不带 conclusion → `47622`。
5. 出勤重复登记 → upsert 幂等，不产生重复行。
6. 共享资源审核未过被列表查询 → 不可见（`RESOURCE_AUDIT_PENDING` 仅本人可见）。
7. 评议邀约超过月度配额 → `47631`；DECLINED 后配额日终回补。
8. 评议人=作者 → `47632`。
9. 评议超时 → 延迟任务置 EXPIRED，reassign 生成新 INVITED 记录，原记录保留。
10. 师徒与自己结对 → `47642`；重复结对 → `47641`。
11. 带教记录重复提交（同 idempotencyKey）→ 返回原 logId；对方确认后 `total_hours` 精确累计，Kafka 收到恰好 1 条 `MENTORSHIP_LOGGED`（重启后 Outbox 不重发）。
12. 非对方教师确认带教记录 → `47644`。
13. 听评课跨校预约 → `47651`；评分后 `followUp=true` 自动生成评议并计入画像。
14. 断开 Kafka：确认带教记录业务成功、Outbox 积压；恢复后事件补投、画像侧幂等。
15. 降级演练：备课辅助不可用时共享资源进入"暂存待审"，恢复后自动重提审核。
