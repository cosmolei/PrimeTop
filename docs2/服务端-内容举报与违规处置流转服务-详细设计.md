# 内容举报与违规处置流转服务 - 详细设计

> 文档版本：v1.0
> 更新日期：2026-08-15
> 上游设计：`docs/design/启硕-PrimeTop-全学段AI辅助学习软件项目设计文档.md` §8.7 安全与合规架构（内容审核、未成年人保护）、§12.4 产品端迭代（用户反馈机制）

## 1. 模块概述

### 1.1 功能定位

本服务是平台**用户侧违规信号的统一受理与处置流转中心**，负责：

1. 聚合全端（学生端、家长端、Web/H5、管理后台）的举报入口，统一受理对**内容、用户、AI 回答**三类对象的举报。
2. 对举报进行**去重合并、频控、优先级分派、快照固化**，形成可审核的举报工单。
3. 承接审核判决结果，编排**违规处置动作**（内容下线、禁言、封禁、警告等）的跨服务执行。
4. 提供**被处置用户的申诉通道**与申诉复核流程。
5. 维护**举报人信用体系**，识别并抑制恶意举报、批量举报。

### 1.2 设计背景与问题

平台已具备以下能力，但彼此割裂：

| 已有能力 | 归属系统 | 缺失部分 |
| --- | --- | --- |
| 内容机器审核（敏感词/图像识别） | UGC 安全审核与未成年人社交保护引擎 | 只处理"内容本身"，无用户发起的举报信号入口 |
| 用户风险画像与风控决策 | 统一风控决策中心与用户安全画像引擎 | 只做隐式风险，无显式举报证据链 |
| 咨询与投诉工单 | 客服与工单系统 | 面向"服务问题"，不承载违规判决与处置执行 |
| 紧急下线工作流 | 教育内容紧急下线与安全事故应急响应工作流引擎 | 面向平台侧事故，非用户举报触发 |

典型断裂场景：学生在学习同伴圈看到不良内容 → 点举报 → **没有服务接收**；家长举报某用户骚扰 → 客服工单无法执行禁言；被误判用户想申诉 → **无申诉入口**。本服务即补齐这条链路。

### 1.3 与现有系统的关系（边界划分）

| 职责 | 归属 | 说明 |
| --- | --- | --- |
| 举报入口 UI 与埋点 | 客户端各业务模块 | 调用本服务统一 API |
| 举报受理/合并/分派/状态流转 | **本服务** |  |
| 内容是否违规的**判定** | UGC 安全审核引擎 / 人工审核 | 本服务只做流转，不做内容定性 |
| 用户风险分更新 | 统一风控决策中心 | 消费本服务发布的处置事件 |
| 处置动作**执行**（下线/禁言/封禁） | 内容服务 / 账号体系 / 权限管理 | 本服务编排并跟踪执行结果 |
| 通知当事双方 | 通知中心与站内消息系统 | 消费本服务事件 |
| 操作留痕 | 审计日志与操作追溯系统 | 管理端判决操作强制审计 |
| 涉未成年人高危举报上报 | 安全事件管理工作台 | 本服务触发移交事件 |

### 1.4 设计目标

1. 举报提交 API P99 < 300ms（不含异步审核）。
2. 安全类（涉未成年人、色情、暴力、诈骗）举报 **5 分钟内**进入审核队列首位；普通举报 24h 内处理。
3. 同一对象重复举报合并率 > 90%，不产生重复审核工单。
4. 处置动作跨服务执行**最终一致**，失败可补偿重试，全程可追溯。
5. 全流程状态机驱动，任何状态变更留审计记录。

## 2. 举报入口与受理范围

### 2.1 举报对象类型清单

| 对象类型 (subject_type) | 来源场景 | 示例 |
| --- | --- | --- |
| `UGC_POST` | 学习同伴圈动态、讨论区帖子 | 动态、评论、回复 |
| `UGC_COMMENT` | 内容评论区、课后答疑讨论 | 评论 |
| `USER_PROFILE` | 个人资料、昵称、头像 | 不当头像、冒充他人 |
| `PRIVATE_MESSAGE` | 家校沟通、同伴私信 | 骚扰、欺凌私信 |
| `AI_ANSWER` | AI 对话中的回答 | AI 回答含错误/不当内容 |
| `QUESTION_CONTENT` | 题库题目、解析 | 题目内容错误或不当 |
| `COURSE_CONTENT` | 同步课堂、课件内容 | 版权问题、内容错误 |
| `REPORT_SHARE_CARD` | 学习报告分享卡片 | 分享图含不当内容 |

> 说明：`AI_ANSWER`/`QUESTION_CONTENT` 类举报在判决后同时路由至「AI 回答质量监控与用户纠错反馈」「教学内容用户纠错反馈」管线做内容修正，本服务只负责违规侧处置。

### 2.2 举报理由分类体系

| 一级分类 (reason_category) | 二级分类 (reason_code) | 优先级 | 时效要求 |
| --- | --- | --- | --- |
| `SAFETY` 未成年人安全 | `CHILD_ABUSE`(侵害未成年人) `GROOMING`(诱骗) `BULLYING`(欺凌) | P0-紧急 | 5 分钟进队，1h 内判决 |
| `ILLEGAL` 违法违规 | `PORN` `VIOLENCE` `GAMBLING` `FRAUD` `DRUG` `POLITICAL` | P0 | 30 分钟进队 |
| `INAPPROPRIATE` 不适宜内容 | `VULGAR`(低俗) `SPAM_AD`(垃圾广告) `OFF_TOPIC`(无关内容) | P1 | 24h |
| `INFRINGEMENT` 侵权 | `COPYRIGHT`(版权) `PRIVACY`(泄露隐私) `IMPERSONATION`(冒充) | P1 | 24h |
| `MISINFO` 虚假错误 | `WRONG_ANSWER`(答案错误) `MISLEADING`(误导信息) | P2 | 48h |
| `OTHER` 其他 | `OTHER` | P2 | 48h |

分类体系通过配置中心热更新（`report.reason.taxonomy` 配置键），新增二级分类无需发版。

### 2.3 入口端约定

- 所有客户端举报入口统一调用 `POST /api/v1/reports`，入口位置埋点 `report_submit_click` 携带 `entry_scene`（如 `peer_circle_detail` / `ai_chat_long_press` / `comment_menu`）。
- 举报入口必须在以下位置可达（验收清单）：动态详情 ⋯ 菜单、评论长按、用户主页 ⋯ 菜单、私信会话设置、AI 回答消息长按、题目详情反馈。
- 涉及未成年人的 P0 入口展示"家长可代为举报"提示，家长端使用被绑定学生上下文提交时携带 `on_behalf_of_student_id`。

## 3. 数据结构设计

### 3.1 举报单主表 `report`

```sql
CREATE TABLE `report` (
  `id`                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `report_no`           VARCHAR(32) NOT NULL COMMENT '举报单号 R{yyyyMMdd}{10位序列}',
  `reporter_id`         BIGINT UNSIGNED NOT NULL COMMENT '举报人用户ID',
  `on_behalf_of_student_id` BIGINT UNSIGNED NULL COMMENT '家长代学生举报时的学生ID',
  `subject_type`        VARCHAR(32) NOT NULL COMMENT '举报对象类型，见2.1',
  `subject_id`          VARCHAR(64) NOT NULL COMMENT '对象业务ID（内容ID/用户ID/消息ID）',
  `subject_owner_id`    BIGINT UNSIGNED NOT NULL COMMENT '对象归属用户（被举报人）',
  `reason_category`     VARCHAR(32) NOT NULL COMMENT '一级分类',
  `reason_code`         VARCHAR(64) NOT NULL COMMENT '二级分类',
  `reason_text`         VARCHAR(500) NULL COMMENT '举报人补充描述',
  `evidence_count`      TINYINT NOT NULL DEFAULT 0 COMMENT '证据快照数量',
  `status`              VARCHAR(16) NOT NULL DEFAULT 'SUBMITTED' COMMENT '状态，见4.1',
  `priority`            TINYINT NOT NULL DEFAULT 2 COMMENT '0紧急 1高 2普通',
  `merged_into_id`      BIGINT UNSIGNED NULL COMMENT '被合并到的主举报单ID',
  `first_report_id`     BIGINT UNSIGNED NULL COMMENT '同对象首条举报ID（冗余，合并用）',
  `assigned_to`         BIGINT UNSIGNED NULL COMMENT '受理审核员（管理后台用户ID）',
  `submitted_at`        DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `first_action_deadline` DATETIME(3) GENERATED ALWAYS AS (
                        CASE WHEN `priority`=0 THEN `submitted_at` + INTERVAL 60 MINUTE
                             WHEN `priority`=1 THEN `submitted_at` + INTERVAL 24 HOUR
                             ELSE `submitted_at` + INTERVAL 48 HOUR END) STORED COMMENT 'SLA首响时限',
  `updated_at`          DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_report_no` (`report_no`),
  UNIQUE KEY `uk_dedup` (`reporter_id`,`subject_type`,`subject_id`,`reason_code`,`submitted_at`), -- 同人同对象同理由当日去重（配合当日分区内）
  KEY `idx_subject` (`subject_type`,`subject_id`,`status`),
  KEY `idx_queue` (`status`,`priority`,`submitted_at`),
  KEY `idx_reporter` (`reporter_id`,`submitted_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='举报单主表';
```

要点：
- `uk_dedup` 利用 `submitted_at` 参与唯一索引实现"同人同对象同理由 24h 内仅一次"，配合应用层捕获 `DuplicateKeyException` 返回已有单号。
- `first_action_deadline` 用生成列落库，便于 SLA 巡检任务直接扫描。

### 3.2 证据快照表 `report_evidence`

举报受理时**立即固化**被举报对象快照，防止后续内容被删除/修改导致无法审核：

```sql
CREATE TABLE `report_evidence` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `report_id`     BIGINT UNSIGNED NOT NULL,
  `evidence_type` VARCHAR(16) NOT NULL COMMENT 'TEXT_SNAPSHOT/IMAGE_URL/FILE_HASH/VIDEO_URL/META',
  `content`       MEDIUMTEXT NULL COMMENT '文本快照或元数据JSON',
  `resource_url`  VARCHAR(512) NULL COMMENT '已转存的资源URL（OSS私有桶）',
  `resource_hash` CHAR(64) NULL COMMENT '资源SHA256，去重用',
  `captured_at`   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  KEY `idx_report` (`report_id`),
  KEY `idx_hash` (`resource_hash`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='举报证据快照';
```

快照固化策略（按 subject_type）：

| 对象类型 | 固化内容 |
| --- | --- |
| `UGC_POST` / `UGC_COMMENT` | 正文全文 JSON + 图片转存 OSS 私有桶（保留 180 天） |
| `USER_PROFILE` | 昵称/头像/简介快照 |
| `PRIVATE_MESSAGE` | 会话最近 20 条消息（脱敏后） |
| `AI_ANSWER` | 完整回答 + 会话上下文摘要 + model/prompt_version |
| `QUESTION_CONTENT` | 题干 + 解析 + 内容版本号 |

## 4. 核心状态机

### 4.1 举报单状态机

| 当前状态 | 事件 | 目标状态 | 动作 | 守卫条件 |
| --- | --- | --- | --- | --- |
| SUBMITTED | assign(审核员领取/自动分派) | REVIEWING | 记录 assigned_to | 队列有权限校验 |
| SUBMITTED | merge(同对象已有主单) | MERGED | 写 merged_into_id，通知举报人"已受理" | 同 subject+reason |
| SUBMITTED | withdraw | WITHDRAWN | — | 仅举报人本人，未分派前 |
| REVIEWING | judge(成立) | ACTIONED | 创建 violation_case 并触发处置编排 | 判决需含 severity |
| REVIEWING | judge(不成立) | DISMISSED | 通知举报人，扣举报人信用加权（仅恶意时） | — |
| REVIEWING | judge(无效) | INVALID | 触发恶意举报检测 | — |
| ACTIONED/DISMISSED | appeal_result(申诉成功回写) | 保持原状态 | 更新关联 case | 由案件侧驱动 |
| MERGED | 主单终态 | 跟随主单结果 | 批量回写 + 批量通知 | 定时任务 |

非法流转（如 WITHDRAWN→REVIEWING）一律拒绝并记录 `report.invalid_transition` 告警日志。

### 4.2 违规案件状态机

| 当前状态 | 事件 | 目标状态 | 动作 |
| --- | --- | --- | --- |
| EXECUTING | all_penalty_success | EXECUTED | 发布 `violation.case.executed` 事件，双方通知 |
| EXECUTING | any_penalty_fail_after_retry | PARTIAL | 告警 + 进入补偿队列 |
| PARTIAL | retry_success | EXECUTED | 同上 |
| EXECUTED | appeal_accepted | REVERSED | 生成撤销动作（恢复内容/解除禁言），发布 `violation.case.reversed` |
| EXECUTED | penalty_expire(定时) | CLOSED | 解除时效性处置（禁言到期），通知用户 |

### 4.3 申诉状态机

`SUBMITTED → REVIEWING → ACCEPTED | REJECTED`，允许 `SUBMITTED → WITHDRAWN`。
约束：复核人 `review_by != case.judge_by`（防止自审自纠），系统强制校验。

### 4.4 并发与幂等控制

1. **提交幂等**：客户端携带 `Idempotency-Key`（UUID），服务端以 `rp:dedup:*` + 唯一索引双层防护，重复提交返回首次结果。
2. **判决幂等**：判决接口带 `report_id + judge_version`，状态机乐观锁 `UPDATE ... WHERE status='REVIEWING'`，影响行数为 0 即冲突拒绝。
3. **处置编排互斥**：以 `rp:lock:execute:{case_id}` 分布式锁保证同一案件同时只有一个编排实例。
4. **合并竞态**：合并与分派并发时，以主单状态 CAS 为准，从单合并失败则留在队列。

## 6. 核心流程详细设计

### 6.1 举报提交流程

```
客户端 → 网关 → ReportService.submit()
  1. 参数与对象存在性校验（调用对象归属服务 exists 接口）
  2. 频控检查（Redis INCR rp:freq:*，超限返回 75001）
  3. 举报人限制检查（reporter_credit.restricted_until）
  4. 快速去重（rp:dedup:* SETNX；命中返回 75002 + 已有单号）
  5. 证据快照固化（异步优先：P0 举报同步固化，其余投递 snapshot-worker）
  6. 写入 report（唯一索引兜底）
  7. 合并检查：同 subject_type+subject_id 存在未终态主单且 reason 相近 → 直接 MERGED；
     否则成为新的主单，burst 计数 +1
  8. 发布 report.submitted 事件（P0 同步发布）
  9. 返回 reportNo
```

### 6.2 队列分派与优先级

- 优先级来源：`reason_category` 映射默认优先级 + 风控加权（被举报人为高危用户 +1 级）+ burst 热点加权。
- 分派模式：**抢单制**。审核员在后台队列点击领取，CAS 更新 `assigned_to`；P0 单超 5 分钟无人领取自动推送值班主管（复用通知中心高优通道）。
- 未成年人安全类（`SAFETY.*`）：进队同时**并行**投递安全工作台 `escalate` 通道，人工审核与安全专员双线处理，先到先判。

### 6.3 审核判决与处置编排

```python
async def execute_case(case: ViolationCase) -> None:
    """判决成立后的处置编排：逐动作执行、失败补偿、最终发布事件。"""
    lock_key = f"rp:lock:execute:{case.id}"
    if not await redis.set(lock_key, "1", nx=True, ex=300):
        raise ConcurrentExecutionError(case.case_no)

    records = penalty_repo.create_for_case(case)   # 按 NOTIFY_PARTIES 最后排序
    executor_map = build_executors(case.penalty_codes)

    for rec in records:
        try:
            await executor_map[rec.penalty_code].execute(case, rec)
            rec.exec_status, rec.executed_at = "SUCCESS", now()
        except Exception as e:                     # 下游超时/5xx
            rec.exec_status, rec.error_msg = "FAILED", str(e)[:500]
            rec.retry_count += 1
            rec.next_retry_at = next_backoff(rec.retry_count)   # 1m/5m/15m/60m，共5次

    await penalty_repo.save_all(records)
    case.status = "EXECUTED" if all(r.exec_status == "SUCCESS" for r in records) else "PARTIAL"
    if case.status == "PARTIAL":
        metrics.incr("report.penalty.partial")     # 告警：处置不完整
    await event_bus.publish("violation.case.event", build_case_event(case, records))
```

补偿任务每分钟扫描 `penalty_record` 中 `FAILED 且 next_retry_at <= now` 的记录重试；连续 5 次失败转人工工单（自动创建客服工单类型 `PENALTY_EXEC_FAIL`）。

### 6.4 申诉流程

1. 用户在"违规通知"消息卡片点击申诉 → 校验时限/次数 → 写入 appeal。
2. 申诉队列分派（复核人 ≠ 原判决人，系统强校验）。
3. `ACCEPTED`：生成**撤销动作集**（恢复内容 `content.restore`、解除禁言 `account.unmute`、回滚风险分由风控消费 reversed 事件完成），案件置 `REVERSED`，双方通知（被举报人"已恢复"、举报人"判决已变更"）。
4. `REJECTED`：维持处置，通知申诉人并附复核结论；同案件申诉机会用尽。
5. 撤销同样走 penalty_record（`exec_status` 记 `ROLLED_BACK`），保证可追溯。

### 6.5 恶意举报识别与举报人信用

判定规则（满足任一记一次 malicious）：

1. 30 天内 ≥5 次举报被判决 `DISMISSED`（内容无问题）；
2. 24h 内对 ≥10 个不同对象提交举报且成立率 < 10%；
3. 同对象换理由反复举报 ≥3 次均不成立；
4. 举报文本命中辱骂/人肉模板词表。

后果：`credit_score -20`/次；score < 60 → `restricted_until = now + 7d`（期间仅可提交 `SAFETY` 类）；恢复举报权后 score 从 60 起步。正向：判决成立 +2 分，上限 150。

### 6.6 未成年人特殊保护通道

- `SAFETY` 类判决成立 → 强制附带 `ESCALATE_SAFETY`，案件摘要（脱敏）推送安全事件管理工作台；
- 被处置人为未成年人时，`USER_BAN_PERM` 降级为 `USER_MUTE_30D + 家长告知通知`（合规要求：不得对未成年人永久封号而不告知监护人）；
- 涉刑事风险线索（如 `GROOMING`）保留证据 3 年，出库需安全负责人审批。

## 7. 处置动作联动设计

### 7.1 处置动作矩阵

| penalty_code | 执行方 | 时效 | 可撤销 | 备注 |
| --- | --- | --- | --- | --- |
| CONTENT_TAKEDOWN | 内容服务（对 UGC）/题库服务 | 即时 | ✅ | 置 content.status=BLOCKED |
| USER_WARNING | 通知中心 | 即时 | — | 模板 `penalty.warning.{reason}` |
| USER_MUTE_{1D,3D,7D} | 账号体系 | 到期自动解除 | ✅ | 写 account.mute_until |
| USER_BAN_PERM | 账号体系 | 永久 | ✅(仅申诉) | 二级审批 |
| USER_DEVICE_BLOCK | 风控决策中心 | 可配置 | ✅ | 设备指纹黑名单 |
| ESCALATE_SAFETY | 安全工作台 | 即时 | — | 见 6.6 |

| NOTIFY_PARTIES | 通知中心 | 即时 | — | 默认附带，最后执行 |

### 7.2 一致性与回滚

- 处置编排为**尽力聚合**：不追求分布式事务，靠 `penalty_record` 重试 + 事件消费方幂等达到最终一致。
- 各执行方必须实现幂等（以 case_no 为幂等键），重复执行返回上次结果。
- 申诉撤销时按 `penalty_record` 逆序回滚，仅回滚"可撤销"动作；已过公示通知不撤回，改为补发更正通知。

## 8. 关键代码示例

### 8.1 提交举报（含频控/去重/合并）

```python
class ReportService:

    DAILY_LIMIT = 20
    MERGE_WINDOW = timedelta(hours=48)

    async def submit(self, cmd: SubmitReportCmd) -> SubmitReportResult:
        # 1. 频控
        freq_key = f"rp:freq:{cmd.reporter_id}:{today()}"
        if await self.redis.incr(freq_key) > self.DAILY_LIMIT:
            await self.redis.decr(freq_key)
            raise BizError(75001, "超出当日举报次数上限")
        if await self.redis.ttl(freq_key) < 0:
            await self.redis.expire(freq_key, 48 * 3600)

        # 2. 举报人限制（仅 SAFETY 类放行）
        credit = await self.credit_repo.get(cmd.reporter_id)
        if credit and credit.restricted_until and credit.restricted_until > now() \
                and cmd.reason_category != "SAFETY":
            raise BizError(75003, "举报功能已被限制")

        # 3. 快速去重
        dedup_key = f"rp:dedup:{cmd.reporter_id}:{cmd.subject_type}:{cmd.subject_id}:{cmd.reason_code}"
        existed = await self.redis.get(dedup_key)
        if existed:
            raise BizError(75002, f"已提交过举报", extra={"reportNo": existed})

        # 4. 合并检查：同对象存在未终态主单
        primary = await self.report_repo.find_active_primary(
            cmd.subject_type, cmd.subject_id)
        merge_target = None
        if primary and now() - primary.submitted_at < self.MERGE_WINDOW \
                and self._reason_adjacent(primary.reason_category, cmd.reason_category):
            merge_target = primary

        # 5. 落库（唯一索引兜底幂等）
        report = Report.create(cmd, priority=self._calc_priority(cmd, credit))
        try:
            await self.report_repo.save(report)
        except DuplicateKeyError:
            raise BizError(75002, "已提交过举报")
        await self.redis.set(dedup_key, report.report_no, ex=24 * 3600)

        # 6. 证据快照：P0 同步固化，其余异步
        if report.priority == 0:
            await self.snapshot_fixer.fix(report)
        else:
            await self.mq.send("report.snapshot.task", {"reportId": report.id})

        # 7. 合并 或 爆发计数
        if merge_target:
            await self.report_repo.merge_into(report, merge_target)
        else:
            burst = await self.redis.incr(
                f"rp:burst:{cmd.subject_type}:{cmd.subject_id}")
            await self.redis.expire(f"rp:burst:{cmd.subject_type}:{cmd.subject_id}", 600)
            if burst == 20:   # 热点对象：升级优先级并推送安全值班
                await self.report_repo.raise_priority(report, floor=1)
                await self.notifier.push_safety_duty(report)

        await self.event_bus.publish("report.lifecycle.event",
                                     {"eventType": "report.submitted", "data": report.to_dto()})
        return SubmitReportResult(report_no=report.report_no,
                                  merged_into=merge_target.report_no if merge_target else None)

    @staticmethod
    def _calc_priority(cmd, credit) -> int:
        base = REASON_PRIORITY.get(cmd.reason_category, 2)
        if credit and credit.credit_score >= 120:   # 高信用举报人加权
            base = max(0, base - 1)
        return base
```

### 8.2 判决入口（状态机 CAS）

```python
async def judge(self, report_no: str, cmd: JudgeCmd, operator: AdminUser) -> str:
    report = await self.report_repo.get_by_no(report_no)
    if report.status != ReportStatus.REVIEWING:
        raise BizError(75101, f"当前状态不可判决: {report.status}")

    if cmd.verdict == "VIOLATION":
        need_confirm = any(p in ("USER_BAN_PERM", "USER_DEVICE_BLOCK")
                           for p in cmd.penalty_codes)
        case = await self.case_svc.create_case(report, cmd, judge_by=operator.id,
                                               pending_confirm=need_confirm)
        await self.report_repo.transition(
            report.id, frm=ReportStatus.REVIEWING, to=ReportStatus.ACTIONED)
        if not need_confirm:
            await self.case_svc.start_execution(case)
        return case.case_no

    target = ReportStatus.DISMISSED if cmd.verdict == "NOT_VIOLATION" else ReportStatus.INVALID
    updated = await self.report_repo.transition(report.id, frm=ReportStatus.REVIEWING, to=target)
    if not updated:                       # 并发判决，乐观锁失败
        raise BizError(75102, "举报单状态已变更，请刷新")
    if target == ReportStatus.INVALID:
        await self.credit_svc.track_malicious_signal(report.reporter_id)
    await self.notifier.notify_reporter(report, verdict=cmd.verdict)
    return None
```

## 12. 测试要点

1. **状态机全路径单测**：枚举所有 (state, event) 组合，断言合法/非法流转（表驱动测试）。
2. **去重并发**：100 并发同 Idempotency-Key 提交，断言仅 1 条落库、其余返回 75002。
3. **合并竞态**：主单判决与从单合并并发，断言从单最终可达终态且收到通知。
4. **处置补偿**：模拟内容服务 5xx，断言 5 次退避重试后 PARTIAL + 工单创建。
5. **申诉撤销闭环**：takedown→mute→appeal accepted，断言内容恢复、禁言解除、双方通知、审计齐全。
6. **未成年人通道**：SAFETY 判决自动携带 ESCALATE_SAFETY；未成年人 ban 降级 mute + 家长通知。
7. **SLA**：时间伪造推进 61 分钟，断言 P0 单告警与升级推送。
