# 服务端 - 实物奖品履约交付与物流跟踪服务 详细设计

## 1. 文档说明

### 1.1 定位

实物奖品履约交付与物流跟踪服务（fulfillment-service）是 PrimeTop 积分商城虚拟经济体系的实物履约后端，负责积分商城实物奖品从「用户兑换下单」到「签收完结」的完整后端链路，包括：

1. **收货地址簿服务**：用户（学生/家长代填）收货地址的增删改查、默认地址、脱敏展示与加密存储。
2. **实物兑换订单与履约单管理**：兑换订单创建（联动学币扣减）、履约单拆分、审核、发货状态机。
3. **实物库存与仓储管理**：奖品 SKU 的入库、可用/锁定库存、库存流水、盘点对账。
4. **发货执行**：管理后台单笔/批量发货（Excel 导入）、电子面单回填、发货通知触达。
5. **物流轨迹跟踪**：对接第三方物流平台（快递100/快递鸟风格），订阅-推送模式下轨迹事件的幂等入库、乱序处理、状态推进。
6. **签收与自动完结**：物流签收判定、超时自动确认收货、订单完结。
7. **异常处理**：丢件、拒收、退回、地址错误等异常单的补发/退币闭环。
8. **对账与监控**：库存对账、发货时效、轨迹停滞告警、实物成本核算数据出口。

本服务是「管理后台-积分商城与虚拟经济运营管理工作台」中实物履约相关页面（`/points/orders/*`、`/points/warehouse/*`）的后端实现方，同时向客户端「积分商城与奖品兑换」模块提供用户侧履约查询与确认收货能力。

## 2. 领域模型

### 2.1 核心实体关系

```
Goods(商品, 外部拥有) ──1:N──> GoodsSku(实物SKU, 外部拥有)
                                    │
                                    ▼
Inventory(实物库存, 本服务拥有) <───入库── InventoryInbound(入库单)
                                    │锁定/扣减
PointsExchangeOrder(实物兑换订单) ──1:1──> FulfillmentOrder(履约单)
        │                                │
        │ wallet/consume 学币扣减         │ 1:N（一单可多包裹，如套装分裹）
        ▼                                ▼
WalletTransaction(积分服务)      FulfillmentPackage(包裹)
                                     │ 贴单/发货
                                     ▼
                              LogisticsProvider(物流渠道) ──> LogisticsTrackEvent(轨迹事件)
                                     │
                                     ▼
                        FulfillmentException(异常处理单) ──> 补发新包裹 / 退币
ShippingAddress(收货地址簿) ──被引用(快照)──> PointsExchangeOrder
```

**关键设计原则：**

1. **地址快照**：兑换订单创建时将地址簿内容快照进订单表，后续地址簿修改/删除不影响已下订单。
2. **订单与履约分离**：`PointsExchangeOrder` 面向交易（学币、退款），`FulfillmentOrder` 面向仓配（发货、物流），虚拟奖品兑换只有订单没有履约单。
3. **一单多裹**：大件套装可能拆多个包裹发货，履约单状态由包裹状态聚合推导。
4. **轨迹外置**：轨迹事件只增不改，状态推进以「事件流」驱动，天然幂等。

## 3. 数据库设计

> 存储选型：MySQL 8.0（履约域强一致），库 `primetop_fulfillment`。轨迹事件表按月分表 `logistics_track_event_YYYYMM`。字符集 utf8mb4。以下 DDL 均含必备索引与注释，可直接建表。

### 3.1 收货地址簿表 `shipping_address`

```sql
CREATE TABLE `shipping_address` (
    `id`               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
    `user_id`          BIGINT UNSIGNED NOT NULL COMMENT '归属用户ID(学生本人)',
    `receiver_name`    VARCHAR(64)  NOT NULL COMMENT '收件人姓名(AES加密存储,密文≤64)',
    `receiver_phone`   VARCHAR(64)  NOT NULL COMMENT '收件人手机号(AES加密存储)',
    `province`         VARCHAR(32)  NOT NULL COMMENT '省/直辖市',
    `city`             VARCHAR(32)  NOT NULL COMMENT '市',
    `district`         VARCHAR(32)  NOT NULL COMMENT '区/县',
    `detail_address`   VARCHAR(255) NOT NULL COMMENT '详细地址(明文,用于面单)',
    `postal_code`      VARCHAR(10)  DEFAULT NULL COMMENT '邮政编码',
    `is_default`       TINYINT NOT NULL DEFAULT 0 COMMENT '是否默认地址 0=否 1=是',
    `tag`              VARCHAR(16)  DEFAULT NULL COMMENT '地址标签:家/学校/其他',
    `province_code`    CHAR(6)      DEFAULT NULL COMMENT '省行政区划码',
    `city_code`        CHAR(6)      DEFAULT NULL COMMENT '市区划码',
    `district_code`    CHAR(6)      DEFAULT NULL COMMENT '区划码(三级)',
    `status`           TINYINT NOT NULL DEFAULT 1 COMMENT '1=有效 0=已删除(软删)',
    `last_used_at`     DATETIME     DEFAULT NULL COMMENT '最近使用时间(默认地址推荐)',
    `version`          INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    `created_at`       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `updated_at`       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    KEY `idx_user_status` (`user_id`, `status`, `is_default` DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='收货地址簿';
```

**约束（应用层保证）：**

- 单用户有效地址上限 **10 条**（超出返回 `ADDRESS_LIMIT_EXCEEDED`）。
- 手机号/姓名 AES-GCM 加密后入库，密钥走 KMS（见 10.2）；`detail_address` 明文（面单打印需要，且不含身份标识强度）。
- 默认地址唯一性：设置默认时同事务内将其他地址 `is_default=0`。

## 5. 核心流程设计

### 5.1 实物兑换下单流程

```
客户端                     履约服务                      积分服务
  │                          │                            │
  │ 1. POST exchange-orders  │                            │
  │   (skuId,qty,addressId,  │                            │
  │    idempotentKey)        │                            │
  │─────────────────────────>│                            │
  │                          │ 2. 幂等检查(uk_idempotent) │
  │                          │    命中且参数一致→返回原单  │
  │                          │                            │
  │                          │ 3. 校验:                   │
  │                          │    SKU实物/上架/学生日限额  │
  │                          │    地址有效                 │
  │                          │                            │
  │                          │ 4. 库存锁定(乐观锁)         │
  │                          │    available-=qty          │
  │                          │    locked+=qty             │
  │                          │                            │
  │                          │ 5. 创建订单 PENDING_PAY     │
  │                          │    生成履约单 WAIT_AUDIT    │
  │                          │    地址快照(加密字段)       │
  │                          │                            │
  │                          │ 6. POST /wallet/consume     │
  │                          │───────────────────────────>│
  │                          │    7. 扣学币(FIFO过期批次)  │
  │                          │<───────────────────────────│
  │                          │ 8. 成功:                    │
  │                          │    订单→FULFILLING          │
  │                          │    记 wallet_txn_no         │
  │                          │    发送审计/行为事件        │
  │                          │ 9. 失败(余额不足等):         │
  │                          │    补偿:UNLOCK库存          │
  │                          │    订单→CANCELED(未支付)    │
  │                          │    返回透传错误码            │
  │<─────────────────────────│                            │
```

**为什么先锁库存再扣币**：学币扣减是外部服务调用（不可与本地事务强一致），库存锁定是本地资源，先锁后扣失败只需本地补偿解锁，方向单一、易于对账。反向（先扣币后锁库存）失败需要跨服务退币，补偿链更长。

**分布式一致性**：第 6 步调用超时（unknown 结果）时，进入「扣币结果待确认」子状态：订单停留 `PENDING_PAY`，由延迟任务每 5 分钟反查积分服务 `GET /wallet/transaction/{idempotentKey}`，10 分钟内确认失败则本地补偿；确认成功则推进。绝不出现「扣了币订单没了」。

### 5.2 发货流程（单笔与批量）

```
仓储运营(后台)              履约服务                    物流平台
    │                        │                          │
    │ 1. /points/orders/:id/ship                         │
    │   {providerCode,trackingNo}                        │
    │───────────────────────>│                          │
    │                        │ 2. 校验履约单=WAIT_SHIP    │
    │                        │    单号格式校验(渠道规则)   │
    │                        │    uk_provider_tracking   │
    │                        │    防重复占用              │
    │                        │                          │
    │                        │ 3. 事务:                   │
    │                        │    包裹→LABELED(回填单号)  │
    │                        │    locked-=qty            │
    │                        │    (available不变,总量守恒) │
    │                        │    写inventory_log DEDUCT │
    │                        │                          │
    │                        │ 4. 订阅轨迹                │
    │                        │    POST /subscribe        │
    │                        │─────────────────────────>│
    │                        │<─────────────────────────│
    │                        │ 5. 成功: subscribe_status=1│
    │                        │    失败: =2 入重试队列      │
    │                        │    (3次后降级轮询=3)       │
    │                        │                          │
    │                        │ 6. 触发发货通知(通知服务)   │
    │                        │    模板: FULFILL_SHIPPED   │
    │<───────────────────────│                          │
    │                        │                          │
    │            后续揽收轨迹到达时:                       │
    │                        │  包裹→SHIPPED, 订单→SHIPPED│
```

**批量发货（Excel 导入）**：模板列 `履约单号 | 快递公司编码 | 物流单号 | 重量(g)`。逐行走单笔发货逻辑（每行独立事务，单行失败不影响整批），响应聚合成功/失败明细并可导出失败原因报表（走统一文件生成与异步报表导出中心服务）。

### 5.3 物流轨迹推送处理流程

```
物流平台                    履约服务
    │                        │
    │ 1. track-callback      │
    │───────────────────────>│
    │                        │ 2. 验签+定位包裹
    │                        │    (providerCode+trackingNo)
    │                        │
    │                        │ 3. INSERT IGNORE 轨迹事件
    │                        │    (唯一索引 pkg+time+code)
    │                        │    受影响行=0 → 纯重复推送，
    │                        │    直接返回成功
    │                        │
    │                        │ 4. 乱序判断:
    │                        │    event_time < 包裹当前
    │                        │    最新轨迹时间 → 仅落库
    │                        │    不推进状态(补录场景)
    │                        │
    │                        │ 5. 状态映射 std_action:
    │                        │    DELIVERED→包裹DELIVERED
    │                        │    REJECTED→触发REJECTED异常单
    │                        │    RETURNED持续15天→退回预警
    │                        │
    │                        │ 6. 终态触发:
    │                        │    DELIVERED:
    │                        │      包裹→DELIVERED
    │                        │      订单→DELIVERED
    │                        │      启动confirm_deadline
    │                        │      (=签收时间+15天)
    │                        │      发送签收提醒通知
    │                        │
    │                        │ 7. 清除轨迹缓存
    │<───────────────────────│
    │   200 {code:0}         │
```

| 平台 action 例 | std_action | 语义 |
| --- | --- | --- |
| 收件/揽收 GOT | GOT | 揽收 |
| 到达 ARRIVED | ARRIVED | 到达网点/中心 |
| 发出/运输 DEPARTED | DEPARTED | 离开分拨 |
| 派送中 DELIVERING | DELIVERING | 派送中 |

### 5.4 自动确认收货流程

> 基于统一延迟任务调度引擎。

```
签收轨迹(DELIVERED) ──> 投递延迟任务 [delay = 15天, topic=FULFILL_AUTO_CONFIRM]
                              │
                              ▼ 到期执行
                     1. 查订单状态仍为 DELIVERED?
                        否(已手动确认/已退款) → 任务结束
                     2. 是 → 订单→COMPLETED
                        包裹→CONFIRMED
                        completed_at=now
                     3. 发送「自动确认收货」站内信
                     4. 释放订单关联缓存
```

用户在截止前手动确认走 4.1.5 接口，同一乐观锁版本控制防止并发双写。

### 5.5 取消订单与退币流程

**取消前置校验**（任一包裹已揽收则拒绝，错误码 64015 CANCEL_FORBIDDEN_SHIPPED）：

```
用户/客服取消请求
    │
    ├── 校验: 全部包裹 status ∈ {CREATED, LABELED}
    │         (LABELED未揽收可拦截: 向物流平台发起拦截,
    │          拦截失败→取消失败转人工)
    │
    ├── 1. 包裹→CLOSED, 履约单→CLOSED
    ├── 2. 库存回补: locked+=qty (available不变)
    │      写inventory_log UNLOCK
    ├── 3. 调用积分服务退款退币:
    │      POST /wallet/refund
    │      { originalTxnNo, amount=cost_coin,
    │        expirePolicy=RESTORE_ORIGINAL }
    │      → 退回学币还原原始过期批次
    │        (已过期的批次按统一90天有效期退回)
    ├── 4. 订单→CANCELED, 记refund_txn_no
    └── 5. 通知用户「兑换取消,学币已退回」
```

**退款超时处理**：`/wallet/refund` 超时或失败 → 订单进入 `REFUND_PENDING` 中间态，延迟任务 5 分钟重试，最多 6 次；仍失败挂起异常告警（`fulfillment_refund_stuck`），人工处理。**宁可订单卡在中间态，不可丢单**。

### 5.6 异常处理流程（丢件/拒收/破损）

```
异常来源:
  A. 系统检测: 轨迹停滞(签收前>7天无新轨迹)
     → 每日扫描任务生成 TRACK_STALLED 异常单
  B. 用户上报: 4.1.5 接口
  C. 轨迹终态: REJECTED/RETURNED 自动生成
  D. 运营录入
    │
    ▼ 创建 fulfillment_exception (OPEN)
    │
    ▼ 客服/仓储核实 → /points/exceptions/:no/resolve
    │
    ├── RESHIP 补发:
    │     1. 原包裹→LOST/CLOSED
    │     2. 新建包裹(同履约单), 库存: locked+=qty(需校验available)
    │     3. 异常单→RESOLVED, 关联reship_package_id
    │     4. 通知用户重新发货
    │
    ├── REFUND 退币完结:
    │     1. 走 5.5 退币子流程(库存不回补,货已灭失/退回仓另入库)
    │     2. RETURNED 包裹: 实物回仓质检
    │        合格→RETURN_IN入库回补available
    │        不合格→报废,写盘点记录
    │     3. 订单→REFUNDED
    │
    └── RESHIP_AND_COMPENSATE: 补发+学币补偿
          compensate_coin 走管理端调账接口(积分服务),
          需二级审批,全程审计
```

### 6.1 实物兑换下单（幂等 + 库存锁定 + 扣币 + 补偿）

```java
@Service
@RequiredArgsConstructor
public class ExchangeOrderService {

    private final GoodsInventoryMapper inventoryMapper;
    private final PointsExchangeOrderMapper orderMapper;
    private final FulfillmentOrderMapper fulfillmentMapper;
    private final WalletClient walletClient;          // 积分服务Feign客户端
    private final AddressCryptoUtil addressCrypto;     // AES-GCM 加解密
    private final DelayTaskProducer delayTaskProducer; // 延迟任务
    private final TransactionTemplate txTemplate;

    /**
     * 创建实物兑换订单。
     * 前置: 商品/限额校验已由上游校验器完成(校验链模式)。
     */
    public ExchangeOrderVO createOrder(long userId, CreateExchangeCmd cmd) {
        // 1. 幂等检查: 同 key 先查已有订单
        PointsExchangeOrder exist = orderMapper.selectByIdempotent(cmd.getIdempotentKey());
        if (exist != null) {
            return assertSameParamsOtherwiseThrow(exist, cmd); // 参数不一致抛 64014
        }

        // 2. 地址加载与快照(解密后重新加密为独立快照密文)
        ShippingAddress addr = addressService.getValidOrThrow(userId, cmd.getAddressId());
        String addressSnapshot = addressCrypto.snapshotJson(addr);

        // 3. 本地事务: 锁库存 + 建订单 + 建履约单
        PointsExchangeOrder order = txTemplate.execute(status -> {
            // 3.1 乐观锁扣减可用库存
            int locked = inventoryMapper.lockStock(cmd.getSkuId(), cmd.getQuantity());
            if (locked == 0) {
                throw new BizException(64011, "INVENTORY_INSUFFICIENT");
            }
            // 3.2 创建订单(PENDING_PAY, 15分钟扣币窗口)
            PointsExchangeOrder o = buildOrder(userId, cmd, addressSnapshot);
            orderMapper.insert(o); // uk_idempotent 冲突→并发下另一请求已建单,捕获后重查返回
            // 3.3 创建履约单(WAIT_AUDIT)
            FulfillmentOrder fo = buildFulfillment(o.getId());
            fulfillmentMapper.insert(fo);
            return o;
        });

        // 4. 跨服务扣币(事务外!)
        ConsumeResult consume;
        try {
            consume = walletClient.consume(ConsumeCmd.builder()
                    .userId(userId)
                    .consumeRuleCode("CONSUME_EXCHANGE_ITEM")
                    .targetType("PHYSICAL_ITEM")
                    .targetId(String.valueOf(cmd.getSkuId()))
                    .idempotentKey(cmd.getIdempotentKey())   // 复用幂等键,积分服务侧同样幂等
                    .expectedCost(order.getCostCoin())
                    .build());
        } catch (RpcTimeoutException e) {
            // 未知结果: 交由对账任务确认, 不立即补偿(见5.1)
            delayTaskProducer.submit("FULFILL_PAY_CONFIRM",
                    order.getOrderNo(), Duration.ofMinutes(5));
            return ExchangeOrderVO.pending(order); // 返回待确认态,客户端提示"兑换处理中"
        } catch (BizException e) {
            compensationCancel(order); // 明确失败: 解锁库存+关闭订单
            throw e;                    // 透传 62011 余额不足等
        }

        // 5. 扣币成功 → 推进状态
        orderMapper.markPaid(order.getId(), consume.getTransactionNo());
        inventoryLogMapper.insertLog(order.getOrderNo(), "LOCK", cmd.getSkuId(), cmd.getQuantity());
        return ExchangeOrderVO.fulfilling(order, consume.getBalanceAfter());
    }

    /** 明确失败时的本地补偿 */
    private void compensationCancel(PointsExchangeOrder order) {
        txTemplate.executeWithoutResult(status -> {
            inventoryMapper.unlockStock(order.getSkuId(), order.getQuantity());
            fulfillmentMapper.closeByExchangeOrderId(order.getId(), "PAY_FAILED");
            orderMapper.updateStatus(order.getId(), "CANCELED", "扣币失败自动取消");
        });
    }
}
```

@Service
@RequiredArgsConstructor
public class BatchShipService {

    private final ShipService singleShipService;
    private final ReportExportClient reportClient;

    @Transactional(propagation = Propagation.NOT_SUPPORTED) // 外层无事务,行级隔离
    public BatchShipResultVO batchShip(MultipartFile excel, String operator) {
        List<ShipRow> rows = ShipExcelParser.parse(excel); // 格式错误行直接进失败列表
        BatchShipResultVO result = new BatchShipResultVO(rows.size());

        for (ShipRow row : rows) {
            try {
                singleShipService.ship(row, operator); // 每行独立事务(REQUIRED新调用)
                result.success(row);
            } catch (BizException e) {
                result.fail(row, e.getUserMessage()); // 单行失败不中断整批
            }
        }
        // 失败明细导出任务(异步报表中心)
        if (result.hasFailure()) {
            result.setExportTaskId(reportClient.submit("BATCH_SHIP_FAIL", result.failRows()));
        }
        auditLogger.log("FULFILL_BATCH_SHIP", operator,
                Map.of("total", result.getTotal(), "success", result.getSuccess()));
        return result;
    }
}

### 6.3 轨迹回调幂等与状态推进

```java
@RestController
@RequestMapping("/api/v1/internal/logistics")
@RequiredArgsConstructor
public class TrackCallbackController {

    private final TrackPushHandler handler;
    private final LogisticsSignVerifier verifier;

    @PostMapping("/track-callback")
    public ApiResponse<Void> onPush(@RequestParam String sign,
                                    @RequestBody TrackPushReq req) {
        if (!verifier.verify(sign, req)) {   // HMAC-SHA256
            return ApiResponse.error(40101, "签名校验失败");
        }
        handler.handle(req);
        return ApiResponse.ok();             // 永远200,失败内部补偿
    }
}

@Service
@RequiredArgsConstructor
public class TrackPushHandler {

    private final LogisticsTrackEventMapper trackMapper;
    private final FulfillmentPackageMapper packageMapper;
    private final ExchangeOrderStateMachine orderStateMachine;
    private final StringRedisTemplate redis;

    public void handle(TrackPushReq req) {
        FulfillmentPackage pkg = packageMapper.lockByTracking(
                req.getProviderCode(), req.getTrackingNo()); // FOR UPDATE
        if (pkg == null) {
            // 单号未登记: 落入待匹配表(可能是先有轨迹后回填), 由对账任务匹配
            trackMapper.insertUnmatched(req);
            return;
        }
        StdAction std = ActionMapping.std(req.getLastResult().getAction());

        // 1. 幂等落轨迹: 唯一索引 (package_id, event_time, event_code)
        TrackEventPO event = buildEvent(pkg, req, std);
        int inserted = trackMapper.insertIgnore(event);
        if (inserted == 0) {
            return; // 纯重复推送
        }

        // 2. 乱序防御: 早于已推进的最新轨迹时间 → 仅补录不推进
        if (event.getEventTime().isBefore(pkg.getLastTrackAt())) {
            return;
        }

        // 3. 状态推进(包裹内乐观锁+状态机校验非法迁移)
        packageMapper.advanceByTrack(pkg.getId(), std, event.getEventTime());

        // 4. 终态联动
        switch (std) {
            case DELIVERED -> orderStateMachine.onPackageDelivered(pkg);
            case REJECTED  -> exceptionFactory.createAuto(pkg, ExceptionType.REJECTED, req);
            case RETURNED  -> exceptionFactory.createAuto(pkg, ExceptionType.ADDRESS_ERROR, req);
            default -> { /* 非终态仅更新 latest_track */ }
        }

        // 5. 失效轨迹缓存
        redis.delete("fulfillment:tracks:" + pkg.getPackageNo());
    }
}
```

### 6.5 退币还原过期批次策略（与积分服务协商的契约）

```json
POST /api/v1/wallet/refund
{
    "userId": 100234,
    "originalTxnNo": "TXN20260915100034552",
    "amount": 1500.00,
    "idempotentKey": "REFUND:PEO20260915100034561",
    "expirePolicy": "RESTORE_ORIGINAL",
    "context": { "bizType": "FULFILLMENT_CANCEL", "orderNo": "PEO20260915100034561" }
}
```

| expirePolicy | 语义 | 本服务使用场景 |
| --- | --- | --- |
| RESTORE_ORIGINAL | 还原扣减时消耗的各过期批次剩余有效期 | 取消/退款（对用户最友好） |
| UNIFORM_90D | 统一从现在起 90 天有效 | 原批次已全部过期时的兜底退回 |

> 积分服务按 `originalTxnNo` 反查 FIFO 消耗明细还原；若某批次在持有期内已过期，退回该部分自动落 UNIFORM_90D。本服务不重复实现过期逻辑，仅透传策略。

## 7. 状态机设计

### 7.1 兑换订单状态机（交易视角）

```
                 ┌──────────────┐
                 │ PENDING_PAY  │──── 超时15min/扣币失败 ───> CANCELED(未支付,库存解锁)
                 └──────┬───────┘
                        │ 扣币成功
                        ▼
                 ┌──────────────┐
        ┌───────>│    PAID      │──────── 用户取消/审核驳回(退币) ──> CANCELED(已退币)
        │        └──────┬───────┘
        │               │ 生成履约单
        │               ▼
        │        ┌──────────────┐
        │        │  FULFILLING  │──── 全部取消(未揽收,退币) ────> CANCELED(已退币)
        │        └──────┬───────┘
        │               │ 首个包裹揽收
        │               ▼
        │        ┌──────────────┐
        │        │   SHIPPED    │──── 丢件退币/客服退款 ────────> REFUNDED
        │        └──────┬───────┘
        │               │ 签收轨迹
        │               ▼
        │        ┌──────────────┐   手动确认 / 15天自动确认
        │        │  DELIVERED   │────────────────────────> COMPLETED(终态)
        │        └──────┬───────┘
        │               │ 异常退币
        │               ▼
        └──────── REFUNDED(终态)
                        │ 丢件且不补不退
                        └───────> CLOSED_EXCEPTION(终态)
```

**迁移合法性表（代码内 `ExchangeOrderStateMachine` 强制）：**

| from | event | to | 副作用 |
| --- | --- | --- | --- |
| PENDING_PAY | PAY_CONFIRMED | PAID/FULFILLING | 记 txn_no |
| PENDING_PAY | PAY_FAILED/TIMEOUT | CANCELED | 解锁库存 |
| PAID | FULFILLMENT_CREATED | FULFILLING | - |
| PAID/FULFILLING | USER_CANCEL(未揽收) | CANCELED | 退币+解锁库存 |
| FULFILLING | FIRST_PACKAGE_GOT | SHIPPED | shipped_at |
| SHIPPED | PACKAGE_DELIVERED | DELIVERED | 启动自动确认延迟任务 |
| DELIVERED | USER_CONFIRM/AUTO_CONFIRM | COMPLETED | completed_at |
| SHIPPED/DELIVERED | REFUND_RESOLVED | REFUNDED | 退币 |
| 任意非终态 | LOST_FINAL | CLOSED_EXCEPTION | 按处置决定退币 |

### 7.2 履约单与包裹状态聚合

```
履约单状态 = f(包裹集合):
  WAIT_AUDIT  : 初始
  WAIT_SHIP   : audit通过
  PARTIAL_SHIPPED : ∃包裹∈{SHIPPED..DELIVERED} ∧ ∃包裹∈{CREATED,LABELED}
  SHIPPED     : ∀包裹 ≥ SHIPPED
  SIGNED      : 主包裹(首包)DELIVERED
  CLOSED      : 订单完结/取消
  EXCEPTION   : ∃异常单 status∈{OPEN,PROCESSING}
  (异常闭环后回到原状态聚合值)
```

聚合由包裹状态变更事件触发重算（单包裹场景直接映射，多包裹走聚合器），避免定时全量刷。

### 8.2 订阅-推送与降级轮询

| 机制 | 说明 |
| --- | --- |
| 订阅时机 | 发货回填单号后同步调用；`subscribe_status=1` |
| 订阅失败重试 | 延迟任务 5min/30min/2h 三次重试，仍失败 `subscribe_status=3` 转轮询 |
| 轮询策略 | 每 12h 拉一次直至终态，终态后再拉一次收尾 |

| 平台故障 | 连续 100 次回调验签失败 → 告警 `logistics_callback_sign_flood`（疑似密钥泄漏/重放攻击） |

| 64014 | IDEMPOTENT_CONFLICT | 幂等键冲突 | 操作处理中，请勿重复提交 |
| 64015 | CANCEL_FORBIDDEN_SHIPPED | 已发货不可取消 | 商品已发货，无法取消，可拒收或签收后联系客服 |
| 64016 | TRACKING_NO_OCCUPIED | 物流单号被占用 | 该物流单号已绑定其他包裹 |
| 64017 | CONFIRM_STATE_INVALID | 非签收态确认 | 订单尚未签收，暂不能确认收货 |

| 64022 | EXCEL_PARSE_FAILED | 批量发货格式错 | 第{row}行格式错误：{reason} |

### 9.2 容错与降级矩阵

| 故障点 | 影响 | 策略 |
| --- | --- | --- |
| 积分服务扣币超时 | 订单状态未知 | PENDING_PAY + 反查确认任务（5.1），绝不双扣（双侧幂等键） |
| 积分服务退款失败 | 用户学币未退 | REFUND_PENDING 重试 6 次 → 告警人工，卡中间态不丢单 |
| 物流订阅失败 | 无推送 | 3 次重试降级 12h 轮询 |
| 回调乱序/重复 | 状态回退 | 唯一索引幂等 + event_time 递增校验 |
| 回调丢失（无轨迹） | 包裹停滞 | 每日扫描：签收前 last_track_at > 7 天 → TRACK_STALLED 异常单 + 主动 pollTracks |
| 库存乐观锁冲突 | 下单失败重试 | 客户端提示刷新库存；服务端不自旋（防超卖优先） |
| 库存与流水不平 | 资损风险 | 每日对账任务（9.3） |
| 月表跨月写入 | 轨迹丢失 | 按轨迹 event_time 路由月表；跨月边界 ±1 天双表探测 |

### 9.3 每日对账任务（03:30）

```
1. 库存对账:
   for each sku:
     available + locked - Σ(inventory_log.qty_change 累计) = 0 ?
     不平 → 告警 fulfillment_inventory_mismatch + 自动生成盘点任务
2. 订单-包裹对账:
   PAID/FULFILLING 订单必有 ≥1 非 CLOSED 包裹; 否则告警
3. 订单-钱包对账:
   status ∉ {PENDING_PAY, CANCELED(未支付)} 必有 wallet_txn_no;
   CANCELED(已退币)/REFUNDED 必有 refund_txn_no 且金额一致
4. 轨迹停滞扫描(见9.2)
5. 发货时效扫描: WAIT_SHIP 超过 ship_deadline → 告警列表推送工作台
```

## 10. 安全与未成年人合规

### 10.1 数据最小化与加密

| 字段 | 处理 |
| --- | --- |
| receiver_name / receiver_phone | AES-256-GCM 加密存储；密钥 KMS 托管、按年轮换；密文参与检索时使用「手机号盲索引」（HMAC-SHA256(phone, salt) 单独列 `phone_index`，管理端手机号搜单用） |
| detail_address | 明文（面单必需），但日志/埋点中**全量脱敏** |
| 地址展示 | 用户端默认脱敏（`王*明 / 138****5678`），编辑时短期解密展示 |

> 补充列（3.1 表已预留位，实施时增加）：`phone_index CHAR(64)` 唯一索引可选（同人多地址允许重复则普通索引）。

### 10.2 未成年人特殊保护

1. **兑换限额**：学生账号单日实物兑换 ≤ 5 单、单月学币消耗实物 ≤ 20000（防沉迷联动，可配置）。
2. **大额引导家长**：单笔 ≥ 5000 学币的实物兑换，发货通知同时抄送绑定家长（家长端可见「孩子兑换记录」，见家长中心文档可见度分级）。
3. **地址提示**：未成年人首次添加地址时弹窗提示「建议在家长陪同下填写」（客户端文案，服务端返回 `firstAddress=true` 标记）。
4. **注销联动**：账户注销流程（数据导出与账户注销服务）调用本服务 `DELETE /internal/fulfillment/user-data` —— 未完结订单阻止注销（返回在途订单列表），完结订单的地址数据 30 天匿名化（姓名/电话/地址替换为占位符，保留统计口径）。
5. **审计**：地址查看（解密）行为记录审计日志——`FULFILL_ADDRESS_DECRYPT` 事件，防止内部滥用。

### 10.3 接口安全

- 用户端接口：JWT 身份 + 数据权限（只能查自己的地址/订单，`user_id` 从上下文注入，禁止 body 传入）。
- 回调接口：HMAC 验签 + IP 白名单（物流平台出口段，配置中心可调）。
- 管理端：RBAC 角色权限（工作台文档 1.3 的四种角色）+ 高危操作（盘点调整、补偿学币）二级审批。
- 限流：地址增删改 10 次/分钟/用户；异常上报 5 次/天/包裹；回调接口按平台维度 500 QPS 令牌桶。

## 12. 测试要点

### 12.1 单元测试

| 对象 | 用例 |
| --- | --- |
| 状态机 | 全部合法迁移 + 全部非法迁移拒绝（如 COMPLETED→CANCELED） |
| 退币策略 | RESTORE_ORIGINAL 批次还原、过期批次落 UNIFORM_90D |

| 轨迹映射 | 各平台 action → std_action 全覆盖，未知 action 落 UNMAPPED 不抛异常 |

### 12.2 集成测试

1. **下单幂等**：并发 10 请求同 idempotentKey → 1 单成功，9 个返回同结果。
2. **库存防超卖**：库存 1、并发 50 下单 → 成功 1、49 个 64011。
3. **扣币超时补偿**：mock 积分服务超时 → 15min 后确认失败 → 库存解锁回原值、订单 CANCELED。
4. **轨迹幂等与乱序**：同轨迹重复推 3 次 → 1 条记录；「签收后到达运输中」→ 状态不回退。
5. **自动确认**：签收后推进 15 天（测试时间快进）→ COMPLETED；期间手动确认 → 任务幂等跳过。
6. **批量发货**：50 行含 4 行坏数据 → 46 成功 4 失败，失败报表可导出。
7. **取消拦截**：LABELED 状态取消 → 拦截成功退币；拦截失败 → 订单恢复 FULFILLING 转人工。
8. **对账**：人工制造库存流水缺口 → 对账任务产出盘点告警。

### 12.3 回归与压测

- 回调链路压测：500 QPS 轨迹推送，P99 入库 < 200ms。
- 下单链路：1000 QPS 混合场景（含 20% 库存不足）下无超卖、无死锁。
- 端到端演练：从兑换→发货→轨迹→签收→自动确认全链路（对接 UAT 物流沙箱）。

## 13. 上线与灰度

1. **功能开关**：`fulfillment.enabled=false` 起步，仅虚拟奖品兑换不受影响；灰度按学段开（幼儿/小学低年级实物奖品 SKU 少，先行）。
2. **数据初始化**：物流渠道种子数据（3.10）；存量无实物订单，无需迁移。
3. **依赖就绪检查**：KMS 密钥、物流平台账号+验签密钥、延迟任务 topic 创建、通知模板 `FULFILL_SHIPPED/FULFILL_DELIVERED/FULFILL_AUTO_CONFIRM/FULFILL_REFUND` 四模板上架。
4. **回滚预案**：关闭功能开关后，已创建订单进入「只读模式」（禁止新下单，存量履约继续人工处理），管理端保留全部操作能力。
