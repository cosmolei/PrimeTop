# 服务端-事件驱动架构与统一事件总线详细设计

## 1. 业务目标
构建一个统一的事件驱动架构与事件总线，实现系统各模块间的异步、解耦、可靠的消息传递，以支持高并发、易扩展的业务演进，并为后续的实时监控、数据分析、流程编排提供基础。  

## 2. 核心概念
- **事件**：描述系统中发生了什么，包含事件ID、类型、发生时间、来源、数据载荷。
- **事件总线**：负责事件的发布、订阅、路由与分发的核心组件。
- **事件处理器**：订阅并处理特定类型事件的服务或组件。
- **事件存储**：持久化事件记录，支持事件溯源、重放、审计与故障排查。
- **事件模式**：领域驱动设计（DDD）中的概念，规范事件的结构与命名。

## 3. 领域事件设计
### 3.1 事件类型分类
| 分类 | 说明 | 示例 |
|------|------|------|
| 用户行为事件 | 用户主动操作或交互 | `UserRegistered`, `UserLogin`, `QuestionAnswered` |
| 业务状态事件 | 业务对象生命周期状态变化 | `LearningPlanCreated`, `MistakeRecordAdded` |
| 系统事件 | 系统内部状态变更或异常 | `ServiceHealthCheckFailed`, `JobExecuted` |
| 外部集成事件 | 与第三方系统交互的事件 | `PaymentSuccess`, `ThirdPartyModelCalled` |

## 4. 事件流技术方案
### 4.1 技术选型
| 组件 | 推荐方案 | 备选方案 |
|------|----------|----------|
| 消息中间件 | Apache Kafka | RabbitMQ, NATS |
| 事件存储 | Apache Kafka (保留历史日志) + 专用存储 (如 MySQL/PostgreSQL) | PostgreSQL, MongoDB |
| 事件路由 | 消费者组、Topic、Partition | 基于规则的动态路由 |
| 序列化 | JSON (便于调试) + Protobuf (高性能场景) | Avro, MessagePack |
| 消费者框架 | Spring Kafka / Kafka Streams | Go-Kafka, Node.js Kafka clients |

### 4.2 Topic 设计原则
- 按业务领域划分 Topic：`user-events`, `learning-events`, `payment-events` 等。
- 为重要事件设置专用 Topic 以实现高优先级处理。
- 事件类型在消息体中通过 `eventType` 字段区分，避免创建过多 Topic。

### 4.3 消息传递可靠性保障
- **消息持久化**：Kafka 开启日志持久化，确保不丢失已提交的消息。
- **生产者确认**：开启 `acks=all`，确保消息写入所有副本。
- **消费者手动提交**：消费者处理成功后手动提交偏移量，防止未处理完即提交。
- **重试策略**：失败事件进入重试队列，最多重试 3 次，超限则转入死信队列（DLQ）。
- **幂等处理**：在消费者端基于 `eventId` 做去重，避免重复处理。

### 4.4 事件版本兼容
- 消息体包含 `version` 字段，如 `"version": "1.0"`。
- 新增字段采用兼容性扩展原则（不可删除已有字段）。
- 消费者支持多版本解析，通过版本号适配处理逻辑。

## 5. 数据结构定义
### 5.1 事件存储表结构（MySQL 示例）
```sql
CREATE TABLE `events` (
  `id` BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '自增主键',
  `event_id` VARCHAR(64) NOT NULL COMMENT '事件唯一ID',
  `event_type` VARCHAR(128) NOT NULL COMMENT '事件类型',
  `event_time` DATETIME(3) NOT NULL COMMENT '事件发生时间',
  `source` VARCHAR(64) NOT NULL COMMENT '事件来源服务',
  `user_id` VARCHAR(32) COMMENT '关联用户ID（如适用）',
  `version` VARCHAR(16) DEFAULT '1.0' COMMENT '事件版本',
  `payload` JSON NOT NULL COMMENT '事件载荷数据',
  `created_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '记录创建时间',
  UNIQUE KEY `uk_event_id` (`event_id`),
  KEY `idx_event_type` (`event_type`),
  KEY `idx_user_id` (`user_id`),
  KEY `idx_event_time` (`event_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='事件存储表';
```

### 5.2 死信事件表（DLQ）
```sql
CREATE TABLE `event_dlq` (
  `id` BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '自增主键',
  `event_id` VARCHAR(64) NOT NULL COMMENT '事件唯一ID',
  `event_type` VARCHAR(128) NOT NULL COMMENT '事件类型',
  `event_time` DATETIME(3) NOT NULL COMMENT '事件发生时间',
  `source` VARCHAR(64) NOT NULL COMMENT '事件来源服务',
  `user_id` VARCHAR(32) COMMENT '关联用户ID（如适用）',
  `version` VARCHAR(16) DEFAULT '1.0' COMMENT '事件版本',
  `payload` JSON NOT NULL COMMENT '事件载荷数据',
  `error_reason` TEXT NOT NULL COMMENT '错误原因',
  `retry_count` INT NOT NULL DEFAULT 0 COMMENT '已重试次数',
  `created_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '记录创建时间',
  UNIQUE KEY `uk_event_id` (`event_id`),
  KEY `idx_event_type` (`event_type`),
  KEY `idx_retry_count` (`retry_count`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='死信事件表';
```

## 7. 状态流转
### 7.1 事件处理生命周期
1. **生成**：业务服务生成领域事件，调用事件发布 API。
2. **发布**：事件总线接收并持久化事件，然后推送到 Kafka Topic。
3. **分发**：各订阅方（消费者组）从 Kafka 拉取并消费事件。
4. **处理**：事件处理器执行业务逻辑，将处理结果写入存储或触发下游动作。
5. **确认**：处理成功则提交 offset，否则触发重试或转入 DLQ。
6. **归档**：超过保留期的 Kafka 日志进行归档清理，对应持久化记录可按策略保留。

### 7.2 事件订阅管理状态
- `ACTIVE`：订阅状态正常，持续消费。
- `PAUSED`：订阅暂停，不接收新事件。
- `ERROR`：订阅异常，需要人工介入。

## 8. 错误处理
### 8.1 错误分类
| 错误类型 | 处理策略 | 示例 |
|----------|----------|------|
| 暂时性错误 | 重试（指数退避） | 网络超时、数据库临时不可用 |
| 永久性错误 | 记录 DLQ，告警 | 数据校验失败、缺失必填字段 |
| 未知错误 | 记录日志，重试 | 未预期的异常 |

### 8.2 监控与告警
- 监控指标：事件发布成功率、消费延迟、消费积压量、重试次数、DLQ 大小。
- 告警策略：积压超过阈值、错误率异常、关键事件未及时消费。

## 9. 质量保障
### 9.1 测试策略
- **单元测试**：验证事件生成与序列化的正确性。
- **集成测试**：启动嵌入式的 Kafka 实例，测试发布、订阅、路由与持久化。
- **重放测试**：使用历史事件进行回放，验证系统状态一致性。
- **压力测试**：模拟高并发事件发布，确保总线吞吐与稳定性。

### 9.2 事件一致性检查
- 定时任务校验事件发布与消费的完整性，发现丢失或重复事件。
- 在关键业务链路中，通过事件溯源实现数据校验与异常追踪。

## 10. 安全与合规
- **鉴权**：发布/消费事件需通过服务鉴权，防止非法访问。
- **敏感数据**：事件载荷中敏感字段加密或脱敏。
- **审计**：对事件的操作（发布、订阅、处理）留存审计日志。

## 11. 关键代码示例（伪代码）
### 11.1 事件发布（生产者）
```java
public class EventPublisher {
    private final KafkaTemplate<String, String> kafkaTemplate;
    private final EventStorage eventStorage;

    public void publish(Event event) {
        // 生成事件ID
        if (event.getEventId() == null) {
            event.setEventId(generateEventId(event.getEventType()));
        }
        // 持久化事件
        eventStorage.save(event);
        // 序列化并推送到Kafka
        String payload = serialize(event);
        kafkaTemplate.send(event.getTopic(), event.getEventId(), payload);
    }
}
```

### 11.2 事件消费者（处理器）
```java
@KafkaListener(topics = "user-events", groupId = "user-service-group")
public void handleUserEvent(String message) {
    try {
        Event event = deserialize(message);
        // 去重检查（基于eventId）
        if (eventStorage.isProcessed(event.getEventId())) {
            return;
        }
        // 路由到具体处理器
        if ("UserRegistered".equals(event.getEventType())) {
            userRegisteredHandler.handle(event);
        }
        // 记录处理成功
        eventStorage.markProcessed(event.getEventId());
    } catch (Exception e) {
        // 重试或转入DLQ
        errorHandler.handle(event, e);
    }
}
```

## 12. 运维与治理
- **监控看板**：展示关键指标与告警状态。
- **事件版本迁移**：逐步迁移消费者至新版本事件格式。
- **Topic 扩容**：根据业务增长调整 Partition 数量，提升并行度。
- **灰度发布**：新版本事件处理器优先在部分节点部署，观察稳定性。
