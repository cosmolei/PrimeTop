## 1. 模块概述

### 1.1 功能定位

数据备份与容灾策略是 PrimeTop 生产环境稳定运行的核心保障。本文档定义各存储组件的备份方案、恢复目标、容灾架构和应急响应流程，确保在硬件故障、软件缺陷、人为误操作或自然灾害场景下，业务数据可恢复、服务可快速重建。

所有策略需在正式上线前完成部署，并至少完成一次全链路恢复演练。

### 1.2 适用范围

| 存储组件 | 用途 | 纳入备份 |
|----------|------|:--------:|
| MySQL / PostgreSQL | 用户、业务、交易等核心关系数据 | ✅ |
| Redis | 会话、缓存、限流计数器 | ✅（部分） |
| Elasticsearch / OpenSearch | 题目检索、知识库搜索、日志 | ✅ |
| Milvus / pgvector | 向量索引（RAG 知识库） | ✅ |
| 对象存储（OSS/MinIO） | 图片、语音、教材资源、头像 | ✅ |
| ClickHouse | 学习行为日志、分析数据 | ✅（部分） |
| Nacos / Apollo 配置中心 | 服务配置、动态配置 | ✅ |
| Git 仓库 | 应用代码、基础设施代码 | ✅（外部） |

### 1.3 RPO 与 RTO 定义

| 业务级别 | 模块举例 | RPO | RTO |
|----------|----------|:---:|:---:|
| **P0 核心交易** | 用户账号、会员订单、支付流水、权益 | ≤ 1 min | ≤ 15 min |
| **P1 核心学习** | 错题记录、学习进度、AI 对话、学习计划 | ≤ 5 min | ≤ 30 min |
| **P2 内容数据** | 题库、知识点、教材章节、考点 | ≤ 1 h | ≤ 2 h |
| **P3 可重建** | 缓存、搜索索引、向量索引、行为日志 | ≤ 24 h | ≤ 4 h |

### 1.4 容灾等级规划

| 阶段 | 架构 | 适用时期 |
|------|------|----------|
| MVP | 单机房 + 定时备份 + 异地归档 | 上线初期 |
| V1.0 | 同城双可用区 + 实时复制 | 用户量 10w+ |
| V1.5+ | 同城双活 + 异地冷备 | 用户量 50w+ |

## 3. 关系数据库备份方案

### 3.1 MySQL 物理全量备份

使用 Percona XtraBackup 执行热备份，不锁表。

```bash
#!/bin/bash
# mysql-full-backup.sh
set -euo pipefail

BACKUP_DIR="/data/backups/mysql"
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_PATH="${BACKUP_DIR}/full_${DATE}"
OSS_BUCKET="oss://primetop-backup/mysql"
RETENTION_DAYS=30

# 1. 物理热备份
xtrabackup --backup \
    --target-dir="${BACKUP_PATH}" \
    --user=backup_user \
    --password="${MYSQL_BACKUP_PASSWORD}" \
    --compress=qpress \
    --compress-threads=4 \
    --parallel=4 \
    --slave-info \
    --safe-slave-backup

# 2. 准备备份（使之一致性可恢复）
xtrabackup --prepare --target-dir="${BACKUP_PATH}"

# 3. 压缩并计算校验和
cd "${BACKUP_DIR}"
tar czf "full_${DATE}.tar.gz" "full_${DATE}"
md5sum "full_${DATE}.tar.gz" > "full_${DATE}.md5"

# 4. 上传至异地 OSS
ossutil cp "full_${DATE}.tar.gz" "${OSS_BUCKET}/full_${DATE}.tar.gz" \
    --config-file ~/.ossutilconfig --force
ossutil cp "full_${DATE}.md5" "${OSS_BUCKET}/full_${DATE}.md5" \
    --config-file ~/.ossutilconfig --force

# 5. 清理本地过期备份
find "${BACKUP_DIR}" -name "full_*" -mtime +${RETENTION_DAYS} -exec rm -rf {} +

echo "[$(date)] MySQL full backup completed: full_${DATE}.tar.gz"
```

### 3.2 MySQL Binlog 实时增量

```bash
#!/bin/bash
# mysql-binlog-sync.sh — 定时将归档 binlog 上传 OSS

SYNC_DIR="/data/backups/mysql/binlog"
OSS_BUCKET="oss://primetop-backup/mysql/binlog"

# 每 5 分钟由 crontab 调用，上传已归档的 binlog
find "${SYNC_DIR}" -name "mysql-bin.*" -mmin +10 ! -name "*.gz" | while read f; do
    gzip "$f"
    ossutil cp "${f}.gz" "${OSS_BUCKET}/$(basename ${f}).gz" \
        --config-file ~/.ossutilconfig --force
done
```

### 3.3 MySQL 恢复流程

```bash
#!/bin/bash
# mysql-restore.sh <backup_date> <target_time>
# Example: mysql-restore.sh 20260519_020000 '2026-05-19 14:30:00'

BACKUP_DATE=$1
TARGET_TIME=$2
BACKUP_FILE="/data/backups/mysql/full_${BACKUP_DATE}.tar.gz"
RESTORE_DIR="/data/restore/mysql/full_${BACKUP_DATE}"
OSS_BUCKET="oss://primetop-backup/mysql"

echo "=== Step 1: Download backup ==="
ossutil cp "${OSS_BUCKET}/full_${BACKUP_DATE}.tar.gz" "${BACKUP_FILE}" \
    --config-file ~/.ossutilconfig
mkdir -p "${RESTORE_DIR}" && tar xzf "${BACKUP_FILE}" -C "${RESTORE_DIR}"

echo "=== Step 2: Prepare ==="
xtrabackup --prepare --target-dir="${RESTORE_DIR}"

echo "=== Step 3: Stop MySQL & restore ==="
systemctl stop mysql
xtrabackup --copy-back --target-dir="${RESTORE_DIR}"
chown -R mysql:mysql /var/lib/mysql

echo "=== Step 4: Start MySQL & replay binlog ==="
systemctl start mysql
# mysqlbinlog --stop-datetime="${TARGET_TIME}" \
#     /data/backups/mysql/binlog/mysql-bin.000XXX | mysql -uroot -p

echo "=== Step 5: Verify ==="
mysqlcheck --all-databases --check
echo "Restore completed."
```

### 3.4 PostgreSQL 备份

**postgresql.conf 关键配置：**

```ini
wal_level = replica
archive_mode = on
archive_command = 'cp %p /data/backups/postgresql/wal/%f'
max_wal_senders = 3
wal_keep_size = 1GB
```

**全量备份脚本：**

```bash
#!/bin/bash
# pg-full-backup.sh
set -euo pipefail

DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR="/data/backups/postgresql"
BACKUP_PATH="${BACKUP_DIR}/full_${DATE}"
OSS_BUCKET="oss://primetop-backup/postgresql"

pg_basebackup \
    -h 127.0.0.1 -p 5432 -U backup_user \
    -D "${BACKUP_PATH}" \
    -Ft -z --checkpoint=fast --progress --wal-method=stream

sha256sum "${BACKUP_PATH}/base.tar.gz" > "${BACKUP_PATH}/base.tar.gz.sha256"
ossutil cp "${BACKUP_PATH}/base.tar.gz" "${OSS_BUCKET}/full_${DATE}/" \
    --config-file ~/.ossutilconfig --force
ossutil cp "${BACKUP_PATH}/base.tar.gz.sha256" "${OSS_BUCKET}/full_${DATE}/" \
    --config-file ~/.ossutilconfig --force

echo "[$(date)] PostgreSQL full backup completed: full_${DATE}"
```

**逻辑备份（每日补充）：**

```bash
#!/bin/bash
# pg-logical-backup.sh
set -euo pipefail

DATE=$(date +%Y%m%d)
BACKUP_DIR="/data/backups/postgresql/logical"
OSS_BUCKET="oss://primetop-backup/postgresql/logical"

for DB in primetop_user primetop_learn primetop_content primetop_analytics; do
    pg_dump -h 127.0.0.1 -U backup_user -d "${DB}" \
        --format=custom --compress=6 \
        -f "${BACKUP_DIR}/${DB}_${DATE}.dump"
    ossutil cp "${BACKUP_DIR}/${DB}_${DATE}.dump" \
        "${OSS_BUCKET}/${DB}_${DATE}.dump" \
        --config-file ~/.ossutilconfig --force
done

find "${BACKUP_DIR}" -name "*.dump" -mtime +7 -delete
echo "[$(date)] PostgreSQL logical backup completed"
```

## 4. 缓存层备份方案

### 4.1 Redis 分级策略

| 实例用途 | 数据性质 | 持久化 | 备份频率 | 保留 |
|----------|----------|--------|----------|------|
| 会话/Token 缓存 | 可丢失 | RDB | 每 6h | 2d |
| 用户等级/积分缓存 | 可重建 | RDB + AOF | 每 6h | 7d |
| 限流计数器 | 可丢失 | 不持久化 | — | — |
| 分布式锁 | 可丢失 | 不持久化 | — | — |

**redis.conf 关键配置：**

```ini
save 900 1
save 300 10
save 60 10000
rdbcompression yes
rdbchecksum yes
dbfilename dump.rdb
dir /data/redis

# 仅关键实例开启 AOF
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

**备份脚本：**

```bash
#!/bin/bash
# redis-backup.sh
set -euo pipefail

DATE=$(date +%Y%m%d_%H%M%S)
REDIS_CLI="redis-cli -h 127.0.0.1 -p 6379"
BACKUP_DIR="/data/backups/redis"
OSS_BUCKET="oss://primetop-backup/redis"

LASTSAVE=$(${REDIS_CLI} LASTSAVE)
${REDIS_CLI} BGSAVE
while [ "$(${REDIS_CLI} LASTSAVE)" == "${LASTSAVE}" ]; do sleep 1; done

cp /data/redis/dump.rdb "${BACKUP_DIR}/dump_${DATE}.rdb"
ossutil cp "${BACKUP_DIR}/dump_${DATE}.rdb" "${OSS_BUCKET}/dump_${DATE}.rdb" \
    --config-file ~/.ossutilconfig --force
find "${BACKUP_DIR}" -name "dump_*.rdb" -mtime +7 -delete

echo "[$(date)] Redis backup completed"
```

> **恢复**：停止 Redis → 替换 dump.rdb → 启动。纯缓存实例无需恢复，应用层自动重建。

## 5. 搜索与向量引擎备份

### 5.1 Elasticsearch Snapshot

```bash
# 注册 OSS 快照仓库
curl -X PUT "http://127.0.0.1:9200/_snapshot/primetop_backup" -H 'Content-Type: application/json' -d '{

  "settings": {
    "endpoint": "oss-cn-hangzhou-internal.aliyuncs.com",

    "secret_access_key": "${OSS_SECRET_KEY}",

    -H 'Content-Type: application/json' -d '{
  "indices": "primetop_*",
  "ignore_unavailable": true,
  "include_global_state": false

```

## 7. ClickHouse 备份方案

```bash
#!/bin/bash
# clickhouse-backup.sh
set -euo pipefail

DATE=$(date +%Y%m%d)
CH_HOST="127.0.0.1"
BACKUP_DIR="/data/backups/clickhouse"
OSS_BUCKET="oss://primetop-backup/clickhouse"

# 按表执行 Freeze（硬链接快照，几乎无 IO 开销）
for TABLE in $(clickhouse-client --query "SHOW TABLES FROM primetop_analytics"); do
    clickhouse-client --query "ALTER TABLE primetop_analytics.${TABLE} FREEZE WITH NAME 'backup_${DATE}'"
done

# 打包并上传
BACKUP_PATH="/var/lib/clickhouse/shadow/backup_${DATE}"
tar czf "${BACKUP_DIR}/daily_${DATE}.tar.gz" -C /var/lib/clickhouse/shadow "backup_${DATE}"
ossutil cp "${BACKUP_DIR}/daily_${DATE}.tar.gz" "${OSS_BUCKET}/daily_${DATE}.tar.gz" \
    --config-file ~/.ossutilconfig --force

# 清理 shadow
clickhouse-client --query "ALTER TABLE ... CLEAR SHADOW" # 逐表清理
find "${BACKUP_DIR}" -name "daily_*.tar.gz" -mtime +7 -delete

echo "[$(date)] ClickHouse backup completed"
```

## 8. 容灾架构设计

### 8.1 MVP 阶段：单机房 + 异地备份

```
                     │    主机房 (杭州 AZ-a) │
                     │                      │

                     │  │   负载均衡 (SLB) │ │
                     │  └────────┬────────┘ │
                     │           │          │
                     │  ┌────────▼────────┐ │
                     │  │   MySQL 主库     │ │
                     │  │   Redis          │ │
                     │  │   ES 集群        │ │
                     │  │   Milvus         │ │
                     │  │   ClickHouse     │ │
                     │  └─────────────────┘ │
                     └──────────┬───────────┘
                                │ 定时备份上传
                                ▼
                     ┌──────────────────────┐
                     │   异地 OSS (上海)     │
                     │                      │
```

**RTO 分析（MVP 单机房）：**

| 故障类型 | 恢复动作 | 预估 RTO |
|----------|----------|----------|
| MySQL 主库宕机 | 从从库提升 + 或从备份恢复 | 15-30 min |
| 单台 App 服务器宕机 | SLB 自动摘除 | < 1 min |
| 整机房故障 | 异地拉起新集群 + 恢复数据 | 2-4 h |

### 8.2 V1.0 阶段：同城双可用区

```
         ┌──────────────────┐    ┌──────────────────┐
         │  杭州可用区 A     │    │  杭州可用区 B     │
         │                  │    │                  │
         │  App Srv ×2      │    │  App Srv ×2      │
         │  MySQL 主库      │───→│  MySQL 从库       │
         │  Redis 主        │───→│  Redis 从         │
         │  ES master+data  │    │  ES data          │
         │  Milvus 写       │    │  Milvus 读        │
         │  CH 分片 1       │    │  CH 分片 2        │
         └──────────────────┘    └──────────────────┘
                    │                        │
                    └─────────┬──────────────┘
                              ▼
                   ┌──────────────────────┐
                   │   异地 OSS (上海)     │
                   └──────────────────────┘
```

**关键能力：**
- MySQL 半同步复制：AZ-A 主库写入后，至少一个从库（AZ-B）确认接收。
- Redis Sentinel 自动故障切换。
- ES 跨 AZ 副本分片。
- AZ 级故障自动切换，RTO ≤ 5 min。

### 8.3 V1.5 阶段：同城双活 + 异地冷备

```
         ┌────────────┐  同步复制  ┌────────────┐
         │  杭州机房   │←─────────→│  上海机房   │
         │  (主)       │           │  (冷备)     │

               │
               │  MySQL 主主
```

**关键能力：**
- 机房级故障可切换，RTO ≤ 30 min。
- 异地冷备保证极端场景下的数据安全。

## 9. 应急响应流程

### 9.1 故障分级

| 级别 | 定义 | 示例 | 响应时间 |
|------|------|------|----------|
| P0 | 核心业务完全不可用 | 数据库宕机、全部服务不可达 | 5 min |
| P1 | 核心功能部分受损 | 单个服务异常、AI 调用失败率飙升 | 15 min |
| P2 | 非核心功能异常 | 后台管理慢、报表延迟 | 1 h |
| P3 | 潜在风险 | 备份延迟、磁盘利用率超 80% | 4 h |

### 9.2 数据恢复决策树

```
数据丢失/损坏发生
    │
    ├── 只影响缓存层？
    │       └── 是 → 清除缓存，应用层自动重建 (RTO < 5min)
    │
    ├── 只影响搜索/向量索引？
    │       └── 是 → 从 Snapshot 恢复 (RTO ~30min)
    │
    ├── 影响关系数据库？
    │       │
    │       ├── 从库可用且数据完整？
    │       │       └── 是 → 从库提升为主库 (RTO < 15min)
    │       │
    │       ├── 有 binlog，可重放至目标时间？
    │       │       └── 是 → 全量恢复 + binlog 重放 (RTO ~30min)
    │       │
    │       └── 只能从全量备份恢复？
    │               └── 评估数据丢失窗口，执行恢复 (RTO ~1h)
    │
    └── 大面积故障（整机房）？
            └── 启动容灾切换流程 (RTO 2-4h)
```

### 9.3 应急通讯模板

## 10. 备份校验与恢复演练

### 10.1 自动化校验

每次备份完成后自动执行以下校验：

```bash
#!/bin/bash
# backup-verify.sh
# 在备份完成后由 cron 调用

set -euo pipefail

DATE=$(date +%Y%m%d)
OSS_BUCKET="oss://primetop-backup"
VERIFY_DIR="/data/restore/verify"

mkdir -p "${VERIFY_DIR}"

# 1. 校验 MySQL 备份 MD5
ossutil cp "${OSS_BUCKET}/mysql/full_${DATE}.md5" "${VERIFY_DIR}/"
cd "${VERIFY_DIR}"
md5sum -c "full_${DATE}.md5" || echo "ALERT: MySQL backup checksum mismatch!"

# 2. 校验 PostgreSQL 备份 SHA256
ossutil cp "${OSS_BUCKET}/postgresql/full_${DATE}/base.tar.gz.sha256" "${VERIFY_DIR}/"
sha256sum -c "base.tar.gz.sha256" || echo "ALERT: PostgreSQL backup checksum mismatch!"

# 3. 检查备份文件大小（非零且合理）
for f in full_${DATE}.tar.gz base.tar.gz; do
    SIZE=$(stat -f%z "$f" 2>/dev/null || stat -c%s "$f" 2>/dev/null || echo 0)
    if [ "$SIZE" -lt 1048576 ]; then  # < 1MB 视为异常
        echo "ALERT: Backup file $f is suspiciously small ($SIZE bytes)"
    fi
done

# 4. 检查备份新鲜度（距离上次成功备份不超过 26 小时）
LAST_BACKUP=$(cat /data/backups/.last_success_timestamp)
HOURS_SINCE=$(( ($(date +%s) - $(date -d "$LAST_BACKUP" +%s)) / 3600 ))
if [ "$HOURS_SINCE" -gt 26 ]; then
    echo "ALERT: No successful backup in ${HOURS_SINCE} hours!"
fi

echo "[$(date)] Backup verification completed"
```

## 11. 备份安全与加密

### 11.1 数据加密策略

| 阶段 | 加密方式 | 说明 |
|------|----------|------|
| 传输中 | TLS 1.2+ | 所有备份上传走 HTTPS |
| OSS 静态 | 服务端加密 (SSE-KMS) | 使用阿里云 KMS 托管密钥 |
| 本地存储 | LUKS 磁盘加密 | 备份目录所在磁盘开启加密 |
| 敏感表 | 字段级加密 | 用户手机号、密码等字段在备份前已加密存储 |

### 11.2 访问控制

```yaml
# 备份系统 IAM 权限策略
backup_operator:
  can:
    - oss:GetObject (primetop-backup/*)
    - oss:PutObject (primetop-backup/*)
    - mysql:RELOAD
    - mysql:SELECT (指定库)
  cannot:
    - oss:DeleteBucket
    - oss:DeleteObject (保留期内)
    - mysql:DROP
    - mysql:ALTER USER

backup_auditor:
  can:
    - oss:GetObject (primetop-backup/*.md5, *.sha256)
    - oss:ListObjects (primetop-backup/)
  cannot:
    - oss:PutObject
    - 数据库直连
```

### 11.3 备份保留与销毁

- 备份保留期外自动清理，通过 OSS 生命周期策略实现。
- 敏感数据备份销毁需双人确认，记录审计日志。
- 用户注销后，30天内清理所有关联备份中的个人数据。

### 12.1 备份监控指标

| 指标 | 告警条件 | 级别 |
|------|----------|------|
| 备份任务执行状态 | 失败或超时（>2h） | P1 |
| 备份文件大小 | 与前日偏差 >50% | P2 |
| 备份上传完成时间 | 05:00 前未完成 | P2 |

| 最后成功备份时间 | 超过 26 小时 | P1 |

| 磁盘使用率 | 备份目录 >85% | P2 |
