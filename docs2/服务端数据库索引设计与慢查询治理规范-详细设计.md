> 版本：v1.0 | 更新日期：2026-05-25 | 状态：初稿

## 1. 文档概述

### 1.2 适用范围

- 所有使用 MySQL/PostgreSQL 作为主存储的业务服务
- 涉及高频读写的核心表（用户、题目、错题、学习记录、AI对话等）

## 2. 设计原则

### 2.1 索引设计核心原则

| 原则 | 说明 |
| --- | --- |
| **查询驱动** | 索引跟着查询走，先确定高频查询模式再建索引 |
| **最左前缀** | 联合索引严格遵循最左前缀匹配，字段顺序按选择性从高到低排列 |
| **覆盖索引优先** | 高频查询尽量通过覆盖索引避免回表 |
| **索引克制** | 单表索引数建议不超过 6 个，写多读少的表不超过 4 个 |
| **定期审计** | 每月审计索引使用率，删除冗余和未使用索引 |

### 2.2 反模式（禁止）

1. **无谓的全表索引**：不要对低选择性字段（如 gender、status）单独建索引
2. **索引冗余**：`INDEX(a, b)` 存在后不再建 `INDEX(a)`
3. **过度联合索引**：联合索引字段数不超过 5 个
4. **在索引列上运算**：`WHERE YEAR(created_at) = 2026` 会导致索引失效
5. **隐式类型转换**：varchar 列用整型参数查询会导致索引失效
6. **OR 条件滥用**：`WHERE a = 1 OR b = 2` 可能使索引失效，改用 UNION

## 3. 核心表索引设计

### 3.1 用户相关表

#### 3.1.1 users（用户基础表）

```sql
CREATE TABLE users (
    id              BIGINT UNSIGNED    NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    phone           VARCHAR(20)        NOT NULL DEFAULT '' COMMENT '手机号（AES加密存储）',
    phone_hash      CHAR(64)           NOT NULL DEFAULT '' COMMENT '手机号SHA256哈希（用于登录查询）',
    nickname        VARCHAR(50)        NOT NULL DEFAULT '' COMMENT '昵称',
    avatar_url      VARCHAR(500)       NOT NULL DEFAULT '' COMMENT '头像URL',
    user_type       TINYINT UNSIGNED   NOT NULL DEFAULT 1 COMMENT '用户类型：1学生 2家长 3教师 4管理员',
    status          TINYINT UNSIGNED   NOT NULL DEFAULT 1 COMMENT '状态：1正常 2冻结 3注销',
    last_login_at   DATETIME           NOT NULL DEFAULT '1970-01-01' COMMENT '最后登录时间',
    created_at      DATETIME           NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME           NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    is_deleted      TINYINT UNSIGNED   NOT NULL DEFAULT 0,
    PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户基础表';

-- 登录查询：手机号哈希精确匹配（最高频查询）
CREATE UNIQUE INDEX uk_phone_hash ON users(phone_hash);

-- 后台用户列表查询：按类型 + 状态 + 注册时间筛选
CREATE INDEX idx_type_status_created ON users(user_type, status, created_at);

-- 最后登录时间（用于活跃用户统计）
CREATE INDEX idx_last_login ON users(last_login_at);
```

**设计说明：**

- 手机号加密存储，用 `phone_hash` 做登录匹配，避免明文查询
- `idx_type_status_created` 是后台管理最常见的组合查询
- 不为 `status`、`user_type` 单独建索引（低选择性）

### 3.2 题目相关表

#### 3.2.1 questions（题目表）

```sql
CREATE TABLE questions (
    id              BIGINT UNSIGNED    NOT NULL AUTO_INCREMENT COMMENT '题目ID',
    subject_id      SMALLINT UNSIGNED  NOT NULL COMMENT '学科ID',
    stage           TINYINT UNSIGNED   NOT NULL COMMENT '学段',
    grade           TINYINT UNSIGNED   NOT NULL COMMENT '年级',
    question_type   TINYINT UNSIGNED   NOT NULL COMMENT '题型：1选择 2填空 3解答 4判断 5作文',
    difficulty      TINYINT UNSIGNED   NOT NULL DEFAULT 3 COMMENT '难度：1-5',
    content_hash    CHAR(64)           NOT NULL DEFAULT '' COMMENT '题干内容哈希（用于去重）',
    source_type     TINYINT UNSIGNED   NOT NULL DEFAULT 1 COMMENT '来源：1人工录入 2OCR 3AI生成',
    status          TINYINT UNSIGNED   NOT NULL DEFAULT 1 COMMENT '1草稿 2已发布 3已下架',
    usage_count     INT UNSIGNED       NOT NULL DEFAULT 0 COMMENT '使用次数',
    correct_rate    DECIMAL(5,4)       NOT NULL DEFAULT 0.0000 COMMENT '正确率',
    created_at      DATETIME           NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME           NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    is_deleted      TINYINT UNSIGNED   NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    -- 题库浏览：按学科+学段+年级+题型筛选（覆盖索引含difficulty避免回表）
    INDEX idx_subject_stage_grade_type_diff (
        subject_id, stage, grade, question_type, difficulty
    ),
    -- 题目去重检查
    INDEX idx_content_hash (content_hash),
    -- 后台按来源+状态管理
    INDEX idx_source_status (source_type, status, created_at),
    -- 热门题目排行
    INDEX idx_usage_count (usage_count DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='题目表';
```

**设计说明：**

- `idx_subject_stage_grade_type_diff` 是 5 字段联合索引，覆盖题库最核心的筛选+排序场景
- 该索引可用于以下查询模式：
  - `WHERE subject_id=? AND stage=? AND grade=?`（最左 3 字段）
  - `WHERE subject_id=? AND stage=? AND grade=? AND question_type=?`（最左 4 字段）
  - `WHERE subject_id=? AND stage=? AND grade=? AND question_type=? ORDER BY difficulty`（完整覆盖）

### 3.3 学习记录相关表

#### 3.3.1 answer_records（答题记录表）

这是数据量增长最快的表之一，需要特别关注索引设计。

```sql
CREATE TABLE answer_records (
    id              BIGINT UNSIGNED    NOT NULL AUTO_INCREMENT,
    user_id         BIGINT UNSIGNED    NOT NULL,
    question_id     BIGINT UNSIGNED    NOT NULL,
    session_id      VARCHAR(50)        NOT NULL DEFAULT '' COMMENT '学习会话ID',
    subject_id      SMALLINT UNSIGNED  NOT NULL,
    is_correct      TINYINT UNSIGNED   NOT NULL COMMENT '0错 1对',
    time_spent_ms   INT UNSIGNED       NOT NULL DEFAULT 0 COMMENT '答题耗时ms',
    answer_mode     TINYINT UNSIGNED   NOT NULL DEFAULT 1 COMMENT '1主动练习 2拍题 3AI推荐 4考试',
    created_at      DATETIME           NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    -- 学情分析：查某用户某学科的所有答题记录（最高频）
    -- 该索引也是分页查询的基础
    INDEX idx_user_subject_created (user_id, subject_id, created_at DESC),
    -- 查某题目的答题统计
    INDEX idx_question_created (question_id, created_at),
    -- 按会话查答题记录
    INDEX idx_session (session_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='答题记录表';
```

**数据量预估与分区策略：**

| 时间范围 | 预估行数 | 单表大小 |
| --- | --- | --- |
| 3 个月 | ~5000万 | ~8GB |
| 6 个月 | ~1亿 | ~16GB |
| 1 年 | ~2亿 | ~32GB |

当单表超过 5000 万行或 8GB 时，启动按月分区：

```sql
-- 按 created_at 做RANGE分区
ALTER TABLE answer_records
PARTITION BY RANGE (TO_DAYS(created_at)) (
    PARTITION p202601 VALUES LESS THAN (TO_DAYS('2026-02-01')),
    PARTITION p202602 VALUES LESS THAN (TO_DAYS('2026-03-01')),
    PARTITION p202603 VALUES LESS THAN (TO_DAYS('2026-04-01')),
    -- ...每月一个分区
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

分区维护存储过程（每月1号自动执行）：

```sql
DELIMITER $$
CREATE PROCEDURE maintain_answer_records_partition()
BEGIN
    DECLARE partition_name VARCHAR(20);
    DECLARE partition_date DATE;
    
    -- 计算下下个月的分区
    SET partition_date = DATE_FORMAT(DATE_ADD(CURDATE(), INTERVAL 2 MONTH), '%Y-%m-01');
    SET partition_name = CONCAT('p', DATE_FORMAT(partition_date, '%Y%m'));
    
    SET @sql = CONCAT(
        'ALTER TABLE answer_records REORGANIZE PARTITION p_future INTO (',
        'PARTITION ', partition_name, ' VALUES LESS THAN (TO_DAYS(''',
        DATE_FORMAT(DATE_ADD(partition_date, INTERVAL 1 MONTH), '%Y-%m-01'), ''')),',
        'PARTITION p_future VALUES LESS THAN MAXVALUE)'
    );
    
    PREPARE stmt FROM @sql;
    EXECUTE stmt;
    DEALLOCATE PREPARE stmt;
    
    -- 删除12个月前的分区（数据已归档到数据仓库）
    -- 注意：需确认归档完成后再执行
END$$
DELIMITER ;
```

### 3.4 错题相关表

#### 3.4.1 mistake_records（错题记录表）

```sql
CREATE TABLE mistake_records (
    id                  BIGINT UNSIGNED    NOT NULL AUTO_INCREMENT,
    user_id             BIGINT UNSIGNED    NOT NULL,
    question_id         BIGINT UNSIGNED    NOT NULL,
    subject_id          SMALLINT UNSIGNED  NOT NULL,
    knowledge_point_id  INT UNSIGNED       NOT NULL DEFAULT 0 COMMENT '主知识点',
    error_type          TINYINT UNSIGNED   NOT NULL DEFAULT 0 COMMENT '错因：1概念不清 2审题 3计算 4方法 5其他',
    source_type         TINYINT UNSIGNED   NOT NULL DEFAULT 1 COMMENT '来源：1拍题 2练习 3手动',
    review_count        TINYINT UNSIGNED   NOT NULL DEFAULT 0 COMMENT '已复习次数',
    mastery_level       TINYINT UNSIGNED   NOT NULL DEFAULT 0 COMMENT '掌握度：0-4（0未掌握 4完全掌握）',
    next_review_at      DATETIME           NOT NULL DEFAULT '1970-01-01' COMMENT '下次复习时间（遗忘曲线）',
    is_mastered         TINYINT UNSIGNED   NOT NULL DEFAULT 0 COMMENT '是否已掌握',
    created_at          DATETIME           NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at          DATETIME           NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    is_deleted          TINYINT UNSIGNED   NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    -- 错题本列表：按用户+学科+时间分页（最高频查询）
    INDEX idx_user_subject_created (user_id, subject_id, created_at DESC),
    -- 复习提醒：查需要复习的错题（遗忘曲线调度引擎高频使用）
    INDEX idx_user_next_review (user_id, next_review_at),
    -- 按知识点归因分析
    INDEX idx_user_kp (user_id, knowledge_point_id, mastery_level),
    -- 错因统计
    INDEX idx_user_error_type (user_id, error_type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='错题记录表';
```

**设计说明：**

- `idx_user_next_review` 是遗忘曲线复习引擎的核心索引，直接支撑"待复习错题"查询
- 查询示例：`WHERE user_id = ? AND next_review_at <= NOW() AND is_mastered = 0 ORDER BY next_review_at`
- `mastery_level` 放在 `idx_user_kp` 尾部，可直接利用索引排序

## 4. 索引命名规范

### 4.1 命名规则

| 索引类型 | 前缀 | 示例 |
| --- | --- | --- |
| 主键 | `PK_` | `PK_users`（由数据库自动管理） |
| 唯一索引 | `uk_` | `uk_phone_hash` |
| 普通索引 | `idx_` | `idx_user_subject_created` |
| 联合索引 | `idx_表名_字段1_字段2` | `idx_user_type_status` |

### 4.2 字段缩写对照表

| 原词 | 缩写 |
| --- | --- |
| created_at | created |
| updated_at | updated |
| user_id | user |

```python
# explain_analyzer.py
"""
EXPLAIN 结果自动分析工具
"""
from dataclasses import dataclass


@dataclass
class ExplainRow:
    id: int
    select_type: str
    table: str
    partitions: str
    type: str          # 访问类型（重点关注）
    possible_keys: str # 可能用到的索引
    key: str           # 实际使用的索引
    key_len: str       # 索引长度
    ref: str
    rows: int          # 预估扫描行数
    filtered: float    # 过滤比例
    extra: str         # 额外信息（重点关注）


# 访问类型性能排序（从好到差）
ACCESS_TYPE_SCORE = {
    'system':    10,  # 系统表，只有一行
    'const':     9,   # 常量查询（主键/唯一索引等值匹配）
    'eq_ref':    8,   # 唯一索引扫描
    'ref':       7,   # 非唯一索引扫描
    'range':     6,   # 索引范围扫描
    'index':     3,   # 全索引扫描
    'all':       1,   # 全表扫描（最差）
}

# Extra 字段中的风险关键词
EXTRA_WARNINGS = {
    'Using filesort':     '需要额外排序，考虑优化ORDER BY',
    'Using temporary':    '使用了临时表，检查GROUP BY/ORDER BY',
    'Using join buffer':  '关联查询缺少索引',
    'Full table scan':    '全表扫描，必须添加索引',
    'Impossible WHERE':   'WHERE条件永远为false，检查逻辑',
}


def analyze_explain(rows: list[ExplainRow]) -> list[str]:
    """分析 EXPLAIN 结果，返回优化建议"""
    issues = []
    
    for row in rows:
        # 1. 检查访问类型
        score = ACCESS_TYPE_SCORE.get(row.type.lower(), 0)
        if score <= 3:
            issues.append(
                f"[严重] 表 {row.table} 访问类型为 {row.type}，"
                f"扫描行数 {row.rows}，建议添加合适索引"
            )
        
        # 2. 检查是否使用了索引
        if not row.key and row.type.lower() == 'all':
            issues.append(
                f"[严重] 表 {row.table} 全表扫描，possible_keys={row.possible_keys}，"
                f"未使用任何索引"
            )
        
        # 3. 检查 possible_keys 过多
        if row.possible_keys and len(row.possible_keys.split(',')) > 3:
            issues.append(
                f"[提示] 表 {row.table} 有 {len(row.possible_keys.split(','))} 个候选索引，"
                f"优化器选择可能不优，考虑精简索引"
            )
        
        # 4. 检查 Extra 字段
        for keyword, desc in EXTRA_WARNINGS.items():
            if keyword.lower() in row.extra.lower():
                issues.append(
                    f"[警告] 表 {row.table} Extra: {keyword} — {desc}"
                )
        
        # 5. 检查预估扫描行数
        if row.rows > 10000:
            issues.append(
                f"[警告] 表 {row.table} 预估扫描 {row.rows} 行，"
                f"考虑缩小查询范围或添加索引"
            )
        
        # 6. 检查 filtered 比例
        if row.filtered < 10:
            issues.append(
                f"[提示] 表 {row.table} 过滤比例仅 {row.filtered}%，"
                f"大量扫描行被丢弃，索引选择性不足"
            )
    
    return issues
```

### 5.3 慢查询优化策略

#### 5.3.1 策略决策树

```
慢查询
├── 全表扫描（type=ALL）
│   ├── WHERE 条件缺少索引 → 添加合适索引
│   ├── 索引存在但未使用 → 检查隐式转换/函数调用/OR条件
│   └── 表数据量小（<1000行） → 可接受，标记观察
│
├── 索引扫描但慢（type=ref/range）
│   ├── 扫描行数多 → 收窄查询范围（加更多WHERE条件）
│   ├── 回表次数多 → 创建覆盖索引
│   └── 排序开销大 → 调整索引字段顺序使ORDER BY走索引
│
├── Using filesort
│   ├── ORDER BY字段不在索引中 → 加入索引尾部
│   └── 多字段排序方向不一致 → 统一排序方向或调整业务
│
├── Using temporary
│   ├── GROUP BY无索引 → 添加GROUP BY字段到索引
│   ├── DISTINCT → 考虑改写为GROUP BY
│   └── UNION → 检查是否可改为OR条件
│
└── JOIN慢
    ├── 关联字段无索引 → 给被驱动表加索引
    ├── 驱动表选择不当 → 用STRAIGHT_JOIN强制指定
    └── 关联表太多 → 拆分为多次查询或在应用层关联
```

### 6.1 定期索引审计

```python
# index_audit.py
"""
索引审计工具：定期扫描索引使用情况，输出优化建议
"""
import datetime


INDEX_AUDIT_QUERIES = {
    # 未使用的索引（30天内从未使用）
    "unused_indexes": """
        SELECT
            s.TABLE_SCHEMA,
            s.TABLE_NAME,
            s.INDEX_NAME,
            s.NON_UNIQUE,
            s.SEQ_IN_INDEX,
            s.COLUMN_NAME
        FROM information_schema.STATISTICS s
        LEFT JOIN (
            SELECT * FROM sys.schema_unused_indexes
            WHERE object_schema NOT IN ('mysql', 'sys', 'performance_schema')
        ) u ON s.TABLE_SCHEMA = u.object_schema
            AND s.TABLE_NAME = u.object_name
            AND s.INDEX_NAME = u.index_name
        WHERE u.object_schema IS NOT NULL
        ORDER BY s.TABLE_SCHEMA, s.TABLE_NAME, s.INDEX_NAME, s.SEQ_IN_INDEX
    """,

    # 冗余索引（前缀被其他索引覆盖）
    "redundant_indexes": """
        SELECT *
        FROM sys.schema_redundant_indexes
    """,

    # 索引碎片率（高于10%建议优化）
    "fragmented_indexes": """
        SELECT
            TABLE_SCHEMA,
            TABLE_NAME,
            INDEX_NAME,
            ROUND(DATA_FREE / (DATA_LENGTH + INDEX_LENGTH + DATA_FREE) * 100, 2)
                AS fragment_ratio_pct,
            DATA_LENGTH,
            INDEX_LENGTH,
            DATA_FREE
        FROM information_schema.TABLES
        WHERE TABLE_SCHEMA NOT IN ('mysql', 'sys', 'performance_schema', 'information_schema')
          AND TABLE_TYPE = 'BASE TABLE'
          AND DATA_FREE / (DATA_LENGTH + INDEX_LENGTH + DATA_FREE) > 0.10
        ORDER BY fragment_ratio_pct DESC
    """,

    # 单表索引数过多（>6）
    "too_many_indexes": """
        SELECT
            TABLE_SCHEMA,
            TABLE_NAME,
            COUNT(DISTINCT INDEX_NAME) AS index_count
        FROM information_schema.STATISTICS
        WHERE TABLE_SCHEMA NOT IN ('mysql', 'sys', 'performance_schema', 'information_schema')
          AND INDEX_NAME != 'PRIMARY'
        GROUP BY TABLE_SCHEMA, TABLE_NAME
        HAVING COUNT(DISTINCT INDEX_NAME) > 6
        ORDER BY index_count DESC
    """,
}


def generate_audit_report(mysql_conn) -> dict:
    """生成索引审计报告"""
    report = {
        "audit_date": datetime.date.today().isoformat(),
        "findings": {},
    }
    
    with mysql_conn.cursor() as cursor:
        for check_name, sql in INDEX_AUDIT_QUERIES.items():
            try:
                cursor.execute(sql)
                rows = cursor.fetchall()
                report["findings"][check_name] = {
                    "count": len(rows),
                    "details": rows[:50],  # 最多50条
                }
            except Exception as e:
                report["findings"][check_name] = {"error": str(e)}
    
    return report


def suggest_actions(report: dict) -> list[str]:
    """根据审计结果生成操作建议"""
    actions = []
    
    # 未使用索引
    unused = report["findings"].get("unused_indexes", {})
    if unused.get("count", 0) > 0:
        actions.append(
            f"发现 {unused['count']} 个未使用索引，建议评估后删除。"
            f"注意：可能是低频但重要的查询在使用，需人工确认。"
        )
    
    # 冗余索引
    redundant = report["findings"].get("redundant_indexes", {})
    if redundant.get("count", 0) > 0:
        actions.append(
            f"发现 {redundant['count']} 个冗余索引，可以直接删除。"
        )
    
    # 碎片率高
    fragmented = report["findings"].get("fragmented_indexes", {})
    if fragmented.get("count", 0) > 0:
        actions.append(
            f"发现 {fragmented['count']} 个碎片率>10%的表，"
            f"建议在低峰期执行 OPTIMIZE TABLE 或 ALTER TABLE ... ENGINE=InnoDB。"
        )
    
    return actions
```

## 8. 开发规范清单

### 8.1 DDL Review Checklist

每个数据库变更必须通过以下检查：

- [ ] 表名使用蛇形命名（snake_case），如 `answer_records`
- [ ] 所有表都有 `created_at` 字段（默认 `CURRENT_TIMESTAMP`）
- [ ] 所有表都有 `updated_at` 字段（自动更新）
- [ ] 需要软删除的表有 `is_deleted` 字段
- [ ] 主键使用 `BIGINT UNSIGNED AUTO_INCREMENT`
- [ ] 字段有明确的 `COMMENT`
- [ ] 索引命名遵循规范（`uk_` / `idx_`）
- [ ] 联合索引字段数 ≤ 5
- [ ] 单表索引总数 ≤ 6
- [ ] 无冗余索引（新索引不是已有索引的前缀）
- [ ] 已使用 `EXPLAIN` 验证查询计划
- [ ] 已评估对写入性能的影响

### 8.2 SQL 编写规范

```python
# SQL编写Do & Don't

# ✅ DO: 使用参数化查询，防止SQL注入
cursor.execute(
    "SELECT id, nickname FROM users WHERE id = %s AND status = %s",
    (user_id, 1)
)

# ❌ DON'T: 字符串拼接SQL
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")

# ✅ DO: 指定查询字段
cursor.execute(
    "SELECT id, nickname, avatar_url FROM users WHERE id = %s",
    (user_id,)
)

# ❌ DON'T: SELECT *
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))

# ✅ DO: 批量操作
cursor.executemany(
    "INSERT INTO mistake_records (user_id, question_id, subject_id) VALUES (%s, %s, %s)",
    [(user_id, q1, subj), (user_id, q2, subj)]
)

# ❌ DON'T: 循环单条操作
for q in questions:
    cursor.execute("INSERT INTO mistake_records (...) VALUES (...)", [...])

# ✅ DO: 使用游标分页
cursor.execute(
    "SELECT ... FROM table WHERE user_id = %s AND created_at < %s ORDER BY created_at DESC LIMIT 20",
    (user_id, last_cursor)
)

# ❌ DON'T: 大offset分页
cursor.execute(
    "SELECT ... FROM table WHERE user_id = %s ORDER BY created_at DESC LIMIT %s, 20",
    (user_id, 100000)
)
```

### 8.3 ORM 注意事项

```python
# SQLAlchemy 示例

# ✅ 正确使用索引提示（必要时）
from sqlalchemy import text

# 强制使用指定索引（仅当优化器选错索引时使用）
query = session.query(AnswerRecord).filter(
    AnswerRecord.user_id == user_id

    AnswerRecord,
    'FORCE INDEX (idx_user_subject_created)',
    'mysql'

# ✅ 批量插入使用 bulk_insert_mappings（跳过ORM事件，更快）
session.bulk_insert_mappings(AnswerRecord, [
    {'user_id': uid, 'question_id': qid, 'is_correct': 0}
    for qid in question_ids
])

# ✅ 大量数据更新使用批量UPDATE
from sqlalchemy import update
stmt = (
    update(MistakeRecord)
    .where(MistakeRecord.user_id == user_id)
    .where(MistakeRecord.id.in_(ids))
    .values(mastery_level=3, is_mastered=1)
)
session.execute(stmt)

# ❌ 避免 N+1 查询
# 错误：循环中发查询
for record in records:
    question = session.query(Question).get(record.question_id)  # N+1!
```

## 10. 应急处理

### 10.1 慢查询导致数据库卡顿

```bash
# 1. 查看当前正在执行的查询
mysql -e "SHOW FULL PROCESSLIST;"

# 2. 找到耗时长的查询，记录后KILL
mysql -e "KILL QUERY <thread_id>;"

# 3. 如果是突发大量慢查询，临时调低慢查询阈值捕获
mysql -e "SET GLOBAL long_query_time = 0.1;"

# 4. 如果是索引失效导致，紧急添加索引
# 使用 pt-online-schema-change 避免锁表
```

### 10.2 死锁处理

```sql
-- 查看最近一次死锁信息
SHOW ENGINE INNODB STATUS\G

-- 死锁分析关键信息：
-- LATEST DETECTED DEADLOCK 部分
-- 包含两个事务各自持有的锁和等待的锁

-- 预防措施：
-- 1. 固定更新顺序（按主键从小到大更新）
-- 2. 大事务拆小
-- 3. 添加合适的索引减少锁范围
-- 4. 使用 SELECT ... FOR UPDATE 时加上 NOWAIT 或 SKIP LOCKED
```

### 10.3 索引损坏恢复


## 11. 附录

### 11.1 EXPLAIN type 字段速查

| type | 含义 | 性能 |
| --- | --- | --- |
| system | 表只有一行（系统表） | ★★★★★ |
| const | 主键/唯一索引等值匹配，最多一行 | ★★★★★ |
| eq_ref | 唯一索引扫描（JOIN场景） | ★★★★ |
| ref | 非唯一索引扫描 | ★★★ |
| range | 索引范围扫描（BETWEEN, >, <, IN） | ★★★ |
| index | 全索引扫描 | ★★ |
| ALL | 全表扫描 | ★ |

### 11.2 EXPLAIN Extra 字段速查

| Extra | 含义 | 影响 |
| --- | --- | --- |
| Using index | 覆盖索引，无需回表 | ✅ 好 |
| Using where | 服务层过滤 | ⚠️ 一般 |
| Using index condition | 索引条件下推（ICP） | ✅ 好 |
| Using filesort | 额外排序操作 | ❌ 需优化 |
| Using temporary | 使用临时表 | ❌ 需优化 |
| Using join buffer | JOIN无索引 | ❌ 需优化 |
| Impossible WHERE | WHERE永远为false | ⚠️ 检查逻辑 |
| Select tables optimized away | 优化器直接从索引取值 | ✅ 好 |

### 11.3 索引选择性计算

```sql
-- 计算字段的选择性（选择性越高越适合放索引前面）
-- 选择性 = DISTINCT(column) / COUNT(*)
-- 越接近1越好

SELECT
    COUNT(DISTINCT user_id) / COUNT(*) AS user_selectivity,
    COUNT(DISTINCT subject_id) / COUNT(*) AS subject_selectivity,
    COUNT(DISTINCT created_at) / COUNT(*) AS created_selectivity
FROM answer_records;

-- 示例结果：
-- user_selectivity:      0.85  （高选择性，适合放索引前面）
-- subject_selectivity:   0.02  （低选择性，不适合单独索引）
-- created_selectivity:   0.99  （高选择性，适合排序字段）

-- 因此联合索引顺序：user_id → subject_id → created_at
```
