# docs2 目录说明

## 目录用途

本目录用于存储 PrimeTop 项目的详细设计文档，为开发人员提供可直接编码参考的技术实现细节。

## 细化原则

1. **可编码性**：每个文档应包含足够的技术细节，使开发人员能够直接开始编码实现。
2. **模块化**：每次针对一个功能模块进行细化，避免在单个功能下过度钻牛角尖。
3. **结构化**：包含数据结构定义、API接口设计、关键代码示例、状态流转、错误处理等。
4. **独立性**：每个文档应独立完整，方便不同团队并行开发。

## 文档命名规范

- 格式：`模块名-详细设计.md`
- 示例：
  - `AI服务-详细设计.md`
  - `题目服务-详细设计.md`
  - `错题服务-详细设计.md`
  - `用户服务-详细设计.md`

## 细化优先级

根据 MVP 阶段的开发优先级，建议的细化顺序：

1. **P0 模块**（MVP 核心）：
   - AI 服务
   - 用户服务
   - 题目服务

2. **P1 模块**（正式版本增强）：
   - 错题服务
   - 学习服务
   - 内容服务

3. **P2 模块**（后续迭代）：
   - 数据分析服务
   - 支付服务
   - 消息服务

## 文档结构模板

每个详细设计文档应包含以下章节：

```markdown
# [模块名] 详细设计

## 1. 概述
- 模块定位
- 核心职责
- 依赖关系

## 2. 数据模型
- 核心实体定义
- 数据库表结构
- 缓存策略

## 3. API 接口设计
- 接口列表
- 请求/响应格式
- 错误码定义

## 4. 业务逻辑
- 核心流程
- 状态机
- 关键算法

## 5. 代码示例
- 核心类定义
- 关键方法实现
- 配置示例

## 6. 错误处理
- 异常类型
- 重试策略
- 降级方案

## 7. 性能优化
- 缓存策略
- 并发控制
- 资源限制

## 8. 安全考虑
- 权限控制
- 数据验证
- 审计日志

## 9. 测试策略
- 单元测试
- 集成测试
- 性能测试
```

## 版本控制

- 每次完成细化后需 git commit 并 push
- 提交信息格式：`细化设计：[模块名] - [主要细化内容]`
- 绝对不能修改 `docs` 目录下的原始设计文档
